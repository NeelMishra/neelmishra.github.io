KV-Cache Rollback, Continuous Batching, and Production Serving

Taking speculative decoding from a single-request benchmark to a high-concurrency production cluster requires solving three systems challenges: zero-recompute PagedAttention KV-cache rollback, the missing KV entry of the bonus token, and dynamic Roofline throttling when batch size pushes verification into the compute-bound regime.

1. The Batch-Size Roofline Crossover: When Does Speculation Hurt?

Throughout this series, our fundamental premise has been that verifying $\gamma + 1$ tokens in parallel takes almost the same wall-clock time as decoding a single token ($T_{\text{verify}}(\gamma) \approx T_{\text{target}}(1)$). While that premise holds at small batch sizes ($B \in [1, 8]$), it breaks down dramatically under high concurrency ($B \ge 32$). Let us derive the exact hardware boundary using the GPU Roofline Model.

1.1 Arithmetic Intensity of Batched Speculative Verification

Consider a Transformer target model with $P$ parameters stored in $b_w$ bytes per parameter (e.g., $b_w = 2$ for FP16/BF16, or $b_w = 1$ for FP8), running a batch of $B$ concurrent requests where each request verifies $M = \gamma + 1$ tokens (either a chain of length $\gamma + 1$ or a tree of $M$ nodes) against an average prefix context of length $L$.

During a single target forward pass:

  • Total Floating-Point Operations ($\text{FLOPs}$): Each of the $B \cdot M$ tokens performs a matrix-vector product with every weight matrix ($2 P$ FLOPs per token), plus attention over $L$ cached keys and values: $$\text{FLOPs}(B, M) \approx 2 B M P + \mathcal{O}(B M L d_{\text{model}} n_{\text{layers}})$$
  • Total HBM Bytes Transferred ($\text{Bytes}$): Model weights ($P \cdot b_w$ bytes) are streamed from HBM once and shared across all $B \cdot M$ tokens, while each request streams its own KV cache of size $B \cdot L \cdot S_{\text{KV}}$ bytes (where $S_{\text{KV}} = 2 \cdot n_{\text{layers}} \cdot n_{\text{kv\_heads}} \cdot d_{\text{head}} \cdot b_{\text{kv}}$): $$\text{Bytes}(B, L) \approx P \cdot b_w + B \cdot L \cdot S_{\text{KV}}$$

In the weight-dominated regime ($P \cdot b_w \gg B \cdot L \cdot S_{\text{KV}}$), the arithmetic intensity $I(B, M)$ (in FLOPs per byte transferred from HBM) simplifies to:

$$I(B, M) = \frac{\text{FLOPs}(B, M)}{\text{Bytes}(B, L)} \approx \frac{2 B M P}{P \cdot b_w + B L S_{\text{KV}}} \xrightarrow{P b_w \gg B L S_{\text{KV}}} \frac{2 B M}{b_w} \text{ FLOPs/byte}$$

1.2 The Hardware Ridge Point $I_{\text{ridge}}$

Every accelerator has a hardware ridge point $I_{\text{ridge}} = \frac{\text{Peak FLOP/s}}{\text{BW}_{\text{HBM}}}$ where its Tensor Cores and HBM memory bus are simultaneously $100\%$ saturated:

  • NVIDIA H100 SXM (BF16): $\text{Peak FLOP/s} = 989\text{ TFLOP/s}$, $\text{BW}_{\text{HBM}} = 3.35\text{ TB/s} \implies I_{\text{ridge}} \approx 295\text{ FLOPs/byte}$.
  • For BF16 weights ($b_w = 2$), $I(B, M) \approx B \cdot M\text{ FLOPs/byte}$. Therefore, the forward pass transitions from memory-bandwidth bound to compute-bound when the total number of tokens in the batch exceeds: $$B \cdot M = B(\gamma + 1) \gtrsim I_{\text{ridge}} \approx 295 \text{ tokens}$$

What happens when $B(\gamma + 1) > I_{\text{ridge}}$? The GPU Tensor Cores are completely saturated! Increasing $\gamma$ from $0$ to $4$ at $B = 128$ increases total batch tokens from $128$ to $640$, causing verification step latency $T_{\text{verify}}(\gamma)$ to scale linearly with $\gamma + 1$. Because a fraction $1 - \alpha$ of those speculated tokens are rejected, every rejected token wastes precious Tensor Core FLOPs that could have gone toward guaranteed target tokens for other users in the batch.

2. PagedAttention KV-Cache Rollback and Tree Compaction

During the target verification pass on a chain of $\gamma + 1$ tokens $[u_0, u_1, \dots, u_\gamma]$ (or a tree of $M$ nodes $[u_0, u_1, \dots, u_{M-1}]$), the attention kernel writes the newly computed Key and Value vectors $(\mathbf{k}_{u_i}, \mathbf{v}_{u_i})$ for every candidate node into the request's PagedAttention KV-cache blocks at positions $L_{\text{prefix}}, L_{\text{prefix}}+1, \dots, L_{\text{prefix}}+M-1$.

Once rejection sampling completes, suppose only $a$ draft tokens along a specific branch $(u_{i_1}, u_{i_2}, \dots, u_{i_a})$ are accepted ($0 \le a \le \gamma$), along with the root $u_{i_0} = u_0$. How do we clean up the KV cache without recomputing keys and values?

2.1 Linear Chain Rollback ($\mathcal{O}(1)$ Metadata Rewind)

For a linear draft chain $(u_0, u_1, \dots, u_\gamma)$, the accepted prefix of the chain $(u_0, u_1, \dots, u_a)$ already occupies contiguous logical positions $L_{\text{prefix}}, L_{\text{prefix}}+1, \dots, L_{\text{prefix}}+a$ in the PagedAttention block table! The rejected draft tokens $(u_{a+1}, \dots, u_\gamma)$ sit at positions $L_{\text{prefix}} + a + 1 \dots L_{\text{prefix}} + \gamma$.

  • We do not zero out HBM memory for rejected tokens.
  • Instead, we simply rewind the request's logical sequence length metadata pointer: $$\texttt{seq\_len} \leftarrow L_{\text{prefix}} + a + 1$$ and release any PagedAttention physical blocks beyond $\lceil \texttt{seq\_len} / \text{block\_size} \rceil$ back to the free-block allocator in $\mathcal{O}(1)$ time. On the next step, new tokens simply overwrite the stale KV slots starting at $L_{\text{prefix}} + a + 1$.

2.2 Tree KV Compaction ($\mathcal{O}(a)$ Slot Gather)

For a branching candidate tree $\mathcal{T}$ of $M$ nodes (Chapter 3.1), the accepted path $[u_{i_0}, u_{i_1}, \dots, u_{i_a}]$ is generally non-contiguous in the 1D packed buffer (for example, indices $[0, 2, 4]$ in Panel 2 of Figure 1 when sibling $u_1$ at index $1$ and its child $u_3$ at index $3$ were rejected).

To restore contiguous logical positions $L_{\text{prefix}}, L_{\text{prefix}}+1, \dots, L_{\text{prefix}}+a$ without re-running attention:

  1. Since topological sorting guarantees $d \le i_d$ for every depth $d \in \{0, \dots, a\}$, we launch a lightweight CUDA copy kernel (or update virtual slot pointers in page-granularity engines like SGLang's RadixAttention) that copies slot $L_{\text{prefix}} + i_d$ into destination slot $L_{\text{prefix}} + d$ in ascending order $d = 1, \dots, a$.
  2. Because $d \le i_d$, copying in ascending order $d = 1 \to a$ never overwrites a source slot $L_{\text{prefix}} + i_{d'}$ ($d' > d$) before it is read!
  3. Finally, we rewind $\texttt{seq\_len} \leftarrow L_{\text{prefix}} + a + 1$ and reclaim the remaining $M - (a + 1)$ temporary tree slots.

3. The Bonus-Token KV Subtlety: Carrying Over $x_{\text{bonus}}$

There is a subtle architectural detail that trips up almost every first-time implementer of speculative decoding: what about the KV cache entry for the bonus (or resampled correction) token $x_{\text{bonus}}$?

Trace the exact dataflow during verification step $s$:

  1. We feed the root token $u_0 = x_t$ and the $\gamma$ draft tokens $(x_1, \dots, x_\gamma)$ into the target model.
  2. During this forward pass, the target model computes and caches the KV vectors for $u_0, x_1, \dots, x_\gamma$.
  3. From the output logits at the last accepted node $x_a$, we sample one extra token $x_{\text{bonus}}$ (either the resampled correction token $x'_{a+1}$ if $a < \gamma$, or the bonus token $x_{\gamma+1}$ if $a = \gamma$).
  4. Crucial observation: Although we now know the token ID of $x_{\text{bonus}}$, $x_{\text{bonus}}$ has never been passed as an input token through the target model's embedding and attention layers! Therefore, its Key and Value vectors $(\mathbf{k}_{\text{bonus}}, \mathbf{v}_{\text{bonus}})$ do not exist in the target KV cache yet.

How is this resolved without an extra forward pass? In verification step $s + 1$, $x_{\text{bonus}}$ becomes the new root node $u_0^{(s+1)}$ at the front of the next speculative batch $[x_{\text{bonus}}, \hat{x}_1^{(s+1)}, \dots, \hat{x}_\gamma^{(s+1)}]$! That is why a speculative verification pass of $\gamma$ draft tokens always feeds $\gamma + 1$ input tokens into the target model:

$$\underbrace{\big[\, x_{\text{bonus}}^{(s-1)},\;\; \hat{x}_1^{(s)},\;\; \hat{x}_2^{(s)},\;\; \dots,\;\; \hat{x}_\gamma^{(s)} \,\big]}_{\gamma + 1 \text{ tokens fed into Target Model at step } s}$$

In one stroke, slot $0$ of step $s$ computes and caches the missing KV entry $(\mathbf{k}_{\text{bonus}}^{(s-1)}, \mathbf{v}_{\text{bonus}}^{(s-1)})$ for the previous step's bonus token and produces the target verification distribution $p(\cdot \mid x_{\le t})$ needed to verify the first new draft token $\hat{x}_1^{(s)}$.

4. Ragged Continuous Batching and Dynamic $\gamma(B)$ Throttling

In production serving engines (vLLM, SGLang, TensorRT-LLM), a single GPU iteration mixes requests in different lifecycle stages: some requests are in chunked prefill ($q_{\text{len}} = 512$), some are in speculative verification ($q_{\text{len}} = \gamma + 1 = 5$ or tree size $M = 16$), and large-batch requests may be in standard decoding ($q_{\text{len}} = 1$).

4.1 Ragged FlashAttention (`cu_seqlens_q`)

Padding every request in the batch to $\max_r q_{\text{len}}^{(r)}$ would waste massive amounts of Tensor Core compute. Instead, production engines concatenate all query tokens across all $B$ requests into a single ragged 1D tensor of shape $[\sum_{r=1}^B q_{\text{len}}^{(r)}, n_{\text{heads}}, d_{\text{head}}]$ and pass cumulative sequence offset arrays to variable-length FlashAttention (`flash_attn_varlen_func` or FlashInfer):

$$\texttt{cu\_seqlens\_q} = \left[0,\; q_{\text{len}}^{(1)},\; q_{\text{len}}^{(1)} + q_{\text{len}}^{(2)},\; \dots,\; \sum_{r=1}^B q_{\text{len}}^{(r)}\right]$$

FlashInfer's block-sparse ragged kernels take both $\texttt{cu\_seqlens\_q}$, the PagedAttention block tables $\texttt{block\_tables}$, and per-request packed bitmasks $M^{\text{tree}(r)}$ so that linear prefill, standard decode, and tree-attention verification execute together in a single fused CUDA kernel launch.

4.2 Dynamic Speculation Throttling $\gamma(B)$

To prevent batch spikes from pushing the GPU past its Roofline ridge point $I_{\text{ridge}}$ and violating Inter-Token Latency (ITL) SLAs, production schedulers dynamically adjust the speculative budget $\gamma(B)$ at every iteration based on the active batch size $B$ and token budget $N_{\text{budget}} \approx I_{\text{ridge}}$:

$$\gamma(B) = \min\!\left(\gamma_{\max},\; \max\!\left(0,\; \left\lfloor \frac{N_{\text{budget}}}{B} \right\rfloor - 1\right)\right)$$
  • When $B = 4$ and $N_{\text{budget}} = 128$, $\gamma(4) = \min(5, 31) = 5$ (full speculation).
  • When $B = 32$, $\gamma(32) = \min(5, 3) = 3$ (throttled speculation).
  • When $B \ge 64$, $\gamma(B) = 0$: the scheduler automatically bypasses the drafter and runs standard 1-token decoding at peak Tensor Core efficiency!

  • Across 4× H100 GPUs, weight streaming per TP rank is $35\text{ GB}$ at $\sim 2.8\text{ TB/s}$ effective HBM bandwidth $\implies$ base memory-bound target forward pass latency is $T_{\text{base}} = 12.5\text{ ms}$.

6. Reference Implementation: Paged KV Compaction & Dynamic Scheduler

The following Python/PyTorch implementation demonstrates both in-place tree KV-cache compaction after verification and a Roofline-aware dynamic speculation scheduler $\gamma(B)$: 

import torch
from typing import List, Tuple

class SpeculativeKVCacheManager:
    """
    Manages KV-cache slot compaction and bonus-token carryover for tree/chain
    speculative decoding without recomputing accepted keys and values.
    """
    def __init__(self, max_seq_len: int, num_heads: int, head_dim: int, device: str = "cpu"):
        self.k_cache = torch.zeros((max_seq_len, num_heads, head_dim), device=device)
        self.v_cache = torch.zeros((max_seq_len, num_heads, head_dim), device=device)
        self.seq_len = 0  # Number of verified tokens with materialized KV entries
        self.pending_bonus_token: int = -1

    def write_candidate_tree_kv(
        self, k_tree: torch.Tensor, v_tree: torch.Tensor
    ) -> None:
        """
        Writes the M candidate tree nodes' K/V tensors into the cache starting at self.seq_len.
        Note: Node 0 is the carried-over bonus token from the previous step!
        """
        M = k_tree.size(0)
        self.k_cache[self.seq_len : self.seq_len + M] = k_tree
        self.v_cache[self.seq_len : self.seq_len + M] = v_tree

    def compact_and_rollback(
        self, accepted_tree_indices: List[int], bonus_token_id: int
    ) -> int:
        """
        Compacts the KV entries along the winning tree path in-place and rewinds seq_len.

        Args:
            accepted_tree_indices: Topological indices [0, i_1, ..., i_a] of accepted nodes.
                                   Because the tree is topologically sorted, d <= i_d always holds.
            bonus_token_id: Newly sampled bonus/correction token (KV will be computed next step).
        Returns:
            new_seq_len: Updated materialized KV cache length (L_prefix + a + 1).
        """
        base = self.seq_len
        for depth, tree_idx in enumerate(accepted_tree_indices):
            assert depth <= tree_idx, "Topological sort guarantees depth <= tree_idx."
            if depth != tree_idx:
                self.k_cache[base + depth] = self.k_cache[base + tree_idx]
                self.v_cache[base + depth] = self.v_cache[base + tree_idx]

        # Advance materialized KV pointer by (1 carried-over root + a accepted draft tokens)
        self.seq_len = base + len(accepted_tree_indices)
        # Store bonus token to serve as root u_0 of the next speculative step
        self.pending_bonus_token = bonus_token_id
        return self.seq_len


def dynamic_speculation_schedule(
    batch_size: int,
    gamma_max: int = 5,
    ridge_token_budget: int = 160,
    estimated_alpha: float = 0.80,
    draft_cost_ratio: float = 0.04,
) -> int:
    """
    Computes the optimal speculative lookahead gamma(B) given current batch concurrency.
    Automatically throttles gamma as B approaches the GPU Roofline ridge point.
    """
    if batch_size <= 0:
        return 0
    # Maximum tokens per request before crossing the Roofline ridge budget
    budget_cap = max(0, (ridge_token_budget // batch_size) - 1)
    gamma_limit = min(gamma_max, budget_cap)

    best_gamma = 0
    best_speedup = 1.0
    for g in range(1, gamma_limit + 1):
        expected_tokens = (1.0 - estimated_alpha ** (g + 1)) / (1.0 - estimated_alpha)
        # Account for linear compute-bound penalty as B * (g + 1) approaches ridge_token_budget
        compute_penalty = max(1.0, (batch_size * (g + 1)) / float(ridge_token_budget))
        relative_step_time = compute_penalty + g * draft_cost_ratio
        speedup = expected_tokens / relative_step_time
        if speedup > best_speedup:
            best_speedup = speedup
            best_gamma = g

    return best_gamma


if __name__ == "__main__":
    kv = SpeculativeKVCacheManager(max_seq_len=64, num_heads=4, head_dim=8)
    # Simulate verifying a 5-node tree where path [0, 2, 4] won and bonus token is 99
    k_tree = torch.arange(5 * 4 * 8, dtype=torch.float32).reshape(5, 4, 8)
    v_tree = k_tree.clone()
    kv.write_candidate_tree_kv(k_tree, v_tree)
    new_len = kv.compact_and_rollback(accepted_tree_indices=[0, 2, 4], bonus_token_id=99)
    print(f"Materialized KV length after compaction: {new_len}, Next root token: {kv.pending_bonus_token}")
    for B in [1, 8, 32, 64, 128, 256]:
        print(f"Batch B={B:3d} -> Optimal gamma(B) = {dynamic_speculation_schedule(B)}")
