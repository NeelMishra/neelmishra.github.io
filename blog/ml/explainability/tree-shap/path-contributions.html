    Tree SHAP Path Contributions

    September 2026 · 14 min read

    A prediction follows one route through a tree. A SHAP explanation must also consider what the tree would output before some features are revealed. Hiding a split feature can make both branches relevant. This chapter makes those branch averages visible on a fitted tree.

    The Shapley foundation already explains why we average reveal orders. Here we focus on how a tree supplies the numbers being averaged.

    Start with a tree you can reproduce

    Fit a regression tree to four equally weighted rows: (A, B) = (0, 0), (0, 1), (1, 0), (1, 1), with target scores 0, 2, 4, and 8. Its first split tests A at 0.5; each child tests B at 0.5. These are constructed score units, not estimated probabilities.

    We explain (1, 1), which reaches the leaf with score 8. Use all four training rows as the reference, each with equal weight. Before revealing any feature, the average prediction is (0 + 2 + 4 + 8) / 4 = 3.5. This is the baseline.

    Cover in the diagram is the training weight reaching a node. Here all row weights are 1, so cover is simply a row count. The numbers beside the edges are the explanation weight reaching the child: they sum to 1 across the active leaves.

    With only B = 1 revealed, A is still unknown. Half the reference weight goes left at the root and half goes right. B = 1 then selects the score-2 leaf on the left and the score-8 leaf on the right, giving 0.5 × 2 + 0.5 × 8 = 5. Following only the original right-hand route would miss the score-2 contribution.

    Turn that diagram into a recursive calculation

    A coalition $S$ is the set of revealed features, and $v(S)$ is its expected model output. Start at the root with weight 1. At a revealed split, follow the explained row’s branch and keep its incoming weight. At a hidden split, send weight down both branches in proportion to their covers. At a leaf, multiply the arriving weight by its score.

    value(node, incoming_weight):
    if node is a leaf:
        return incoming_weight * leaf_score
    if split_feature is revealed:
        return value(the row's child, incoming_weight)
    return value(left, incoming_weight * left_cover / node_cover)
         + value(right, incoming_weight * right_cover / node_cover)

    This is the tree-path-dependent averaging rule. On our balanced independent reference it agrees with explicitly replacing hidden features from each reference row and averaging predictions. That agreement is special to this setup; the reference chapter separates tree-path weights, background replacement, and actual conditioning.

    To see the weight propagation at a hidden root, split 1 into 2/4 on each child. If that child’s B split is also hidden, split its 0.5 weight again using 1/2 on each branch. Each leaf receives 0.25. A revealed B split instead passes the whole 0.5 to the selected leaf.

    Compare a prediction-path explanation with SHAP

    The actual path for (1, 1) moves from root mean 3.5 to right-subtree mean 6 to leaf score 8. Attributing those changes to the split features gives A: 2.5 and B: 2. This is a valid decomposition of that route, but it considers only A before B.

    Reverse the feature reveal order without changing the tree. B first changes 3.5 to 5, contributing 1.5; A then changes 5 to 8, contributing 3. SHAP averages the two orders. Write $\phi_A$ and $\phi_B$ for those averaged contributions:

    $$\phi_A=\frac{2.5+3}{2}=2.75,\qquad \phi_B=\frac{2+1.5}{2}=1.75.$$

    The library’s approximate=True option uses a single-order Saabas approximation for this supported model. We ran it: it gives (2.5, 2) for this row. Exact TreeSHAP gives (2.75, 1.75). Both pass the summation check. The TreeExplainer documentation describes the approximation and its limits.

    Two splits can still mean one feature

    Now fit a separate one-feature tree on A = 0, 1, 2 with scores 0, 2, 8. The root tests A ≤ 1.5, and its left child tests A ≤ 0.5. An explanation still has one player, A. Revealing A supplies its value to every split that tests it.

    For A = 0, the path changes are about −2.3333 at the first split and −1 at the second. Both belong to A; together they equal −3.3333. In a multi-feature tree, the efficient algorithm must also keep the reveal-order bookkeeping consistent when a feature reappears. The next computational explanation develops what is being reused.

    Check the calculation against the fitted model

    The reproduction script fits both trees and exports their actual thresholds, covers, leaf values, all coalition weights, and library results. It enumerates small coalition games as a reference calculation; it does not implement the efficient TreeSHAP algorithm.

    For all seven explained rows across the two trees, we checked direct enumeration against both exact tree-path-dependent and interventional TreeExplainer calls. We also saved the approximate results for comparison. The runs use SHAP 0.52.0, scikit-learn 1.9.1, and NumPy 2.5.3; see the pinned requirements and full exported data.

    python -m pip install -r tree-shap-requirements.txt
python tree_shap_examples.py > assets/tree-shap-examples.json

    Check each contribution against the reference calculation as well as checking their sum. Preserve the output, feature order, tree limit, and reference convention when comparing implementations. A correct reconstruction alone would not distinguish the two allocations above.
