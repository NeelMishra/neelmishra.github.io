    Tree SHAP: Row-Level Explanations for Tree Models

    September 2026 · 8 min read

    A tree’s prediction route tells you which leaf supplied a score. A TreeSHAP explanation answers a further question: how should the difference between this score and a reference prediction be shared among the input features? The distinction matters because a leaf route, a reference average, and an allocation are three different objects.

    This series starts with a fitted four-leaf regression tree, then builds toward ensembles and interpretation checks. You only need to know how a decision tree follows split tests and how a weighted average works. If SHAP itself is new, the two-feature reveal-order example introduces its allocation rule.

    Read one explanation in three parts

    Our tree uses binary features A and B. Its scores are 0, 2, 4, and 8 for inputs (0, 0), (0, 1), (1, 0), and (1, 1). We explain the final row, (1, 1), and use all four inputs equally often as the reference.

    Start with the prediction: the fully observed row reaches the score-8 leaf. Then find the baseline: the reference average is (0 + 2 + 4 + 8) / 4 = 3.5. Finally, allocate the difference of 4.5. SHAP’s reveal-order calculation gives A a contribution of 2.75 and B a contribution of 1.75.

    The numbers in the allocation panel are not increments gathered from the highlighted prediction route. They average what each feature adds when revealed before or after the other feature. The worked chapter opens that calculation and checks it against TreeExplainer. Following only the observed route misses comparisons that involve other leaves.

    A positive contribution raises the explained output relative to its baseline; a negative contribution lowers it. Contributions use the output’s units. Here they are regression-score units. For a classifier, inspect whether you are explaining a raw decision score or a probability before assigning a meaning to a number.

    What the tree structure saves

    SHAP defines an allocation by averaging marginal changes across feature reveal orders. Directly listing those possibilities grows rapidly as more features are added. TreeSHAP uses tree structure to share calculations across the feature sets that matter along a path.

    The reuse chapter starts with each leaf’s piece of the answer, then shows how contributions can be grouped by the number of revealed features. Its scaling plot compares mathematical growth terms, while the detailed bookkeeping is optional. You can use the small worked explanation before studying the faster algorithm.

    Computational exactness still needs a specified question. The tree’s stored path covers and explicit replacement from background rows can define different hidden-feature averages. They agree in this balanced example. The correlated example shows precisely where they diverge.

    Keep enough context to reproduce an explanation

    An explanation record should identify the row and model, the output being explained, the feature order, and the reference rule. Save the baseline and contributions with that context. Reconstructing the output is a useful first check, but many incorrect allocations can still add to the same total; verify a tiny case independently too.

    All figures in this series use exported example data. Start with the fitted-tree script and its pinned dependencies; the JSON export includes the tree structure, reveal-set values, and library results. The later chapters provide their own ensemble, reference, and plotting scripts.

    Once these comparisons are clear, the C++ companion is a useful place to implement the small cases. If your model is not a supported tree model, continue with the SHAP and LIME guide to choose another computation method or a local surrogate.
