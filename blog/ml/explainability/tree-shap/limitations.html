    Check a TreeSHAP Explanation Before You Trust It

    October 2026 · 6 min read

    A TreeSHAP calculation can be exact and still answer a question different from the one you intended. The useful final check is therefore broader than “did the contributions sum correctly?” We need the prediction target, reference rule, input representation, and interpretation to line up.

    We will use the examples from the series to make that check concrete. Each one gives a recognizable failure mode and a way to investigate it.

    First, identify the output being reconstructed

    Record the model’s prediction method and units. For the regression forest, we reconstructed a numeric prediction of 41.063064. For the random-forest classifier, we reconstructed the probability for a specified class. An additive boosted classifier can instead require a margin or log-odds target.

    Check the array shape, class order, and feature order before summing. For multiclass output, sum over features while keeping the class axis. If the model includes preprocessing, pass the same transformed column order and values the model received during prediction.

    An explanation of one output is not automatically an explanation of a downstream decision. A threshold, calibration function, business rule, or ranking step may change what the final system does. State which stage the displayed values actually describe.

    Second, name the comparison population

    Our hand-built tree began at 52 because that was its cover-weighted reference output. The fitted forest used either its stored covers or a specific sample of 64 training rows. A reader cannot interpret the gap from the baseline without knowing which comparison produced it.

    For a background dataset, preserve the sampling procedure, seed, preprocessing, and row identifiers when available. Keep explained rows separate from reference rows. If the question changes from “compared with training customers” to “compared with this month’s customers,” compute and label a new explanation.

    A simple sensitivity check repeats the calculation with several defensible reference samples and compares baselines and feature values. This assesses reference-sampling sensitivity for the chosen model. It is not a confidence interval for causal effects or a substitute for assessing model uncertainty.

    Third, distinguish covers from conditional distributions

    In our ten-row correlated example, path-dependent, replacement, and full conditional rules gave A contributions of 18.5, 14, and 12.5. All shared the same baseline of 27 and prediction of 50. Those differences were consequences of the group definitions, not rounding errors.

    Tree-path-dependent mode generally should not be described as “conditioning on all known features.” It conditions traversal on revealed splits and uses recorded ratios at unrevealed splits. The worked conditional comparison shows where that differs from filtering a joint reference distribution.

    Even the same prediction function can have different path-dependent explanations under different tree representations. The reordered-tree example makes this visible. A comparison across models should therefore preserve or carefully examine the explanation game, not just the feature names.

    Check what the fitted model stores as cover

    Our toy covers were ordinary row counts. Fitted libraries may expose weighted counts or other training statistics. The scikit-learn adapter in this series uses the tree’s weighted_n_node_samples. Do not describe a weighted cover of 40 as “40 customers” unless the weighting actually makes that true.

    The path rule uses child-to-parent ratios, so the relevant stored weights must be valid for the model adapter. The educational polynomial implementation deliberately requires positive covers and finite numeric inputs. It does not implement every library’s missing-value routing, categorical split representation, or unsupported-model behavior.

    Use the compiled library for supported production models, and keep a small independently checked example for any custom adapter. SHAP’s custom-tree example shows the arrays an adapter must describe. Verifying that the ingested tree predicts the same outputs should precede attribution checks.

    Verify the allocation as well as the total

    The prediction-path allocation from Part 2 passed the total-sum check but gave B zero instead of 3. Repeated-feature bookkeeping can also produce a plausible total while dividing credit among the wrong participants. Test the individual values against exhaustive feature groups on small cases.

    Useful cases include a feature unused anywhere in the tree, a feature used only outside the explained path, a repeated split feature, and a constant tree. Our lab checks those cases and 100 deterministically generated trees. Its polynomial calculation and its exhaustive calculation agree exactly as fractions.

    For the fitted forest, we used explicit approximate=False and compared a background-replacement row against exhaustive masking. If you use an approximate mode for speed, report that choice and measure its error on representative examples. A faster path-based approximation should not inherit an exact-Shapley claim merely because it uses the same class name.

    Budget for the model and the requested explanation

    The path algorithm’s familiar $O(TLD^2)$ bound depends on tree count, leaf count, and depth. Explaining more rows repeats the work. Interventional calculations also depend on the size of the reference sample, and pairwise interactions produce many more output entries than ordinary attributions.

    Measure runtime and memory on the actual model and requested output. Start with a small representative batch, then choose the size of the explained cohort and background deliberately. A shallow tree ensemble with many input columns can be tractable because each leaf path uses relatively few distinct features; a deep ensemble can be expensive despite a modest column count.

    Keep model explanation separate from model quality

    The fitted forest’s first prediction was 41.063064 while the observed target was 38.316947. Its explanation faithfully reconstructs 41.063064. It does not explain away the prediction error or show that the model is right for that individual.

    Likewise, the correlated input received a contribution even though it had no separate term in our generating formula. The model learned to use information available in that input. A model explanation is not a recovery guarantee for the original generating process.

    A positive SHAP value does not establish that increasing the feature will increase the output, nor that changing it will improve a real-world outcome. Contributions compare a particular row with partially hidden versions defined by the explanation rule. A proposed intervention asks a different question, with additional assumptions and evidence.

    What to preserve with a result

    A compact record should include the model version, input feature order, explained rows, output method and units, class index if relevant, explanation mode, reference selection, baseline, contributions, library versions, and reconstruction tolerance. Keep the observed outcome separately when evaluating prediction quality.

    For our Python example, that record includes a regression forest, raw numeric output, 64 fixed reference rows, 32 explained test rows, a first baseline of 24.851337, and a first prediction of 41.063064. The exhaustive contribution check differs by at most about $2.13\times10^{-7}$. These details make the explanation reproducible and its scope clear.

    The machine-readable results and verification script preserve those calculations. For small-tree enumeration and a comparison with a path-difference approximation, see the C++ implementation notes. The broader SHAP plotting chapter explains how to present individual and dataset-level results once these checks are complete.
