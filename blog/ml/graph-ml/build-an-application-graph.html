    Graph-Based Risk Modeling: Start with the Relationships

    September 2026 · 4 min read

    Before you start: Tabular classification and LightGBM/boosting fundamentals.

    A row-based classifier sees one application’s permissions, age, and behavior. A graph lets it ask another question: which other applications share meaningful evidence with this one? The first modeling decision is what a connection means. A shared publisher and a shared cloud-hosting domain should not automatically have the same strength.

    Represent the evidence before aggregating it

    Use separate node types for applications and metadata entities. An edge records the relation type, when it was first and last observed, and the source of the observation. Keep entity identifiers stable and normalize them carefully: two visually similar domains are not necessarily the same entity, and two differently formatted publisher strings may refer to one entity.

    Keep unknown labels distinct from confirmed benign labels. Unknown means no trusted conclusion is available. If unknown nodes become zero-risk training labels, the graph can mostly learn how investigation coverage was allocated. Include label provenance and observation time, because a label discovered next month was unavailable to a decision made today.

    What is lost when you project the graph?

    A simple projection connects two applications when they share metadata. A metadata entity connected to a million applications induces an enormous clique if expanded literally. It also creates a weak relationship: a generic platform says less than a rare signing identity. Keep the bipartite representation for joins and compute typed features without materializing every pair.

    $$w(a,b)=\sum_{m\in N(a)\cap N(b)}\frac{\alpha_{\operatorname{type}(m)}}{\max(1,\deg(m)-1)}.$$

    This is an illustrative weighting rule, not a universal estimator of maliciousness. The denominator reduces the contribution of common metadata; α lets relation types differ. A shared metadata item of degree 2 contributes its full type weight, while degree 101 contributes one hundredth. Learn or validate these choices on held-out data rather than selecting them because the formula looks plausible.

    Make the first baseline understandable

    Start with a few features per relation type: neighbor count, fraction with trusted risky labels, count of independent risky publishers, maximum neighboring base score, and recency of the strongest evidence. Include denominators and missingness flags. A risky fraction of 1 from one observed neighbor is different from a fraction of 1 from a hundred independent neighbors.

    Preserve the application’s intrinsic features too. The graph augments its own evidence; it should not erase it. A clean application can use infrastructure that was also abused by someone else. A new risky application can have no known risky neighbors. Those cases make useful diagnostic slices.

    A reproducible construction contract

    # Conceptual input schema, shared by training and scoring:
edge = {
    "app_id": "A", "entity_type": "publisher", "entity_id": "P1",
    "observed_at": "2026-08-01T00:00:00Z",
    "source_version": "metadata-v3",
}
# For a cutoff t:
# 1. Keep observations available by t.
# 2. Deduplicate (app_id, entity_type, entity_id) under a declared rule.
# 3. Compute entity degrees on this same snapshot.
# 4. Join only labels available by t.
# 5. Aggregate by app_id, keeping counts and evidence provenance.

    Test invariants before modeling: no accidental self-neighbor contribution, no duplicate edge inflation, no null identifier that connects every missing value into one giant entity, and no future timestamp. A missing domain should be missing evidence, not a universal shared domain named “unknown.”

    Relationships are observations, not causal explanations

    Homophily means connected nodes often resemble each other with respect to a particular property. It is an empirical condition, not a law of graphs. Check it separately for each relation and time period. Some relationships can be uninformative or connect opposites. The next chapter shows how to use neighborhood evidence while keeping this assumption visible.

    Check your understanding: Why is a shared null publisher dangerous?

    If null is converted into an ordinary node, all applications with missing publishers become neighbors. The resulting degree and risk features measure missing-data handling, not a real relationship.
