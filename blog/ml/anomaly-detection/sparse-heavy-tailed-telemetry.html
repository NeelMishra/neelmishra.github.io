    Model Sparse, Heavy-Tailed Telemetry Without Flagging Every Large Customer

    September 2026 · 4 min read

    Before you start: Isolation Forest scoring.

    One application sends 10,000 events and another sends 10. The first may be suspicious, or it may serve a thousand times as many users. Raw magnitude is not a complete behavioral story. Sparse, heavy-tailed telemetry requires a model of exposure, a clear scoring unit, and an explicit reference population.

    Application versus application–tenant pair

    An application-level row aggregates across every organization using it. That is useful for global reputation but can hide a local compromise. An application–tenant row preserves local behavior but creates many sparse observations. Keep the two models or feature families conceptually separate: a local anomaly is not automatically a global app verdict.

    Do not reuse a feature name if its denominator or aggregation level changed.
    FeatureApp-level meaningApp–tenant meaning
    Event countTotal activity across organizationsActivity in one organization
    Tenant diversityBreadth of deploymentNot defined in the same way
    Permission changeGlobal configuration transitionLocal consent or use change
    Peer baselineSimilar applicationsComparable applications within similar tenants

    Counts need a denominator

    For an event count c over n active users, c/n is a crude rate, but a tiny denominator is unstable. Preserve both c and n. A smoothed rate (c+α)/(n+β) can express a prior rate α/β, provided c and n describe compatible exposure. For time windows, distinguish ten events in ten minutes from ten events in a month. An inactive tenant should not create a divide-by-zero anomaly.

    Count features can benefit from log1p transforms when orders of magnitude dominate. Tree partitions are not invariant to nonlinear transforms: a threshold drawn uniformly in log space differs from one drawn uniformly in raw space. That is a modeling change to validate, not a harmless formatting choice. Robust quantile or median-based peer features can be useful, but fit their reference statistics on training data.

    Zero, missing, and absent are different observations

    A zero count may mean the application was observed and did nothing. A missing count may mean collection failed. No row may mean the pair did not exist in the observation window. Create explicit coverage and missingness indicators, and specify whether inactive pairs belong in the scoring universe. Otherwise a telemetry outage can resemble a widespread behavior change.

    # Feature contract for one app–tenant window.
features = {
    "events_7d": 40,
    "active_users_7d": 20,
    "observed_hours_7d": 168,
    "collection_complete": True,
    "events_per_user_smoothed": (40 + 2) / (20 + 1),

    Choose peers with enough support

    A single global forest can spend its capacity separating organization sizes or app categories. Peer-group models or peer-normalized features can help, but a group with twenty observations cannot support the same complexity as one with millions. Use minimum-support rules, shared global fallbacks, and report which model scored each row.

    Define peers using information available at scoring time. Grouping by an investigator’s eventual finding leaks the answer. Very fine segmentation can also make the reference population unstable from week to week. Compare global, grouped, and hybrid baselines on a fixed evaluation workload.

    Test for useful unusualness

    Evaluate by tenant size, activity density, app age, permission category, and telemetry completeness. Measure whether the top queue is dominated by one legitimate large organization. Include known incidents when available, but do not train the entire feature design to rediscover only those incidents. Inspect an unbiased or probability-sampled background to understand what the queue misses.

    Use forward-time splits and test score stability under routine window shifts. A deterministic seed gives repeatability on the same inputs; it does not guarantee stable rankings when the population changes. Distinguish model drift from a feature-pipeline regression by comparing frozen-data scores before and after a deployment.

    Check your understanding: Why keep the denominator after computing an event rate?

    A rate of 1 from one exposure and a rate of 1 from a million exposures have different uncertainty. The denominator also reveals whether changes came from behavior or exposure.
