    Model Sparse, Heavy-Tailed Telemetry Without Flagging Every Large Customer

    September 2026 · 5 min read

    An application sends 10,000 events while another sends 10. The first may behave unusually, or it may simply serve many more users. Before fitting a forest, decide what one row describes and what population it should be compared with.

    Choose one unit of behavior

    An application-level row combines activity across organizations. An application–tenant row describes that application inside one organization. Here “tenant” means an organization using the service.

    A global total can hide a local change. Conversely, a new application–tenant pair may have too little activity for a stable rate. Give every feature a clear unit and observation window, such as “events for this app in this tenant during the last seven days.”

    Compare counts with their opportunity to occur

    Suppose one row has 100 events from 50 active users and another has 10 events from 5 users. Both have 2 events per user. Keep the count and user count alongside this rate: a rate based on 5 users carries less evidence than one based on 50.

    For tiny denominators, one option is to blend the observed rate with a peer rate. Let $c$ be the event count, $n$ the active-user count, and $r_0$ the peer rate. Choose a smoothing strength $k$ in units of extra user exposures:

    $$r_{\mathrm{smooth}}=\frac{c+k r_0}{n+k}.$$

    With 0 events from 1 user, peer rate 2, and $k=10$, the smoothed rate is 20/11, about 1.82. As real exposure grows, it outweighs these ten prior exposures. Choose the peer estimate from training data and validate the strength; this is a modeling choice, not a required Isolation Forest step.

    Telemetry is often heavy-tailed: many small counts and a few enormous ones. A log transform can compress that range, but it changes Isolation Forest’s uniformly sampled cut locations. Fit and compare the transformed and raw feature designs rather than treating the transform as cosmetic.

    Do not confuse silence with missing observations

    ObservationMeaning to preserve
    Zero events, complete collectionThe pair was observed and produced no events.
    Missing count, incomplete collectionThe activity is unknown.
    No app–tenant rowThe pair may not belong to this window’s scoring population.

    Store collection coverage separately. Filling every missing count with zero can turn a telemetry outage into an apparent behavior change.

    Use peers that answer the intended question

    A global forest may mostly distinguish organization size or application category. Peer-normalized features or group-specific models can make more useful comparisons, but very small groups need a shared fallback. Record which reference population or model scored each row.

    Define peers using information available at scoring time. An investigator’s later finding cannot be used to assign historical peers without leaking the answer.

    Inspect who dominates the queue

    Score later windows and break down the top-ranked cases by organization size, activity, application age, and collection completeness. If one legitimate customer dominates, inspect its features before tuning the forest. Include sampled cases outside the queue to learn what the ranking misses.

    When rankings change after a deployment, score a frozen dataset with both versions. This helps separate a pipeline change from a changed population. Continue to turning scores into a review queue.
