    Turn Anomaly Scores into an Investigation Queue

    September 2026 · 4 min read

    Before you start: Telemetry features and reference populations.

    Anomaly detection usually ends in a queue, not a label. Someone has capacity to review a limited number of cases and wants that work to be useful. The operational design must connect score ordering, alert grouping, evidence, and feedback. A raw score threshold alone does not do that.

    Thresholds and budgets answer different questions

    A fixed threshold asks whether a case is unusual enough under the score scale. A top-B policy asks which B cases deserve the available review slots. A percentile threshold approximately fixes volume relative to a reference distribution, but can hide a genuine surge if it always discards the same fraction. A fixed threshold can overwhelm reviewers when the population or feature distribution shifts.

    Use validation data to choose a policy, then replay it on future windows. Include queue volume, unique incidents, duplicate cases, and reviewer time. If hundreds of application–tenant pairs belong to the same incident, group them so one investigation can inspect the shared evidence. Grouping should preserve the underlying cases and their scores rather than deleting them from audit records.

    Measure what the observed labels support

    If every reviewed case gets a reliable outcome, precision among reviewed cases is estimable. Population recall requires information about positives outside the queue. Random or stratified audits can supply that information; record inclusion probabilities if using weighted estimates. Reviewer-selected cases alone cannot identify how many threats were missed.

    Track unresolved outcomes and time to resolution. A model that surfaces harder cases may initially show a lower confirmed-positive rate simply because investigations take longer. Compare matured cohorts or model the delay explicitly. Keep the definitions of confirmed benign, confirmed harmful, insufficient evidence, and unresolved separate.

    Explain the score in the units it actually uses

    A useful explanation contains the unusual raw behavior, the relevant peer baseline, the model’s feature contribution when valid, and supporting records. For example: “Seven-day activity is at the 99.7th percentile among the declared peer group; the feature contributed +0.12 to the model output under this explainer.” The percentile and contribution answer different questions; neither independently establishes maliciousness.

    If using SHAP for an isolation model, verify the explainer’s output space. An implementation may explain an isolation-related quantity rather than your transformed anomaly score. A nonlinear transformation does not preserve additive feature contributions. Test that baseline plus contributions reconstructs the exact output being displayed, and label that output clearly.

    Feedback should improve the next model without leaking into this one

    Store reviewer outcomes with timestamps, confidence, and reason codes. A future supervised model can learn from these labels, but the labels inherit the queue’s selection policy. Preserve sampled background reviews and model versions so training can distinguish policy changes from population changes. Never backfill future outcomes into historical features during evaluation.

    Monitor queue concentration by tenant, category, and missing-data state. A sudden surge can be a real incident, a schema change, or an outage. Compare feature distributions and model outputs on a frozen reference set to separate those explanations. Keep a fallback queue policy and a way to replay failed scoring partitions without emitting duplicate alerts.

    A compact case record

    case = {
    "entity_key": ["app-A", "tenant-7"],
    "window_end": "2026-08-01",
    "model_version": "iforest-v3",
    "score_name": "negative_score_samples",
    "score": 0.63,
    "queue_policy": "top-200-per-day-v2",
    "feature_snapshot": "features-v8",
    "evidence_ids": ["event-group-41"],
    "outcome": "unresolved",
}  # Synthetic schema; explanation output is stored separately.
    Check your understanding: Can a top-1% queue prove that the true anomaly rate is 1%?

    No. The queue policy selects a fraction by construction. The underlying prevalence and the usefulness of those cases require independent evidence.
