    RAG Evaluation: Find the Evidence, Use It, and Cite It

    September 2026 · 4 min read

    Before you start: Pipeline-stage diagnosis and RAG fundamentals.

    A RAG answer can sound convincing while citing the wrong passage. It can faithfully repeat an outdated document. It can retrieve the right evidence and then ignore it. Evaluate the pipeline at these separate boundaries so a poor answer leads to a specific repair.

    Define the evidence set and its granularity

    For “Can I return a discounted item after 20 days?”, the answer may require a general return window and a sale-item exception. A single relevant passage is not necessarily sufficient. Annotate atomic evidence requirements and whether one passage can satisfy each requirement. Keep document identity, revision time, passage offsets, and access rules with every judgment.

    Retrieval succeeded in finding the exception. Context construction failed to preserve it. Increasing top-K alone may not fix the answer.
    RequirementRetrieved?In final context?
    General 30-day return windowYesYes
    Discounted items have a 14-day windowYesNo: dropped during truncation
    Applicable purchase dateProvided by userYes

    Evidence recall measures how many annotated requirements have supporting material in the retrieved set or final context. Context precision asks how much supplied material is useful under a declared labeling unit. Neither should use answer similarity as a substitute for passage relevance. Track the budget in tokens because a hundred tiny chunks and a hundred full pages impose different generation workloads.

    Correctness and faithfulness are different axes

    Correctness compares the answer with the task’s truth or accepted reference. Faithfulness asks whether the answer’s claims follow from the supplied evidence. An answer can be faithful to a stale policy and still be wrong today. It can also be correct by coincidence while unsupported by its citations. Store both judgments, and define how temporal truth is resolved.

    Break the answer into checkable claims. For each claim, identify supporting evidence, contradiction, or insufficient support. Then assess completeness: did the answer include the exception that changes the user’s action? Averaging many trivial supported claims can hide one unsupported consequential claim, so include a task-level success judgment and severity labels.

    Evaluate links and support separately

    Citation validity checks whether the reference resolves to the correct document and revision. Citation support checks whether the cited span entails the associated claim. Citation completeness asks whether claims needing evidence actually have it. A real URL attached to an unsupported sentence passes the first test and fails the second. Avoid scoring the mere presence of brackets as grounding.

    Three runs that localize the problem

    Gold-context performance is a diagnostic ceiling under that context, not a production benchmark. Keep the prompt and generation settings matched.
    RunPurposeInterpretation
    Retrieved context + generatorMeasures the deployed pipelineThe end-to-end baseline
    Gold sufficient context + same generatorRemoves retrieval/context failureRemaining errors belong to generation or the task specification
    Retrieved context + evidence-only inspectionAudits usable evidence before generationReveals missing, conflicting, stale, or truncated support

    Also test irrelevant context, conflicting passages, document prompt injection, and genuinely unanswerable questions. A system that confidently answers every query can look good on an all-answerable benchmark and fail badly in use. Measure answer coverage alongside correctness among answered cases and the rate of unsupported answers; abstaining on everything should not win.

    Use an LLM judge as a measured instrument

    Give the judge the question, candidate answer, evidence actually supplied, and a precise rubric. Hide system identity, randomize pairwise order where relevant, and audit disagreement against human judgments. Freeze judge configuration and save raw outputs. Treat the judge’s labels as measurements with errors, especially for domain-specific exceptions and arithmetic.

    Use paired comparisons on the same questions and report uncertainty as in the model-comparison chapter. Segment by answerability, evidence count, document age, and query type. A single “RAG score” obscures whether the system retrieves, reasons, cites, or abstains well.

    Check your understanding: Gold-context accuracy is high but deployed accuracy is low. What should you inspect first?

    Inspect retrieval coverage and the final context after filtering, reranking, deduplication, and truncation. The gap suggests an evidence-supply problem; it does not prove that the embedding model alone is responsible.
