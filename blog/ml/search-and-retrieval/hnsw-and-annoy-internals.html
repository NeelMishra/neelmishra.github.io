    HNSW and Annoy: Two Ways to Avoid Comparing Every Vector

    September 2026 · 4 min read

    Before you start: Vectors, dot products, and the existing indexing overview.

    With a million item vectors, exact search computes a similarity against every item. Approximate nearest-neighbor methods spend less work by exploring promising regions. HNSW organizes vectors as a navigable graph; Annoy partitions space with a forest of random-projection trees. Both trade search work, memory, and recall, but their mechanics differ.

    A hierarchy of graphs

    HNSW assigns nodes to random levels, with fewer nodes in higher levels. Search starts near the top and greedily moves to closer neighbors. At the lowest layer, it maintains a candidate frontier and a bounded set of promising results. A larger search frontier gives more chances to cross local traps, at the cost of more distance computations.

    During insertion, the algorithm searches for candidate neighbors and selects connections that support navigation. The neighbor count parameter M affects connectivity and memory. Construction effort influences graph quality; query-time efSearch controls exploration in the built graph. Increasing efSearch cannot recreate every connection that poor construction omitted, although it can compensate partially by doing more work.

    A forest of random projection splits

    Annoy builds several trees that split the vector space using random hyperplanes. A query descends through trees, gathers candidates from promising leaves, then compares candidate vectors. Multiple trees provide different partitions so a boundary mistake in one tree can be corrected by another. The index can be saved and memory-mapped across processes.

    The number of trees controls build cost, size, and potential recall. search_k controls search effort; its default depends on the requested neighbors and tree count in Annoy’s API. Benchmark explicit values rather than assuming two runs with different K used equal effort. Annoy’s normal workflow builds an immutable index; updates generally require rebuilding rather than arbitrary insertion into a finalized index.

    Similarity choices must agree

    Cosine similarity, inner product, and Euclidean distance are not interchangeable on unnormalized vectors. For unit vectors, squared Euclidean distance is 2−2cosine, so their neighbor order agrees. Annoy’s angular distance corresponds to a transformation of cosine distance; do not display it as a raw cosine score. For inner product search, use an implementation and index type that supports the intended objective.

    Tie handling matters for duplicated or quantized vectors. Deduplicate IDs, keep deterministic ordering for equal scores, and decide whether exact-ground-truth ties allow any equally distant neighbor. A strict ID-overlap recall can penalize a valid alternative tie unless the benchmark defines its policy.

    Choose by workload, not a universal winner

    Evaluate the real vector distribution, query mix, dimensionality, filtering, update pattern, and process model. An immutable memory-mapped catalog and a frequently updated online graph have different operational needs. Index memory includes graph links or tree structures, IDs, and overhead in addition to vectors. Cold-page behavior can matter when using mapped files.

    Use the benchmarking chapter to compare methods against the same exact neighbors and resource constraints. Keep human relevance evaluation separate: an index can faithfully recover neighbors from a poor representation.

    Check your understanding: If two unit vectors have cosine similarity 0.8, what is their squared Euclidean distance?

    2−2×0.8=0.4. This ordering equivalence depends on normalization; it does not hold for arbitrary vector norms.
