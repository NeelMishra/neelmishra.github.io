    DPO and PPO: Same Motivation, Different Learning Problems

    September 2026 · 4 min read + experiments

    Compare data collection, policy ratios, credit assignment, and evaluation so you can explain precisely what changes when moving between DPO and PPO.

    Read the explanation

    Compare the evidence each method receives

    DPO and PPO can both be used to improve a language model’s answers. The most useful distinction is how they obtain a training signal. Standard offline DPO uses recorded chosen/rejected pairs. Language-model PPO samples responses, scores them, and estimates advantages.

    If one experiment uses style preferences and another uses executable correctness rewards, their results reflect different evidence as well as different algorithms. First state what each method was asked to learn.

    Keep five differences in view

    QuestionOffline DPOPPO for language models
    What is one example?A prompt with chosen/rejected answersA sampled response with rewards
    What weights the update?A coefficient from the pair lossEstimated advantages, often using a critic
    What does the reference do?Defines the baseline for preference scoresOften supplies a penalty for drifting from a starting model
    Is there an old-policy ratio?No, not in the standard DPO lossYes; it compares against the policy that sampled the batch
    When is new data generated?Before a fixed-dataset training stageBetween rollout-and-update iterations

    The original DPO paper and PPO paper define these two objectives. The PPO role table explains why its old policy and longer-lived reference are separate.

    A pair label is not a token-level explanation

    DPO sums the response’s token log probabilities, then applies the pair loss. Each chosen token contributes through that sum; rejected tokens contribute with the opposing incentive. A response-level preference does not explicitly identify which sentence caused the judgment.

    PPO uses an advantage estimator to assign weights along a sampled response. This is a different credit-assignment mechanism, but its usefulness still depends on the reward and critic. Neither method knows the judge’s reason unless the training signal actually contains it.

    A shared motivation does not make the updates identical

    DPO’s derivation relates preferences to reward optimization with a reference penalty. PPO can optimize a reward-based objective. That connection does not make finite DPO and PPO runs equivalent: their sampled data, estimated signals, and optimizer steps differ.

    Count the actual work

    Offline DPO removes online rollout generation and a learned critic from its basic training loop. It still scores two answers per pair, needs reference scores, and backpropagates through the trainable policy. Long responses can make that expensive. Compare scored tokens, generated tokens, and memory use under a stated configuration.

    New pairs can update what DPO learns from

    An iterative pipeline can generate answers from an improved model, judge new pairs, and run another DPO stage. This can reveal mistakes absent from the original dataset. It also adds generation and labeling costs. State whether a result uses a fixed dataset or repeated collection.

    Some trainers support several preference losses under one API. TRL documents those options; record the selected loss and reference configuration when comparing runs.

    Choose the next experiment from the available signal

    • Representative, trustworthy pairs: test whether offline DPO learns the distinctions they contain.
    • Failures that emerge in fresh model outputs: budget for new generation and judging, whichever optimizer you use.
    • A direct task verifier: consider a reward-based workflow such as PPO or GRPO, and first inspect whether the verifier measures the intended behavior.

    Use the same held-out prompts and evaluation protocol to compare the resulting models. The data and diagnostics chapter provides the checks for separating pair fit from generated-answer quality.
