    PPO for Language Models: Tokens, Rewards, and Two Different Anchors

    September 2026 · 5 min read + experiments

    Apply the general algorithm to text while separating old and reference policies, handling token masks, and making the sampling distribution explicit.

    Read the explanationTry the calculation

    Generating a response is a sequence of actions

    For a language model, the state is the prompt plus the response so far. The action is the next token. Appending it creates the next state. A complete response is an episode, often ending when the model emits an end-of-sequence token, EOS.

    The PPO loop is familiar: generate responses, score them, estimate advantages, and update on that fixed batch. The InstructGPT paper gives a concrete example using a learned human-preference reward model. A verifier, such as a test runner, can supply the task score instead.

    Keep the old policy separate from the reference

    PPO needs a record of the policy that generated the current batch. Language-model training often also uses a longer-lived reference to discourage excessive drift. They have different jobs:

    RoleWhat it measuresWhen it changes
    $\pi_{\mathrm{old}}$Which policy generated this batch?Refresh at each rollout iteration
    $\pi_\theta$How likely is this action under the trainable actor?Every optimizer step
    $\pi_{\mathrm{ref}}$How far is behavior from a chosen reference?Often held fixed across the run
    $V_\phi$What return is expected from this prefix?Critic optimization
    Task scorerHow good was the response under the task definition?Fixed for a simple PPO training stage

    The old policy is yesterday’s snapshot for this update: compare current probabilities with it for PPO clipping. The reference is the chosen starting anchor for the training stage. Many small updates can stay close to their individual snapshots while accumulating a large change from that reference.

    You do not necessarily need a full model copy for every role. Old sampled-token log probabilities can be stored in the batch. The critic can share features with the actor, and the task scorer can be a separate program.

    Give the answer a score and account for reference drift

    A common recipe assigns a score to the completed answer and a reference penalty along the response. At each sampled token, compare the old policy’s log probability with the reference’s log probability for that same token and prefix. Multiply the difference by a positive penalty strength, $\beta$:

    reference_log_ratio = old_logp - ref_logp
reward = -beta * reference_log_ratio
reward[last_response_token] += answer_score

    Here the arrays cover response tokens only. The final line adds the task score once. Compute these rollout rewards before GAE and hold them fixed during the batch’s optimizer passes. With no time discount, the return is the answer score minus the sum of sampled reference penalties.

    A single sampled log ratio can be negative. Its average under the old policy corresponds to KL divergence from old to reference. The recipe is illustrated in InstructGPT’s PPO training objective. Other recipes put an explicit reference loss in the optimizer; choose one definition and avoid accidentally counting the same penalty twice.

    Score the token from the prefix that produced it

    A causal model’s output at a position predicts the next token. When re-scoring a saved response, align each prediction with that next token’s ID. The critic prediction also belongs to the prefix before the action. Use the figure to follow one response token at a time:

    A loss mask is simply a keep-or-ignore flag: 1 for generated response actions, 0 for prompt and padding positions. Include EOS when it was sampled as an action. The model reads the prompt, but PPO does not train it as if the prompt tokens were actions the model chose.

    State how you average variable-length responses. Summing token contributions within each response and then averaging responses gives every episode its summed contribution. Averaging tokens separately inside each response gives long responses less weight per token. Both can be implemented; they are different training rules.

    The saved probabilities must match generation

    If generation uses a temperature, apply that same temperature when recording and re-computing action probabilities. Otherwise, the denominator describes a different sampler. Top-k and top-p filtering also alter the distribution and can remove actions entirely; a simple teaching implementation can avoid these filters.

    Before the first optimizer step, verify that current/old ratios are near 1 on valid response positions. Compare a few generation-time scores with a full scoring pass. Mismatches often reveal a token shift, attention-mask error, or inconsistent sampling setting.

    Also decide what the maximum-length cutoff means. If it ends the task, there is no future value; if it merely interrupts collection, apply the truncation rule. A configuration label alone cannot make that decision.

    Check the answers, not just the training score

    A model can exploit a scorer through verbosity, formatting, or verifier loopholes. Evaluate with checks independent of the training reward and inspect generated answers. Track task score, reference penalty, response length, and EOS frequency separately so a rising combined score has an explanation.

    Continue with preference pairs

    DPO changes the evidence used for training: it learns from chosen/rejected answer pairs. Its series starts with one comparison and builds the loss from there. The DPO/PPO comparison connects the workflows after those pieces are clear.
