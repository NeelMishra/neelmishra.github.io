    Rotated Sorted Arrays

    March 2026 · 24 min read

    So far the series has generalized binary search away from arrays entirely — onto a predicate over the answer space and its min-max optimization variants. This post returns to arrays, but broken ones. A rotated sorted array is a sorted array whose sort order is severed at a single point. It is no longer globally sorted, so the plain exact-match template does not apply directly — yet a slightly cleverer invariant recovers the full $O(\log n)$ search. We cover finding the pivot (minimum), searching for a target, and the honest reason duplicates can drag the worst case down to $O(n)$.

    The load-bearing fact. When you split a rotated sorted array at any midpoint, at least one of the two halves is still fully sorted. Every algorithm below is just "identify the sorted half, then decide with an ordinary range check."

    Rotated Sorted Array

    A rotated sorted array is a sorted array that has been cycled: some suffix has been moved to the front. For example, [4, 5, 6, 7, 0, 1, 2] is [0, 1, 2, 4, 5, 6, 7] rotated at index 4. The array is no longer globally sorted, but each "half" around the rotation point is individually sorted.

    Finding the Pivot (Minimum Element)

    The pivot is the index of the smallest element. In a rotated sorted array, it is the point where the value drops. Finding the pivot is a binary search problem: at each step, check which half is sorted and which half contains the drop.

    Find Minimum in Rotated Sorted Array

    int findMin(vector<int>& nums) {
    int lo = 0, hi = (int)nums.size() - 1;

    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;

        if (nums[mid] > nums[hi]) {
            // mid is in the left (larger) portion
            // pivot is in (mid, hi]
            lo = mid + 1;
        } else {
            // mid is in the right (smaller) portion
            // pivot is in [lo, mid]
            hi = mid;
        }
    }

    return nums[lo];  // minimum value; lo is the pivot index
}

    Why compare with nums[hi]?

    • If nums[mid] > nums[hi], the rotation break must be between mid and hi. The left portion is sorted but contains larger values. So lo = mid + 1.
    • If nums[mid] <= nums[hi], the right portion from mid to hi is sorted and mid could be the minimum. So hi = mid.

    Complexity: $O(\log n)$ time, $O(1)$ space.

    Searching in a Rotated Sorted Array

    Once you know the structure, searching becomes possible in a single pass. The key observation: when you pick mid, at least one of the two halves (lo to mid, or mid to hi) must be sorted. Check that sorted half to decide which side the target is on.

    Search in Rotated Sorted Array

    int search(vector<int>& nums, int target) {
    int lo = 0, hi = (int)nums.size() - 1;

    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;

        if (nums[mid] == target) return mid;

        if (nums[lo] <= nums[mid]) {
            // Left half [lo..mid] is sorted
            if (target >= nums[lo] && target < nums[mid]) {
                hi = mid - 1;
            } else {
                lo = mid + 1;
            }
        } else {
            // Right half [mid..hi] is sorted
            if (target > nums[mid] && target <= nums[hi]) {
                lo = mid + 1;
            } else {
                hi = mid - 1;
            }
        }
    }

    return -1;
}

    Step-by-step logic

    1. Compute mid. If it is the target, return.
    2. Check if the left half [lo..mid] is sorted by comparing nums[lo] with nums[mid].
    3. If the left half is sorted, check if the target falls within [nums[lo], nums[mid]). If yes, search left. Otherwise, search right.
    4. If the left half is not sorted, the right half must be sorted. Apply the symmetric check.

    Handling Duplicates — and Why O(n) Is Unavoidable

    Everything so far assumed distinct values. With duplicates, the comparison against nums[hi] (for the pivot) or the "which half is sorted" test (for the search) can become ambiguous. The dangerous case is nums[lo] == nums[mid] == nums[hi]: both halves look equally (un)sorted, and neither range check can rule out a side.

    Find Minimum II (with duplicates)

    int findMinWithDup(vector<int>& nums) {
    int lo = 0, hi = (int)nums.size() - 1;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (nums[mid] > nums[hi]) {
            lo = mid + 1;          // pivot strictly right of mid
        } else if (nums[mid] < nums[hi]) {
            hi = mid;              // pivot at mid or left
        } else {
            // nums[mid] == nums[hi]: cannot tell. hi is a duplicate
            // of mid, so dropping it cannot remove every copy of the minimum.
            hi--;
        }
    }
    return nums[lo];
}

    The else branch shrinks hi by one instead of halving. This is safe — nums[hi] equals nums[mid], which stays in the window, so we never discard the only copy of the minimum — but it is slow. On an input like [1, 1, 1, 1, 1, 0, 1] (or the all-equal [2, 2, 2, 2, 2]), the ambiguous branch fires every iteration and the search decays to a linear scan.

    Why O(n) is fundamental here, not just a weak implementation. Consider [1, 1, …, 1] with a single 0 hidden at an unknown index. Any algorithm that has only looked at 1s so far has learned nothing about where the 0 is; an adversary can always place the 0 in whichever half you did not examine. Distinguishing "all ones" from "ones with one zero" therefore requires inspecting $\Omega(n)$ positions in the worst case. Duplicates destroy the strict monotonicity that binary search feeds on.

    The search-for-target variant (LeetCode 81) takes the same medicine: when nums[lo] == nums[mid] == nums[hi], do lo++; hi--; and continue. Average case stays $O(\log n)$ when duplicates are rare; worst case is $O(n)$.

    bool searchWithDup(vector<int>& nums, int target) {
    int lo = 0, hi = (int)nums.size() - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (nums[mid] == target) return true;
        if (nums[lo] == nums[mid] && nums[mid] == nums[hi]) {
            lo++; hi--;                       // strip ambiguous ends
        } else if (nums[lo] <= nums[mid]) {   // left half sorted
            if (nums[lo] <= target && target < nums[mid]) hi = mid - 1;
            else lo = mid + 1;
        } else {                              // right half sorted
            if (nums[mid] < target && target <= nums[hi]) lo = mid + 1;
            else hi = mid - 1;
        }
    }
    return false;
}

    Problem Recognition Guide

    How do you recognize a rotated-array problem, and which routine does it need?

    Task Clues in the problem Comparison to make
    Find pivot / minimum "Sorted and rotated", find the smallest / the rotation count Compare nums[mid] with nums[hi]
    Search for a target "Search in rotated sorted array", membership or index query Compare nums[lo] with nums[mid] to find the sorted half
    Same, with duplicates "May contain duplicates" (LeetCode 81 / 154) Add the nums[lo]==nums[mid]==nums[hi] shrink; accept $O(n)$ worst case

    Key Takeaways

    • A distinct rotated sorted array has at most one strict drop (zero if unrotated); splitting at any midpoint leaves at least one half fully sorted.
    • To find the pivot/minimum, compare nums[mid] with nums[hi]: > means the drop is to the right (lo = mid + 1), otherwise the minimum is at mid or left (hi = mid).
    • To search for a target, compare nums[lo] with nums[mid] to detect the sorted half, then use an ordinary range check to decide which side to keep.
    • Use nums[hi] for the pivot but nums[lo] vs nums[mid] for the target search — mixing them up is the classic bug.
    • Duplicates can make nums[lo] == nums[mid] == nums[hi], forcing a one-step lo++/hi-- shrink and an $O(n)$ worst case that is information-theoretically unavoidable.
