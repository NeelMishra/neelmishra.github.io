    Partition-Based Search: Median of Two Sorted Arrays

    March 2026 · 26 min read

    Earlier posts searched array positions, answer values, pivots, and peaks. This post introduces another search object: a partition cut. To find the median of two sorted arrays we do not search for the median directly — we search for the cut that splits their conceptual merge into two ordered halves. We never merge anything. Failed cross-boundary checks tell us whether the cut must move left or right, producing an $O(\log(\min(m,n)))$ solution to LeetCode 4.

    The problem (LeetCode 4)

    We are given two sorted arrays $A$ of length $m$ and $B$ of length $n$. Imagine merging them into one sorted array $C$ of length $m+n$. The median is the middle element of $C$ when $m+n$ is odd, and the average of the two middle elements when $m+n$ is even. We must return it in $O(\log(\min(m,n)))$ time without materializing $C$.

    The obvious approach is to merge with two pointers, walking both arrays in lockstep and copying the smaller front element each time. That produces $C$ correctly, but it touches every element, so it is $O(m+n)$ time and $O(m+n)$ space. We can shave the space to $O(1)$ by counting up to the middle instead of copying, but the time stays linear: we still advance a pointer once per element up to the median position.

    Linear is fine for many inputs, but the $O(\log(\min(m,n)))$ bound tells us something deeper is possible. The median does not depend on where most elements are — it depends only on the handful of elements straddling the middle. If we could jump straight to the right split of the two arrays, we would never touch the bulk. That is exactly what partition-based binary search does: it converges on the split in a logarithmic number of steps, inspecting only four boundary elements per step.

    Why partitioning beats merging. Merging computes the entire order of $C$; the median only needs the order at the middle. Binary searching the partition point discards half the candidate splits per step, so we reach the correct split in $O(\log(\min(m,n)))$ comparisons — an exponential improvement over the linear walk when the arrays are large.

    The partition invariant

    Fix a number $\text{halfLen} = \lfloor (m+n+1)/2 \rfloor$. This is the size of the “left half” we want to carve out: the $\text{halfLen}$ smallest elements of the combined multiset. The $+1$ before the floor makes the left half hold the extra element when $m+n$ is odd, which is exactly where the median lives, so the median is always the largest element of the left half (for odd totals) or sits on the boundary (for even totals).

    Now choose an integer $\text{cutA} \in [0, m]$: take the first $\text{cutA}$ elements of $A$ into the left half. Because the left half must total $\text{halfLen}$, the number taken from $B$ is forced:

    $$\text{cutB} = \text{halfLen} - \text{cutA}.$$

    So a single scalar $\text{cutA}$ determines the whole split. We name the four elements straddling the two cuts:

    • Aleft = A[cutA - 1] — the last element of $A$ on the left side.
    • Aright = A[cutA] — the first element of $A$ on the right side.
    • Bleft = B[cutB - 1] — the last element of $B$ on the left side.
    • Bright = B[cutB] — the first element of $B$ on the right side.

    The partition is valid iff

    $$\text{Aleft} \le \text{Bright} \quad\text{and}\quad \text{Bleft} \le \text{Aright}.$$

    Why validity means “left half is the smallest halfLen elements”

    The left half consists of $A[0..\text{cutA}-1]$ and $B[0..\text{cutB}-1]$; the right half is everything else. We want every left element $\le$ every right element. Because both arrays are individually sorted, the only comparisons that can fail are the cross comparisons between one array's left tail and the other array's right head. Concretely:

    • Within $A$: $A[\text{cutA}-1] \le A[\text{cutA}]$ automatically (sorted).
    • Within $B$: $B[\text{cutB}-1] \le B[\text{cutB}]$ automatically (sorted).
    • Cross 1: is $\text{Aleft} \le \text{Bright}$? — $A$'s left tail vs $B$'s right head.
    • Cross 2: is $\text{Bleft} \le \text{Aright}$? — $B$'s left tail vs $A$'s right head.

    If both cross checks hold, then $\max(\text{Aleft}, \text{Bleft}) \le \min(\text{Aright}, \text{Bright})$: the largest left element does not exceed the smallest right element. Hence the left half is exactly a set of $\text{halfLen}$ elements no larger than any right element — that is the definition of “the $\text{halfLen}$ smallest.” The median then reads straight off the boundary: $\max(\text{Aleft}, \text{Bleft})$ for odd totals, and the average of $\max(\text{Aleft}, \text{Bleft})$ and $\min(\text{Aright}, \text{Bright})$ for even totals.

    Monotonicity (why binary search applies). As $\text{cutA}$ increases by one, $\text{Aleft}$ can only grow and $\text{Aright}$ moves to a larger element, while $\text{cutB}$ decreases so $\text{Bright}$ can only shrink. So the quantity $\text{Aleft} - \text{Bright}$ is non-decreasing in $\text{cutA}$. There is a single threshold: below it $\text{Aleft} \le \text{Bright}$ holds and the partition is too far left; above it, it is too far right. That monotone flip is precisely what binary search locates.

    Sentinels for the edges

    When a cut sits at position $0$ there is no Aleft; when it sits at the end there is no Aright. Rather than special-casing these, we define

    $$\text{Aleft} = -\infty \text{ if } \text{cutA}=0, \qquad \text{Aright} = +\infty \text{ if } \text{cutA}=m,$$

    and symmetrically for $B$. A missing left element is $-\infty$ so it never violates “left $\le$ right”; a missing right element is $+\infty$ so nothing on the left can exceed it. With sentinels, the two-line validity test is correct for every cut, including the extremes, with no index ever going out of bounds.

    The search

    We binary search $\text{cutA}$ over the closed interval $[0, m]$. At each step we compute the four boundary values (with sentinels) and test validity:

    • If $\text{Aleft} > \text{Bright}$: we pulled too many elements from $A$ into the left half. Shrink: hi = cutA - 1.
    • If $\text{Bleft} > \text{Aright}$: we pulled too few from $A$. Grow: lo = cutA + 1.
    • Otherwise both cross checks hold — valid partition, read off the median.

    The two failed cross-checks point in opposite directions, so each iteration discards cuts that cannot work and the loop reaches a valid $\text{cutA}$. With duplicates, several adjacent cuts may all be valid; any one yields the same median. Here is the complete implementation:

    #include <vector>
#include <algorithm>
#include <climits>
#include <stdexcept>
using namespace std;

double findMedianSortedArrays(vector<int>& A, vector<int>& B) {
    if (A.empty() && B.empty())
        throw invalid_argument("median is undefined for two empty arrays");
    // Always binary search the shorter array (see next section).
    if (A.size() > B.size()) return findMedianSortedArrays(B, A);

    int m = A.size(), n = B.size();
    int lo = 0, hi = m;
    int halfLen = (m + n + 1) / 2;

    // Sentinels wider than any possible int value.
    const long long NEG = LLONG_MIN, POS = LLONG_MAX;

    while (lo <= hi) {
        int cutA = lo + (hi - lo) / 2;   // elements of A on the left
        int cutB = halfLen - cutA;       // forced: elements of B on the left

        long long Aleft  = (cutA == 0) ? NEG : (long long)A[cutA - 1];
        long long Aright = (cutA == m) ? POS : (long long)A[cutA];
        long long Bleft  = (cutB == 0) ? NEG : (long long)B[cutB - 1];
        long long Bright = (cutB == n) ? POS : (long long)B[cutB];

        if (Aleft <= Bright && Bleft <= Aright) {
            // Valid partition.
            if ((m + n) % 2 == 1)
                return (double)max(Aleft, Bleft);
            return ((double)max(Aleft, Bleft) + (double)min(Aright, Bright)) / 2.0;
        } else if (Aleft > Bright) {
            hi = cutA - 1;   // too many from A
        } else {
            lo = cutA + 1;   // too few from A
        }
    }
    throw logic_error("sorted inputs must admit a valid partition");
}
    Sentinel choice. INT_MIN/INT_MAX are valid sentinels for int data even when the data equals those extremes: the algorithm uses non-strict comparisons, so equality causes no ambiguity. Promoting boundaries to long long and using LLONG_MIN/LLONG_MAX simply makes the conceptual infinities distinct from every real int and keeps later arithmetic explicit. We cast to double before averaging so the even-length result preserves its fractional half.

    Always binary search the shorter array

    The first line swaps so that $m = |A| \le |B| = n$. For the simple search interval cutA in [0,m] used here, this guarantees the forced cutB stays in range and delivers the $O(\log(\min(m,n)))$ bound. A longer-array implementation can still be correct, but it must tighten the cut bounds to [max(0, halfLen-n), min(m, halfLen)]; blindly searching its full range is what causes invalid partner cuts.

    Why the swap keeps cutB valid

    We search $\text{cutA} \in [0, m]$ and set $\text{cutB} = \text{halfLen} - \text{cutA}$ with $\text{halfLen} = \lfloor (m+n+1)/2 \rfloor$. For the four-boundary logic to be sound we need $\text{cutB} \in [0, n]$ for every $\text{cutA}$ in range.

    • Upper bound. $\text{cutB}$ is largest when $\text{cutA}=0$: then $\text{cutB} = \text{halfLen} = \lfloor (m+n+1)/2 \rfloor$. Since $m \le n$, we have $m + n + 1 \le 2n + 1$, so $\text{halfLen} \le \lfloor (2n+1)/2 \rfloor = n$. Thus $\text{cutB} \le n$. ✓
    • Lower bound. $\text{cutB}$ is smallest when $\text{cutA}=m$: then $\text{cutB} = \text{halfLen} - m = \lfloor (m+n+1)/2 \rfloor - m = \lfloor (n-m+1)/2 \rfloor \ge 0$ because $n \ge m$. Thus $\text{cutB} \ge 0$. ✓

    If we searched the longer array over its full interval, $\text{cutB} = \text{halfLen} - \text{cutA}$ could go negative or exceed $n$. Searching the shorter array lets us use the clean full interval without deriving tighter endpoints. The guard/swap is simply:

    if (A.size() > B.size()) return findMedianSortedArrays(B, A);
// From here on, m = A.size() <= n = B.size().

    Complexity. The loop halves an interval of size $m+1$ each step, so it runs in $O(\log m) = O(\log(\min(m,n)))$ time and $O(1)$ extra space. Each step does a constant amount of work (four look-ups and two comparisons). That is optimal: any correct algorithm must at least read enough to distinguish the median, and the logarithm of the shorter length is the known lower bound for this comparison structure.

    Generalization to the Kth element

    The median is a special case of a more general question: what is the $k$-th smallest element of the merge of $A$ and $B$? The partition idea handles it — just target a left half of size $k$ instead of $\text{halfLen}$ — but there is a second, equally famous view that many find easier to reason about: the discard-$k/2$ recursion, which runs in $O(\log(m+n))$.

    The discard-k/2 method

    To find the $k$-th smallest (1-indexed) across two sorted arrays, look at the $\lfloor k/2 \rfloor$-th element of each remaining prefix. Whichever is smaller cannot be the answer and neither can anything before it: those $\lfloor k/2 \rfloor$ elements are all guaranteed to be among the $k-1$ smallest. So we discard that prefix and reduce $k$ accordingly. Each round throws away roughly $k/2$ elements, halving $k$, hence the logarithmic bound.

    #include <vector>
#include <algorithm>
using namespace std;

// k is 1-indexed: k = 1 returns the smallest element overall.
int kthElement(const vector<int>& A, const vector<int>& B, int k) {
    int ia = 0, ib = 0;                 // current front of each array
    int na = A.size(), nb = B.size();
    if (k < 1 || k > na + nb)
        throw out_of_range("k must be in [1, A.size() + B.size()]");
    while (true) {
        if (ia == na) return B[ib + k - 1];   // A exhausted
        if (ib == nb) return A[ia + k - 1];   // B exhausted
        if (k == 1) return min(A[ia], B[ib]); // smallest remaining

        int half = k / 2;
        // Peek at up to 'half' elements in each (clamped to what remains).
        int pa = min(ia + half, na) - 1;      // index of A's candidate
        int pb = min(ib + half, nb) - 1;      // index of B's candidate

        if (A[pa] <= B[pb]) {
            k -= (pa - ia + 1);   // discard A[ia..pa]
            ia = pa + 1;
        } else {
            k -= (pb - ib + 1);   // discard B[ib..pb]
            ib = pb + 1;
        }
    }
}

    Clamping each peek to the array's end (min(ia + half, na)) is what lets one array run shorter than the other without a special case: if $A$ has fewer than $\lfloor k/2 \rfloor$ elements left, we peek at its last element instead, and the exhaustion checks at the top finish the job on the next turn.

    Relating Kth back to the median

    Let $N = m + n$. The median is a specific order statistic, so we can express it purely through kthElement:

    • Odd $N$: the median is the $\lceil N/2 \rceil$-th smallest, i.e. kthElement(A, B, (N + 1) / 2). For our running example $N = 11$, that is $k = 6$.
    • Even $N$: average the two central order statistics, casting before addition so two large ints cannot overflow: ((double)kthElement(A, B, N/2) + kthElement(A, B, N/2 + 1)) / 2.0.

    Both views are correct; the partition method is $O(\log(\min(m,n)))$ (slightly tighter) while discard-$k/2$ is $O(\log(m+n))$ and generalizes verbatim to any $k$. Pick whichever you can write bug-free under pressure.

    A full dry run

    Let $A = [1, 3, 8, 9, 15]$ ($m = 5$) and $B = [7, 11, 18, 19, 21, 25]$ ($n = 6$). $A$ is already the shorter array, so no swap. Total $N = 11$ is odd, and $\text{halfLen} = \lfloor (11 + 1)/2 \rfloor = 6$. We search $\text{cutA} \in [0, 5]$.

    lo = 0, hi = 5 → cutA = 2, cutB = 4

    Left of $A$: $[1, 3]$; left of $B$: $[7, 11, 18, 19]$. Boundaries: Aleft = A[1] = 3, Aright = A[2] = 8, Bleft = B[3] = 19, Bright = B[4] = 21.

    Test: $\text{Aleft} \le \text{Bright}$? $3 \le 21$ ✓. $\text{Bleft} \le \text{Aright}$? $19 \le 8$ ✗. Cross 2 fails — $B$'s left tail ($19$) is bigger than $A$'s right head ($8$), so we took too few from $A$. Move lo = cutA + 1 = 3.

    lo = 3, hi = 5 → cutA = 4, cutB = 2

    Left of $A$: $[1, 3, 8, 9]$; left of $B$: $[7, 11]$. Boundaries: Aleft = A[3] = 9, Aright = A[4] = 15, Bleft = B[1] = 11, Bright = B[2] = 18.

    Test: $\text{Aleft} \le \text{Bright}$? $9 \le 18$ ✓. $\text{Bleft} \le \text{Aright}$? $11 \le 15$ ✓. Valid partition!

    Read off the median

    The left half is $\{1, 3, 8, 9\} \cup \{7, 11\} = \{1,3,7,8,9,11\}$ — exactly the 6 smallest. Since $N = 11$ is odd, the median is $\max(\text{Aleft}, \text{Bleft}) = \max(9, 11) = \boxed{11}$.

    Sanity check by merging: $[1, 3, 7, 8, 9, \mathbf{11}, 15, 18, 19, 21, 25]$ — the 6th of 11 elements is indeed $11$.

    Common Mistakes

    Searching the longer array with naive bounds. If you binary search its full interval, the forced $\text{cutB}$ can leave $[0,n]$. Either swap so $m \le n$ (the clean, standard solution) or derive the tighter legal interval explicitly.
    Wrong halfLen parity. Using $\lfloor (m+n)/2 \rfloor$ instead of $\lfloor (m+n+1)/2 \rfloor$ silently breaks the odd case: the median stops being the maximum of the left half. The $+1$ puts the middle element on the left side so max(Aleft, Bleft) is the answer for odd totals.
    Missing sentinels. Forgetting the $\pm\infty$ guards at $\text{cutA}=0$ / $\text{cutA}=m$ (or the same for $B$) reads A[-1] or A[m] — out-of-bounds, undefined behavior. Sentinels make the edges just work.
    Integer overflow / wrong average type. The sentinels themselves are safe, but adding two central int values before converting can overflow, and integer division truncates halves. Promote or cast before addition, then divide by 2.0.
    Using < instead of <= in the validity test. With duplicates across the cut, the correct condition is $\text{Aleft} \le \text{Bright}$ and $\text{Bleft} \le \text{Aright}$. Strict < rejects valid partitions where a left boundary equals a right boundary, sending the search into an infinite loop or a wrong answer on tied values.

    Key Takeaways

    • Search the partition point, not a value: one scalar $\text{cutA}$ fixes the whole split because $\text{cutB} = \text{halfLen} - \text{cutA}$ is forced.
    • A partition is valid iff $\text{Aleft} \le \text{Bright}$ and $\text{Bleft} \le \text{Aright}$; that makes the left half exactly the $\text{halfLen}$ smallest elements, and the median reads off the boundary.
    • The cross-boundary comparisons steer binary search to a valid cut in $O(\log(\min(m,n)))$; duplicates may make more than one cut valid, and any of them yields the same median.
    • Use $\pm\infty$ sentinels for out-of-range boundaries and cast to double before adding the two central values.
    • Searching the shorter array permits the clean full cut interval and gives the $\log(\min(m,n))$ bound; otherwise derive tighter legal cut bounds.
    • The median is one order statistic; the discard-$k/2$ recursion generalizes to any Kth element in $O(\log(m+n))$ and reproduces the median directly.
