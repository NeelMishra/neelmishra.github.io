    Continuous & Real-Valued Binary Search

    March 2026 · 22 min read

    Every binary search so far has lived on integer indices or integer answers: there was always a next candidate, a discrete step of size one. But some problems ask for an answer that is a genuine real number — the square root of $2$, the length of a rope that satisfies a constraint, the speed at which a machine finishes on time to a fraction of a unit. Here the search space is not a list of slots; it is a continuous interval $[lo, hi]$ of the real line. There is no mid + 1 to jump to, because between any two distinct reals there are infinitely many more. Instead, we shrink the interval by half each step — setting lo = mid or hi = mid — until it is narrow enough that any point inside it is an acceptable answer. This post covers the real-valued template, the choice between fixed iteration counts and an epsilon threshold, the classic square-root and nth-root problems (with the overflow trap that catches everyone), precision conventions, and the floating-point pitfalls that make continuous search subtly different from its integer cousin.

    The real-valued template

    The mechanics are the same as ordinary binary search: keep a feasible/infeasible boundary and squeeze it. What changes is that lo, hi, and mid are doubles, and the update is lo = mid or hi = mid — never mid + 1 or mid - 1. Adding one to a real number is meaningless for precision; the reals are dense, so the interval already contains the answer to any resolution we care about, and halving is what buys us that resolution.

    We assume a monotone predicate feasible(mid): it is false for everything below the answer and true for everything at or above it (or vice-versa). We want the crossover point $x^\*$ where it flips. Two things control when to stop: a fixed number of iterations, or an epsilon threshold on the interval width.

    Fixed-iteration form (recommended)

    #include <stdexcept>

// Find the smallest x in [lo, hi] with feasible(x) == true.
// feasible is monotone: false ... false | true ... true.
double searchReal(double lo, double hi, int iterations) {
    if (iterations <= 0)
        throw std::invalid_argument("iterations must be positive");
    for (int i = 0; i < iterations; i++) {
        double mid = lo + (hi - lo) / 2.0;  // avoids (lo+hi) overflow
        if (feasible(mid)) {
            hi = mid;   // answer is at mid or to the left
        } else {
            lo = mid;   // answer is strictly to the right; NO mid+1
        }
    }
    return lo;          // remaining width = (initial width) / 2^iterations
}

    Epsilon-threshold form

    double searchRealEps(double lo, double hi) {
    const double eps = 1e-9;
    while (hi - lo > eps) {
        double mid = lo + (hi - lo) / 2.0;
        if (feasible(mid)) hi = mid;
        else               lo = mid;
    }
    return lo;
}

    Both forms compute mid = lo + (hi - lo) / 2.0 rather than (lo + hi) / 2.0. For the finite, non-negative intervals used throughout this post, the difference is representable and this form avoids overflowing the endpoint sum. If your domain spans opposite-signed values near the limits of double, use a scaled interval or C++20's std::midpoint instead. Notice there is no equality branch: with reals we almost never hit the exact crossover, so we keep shrinking the bracket.

    Why hi = mid / lo = mid and not ±1? Because reals are dense, mid itself is a valid new endpoint. Using mid + 1 would skip an interval of width one — enormous compared to the $10^{-9}$ precision we are chasing — and would break convergence entirely.

    Fixed iterations vs epsilon

    Each iteration halves the interval. If we start with width $w_0 = hi_0 - lo_0$, then after $k$ halvings the width is

    $$w_k = \frac{hi_0 - lo_0}{2^{k}}.$$

    This is the whole story. To reach an absolute precision $\varepsilon$ we need $w_k \le \varepsilon$, i.e.

    $$k \ge \log_2\!\left(\frac{hi_0 - lo_0}{\varepsilon}\right).$$

    For a starting width of, say, $10^{9}$ and a target precision of $10^{-9}$, that is $\log_2(10^{18}) \approx 60$ iterations. Round up to be safe. Running a flat 100 iterations shrinks the interval by a factor of $2^{100} \approx 1.27 \times 10^{30}$ — astronomically finer than a 64-bit double can even represent (a double carries about 15–16 significant decimal digits, roughly $2^{52}$ of relative resolution). At that point extra iterations do nothing but spin.

    So why prefer fixed iterations over while (hi - lo > eps)? Robustness. The epsilon loop can run forever. Floating-point numbers are spaced apart by their unit in the last place (ULP), and the ULP grows with magnitude. Near $10^{18}$ the gap between consecutive doubles is larger than $1$ — far larger than a typical eps = 1e-9. If lo and hi are large and close, hi - lo may plateau at a value that is above eps yet cannot shrink further, because mid rounds to exactly lo or hi. The condition hi - lo > eps stays true forever and the loop hangs.

    Rule of thumb. Compute the required count from $\lceil\log_2(w_0/\varepsilon)\rceil$, then add a safety margin. For typical contest ranges up to roughly $10^{18}$ and tolerances around $10^{-9}$, 100 iterations is comfortably sufficient and always terminates. It is not a universal constant for an arbitrarily huge interval: the guarantee still scales with the starting width.

    Square root by binary search

    The canonical warm-up is LeetCode 69 — Sqrt(x): given a non-negative integer x, return $\lfloor \sqrt{x} \rfloor$. The function $g(m) = m^2$ is monotonically increasing for $m \ge 0$, so “is $m^2 \le x$?” is a monotone predicate — exactly what binary search needs. The integer version searches indices; the real version searches the continuous line.

    Integer isqrt — and the overflow trap

    The obvious test is mid * mid <= x. For x up to $2^{31}-1$, $\sqrt{x}$ can be about $46341$, and $46341^2 \approx 2.1\times 10^{9}$ — already past the int range. Compute mid * mid in 32-bit arithmetic and it overflows to garbage, breaking the comparison. There are two fixes, and using both is cheapest insurance:

    • Promote to long long so mid * mid cannot overflow for 32-bit inputs.
    • Better still, avoid the product entirely and compare with division: mid <= x / mid is algebraically the same test as mid * mid <= x for positive values, but never overflows because the operands never grow.

    Integer square root (floor), overflow-safe

    // Returns floor(sqrt(x)) for x >= 0.
int isqrt(int x) {
    if (x < 2) return x;                 // sqrt(0)=0, sqrt(1)=1
    long long lo = 1, hi = x, ans = 1;   // long long guards mid*mid
    while (lo <= hi) {
        long long mid = lo + (hi - lo) / 2;
        // Division trick: equivalent to mid*mid <= x, no overflow.
        if (mid <= (long long)x / mid) {
            ans = mid;                    // mid is feasible; try larger
            lo = mid + 1;
        } else {
            hi = mid - 1;                 // mid too big
        }
    }
    return (int)ans;
}

    Note that the integer version does use mid + 1 / mid - 1: it is an ordinary discrete search over integer candidates, and we want the largest mid with mid*mid <= x. The continuous flavour is what drops the ±1. The related LeetCode 367 — Valid Perfect Square is the same search, returning whether some mid satisfies mid * mid == x exactly.

    Real-valued square root

    To get $\sqrt{x}$ to arbitrary precision, search the real interval. A subtlety: for $0 < x < 1$ the root is larger than $x$ (e.g. $\sqrt{0.25} = 0.5$), so the upper bound must be at least $1$. Set hi = max(1.0, x).

    Real square root, fixed iterations

    #include <stdexcept>

double sqrtReal(double x, int iterations) {
    if (x < 0) throw std::invalid_argument("sqrtReal requires x >= 0");
    if (iterations <= 0)
        throw std::invalid_argument("iterations must be positive");
    if (x == 0) return 0.0;
    double lo = 0.0, hi = (x < 1.0 ? 1.0 : x);
    for (int i = 0; i < iterations; i++) {
        double mid = lo + (hi - lo) / 2.0;
        // Compare without squaring: mid*mid >= x iff mid >= x/mid.
        if (mid >= x / mid) hi = mid;     // mid too big or exact
        else                lo = mid;     // mid too small
    }
    return lo;   // error is at most (initial interval width) / 2^iterations
}

    A double product can still overflow to inf near the top of its range, so the implementation uses the same division idea as integer square root. Because x > 0 and every tested mid is positive, mid >= x / mid is equivalent to mid^2 >= x without forming the square. Complexity is $O(\text{iterations})$, or $O\!\left(\log\frac{hi-lo}{\varepsilon}\right)$ when expressed in terms of a target precision.

    Nth root

    Generalizing from square root to the $n$-th root, we need $x^{1/n}$: the value $m \ge 0$ with $m^n = x$. For $m \ge 0$ and integer $n \ge 1$, the map $m \mapsto m^n$ is monotonically non-decreasing — multiplying a larger non-negative base by itself more times can only produce a larger (or equal) result. That monotonicity is exactly the property binary search exploits, so “is $m^n \ge x$?” flips from false to true at the root.

    The one hazard is computing $m^n$. For large mid and n the product can blow up to inf. For bases at least 1, the running product only grows, so we can compare against target / base before multiplying and stop safely. For bases below 1, the running product decreases; an early “already above target” return would be wrong, so we must finish all $n$ multiplications.

    Real nth root, fixed iterations

    #include <stdexcept>

// Assumes base >= 0, target >= 0, n >= 1.
bool powAtLeast(double base, int n, double target) {
    double prod = 1.0;
    for (int i = 0; i < n; i++) {
        // Only safe to short-circuit while powers are non-decreasing.
        if (base >= 1.0 && prod >= target / base) return true;
        prod *= base;
    }
    return prod >= target;
}

double nthRoot(double x, int n, int iterations) {
    if (x < 0 || n <= 0)
        throw std::invalid_argument("nthRoot requires x >= 0 and n >= 1");
    if (iterations <= 0)
        throw std::invalid_argument("iterations must be positive");
    if (x == 0) return 0.0;
    double lo = 0.0, hi = (x < 1.0 ? 1.0 : x);
    for (int i = 0; i < iterations; i++) {
        double mid = lo + (hi - lo) / 2.0;
        if (powAtLeast(mid, n, x)) hi = mid;  // mid^n >= x -> go lower
        else                       lo = mid;  // mid^n <  x -> go higher
    }
    return lo;
}

    For base >= 1, checking prod >= target / base before multiplication proves the next product reaches the target without risking overflow. For base < 1, powers shrink, so the helper deliberately performs all $n$ multiplications; this distinction is essential for roots of values in $(0,1)$. As with square root, use hi = max(1.0, x). The overall cost is $O(n \cdot \text{iterations})$.

    Related: LeetCode 50 — Pow(x, n) is the inverse operation (compute $x^n$, typically by fast exponentiation rather than binary search), but it shares the same “multiply carefully, watch for overflow and negative exponents” discipline.

    Precision & return conventions

    Once the interval is tiny, three practical questions remain: how many iterations to run, what value to return, and how to print it.

    How many iterations. Invert the width formula. To guarantee absolute error at most $\varepsilon$ starting from width $w_0$, take

    $$k = \left\lceil \log_2\!\frac{w_0}{\varepsilon} \right\rceil.$$

    For $w_0 \approx 10^{4}$ and $\varepsilon = 10^{-6}$ that is $\lceil \log_2 10^{10} \rceil = 34$ iterations; 100 is comfortably above anything you will meet in practice.

    Absolute vs relative error. Many judges accept an answer “within $10^{-6}$”. Read carefully whether that is absolute ($|\text{ans} - \text{true}| \le 10^{-6}$) or relative ($|\text{ans} - \text{true}| \le 10^{-6}\,|\text{true}|$). For large answers, absolute precision is much harder to hit than relative; if the problem promises relative error, you can stop the interval when $hi - lo \le \varepsilon \cdot \max(1, |lo|)$ rather than a flat $\varepsilon$.

    Value vs integer floor. Some problems want the real value (print the double); others want an integer, usually a floor or ceiling. For a floor, either use the integer template directly or take (long long)lo after a real search — but guard against a result that landed at 3.9999999 when the true answer is 4: nudging with a tiny epsilon (floor(lo + 1e-9)) or verifying the neighbours avoids the off-by-one.

    Printing. Use fixed-point formatting with an explicit precision so trailing digits are not truncated or shown in scientific notation:

    Formatting the answer

    #include <iomanip>
#include <iostream>

double ans = sqrtReal(2.0, 100);       // 100 suits this small interval
std::cout << std::fixed
          << std::setprecision(6)     // 6 digits after the point
          << ans << "\n";              // prints 1.414214

    Numerical safety recap

    Continuous binary search is short, but the failure modes are all about arithmetic rather than logic. A checklist:

    • Avoid mid * mid for integer tests. Prefer the division form mid <= x / mid, or promote to long long. The product is the single most common overflow bug in isqrt-style code.
    • Do not subtract nearly-equal large doubles. Catastrophic cancellation destroys significant digits; if you find yourself computing big - almostBig, restructure. The lo + (hi - lo)/2 midpoint is safe because hi - lo is the quantity we want to shrink.
    • Prefer long long for integer variants so intermediate products stay in range; cast the input inside the comparison ((long long)x / mid) so the division itself is 64-bit.
    • Beware NaN and inf. Overflowing arithmetic can produce inf, while invalid operations can produce NaN; comparisons with NaN are false and can silently steer the search the wrong way. Guard the domain and compare before multiplying when the product is monotone.

    Common mistakes

    while (lo < hi) on doubles. Two distinct doubles are essentially never equal after halving, so lo and hi approach but do not meet: the loop spins forever. Terminate with a fixed iteration count or an epsilon check, never with equality on reals.
    mid + 1 / mid - 1 on reals. A step of one is gigantic next to $10^{-9}$ precision and skips the answer entirely. On the continuous line the updates must be plain lo = mid and hi = mid.
    mid * mid overflow in the integer variant. For int inputs the square exceeds the 32-bit range. Use long long or, better, the division test mid <= x / mid.
    Too few iterations. If the starting interval is wide, a handful of halvings leaves the answer coarse. Compute $k = \lceil \log_2(w_0/\varepsilon) \rceil$, or just run 100 and stop worrying.
    Using float instead of double. A 32-bit float carries only ~7 significant digits — not enough for $10^{-6}$ absolute precision on non-trivial magnitudes. Always search in double.

    Key takeaways

    • When the answer is a real number, the search space is a continuous interval $[lo, hi]$; shrink it with lo = mid / hi = mid, never ±1.
    • After $k$ halvings the width is $(hi_0 - lo_0)/2^{k}$; needing precision $\varepsilon$ costs $k = \lceil \log_2((hi_0-lo_0)/\varepsilon) \rceil$ iterations.
    • Prefer a fixed iteration count derived from $\lceil\log_2(w_0/\varepsilon)\rceil$ over while (hi - lo > eps): the counter always terminates, whereas the epsilon loop can hang when eps falls below the ULP at large magnitudes.
    • For square root, compare with division (mid <= x / mid or its real-valued mirror) to dodge multiplication overflow.
    • For nth roots, early exit is safe only when base >= 1; powers below 1 decrease, so their full product must be evaluated.
    • Mind precision conventions (absolute vs relative), return type (value vs floor), and print with std::fixed + setprecision. Search in double, never float.
