    Boundary Search: lower_bound, upper_bound & First/Last

    March 2026 · 26 min read

    In Part 1 we searched for an exact value. But most real problems do not ask “is $x$ present?” They ask “where would $x$ go?”, “what is the first element $\ge x$?”, “how many copies of $x$ are there?”, or “what is the first broken build?” All of these are boundary queries, and they share one skeleton. Once you internalise that skeleton, lower_bound, upper_bound, first/last occurrence, search-insert, and first-bad-version stop being five different algorithms and become five inputs to the same algorithm. This post builds that unifying frame, derives the STL functions from it, and ends with the subtle comparator traps in std::partition_point.

    The one idea. Every problem in this post reduces to: find the first index where a monotone predicate flips from false to true. Master the half-open template once and you get all of them for free.

    First-True / Last-False Framing

    Forget values for a moment. Imagine a boolean predicate pred(i) defined on real indices $0 \le i < n$. Suppose it is monotone: once it becomes true it stays true. Laid out, the sequence of answers looks like:

    $$\underbrace{F\;F\;F\;\cdots\;F}_{\text{prefix}}\;\underbrace{T\;T\;T\;\cdots\;T}_{\text{suffix}}$$

    There is exactly one place where F turns into T. Binary search finds that boundary. This is the single most important reframing in the entire series: binary search does not need a sorted array — it needs a monotone predicate. A sorted array is just the easiest way to build one.

    We also reserve index n as a virtual true sentinel. It is not passed to pred; it represents the answer “no real index is true.”

    Canonical first-true template (half-open)

    // Returns the first real index i in [0, n) with pred(i) == true.
// Index n is a virtual sentinel: if pred is never true, return n.
int firstTrue(int n) {
    int lo = 0, hi = n;            // candidates [lo, hi); hi may be sentinel n
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;   // overflow-safe midpoint
        if (pred(mid)) hi = mid;   // mid might be the answer, keep it
        else           lo = mid + 1;   // mid is false, discard it
    }
    return lo;                     // lo == hi == boundary
}

    Two details make this template bulletproof:

    • Half-open interval. hi starts at $n$, not $n-1$, so we can represent “the answer is past the end”. Real candidates live in $[\texttt{lo}, \texttt{hi})$; n is a virtual sentinel and is never evaluated.
    • Asymmetric update. When pred(mid) is true we set hi = mid (keep mid, it could be the boundary); when false we set lo = mid + 1 (discard mid). This asymmetry is exactly why the loop cannot spin forever: mid is always strictly less than hi, so hi = mid makes real progress.
    Invariant. At the top of every iteration, every real index strictly left of lo is false, and every real index in [hi, n) is true. That suffix may be empty when hi == n, which is exactly how the sentinel represents “no true index.” When lo == hi, the guarantees meet at the first true index or at sentinel n. The interval shrinks every step, guaranteeing $O(\log n)$ termination.

    lower_bound and upper_bound as Instances

    Now specialise the predicate to a sorted array a and a query x:

    • lower_bound(x) = first index $i$ with a[i] >= x. The predicate is pred(i) = (a[i] >= x), which is monotone because the array is sorted.
    • upper_bound(x) = first index $i$ with a[i] > x. The predicate is pred(i) = (a[i] > x).

    They are the same code with a single character changed — < versus <= in the comparison that decides whether mid is still on the false side:

    Both bounds, hand-written

    // first index with a[i] >= x
int lowerBound(const vector<int>& a, int x) {
    int lo = 0, hi = (int)a.size();
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < x) lo = mid + 1;    // mid is too small -> false side
        else            hi = mid;        // a[mid] >= x -> candidate
    }
    return lo;
}

// first index with a[i] > x
int upperBound(const vector<int>& a, int x) {
    int lo = 0, hi = (int)a.size();
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] <= x) lo = mid + 1;   // a[mid] <= x -> false side
        else             hi = mid;       // a[mid] > x -> candidate
    }
    return lo;
}

    The only difference is a[mid] < x (lower) versus a[mid] <= x (upper). Everything else is identical. This one-character duality has a beautiful payoff:

    $$\text{count of } x \;=\; \texttt{upper\_bound}(x) - \texttt{lower\_bound}(x)$$

    Because lower_bound lands on the first $x$ and upper_bound lands just past the last $x$, their difference is exactly the number of copies — computed in $O(\log n)$ without scanning the run.

    Return contract. Both functions return an index in $[0, n]$. A returned value of n means “no such element”. Neither guarantees a[result] == x; you must validate that yourself, which is the theme of the next section.

    First and Last Occurrence (LeetCode 34)

    Find the first and last position of a target in a sorted array with duplicates. This is a direct composition of the two bounds:

    • First occurrence = lower_bound(x), but only if that index is in range and a[idx] == x. If the predicate never fired, lower_bound returns n; if it fired on a value strictly greater than x, then x is absent.
    • Last occurrence = upper_bound(x) - 1, again validated by a[idx] == x. Since upper_bound is one past the last x, subtracting one lands on it — provided any x exists at all.

    LeetCode 34 — searchRange

    vector<int> searchRange(vector<int>& a, int x) {
    int n = (int)a.size();
    int lo = (int)(lower_bound(a.begin(), a.end(), x) - a.begin());
    if (lo == n || a[lo] != x) return {-1, -1};       // x absent
    int hi = (int)(upper_bound(a.begin(), a.end(), x) - a.begin()) - 1;
    return {lo, hi};
}

    Once lower_bound confirms an x exists, the matching upper_bound - 1 is guaranteed valid, so a single existence check up front is enough.

    A = [5, 7, 7, 8, 8, 10], target = 8

    lower_bound(8): first index with a[i] >= 8. Indices 0..3 hold 5,7,7,8; the first value $\ge 8$ is a[3] = 8. So lo = 3. Validate: a[3] == 8 ✓.

    upper_bound(8): first index with a[i] > 8. Values 8,8 at indices 3,4 are not > 8; the first strictly greater is a[5] = 10. So upper_bound = 5, and hi = 5 - 1 = 4. Validate: a[4] == 8 ✓.

    Answer: {3, 4}. The two 8’s occupy indices 3 and 4 — count = $5 - 3 = 2$, matching upper - lower.

    Search Insert Position (LeetCode 35)

    Given a sorted array and a target, return the index where the target is (or where it would be inserted to keep the array sorted). That is precisely the definition of lower_bound: the first slot whose value is $\ge$ target. If the target exists you land on it; if not, you land on the position that shifts everything to its right.

    LeetCode 35 — searchInsert

    int searchInsert(vector<int>& a, int x) {
    int lo = 0, hi = (int)a.size();
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < x) lo = mid + 1;
        else            hi = mid;
    }
    return lo;                       // first index with a[i] >= x
}

    No special-casing, no post-validation — the half-open template returns the insertion point directly, including n when the target exceeds every element.

    First Bad Version (LeetCode 278)

    You have versions $1 \ldots n$. Some version broke the build, and every version after a bad one is also bad. The API isBad(v) returns a boolean, and it is monotone: false, false, ..., false, true, true, ..., true. Find the first bad version. This is first-true search with no array at all — the predicate is the data.

    LeetCode 278 — firstBadVersion

    // isBadVersion(v) is provided by the platform.
int firstBadVersion(int n) {
    long long lo = 1, hi = n;         // search over [1, n]
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;   // no overflow
        if (isBadVersion((int)mid)) hi = mid; // mid bad -> candidate
        else                        lo = mid + 1;
    }
    return (int)lo;                   // first bad version
}
    Overflow trap. The naive midpoint mid = (lo + hi) / 2 overflows a 32-bit int when lo + hi > INT_MAX — and this problem is specifically tuned with n near INT_MAX to punish it. Two fixes: use mid = lo + (hi - lo) / 2 (the difference never overflows), and/or widen to long long as above. Prefer the lo + (hi - lo) / 2 form everywhere — it is free insurance.

    STL partition_point & Comparator Caveats

    The standard library exposes the raw first-true machinery as std::partition_point. Given a range that is partitioned with respect to a predicate (all elements satisfying it come first), it returns an iterator to the first element for which the predicate is false.

    Read that carefully. partition_point returns the first element where the predicate is false, i.e. it locates the true→false boundary of a $T\,T\,\cdots\,T\,F\,F\,\cdots\,F$ layout — the mirror image of our firstTrue template, which finds the false→true boundary. If you feed it a predicate shaped like isBad (false-then-true) you must negate it to keep the range partitioned in the true-first order it expects.

    Here we reimplement first-bad-version-style search with partition_point. The range is partitioned by the predicate “version is still good” (good, good, ..., bad, bad), so partition_point returns the first not-good = first bad element:

    partition_point on a good/bad range

    #include <algorithm>
#include <vector>
#include <numeric>
using namespace std;

int firstBadWithPartition(int n, bool (*isBad)(int)) {
    vector<int> versions(n);
    iota(versions.begin(), versions.end(), 1);   // 1..n
    // Range is partitioned as: good... | bad...
    // Predicate for partition_point must be TRUE on the prefix.
    auto it = partition_point(versions.begin(), versions.end(),
                              [&](int v){ return !isBad(v); }); // "is good"
    return (it == versions.end()) ? -1 : *it;    // first bad version
}

    This vector example demonstrates the library contract, not an efficient replacement for the numeric search above: materializing 1..n costs $O(n)$ time and space before partition_point even starts. Use partition_point when the range already exists as iterators; use the direct first-true loop for an API-only numeric domain such as version numbers.

    Next, lower_bound / upper_bound with a custom comparator. The classic use is a descending array, where you must pass greater<>() so the library’s notion of order matches the data:

    lower_bound on a descending array

    // a is sorted in DESCENDING order, e.g. {9, 7, 4, 4, 2}
vector<int> a = {9, 7, 4, 4, 2};
int x = 4;
// Must pass the SAME comparator the range is sorted by.
auto it = lower_bound(a.begin(), a.end(), x, greater<int>());
// it -> first element NOT greater than x, i.e. first a[i] <= x = first 4.
int idx = (int)(it - a.begin());   // idx == 2

    Three caveats hide in that innocent-looking call:

    1. The range must be partitioned/sorted with respect to the same comparator. Calling lower_bound(..., greater<>()) on an ascending array is undefined behaviour — the monotonicity the algorithm relies on simply is not there.
    2. Argument order differs between the two functions. Internally lower_bound evaluates comp(element, value) while upper_bound evaluates comp(value, element). With a symmetric comparator like greater<> this is invisible, but with a custom projection comparator (comparing a struct field, say) getting the argument order backwards silently returns the wrong bound.
    3. A comparator that is not a strict weak ordering gives silent wrong answers. If comp(a,b) and comp(b,a) can both be true, or equality is inconsistent, the library still runs — it just returns garbage with no error. Always ensure comp is irreflexive, asymmetric, and transitive.
    Rule of thumb. Whatever comparator sorted (or partitioned) the range is the exact comparator you must hand to lower_bound, upper_bound, and partition_point. Mixing them compiles cleanly and fails quietly — the worst kind of bug.

    Common Mistakes

    Mixing closed and half-open intervals. If you start hi = n - 1 (closed) but keep while (lo < hi) and hi = mid, you can never represent “answer is past the end” and you lose the last element. Pick one convention — half-open hi = n with while (lo < hi) — and use it everywhere.
    Returning mid mid-loop. For boundary queries there is no early return mid. The whole point is to let lo and hi converge; returning the first mid that matches gives an occurrence, not the first. Let the loop finish and return lo.
    Forgetting the existence check. lower_bound / upper_bound always return a valid insertion index, never a “not found” sentinel. You must test idx < n && a[idx] == x before claiming the element is present. Skipping this reports phantom matches.
    Off-by-one in last = upper_bound - 1 when x is absent. If no x exists, upper_bound(x) == lower_bound(x), so upper_bound - 1 points at some other value (or -1). Always gate the -1 subtraction behind the “does x exist” check, as in the LeetCode 34 code above.

    Practice

    • LeetCode 35 — Search Insert Position: literally lower_bound.
    • LeetCode 34 — First and Last Position: lower_bound and upper_bound - 1 with an existence check.
    • LeetCode 278 — First Bad Version: first-true search over a monotone predicate (mind the overflow).
    • LeetCode 704 — Binary Search: the exact-match baseline from Part 1; solve it as lower_bound + validation.
    • LeetCode 744 — Smallest Letter Greater Than Target: an upper_bound with wrap-around at the end.
    • LeetCode 2529 — Max Count of Positive and Negative: lower_bound(0) and upper_bound(0) give the two counts directly.

    Key Takeaways

    • Binary search finds the first index where a monotone predicate flips false→true — a sorted array is just the simplest such predicate.
    • The half-open template (lo = 0, hi = n, while (lo < hi), pred ⇒ hi = mid else lo = mid + 1) returns that boundary and cannot loop forever.
    • lower_bound (>= x) and upper_bound (> x) differ by a single character; their difference is the count of x.
    • First/last occurrence = lower_bound and upper_bound - 1, each gated by an a[idx] == x existence check.
    • Search-insert is lower_bound; first-bad-version is first-true search with the API as the predicate.
    • Use mid = lo + (hi - lo) / 2 and long long when bounds approach INT_MAX.
    • partition_point finds the first element where the predicate is false; always pass the same comparator the range was sorted/partitioned by, and mind the lower_bound/upper_bound argument-order asymmetry.
