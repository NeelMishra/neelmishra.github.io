    The Ultimate First-True Binary Search Template

    August 2026 · 26 min read

    Most people learn binary search as "find a target in a sorted array" and then spend years re-deriving off-by-one bugs every time a problem is slightly different. This series takes the opposite approach. There is exactly one template, and every problem — searching an array, finding a square root, sizing a ship, feeding monkeys, ranking a multiplication table — is solved by plugging three small decisions into it. This first post builds that template from the ground up: the reframing into minimize k such that condition(k) is true, the loop invariant that makes it correct, the virtual sentinel that removes the last edge case, the overflow-safe midpoint, and why the loop always terminates. Every later post reuses this exact skeleton and only ever changes the three moving parts.

    Series roadmap. (1) The ultimate first-true template · (2) Basic applications (First Bad Version, Search Insert, integer sqrt) · (3) Capacity & partition (Ship Packages, Split Array Largest Sum) · (4) Rates & days (Koko, Bouquets, Smallest Divisor) · (5) Kth smallest (Multiplication Table, Pair Distance) · (6) Inclusion–exclusion (Ugly Number III) · (7) Template playbook & capstone. The single through-line: find where a monotone yes/no condition first flips from false to true.
    Credit where it is due. The "minimize k such that condition(k)" framing that unifies this whole series was popularized by the best binary search blog ever on LeetCode. That post is in Python; here we rebuild the idea independently in C++, add explicit invariants and correctness proofs, and make every step overflow-safe.

    The Reframe: Minimize k Such That condition(k)

    Forget "find the target" for a moment. Almost every binary search problem can be rewritten into one canonical shape:

    The canonical question

    Find the smallest value k in some candidate range for which a boolean function condition(k) is true.

    The only thing that makes this searchable is monotonicity: once condition becomes true it never goes back to false. Reading the candidate range left to right, you see a block of falses followed by a block of trues:

    condition: false false false true true true index: 0 1 2 3 4 5 ^ answer = first k with condition(k) == true

    There is a single point where the value flips. That flip point is the answer. Binary search is nothing more than a fast way to locate that flip:

    • If condition(mid) is true, the answer is mid or something to its left — the flip is at mid or earlier, so we keep mid as a candidate and drop everything to the right.
    • If condition(mid) is false, the answer is strictly to the right — mid can never be the first true, so we discard it.

    That is the entire idea. The rest of this post makes it airtight, and the rest of the series is just: for each new problem, decide what condition means and where the candidate range lives.

    The Template

    Here is the one function you will reuse for the entire series. Read it once now; every later post is a thin wrapper around it.

    The first-true template

    // Returns the smallest x in [lo, hi] with condition(x) == true.
// If no x in [lo, hi) is true, returns hi (the virtual sentinel).
// Precondition: condition is monotone on [lo, hi] -- once true, stays true --
// and condition(hi) is true (hi is a real true value or a sentinel).
long long firstTrue(long long lo, long long hi,
                    const std::function<bool(long long)>& condition) {
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;   // overflow-safe midpoint
        if (condition(mid)) {
            hi = mid;         // mid might be the answer -- keep it in range
        } else {
            lo = mid + 1;     // mid is false -- it can never be the answer
        }
    }
    return lo;                // lo == hi: the boundary, i.e. the first true
}

    Five lines of logic. Notice what is not here: there is no == target check, no early return mid, no separate handling of "found" versus "not found". The loop runs until the interval collapses to a single point, and that point is the boundary between false and true. This uniformity is exactly why the template survives being pointed at eleven very different problems.

    The Loop Invariant and the Boundary

    Correctness comes from one invariant that holds at the top of every iteration. Picture the candidate range as cells, with left and right bracketing the part we have not yet resolved:

    false false false | true true true |(n) ^ ^ left right <--- all false ---> <-- answer lives in [left, right] -->

    The invariant, stated precisely and maintained forever:

    • Every index before left is false. We have proven those can never be the first true.
    • right is a true candidate — either a real index where condition holds, or the virtual sentinel n that we treat as true by fiat.
    • The answer always stays in [left, right]. We never let it escape the bracket.

    The update rules preserve exactly this:

    • condition(mid) == true → right = mid. Everything at or after mid’s successor is now known-or-assumed true; mid stays a candidate, so we do not write mid - 1.
    • condition(mid) == false → left = mid + 1. Everything up to and including mid is now known false, so we push the left wall just past it.

    When left == right, the bracket is a single cell. By the invariant everything before it is false and it is itself a true candidate: it is the boundary. We return left. And critically — we never access nums[n]. The sentinel n is only ever a value that right can hold; the code never dereferences it, it just means "no real element satisfied the condition."

    Why the sentinel matters. Many problems have inputs for which no element is true (target larger than everything, no feasible answer below the cap, etc.). Instead of special-casing that, we let right start at n (or hi + 1) and treat position n as an imaginary always-true cell. If the search converges there, the caller interprets n as "not found" — no branchy edge-case code required.

    Step-Through: Locating the Boundary

    The array below is a pure boolean condition: red cells are false, green cells are true, and the dashed cell on the right is the virtual sentinel at index n. Watch left (green pointer), mid (orange), and right (red) squeeze onto the first true cell. Press Step to advance one iteration.

    firstTrue over [F F F F T T T]

    Trace it by hand. The boolean array is [F, F, F, F, T, T, T] (first true at index 4), and right starts at the sentinel index 7.

    Initialize

    left = 0, right = 7 (sentinel). mid = 0 + (7-0)/2 = 3. condition(3) = false, so the first true is strictly to the right: left = 4.

    Right half

    left = 4, right = 7. mid = 4 + (7-4)/2 = 5. condition(5) = true, so 5 is a candidate but maybe not the first: right = 5.

    Shrink

    left = 4, right = 5. mid = 4 + (5-4)/2 = 4. condition(4) = true: right = 4.

    Converged

    left = 4, right = 4. Loop exits. Return 4 — the first true index, found in 3 comparisons. Had the array been all false, the search would have converged on the sentinel 7 instead.

    The Three Decisions

    The template never changes. For any new problem, you only ever answer three questions. The entire rest of this series is a tour of how the answers shift.

    DecisionQuestionWhat can go wrong
    1. Bounds What is the inclusive candidate range [lo, hi] that provably contains every possible answer, plus a true sentinel at the top? Too narrow → you miss the answer. Too wide → slower but still correct (usually the safe default).
    2. Condition What monotone boolean condition(mid) flips from false to true exactly at the answer? Non-monotone → binary search is invalid. Off-by-one in the predicate → you find a neighbor of the answer.
    3. Return Is the answer left itself, or a transform such as left - 1 (the last false), or does left == sentinel mean "impossible"? Returning left when the problem wants the last false, or forgetting the "impossible" check.
    Every future post explicitly labels which of these three changed. That is the discipline that turns "I hope this binary search is right" into "I know exactly why this is right."

    The Overflow-Safe Midpoint

    The line mid = lo + (hi - lo) / 2 is not a stylistic preference; it is a correctness requirement. The naive mid = (lo + hi) / 2 overflows when lo + hi exceeds the type’s maximum. For 32-bit int, two indices near $2^{31}$ sum past INT_MAX and wrap to a negative number, sending mid out of bounds.

    The bug: mid = (lo + hi) / 2 with lo = hi = 1{,}500{,}000{,}000 computes 3{,}000{,}000{,}000, which overflows a signed 32-bit int to a negative value.
    The fix: mid = lo + (hi - lo) / 2. For the ordered, non-negative ranges used throughout this series, hi - lo fits the chosen type, and adding half of it to lo never leaves [lo, hi].

    Because several problems in this series binary search over values that reach $10^9$ or beyond (Koko’s banana piles, ship capacities, the multiplication table), we default the whole template to long long. The gap-form midpoint plus a 64-bit type makes overflow impossible in practice for the ranges these problems specify.

    Why the Loop Always Terminates

    The loop condition is lo < hi, so we must show the interval strictly shrinks every iteration and cannot get stuck.

    With lo < hi, the floored midpoint satisfies lo ≤ mid < hi (the midpoint of a range of length $\ge 1$ can equal lo but never reaches hi). Consider each branch:

    • True branch: hi = mid. Since mid < hi before the update, hi strictly decreases.
    • False branch: lo = mid + 1. Since mid ≥ lo, lo strictly increases.

    Either way the length hi - lo drops by at least one, and it is bounded below by zero, so a non-empty range of initial width $R$ needs at most $\lceil \log_2(R + 1) \rceil$ iterations. The crucial detail is mid < hi: it is what guarantees the true branch makes progress. Writing mid = lo + (hi - lo + 1) / 2 (rounding up) with hi = mid would let mid == hi and spin forever — a classic infinite-loop bug we revisit in Part 7.

    Exact Match Is Just lower_bound Plus Validation

    "But I really do just want to find a target in a sorted array." Fine — that is a special case of the template, not a different algorithm. Define condition(i) as nums[i] >= target. It is monotone on a sorted array (once an element is $\ge$ target, all later ones are too), so firstTrue returns the first index whose value is at least the target — exactly C++’s lower_bound. Then you validate.

    Exact match via the template

    int searchExact(const std::vector<int>& nums, int target) {
    int n = (int)nums.size();
    int lo = 0, hi = n;                 // hi = n is the virtual sentinel
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (nums[mid] >= target) hi = mid;   // condition: value reaches target
        else                     lo = mid + 1;
    }
    // lo is the first index with nums[lo] >= target (or n if none).
    if (lo < n && nums[lo] == target) return lo;   // validation step
    return -1;                                       // target absent
}

    This is the decisions in miniature. Bounds: [0, n] with sentinel n. Condition: nums[mid] >= target. Return: lo, then a single validation to convert "first index $\ge$ target" into "index equal to target, or -1." Note the return never fabricates a success — if lo == n the guard lo < n short-circuits and we never read the sentinel cell, and if the value there is not the target we honestly return -1.

    Takeaway. There is no separate "exact-match binary search" to memorize. It is firstTrue with the predicate value reaches target, plus one comparison to confirm the boundary element actually equals the target.

    Edge Cases the Template Handles for Free

    • Empty range / all false. If nothing satisfies the condition, the search converges on the sentinel hi; the caller checks for it. No crash, no special branch.
    • Answer at the first cell. If condition(lo) is already true, the loop keeps setting hi = mid until hi == lo, returning lo.
    • Single-element range. lo == hi from the start: the loop body never runs and returns lo, which is correct by the invariant.
    • Duplicates. Because we always keep the leftmost true (hi = mid, not mid - 1), the template returns the first true even when many equal elements exist.

    Complexity

    The candidate range has length $R = hi - lo$. Each iteration at least halves it, so the loop runs $O(\log R)$ times. If evaluating condition costs $C$, total time is $O(C \log R)$. For a plain array lookup $C = O(1)$ and we recover the familiar $O(\log n)$. In later posts condition is a greedy feasibility scan ($C = O(n)$) or a counting pass, and the $\log R$ factor multiplies that cost — still dramatically better than scanning the whole answer space.

    Common Mistakes

    • Writing hi = mid - 1 in the true branch. That discards the very candidate that might be the answer. In the first-true template the true branch is always hi = mid.
    • Mixing loop conditions. With while (lo < hi) you must use hi = mid / lo = mid + 1. Pairing it with a closed-interval update (hi = mid - 1) breaks the invariant.
    • Rounding the midpoint up (lo + (hi - lo + 1)/2) while using hi = mid: causes an infinite loop when hi - lo == 1. Round-up pairs with the last-true template, not this one.
    • Forgetting the sentinel check. If your bounds allow "no answer," the caller must test lo == hi_sentinel before trusting the result — never read nums[n].
    • Non-monotone condition. If condition can go true→false→true, the whole premise collapses. Proving monotonicity is the real work, covered in every later post.

    Key Takeaways

    • Reframe every problem as minimize k such that condition(k) is true; the answer is where a monotone condition first flips false→true.
    • The template is fixed: while (lo < hi), mid = lo + (hi-lo)/2, true → hi = mid, false → lo = mid + 1, return lo.
    • The invariant: everything before left is false, right is a true candidate or the virtual sentinel n, and the answer stays in [left, right]. Never dereference the sentinel.
    • Only three things ever change: the bounds, the condition, and the return transform.
    • Use the gap-form midpoint and long long to stay overflow-safe; termination is guaranteed because lo ≤ mid < hi.
    • Exact match is not special: it is lower_bound plus one validation comparison.
