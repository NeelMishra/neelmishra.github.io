    Binary Search Fundamentals

    March 2026 · 24 min read

    Binary search is one of the most important algorithms you will ever learn. It transforms a linear scan into a logarithmic one by exploiting a single property: order. If the data is sorted, you can eliminate half the candidates with every comparison. This first post of a ten-part series covers the core idea, the mathematics behind $O(\log n)$, a full step-through animation, iterative and recursive code, the loop invariant that proves correctness, the two ways to frame the search interval (closed versus half-open), why the loop is guaranteed to terminate, and the classic off-by-one pitfalls. We deliberately keep the scope tight — the exact-match search. The boundary variants (lower_bound / upper_bound) get a post of their own in Part 2, and everything after that generalizes binary search far beyond sorted arrays.

    Series roadmap. (1) Fundamentals · (2) Boundary search · (3) Binary search on the answer · (4) Minimize max / maximize min · (5) Rotated arrays · (6) Peaks & mountains · (7) Order statistics · (8) Median of two arrays · (9) Real-valued search · (10) Recognition & capstone. The most reusable through-line is finding where a monotone yes/no condition flips. Rotated and peak searches add a second proof style: a local comparison certifies that at least one solution remains in the half we keep.

    The Core Idea

    Suppose you have a sorted array of $n$ elements and you want to find whether a target value exists. A naive linear scan checks every element one by one: $O(n)$. Binary search does something smarter.

    1. Look at the middle element.
    2. If it equals the target, you are done.
    3. If the target is smaller, discard the right half. The target cannot be there because the array is sorted.
    4. If the target is larger, discard the left half.
    5. Repeat on the remaining half.

    Each step eliminates exactly half of the remaining elements. After $k$ steps, only $\frac{n}{2^k}$ elements remain. The search ends when one element is left:

    $$\frac{n}{2^k} = 1 \implies k = \log_2 n$$

    So binary search runs in $O(\log n)$ time. For an array of one million elements, that is at most 20 comparisons instead of one million.

    Prerequisite: The array must be sorted. Binary search on an unsorted array gives meaningless results. If you need to search repeatedly, sort once in $O(n \log n)$ and then binary search each query in $O(\log n)$.

    Why $O(\log n)$?

    At each level of recursion, we do $O(1)$ work (one comparison) and recurse on half the input. By the Master Theorem (Case 2 with $a=1, b=2, f(n)=O(1)$), this resolves to $T(n) = O(\log n)$.

    Alternatively, think of it as a decision tree. Each comparison gives a binary outcome (go left or go right), and the tree has depth $\log_2 n$. The number of comparisons is the depth of the path from root to leaf.

    Concrete numbers

    Array size $n$ Linear scan (worst) Binary search (worst)

    1,0241,02410
    1,000,0001,000,00020

    The jump from $10^{18}$ operations to 60 comparisons is staggering. This is the power of logarithmic time.

    Manual Walkthrough

    Let us trace binary search on the array [3, 7, 11, 18, 24, 37, 42, 55, 68, 91] searching for target = 37.

    Initialize pointers

    lo = 0, hi = 9, mid = (0 + 9) / 2 = 4.

    Compare arr[4] = 24 with target 37. Since 24 < 37, the target is in the right half.

    Update: lo = mid + 1 = 5.

    24 < 37, so we discard indices 0 through 4.

    Narrow to right half

    lo = 5, hi = 9, mid = (5 + 9) / 2 = 7.

    Compare arr[7] = 55 with target 37. Since 55 > 37, the target is in the left half.

    Update: hi = mid - 1 = 6.

    55 > 37, so we discard indices 7 through 9.

    Two elements remain

    lo = 5, hi = 6, mid = (5 + 6) / 2 = 5.

    Compare arr[5] = 37 with target 37. Match found!

    Found target 37 at index 5 in just 3 comparisons out of 10 elements.

    Template 1: Exact Match

    This is the standard binary search. The search space uses inclusive bounds on both ends: lo and hi both point to valid indices. The loop condition is lo <= hi and we return as soon as we find the target.

    Exact Match Template

    int binarySearch(vector<int>& arr, int target) {
    int lo = 0, hi = (int)arr.size() - 1;

    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;

        if (arr[mid] == target) {
            return mid;
        } else if (arr[mid] < target) {
            lo = mid + 1;
        } else {
            hi = mid - 1;
        }
    }

    return -1;  // not found
}

    Line-by-line analysis

    • lo = 0, hi = n - 1: The search space is the entire array, inclusive on both ends.
    • while (lo <= hi): We continue as long as at least one element remains. When lo > hi, the window is empty and the target does not exist.
    • mid = lo + (hi - lo) / 2: Equivalent to (lo + hi) / 2 but avoids integer overflow when lo + hi exceeds INT_MAX. This is a real bug that existed in the Java standard library for years.
    • arr[mid] < target: Target is larger, so everything at index mid and below is irrelevant. Set lo = mid + 1.
    • arr[mid] > target: Target is smaller, so everything at index mid and above is irrelevant. Set hi = mid - 1.

    Recursive Binary Search

    The recursive form mirrors the mathematical definition more closely but uses $O(\log n)$ stack space.

    int binarySearchRec(vector<int>& arr, int target, int lo, int hi) {
    if (lo > hi) return -1;

    int mid = lo + (hi - lo) / 2;

    if (arr[mid] == target) return mid;
    if (arr[mid] < target)
        return binarySearchRec(arr, target, mid + 1, hi);
    return binarySearchRec(arr, target, lo, mid - 1);
}

// Call: binarySearchRec(arr, target, 0, arr.size() - 1);

    Both versions have identical time complexity: $O(\log n)$. The iterative version uses $O(1)$ auxiliary space while the recursive version uses $O(\log n)$ due to the call stack. Prefer iterative in practice.

    The Loop Invariant

    A correct binary search maintains this invariant at the start of every iteration:

    Invariant: If the target exists in the array, it is within arr[lo..hi] (inclusive).

    Proving correctness requires showing three things:

    1. Initialization: Before the loop, lo = 0 and hi = n - 1, which covers the entire array. The invariant holds.
    2. Maintenance: If arr[mid] < target, then all elements at indices lo through mid are less than or equal to arr[mid] (sorted order), so they cannot be the target. Setting lo = mid + 1 preserves the invariant. The symmetric argument holds when arr[mid] > target.
    3. Termination: When lo > hi, the search space is empty. Combined with the invariant, this means the target is not in the array. Returning -1 is correct.

    The invariant also guarantees termination: each iteration either finds the target (done) or strictly shrinks the window by at least one element (lo increases or hi decreases). A window of size $n$ can shrink at most $n$ times.

    Closed vs Half-Open Intervals

    Almost every binary-search bug traces back to a single design decision made implicitly: what does the pair [lo, hi] represent? There are two disciplined conventions, and the rule is to pick one and never mix them within a single function.

    The closed interval [lo, hi]

    Both endpoints are valid indices you still might inspect. The search space is arr[lo], arr[lo+1], …, arr[hi]. It is non-empty exactly when lo <= hi, which is why the exact-match template loops on while (lo <= hi) and why "no candidates left" is expressed as lo > hi. Because arr[mid] has been fully examined by the time we recurse, we exclude it: lo = mid + 1 or hi = mid - 1.

    Closed-interval skeleton

    int lo = 0, hi = n - 1;        // both ends inclusive
while (lo <= hi) {             // non-empty while lo <= hi
    int mid = lo + (hi - lo) / 2;
    if (good(mid)) hi = mid - 1;   // drop mid and everything right
    else           lo = mid + 1;   // drop mid and everything left
}

    The half-open interval [lo, hi)

    Here lo is inclusive but hi is one past the last candidate; arr[hi] is never read. The space is non-empty exactly when lo < hi, so the loop is while (lo < hi) and it collapses to a single index when lo == hi. This convention shines for boundary queries (Part 2) because the answer "the position just past the end" (hi = n) is representable without a special case. Note the asymmetry: when we keep mid as a candidate we write hi = mid (not mid - 1), because hi is exclusive so arr[mid] stays in range.

    Half-open skeleton

    int lo = 0, hi = n;            // hi is one-past-the-end
while (lo < hi) {              // non-empty while lo < hi
    int mid = lo + (hi - lo) / 2;
    if (good(mid)) hi = mid;       // mid may be the answer, keep it
    else           lo = mid + 1;   // mid ruled out, drop it
}
// lo == hi is the converged boundary
    The one rule. Mixing conventions — e.g. initializing hi = n but writing hi = mid - 1, or looping lo <= hi with hi = mid — produces either a skipped element or an infinite loop. Decide "is hi inclusive?" first; every other choice (loop test, update rule) follows mechanically from that answer.

    Why the Loop Always Terminates

    A binary search that never ends is the most common failure among beginners, so it is worth stating termination as a small theorem rather than a hope.

    Claim. Both skeletons above run for at most $\lceil \log_2(n+1) \rceil$ iterations. Proof. Let $w = hi - lo$ (closed: candidates $= w + 1$; half-open: candidates $= w$). Because integer division rounds down, mid = lo + (hi - lo)/2 satisfies lo <= mid and, whenever the interval has at least two candidates, mid < hi. Each branch replaces one endpoint with a value strictly on the far side of mid, so the candidate count drops to at most $\lceil w/2 \rceil$. A quantity that at least halves each step reaches size $\le 1$ in $O(\log n)$ steps, after which the loop test fails. $\blacksquare$

    The load-bearing detail is mid < hi when two or more candidates remain. If you ever write lo = mid in the half-open form (instead of mid + 1) or hi = mid in the closed form (instead of mid - 1), and the branch that fires leaves the interval size unchanged, the search spins forever. Rounding mid down pairs with excluding the left side; a search that must keep the right half and update lo to mid needs an upward-rounding midpoint mid = lo + (hi - lo + 1)/2 instead — a pattern we will need for answer-space maximization later in the series.

    Off-by-One Pitfalls

    Binary search is famously easy to get wrong. Knuth noted that while the idea was published in 1946, the first correct implementation did not appear until 1962. Here are the most common mistakes.

    Pitfall 1: Using < instead of <=

    Bug: 
    while (lo < hi) {  // WRONG for exact match template
    ...
}

    This terminates when lo == hi, skipping the last element. If the target is at that position, it will be missed.

    Fix: 
    while (lo <= hi) {  // Correct: checks the last remaining element
    ...
}

    Pitfall 2: Not moving past mid

    Bug: 
    lo = mid;      // WRONG: infinite loop when lo == mid
hi = mid;     // WRONG: infinite loop when hi == mid

    In this exact-match closed-interval template, when two elements remain (lo + 1 == hi), mid equals lo. Setting lo = mid does not shrink the window, causing an infinite loop. Boundary templates deliberately use hi = mid with a different interval invariant, as Part 2 explains.

    Fix: 
    lo = mid + 1;   // Always move past mid
hi = mid - 1;  // Always move past mid

    Pitfall 3: Integer overflow in mid calculation

    Bug: 
    int mid = (lo + hi) / 2;  // Overflows if lo + hi > INT_MAX
    Fix: 
    int mid = lo + (hi - lo) / 2;  // Overflow-safe

    Alternatively, in languages with unsigned right shift: int mid = (lo + hi) >>> 1;

    Pitfall 4: Signed vs unsigned comparison

    Bug: 
    int hi = arr.size() - 1;  // If arr is empty, size() returns 0
                           // and size() - 1 wraps to a huge number
                           // because size() returns size_t (unsigned)
    Fix: 
    int hi = (int)arr.size() - 1;  // Cast to signed first

    Or check for emptiness before searching.

    Beyond Exact Match

    Exact match answers a yes/no question: "is target present, and if so where?" But most real problems ask something subtly different — "where would it go?", "what is the first element $\ge x$?", "how many copies are there?", "what is the first version that is broken?". These are boundary queries, and they are best expressed with the half-open interval and the first-true / last-false framing introduced above.

    The one template to memorize. Find the first index where a monotone condition becomes true. Exact match, insert position, first/last occurrence, and every answer-space problem in this series are special cases of that one search. We build it carefully in Part 2.

    Binary Search in the C++ STL

    You rarely have to hand-roll the exact-match search: the C++ Standard Library ships it (and the boundary variants we defer to Part 2).

    #include <algorithm>
#include <vector>

vector<int> arr = {3, 7, 11, 18, 24, 37, 37, 42, 55, 68};

// Exact match: returns a bool, not an index.
bool found = binary_search(arr.begin(), arr.end(), 37);   // true

// To recover the index, use lower_bound (detailed in Part 2):
auto it = lower_bound(arr.begin(), arr.end(), 37);
if (it != arr.end() && *it == 37) {
    int idx = int(it - arr.begin());   // 5
}

    Python's bisect module is the direct analogue: bisect_left is lower_bound and bisect_right is upper_bound. In every language the same warning applies: these functions assume the range is sorted with respect to the comparator you pass. Feed them an unsorted range and they return meaningless results with no error — a caveat we revisit in Part 2.

    Key Takeaways

    • Binary search halves the search space at every step, giving $O(\log n)$ time.
    • The array (or search space) must have a monotonic property with respect to the question you ask.
    • Use lo + (hi - lo) / 2 to avoid the (lo + hi) integer overflow.
    • The exact-match template uses a closed interval: lo <= hi with lo = mid + 1 and hi = mid - 1, and returns early on a hit.
    • The half-open interval [lo, hi) (loop lo < hi, update hi = mid) converges to a boundary at lo == hi; it is the foundation for the boundary and answer-space searches in the rest of the series.
    • Pick one interval convention per function and never mix the loop test with the wrong update rule.
    • Termination is guaranteed because a rounded-down midpoint plus a strictly-excluding update at least halves the candidate count every iteration.
