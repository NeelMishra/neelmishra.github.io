    Order Statistics in Implicit Value Spaces

    March 2026 · 26 min read

    An order statistic is the $K$th smallest value of a collection. When the collection is a plain array, the classic answers are sorting ($O(n \log n)$) or quickselect ($O(n)$ average). But some of the most instructive problems hand you a set that is enormous and never written down — the $n \times n$ cells of a sorted matrix, the $m \times n$ products of a multiplication table, the $\binom{n}{2}$ pairwise distances of an array. Materializing all of those and sorting them is quadratic or worse and defeats the purpose. This seventh post of the series shows the technique that dissolves the difficulty: binary search over the value range, driven by a monotone counting predicate. You never build the set. You ask a single question — “how many elements are $\leq x$?” — and let its monotonicity carry you to the answer.

    The value-space technique

    Every technique in this series has searched over indices so far — positions in a sorted array, split points, mountain peaks. Order statistics need a different axis. We binary search over the value itself.

    Let $S$ be the (possibly implicit) multiset whose $K$th smallest element we want, and let $V_{\min}$ and $V_{\max}$ bound its values. Define the counting function

    $$\text{count}(x) = \big|\{\, s \in S : s \leq x \,\}\big|,$$

    the number of elements of $S$ that are less than or equal to $x$. The whole method rests on one observation.

    Monotonicity. $\text{count}(x)$ is non-decreasing in $x$. If $x_1 \leq x_2$ then every element $\leq x_1$ is also $\leq x_2$, so $\text{count}(x_1) \leq \text{count}(x_2)$. The predicate never turns off once it turns on.

    Define the feasibility predicate

    $$\text{feasible}(x) = \big[\, \text{count}(x) \geq K \,\big].$$

    Because $\text{count}$ is non-decreasing, $\text{feasible}$ is monotone: once it becomes true it stays true. That is exactly the shape binary search loves — a single flip from false to true. We want the smallest $x$ with $\text{feasible}(x) = \text{true}$, i.e. the smallest $x$ with $\text{count}(x) \geq K$. Call it $x^\star$. The claim is that $x^\star$ is the $K$th smallest element of $S$.

    The universal template

    // find the smallest x in [lo, hi] with count(x) >= K
while (lo < hi) {
    long long mid = lo + (hi - lo) / 2;   // long long guards overflow
    if (count(mid) >= K) hi = mid;        // feasible: answer is mid or lower
    else                 lo = mid + 1;    // infeasible: answer is strictly higher
}
return lo;   // == hi == smallest feasible value == Kth smallest

    The three concrete problems below differ only in how count is implemented and how lo/hi are seeded. The convergence skeleton is identical.

    Why the answer is always a real element of $S$

    This is the subtle, essential part. Binary search over a continuous-looking value range could in principle return a value that is not in $S$ at all. It never does here. Here is the proof.

    Let $x^\star$ be the smallest integer with $\text{count}(x^\star) \geq K$. Because $x^\star$ is the smallest such value, its predecessor fails the test:

    $$\text{count}(x^\star - 1) < K \leq \text{count}(x^\star).$$

    The count strictly increased when we went from $x^\star - 1$ to $x^\star$. But $\text{count}$ can only increase at a value $v$ if $v$ is actually present in $S$ — $\text{count}(v) - \text{count}(v-1)$ equals the number of copies of $v$ in $S$, which is zero for any value not in the set. Since the count jumped at $x^\star$, at least one element of $S$ equals $x^\star$. Therefore $x^\star \in S$.

    Moreover $x^\star$ is precisely the $K$th smallest. There are $\text{count}(x^\star - 1) < K$ elements strictly below $x^\star$, and there are $\text{count}(x^\star) \geq K$ elements $\leq x^\star$. So the ranks occupied by the copies of $x^\star$ span from $\text{count}(x^\star - 1) + 1$ up to $\text{count}(x^\star)$, an interval that contains rank $K$. The value sitting at rank $K$ is $x^\star$. $\blacksquare$

    Takeaway: counting with $\leq$ (not $<$) and converging to the smallest feasible value guarantees the result is a genuine member of the set at exactly rank $K$. You never need to check membership separately.

    Kth smallest in a sorted matrix (LeetCode 378)

    You are given an $n \times n$ matrix where every row is sorted ascending and every column is sorted ascending. Return the $K$th smallest element in the whole matrix (in sorted order, counting duplicates). The matrix has $n^2$ cells; for $n = 300$ that is 90,000 values, but $K$ can be any rank and we want a method that scales with $n$, not $n^2$.

    The smallest value is the top-left corner matrix[0][0] and the largest is the bottom-right corner matrix[n-1][n-1], so the value range is $[\,\text{matrix}[0][0],\ \text{matrix}[n-1][n-1]\,]$. We binary search that range for the smallest $x$ with $\text{count}(x) \geq K$.

    The $O(n)$ staircase count

    The naive count runs a per-row upper_bound: for each of the $n$ rows do a binary search for $x$, giving $O(n \log n)$ per count. We can do better with a single staircase walk that exploits both sortings at once. Start in the bottom-left corner, at row $r = n-1$, column $c = 0$.

    • If matrix[r][c] <= x: since the column is sorted ascending, every cell above (r, c) in column $c$ is also $\leq x$. That is $r + 1$ cells. Add $r + 1$ to the count and step right ($c \mathrel{+}= 1$).
    • Otherwise matrix[r][c] > x: this cell and everything below it in the column exceeds $x$ (column sorted), so nothing in column $c$ at row $r$ or above is guaranteed — step up ($r \mathrel{-}= 1$) to a smaller value.

    Each step either increments $c$ (at most $n$ times) or decrements $r$ (at most $n$ times), so the walk visits at most $2n$ cells: $O(n)$.

    Proof the staircase count is correct

    Maintain the invariant that all cells in columns $0 \ldots c-1$ have already been fully accounted for. At (r, c) we decide the boundary within column $c$. If matrix[r][c] <= x, then because the column is ascending, rows $0 \ldots r$ of column $c$ are all $\leq x$ (that is $r+1$ cells) and rows $r+1 \ldots n-1$ we will never revisit because we move right; adding $r+1$ and advancing $c$ preserves the invariant. If matrix[r][c] > x, then because the column is ascending, rows $r \ldots n-1$ of column $c$ are all $> x$; none of them count, and we drop to row $r-1$ to test the remaining prefix of the column. Every cell is classified $\leq x$ or $> x$ exactly once, so the accumulated total equals $\text{count}(x)$. $\blacksquare$

    Complete C++

    class Solution {
public:
    int kthSmallest(vector<vector<int>>& matrix, int k) {
        int n = matrix.size();

        // count of entries <= x via bottom-left staircase, O(n)
        auto count = [&](long long x) -> int {
            int c = 0, r = n - 1, cnt = 0;
            while (r >= 0 && c < n) {
                if (matrix[r][c] <= x) {   // whole column above is <= x
                    cnt += r + 1;
                    ++c;                    // step right
                } else {
                    --r;                    // step up
                }
            }
            return cnt;
        };

        long long lo = matrix[0][0], hi = matrix[n - 1][n - 1];
        while (lo < hi) {
            long long mid = lo + (hi - lo) / 2;
            if (count(mid) >= k) hi = mid;      // feasible: shrink upward bound
            else                 lo = mid + 1;  // infeasible: need larger value
        }
        return (int)lo;   // smallest feasible value == kth smallest, a real cell
    }
};

    The values are 32-bit here (LeetCode 378 constrains entries to $\pm 10^9$ and $n \leq 300$, so count tops out at $90{,}000$, well within int). No long long is required for this one — but keep the mental checklist for the next two problems where products blow past 32 bits.

    Kth smallest in a multiplication table (LeetCode 668)

    The $m \times n$ multiplication table has entry $\text{tbl}[i][j] = i \cdot j$ for $1 \leq i \leq m$, $1 \leq j \leq n$. Return the $K$th smallest value in this table. With $m, n$ up to $3 \times 10^4$ the table holds up to $9 \times 10^8$ entries — building it is out of the question. This is the purest “implicit set” example: the table is defined by a formula, never stored.

    Values range over $[\,1,\ m \cdot n\,]$. We binary search that range. The counting question is: how many products $i \cdot j$ are $\leq x$? Fix a row $i$. The entries in row $i$ are $i, 2i, 3i, \ldots, ni$. Those that are $\leq x$ satisfy $j \leq x / i$, and $j$ is also capped at $n$. So row $i$ contributes

    $$\min\!\Big(\Big\lfloor \tfrac{x}{i} \Big\rfloor,\ n\Big)$$

    entries, and summing over rows gives the count in $O(m)$:

    $$\text{count}(x) = \sum_{i=1}^{m} \min\!\Big(\Big\lfloor \tfrac{x}{i} \Big\rfloor,\ n\Big).$$

    The same monotonicity argument applies: each term $\min(\lfloor x/i \rfloor, n)$ is non-decreasing in $x$, so the sum is too.

    Overflow watch. The range upper bound $m \cdot n$ can reach $9 \times 10^8$, which still fits in a 32-bit signed int — but only barely, and intermediate expressions are risky. Use long long for hi, mid, and the accumulator so nothing silently wraps.

    Complete C++

    class Solution {
public:
    int findKthNumber(int m, int n, int k) {
        // count of products i*j <= x, i in [1,m], j in [1,n], O(m)
        auto count = [&](long long x) -> long long {
            long long cnt = 0;
            for (long long i = 1; i <= m; ++i)
                cnt += min(x / i, (long long)n);   // row i contributes min(x/i, n)
            return cnt;
        };

        long long lo = 1, hi = (long long)m * n;   // implicit table, never built
        while (lo < hi) {
            long long mid = lo + (hi - lo) / 2;
            if (count(mid) >= k) hi = mid;
            else                 lo = mid + 1;
        }
        return (int)lo;   // smallest feasible value == kth smallest product
    }
};

    Dry run: $m = 3$, $n = 3$, $K = 5$

    Kth smallest pair distance (LeetCode 719)

    Given an array nums, the distance of a pair $(a, b)$ is $|a - b|$. Among all $\binom{n}{2}$ pairs, return the $K$th smallest distance. The set of distances is implicit and quadratic in size, so once again we binary search the value, not the pairs.

    First sort nums. After sorting, the smallest possible distance is $0$ (equal elements) and the largest is nums[n-1] - nums[0], so the value range is $[\,0,\ \text{nums}[n-1] - \text{nums}[0]\,]$. We search for the smallest distance $d$ with $\text{count}(d) \geq K$, where $\text{count}(d)$ is the number of pairs whose distance is $\leq d$.

    Counting pairs $\leq d$ with a sliding window in $O(n)$

    On the sorted array, for each right endpoint $j$ we want the number of left endpoints $i < j$ with $\text{nums}[j] - \text{nums}[i] \leq d$, i.e. $\text{nums}[i] \geq \text{nums}[j] - d$. Because the array is sorted, the set of valid $i$ is a contiguous suffix ending at $j-1$. Maintain a left pointer $lo$: advance it while $\text{nums}[j] - \text{nums}[lo] > d$. Then all indices $lo, lo+1, \ldots, j-1$ form valid pairs with $j$, contributing $j - lo$ pairs.

    Proof the two-pointer count is correct and $O(n)$

    Correctness. Fix $j$. We need every $i < j$ with $\text{nums}[j] - \text{nums}[i] \leq d$. Since nums is sorted ascending, $\text{nums}[j] - \text{nums}[i]$ is non-increasing as $i$ grows toward $j$, so the valid $i$ form a suffix $[lo_j,\ j-1]$ where $lo_j$ is the smallest index with $\text{nums}[j] - \text{nums}[lo_j] \leq d$. The loop advances $lo$ exactly until that condition holds, then counts $j - lo$ pairs, which is $|[lo_j,\ j-1]|$. Correct for every $j$; summing over $j$ counts each qualifying pair once (charged to its larger endpoint).

    Monotonicity of $lo_j$. As $j$ increases, $\text{nums}[j]$ does not decrease, so the threshold $\text{nums}[j] - d$ does not decrease, so $lo_j$ never moves left. That is why a single left pointer suffices: it only ever advances. Complexity. The right pointer $j$ moves $n$ times and the left pointer $lo$ moves at most $n$ times total across the whole scan, so one count is $O(n)$. $\blacksquare$

    Complete C++

    class Solution {
public:
    int smallestDistancePair(vector<int>& nums, int k) {
        sort(nums.begin(), nums.end());   // required: window relies on order
        int n = nums.size();

        // number of pairs with distance <= d, sliding window O(n)
        auto count = [&](long long d) -> long long {
            long long cnt = 0;
            int lo = 0;
            for (int j = 0; j < n; ++j) {
                while ((long long)nums[j] - nums[lo] > d) ++lo;
                cnt += j - lo;                         // pairs (lo..j-1, j)
            }
            return cnt;
        };

        long long lo = 0, hi = (long long)nums[n - 1] - nums[0];
        while (lo < hi) {
            long long mid = lo + (hi - lo) / 2;
            if (count(mid) >= k) hi = mid;
            else                 lo = mid + 1;
        }
        return (int)lo;   // LeetCode constraints guarantee the distance fits int
    }
};

    Dry run: nums = [1, 3, 1], $K = 1$

    Sort to $[1, 1, 3]$. Pair distances: $|1-1| = 0$, $|1-3| = 2$, $|1-3| = 2$; sorted $0, 2, 2$. The 1st smallest is $0$. Range $[0, 2]$.

    lohimidcount(mid)≥ 1?action
    0211  (pair (1,1))yeshi = 1
    0101  (pair (1,1))yeshi = 0

    Now $lo = hi = 0$: return $0$. The count at $d = 0$ is already $1$ because the two equal elements form a distance-0 pair — and $\text{count}(-1) = 0 < 1$, so the jump happens at a real distance value.

    Duplicates and value gaps

    Two features of value-space search deserve a spotlight, because they are precisely where index-based reasoning collapses.

    Duplicates are handled for free

    When $S$ contains several copies of a value $v$, $\text{count}$ simply jumps by more than one at $v$: $\text{count}(v) - \text{count}(v-1)$ equals the multiplicity of $v$. The proof from the first section never assumed the jump was exactly $1$. If ranks $K$ through $K+2$ all correspond to three copies of $13$, the search still converges to $13$ and returns it for any of those $K$. In the sorted-matrix dry run, the value $13$ appeared twice; the search landed on it without any special handling. Duplicate values, duplicate products, and duplicate pair distances all “just work.”

    Gaps in the value range are harmless

    The value range $[V_{\min}, V_{\max}]$ almost always contains integers that are not in $S$ — the multiplication table skips $5$ when $m = n = 3$, the matrix skips $2,3,4,6,7,8,14$. Binary search may probe those absent values as $mid$, but it never returns one. Whenever $mid$ is a gap value, $\text{count}(mid) = \text{count}(mid')$ for the largest real element $mid' \leq mid$; the feasibility verdict is identical, and the “smallest feasible” convergence slides the answer down to the real element where the count actually jumped. The result snaps to a genuine member of $S$ automatically.

    Why binary searching indices fails here. You might hope to index into a “virtual sorted array” of $S$ directly. But $S$ is not laid out in memory in sorted order — the matrix is sorted per-row and per-column but not globally, the table's row-major order is unsorted, and the pair distances have no natural array at all. There is no index $\to$ value map to binary search over without first materializing and sorting $S$, which is the very $O(|S| \log |S|)$ cost we are avoiding. Searching the value axis sidesteps the missing layout entirely: values live on the number line whether or not $S$ stores them, and $\text{count}$ is a $O(\text{cheap})$ oracle over that line.

    Complexity

    Every problem in this family costs

    $$O\big(\underbrace{C}_{\text{one count}} \times \underbrace{\log(V_{\max} - V_{\min} + 1)}_{\text{search steps}}\big),$$

    where $C$ is the time for a single $\text{count}$ call and $V_{\max} - V_{\min}$ is the width of the value range. The binary search does $O(\log(\text{range}))$ iterations; each does one count.

    Problemcount cost $C$value rangetotal
    378 — sorted matrix$O(n)$ staircase$[\,\text{m}[0][0],\ \text{m}[n{-}1][n{-}1]\,]$$O(n \log(\text{range}))$
    668 — multiplication table$O(m)$ row sum$[1,\ m \cdot n]$$O(m \log(mn))$
    719 — pair distance$O(n)$ two-pointer$[0,\ \max - \min]$$O(n \log n + n \log(\text{range}))$

    For 719 the $O(n \log n)$ term is the one-time sort; the search itself is $O(n \log(\text{range}))$ because the range is bounded by the value span, not by $n$. All three are dramatically better than materializing $S$ (which is $O(n^2)$, $O(mn)$, and $O(n^2)$ elements respectively) and sorting it.

    Common mistakes

    Counting with $< x$ instead of $\leq x$. If count returns the number of elements strictly less than $x$, the “smallest $x$ with count $\geq K$” can overshoot to a non-member. Always count elements $\leq x$; then the jump-at-a-real-element proof holds.
    Returning mid directly. Do not return mid the moment $\text{count}(mid) \geq K$. That mid may be a gap value. Let the loop converge (hi = mid on feasible, lo = mid + 1 on infeasible) and return lo; the “smallest feasible” convergence is what snaps to a real element.
    Overflow in $m \cdot n$. In the multiplication table, hi = m * n and the count accumulator can exceed 32 bits. Cast to long long before multiplying: (long long)m * n, and accumulate in long long.
    Wrong initial hi. Seed hi to a true upper bound of the value range: matrix[n-1][n-1], m*n, or nums.back() - nums.front(). A too-small hi makes the loop miss large answers; a needlessly huge hi just wastes a few iterations.
    Forgetting to sort for pair distance. The $O(n)$ sliding-window count assumes nums is sorted — the valid left endpoints form a contiguous suffix only under order. Without the sort the count is wrong and the whole search is garbage.

    Key takeaways

    • To find the $K$th smallest value of an implicit set, binary search the value range, not indices, and never materialize the set.
    • The engine is a monotone predicate $\text{count}(x) = |\{s \leq x\}|$; feasibility is $\text{count}(x) \geq K$; the smallest feasible $x$ is the answer.
    • The returned value is always a real element at rank $K$, because the count only jumps at values actually present, and convergence lands on that jump.
    • Count with $\leq$, not $<$. Duplicates (count jumps by $>1$) and gaps (answer snaps to a real value) are handled automatically.
    • Design the count to be cheap: $O(n)$ staircase (378), $O(m)$ row sum (668), $O(n)$ two-pointer (719). Total cost is $O(C \log(\text{range}))$.
    • Watch overflow (long long for products), seed lo/hi to true value bounds, and sort when the count relies on order.
