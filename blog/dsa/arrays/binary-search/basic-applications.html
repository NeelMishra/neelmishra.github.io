    Basic Applications: First Bad Version, Search Insert, Integer Sqrt

    August 2026 · 22 min read

    In Part 1 we built a single first-true template and promised that every future problem only changes three things: the bounds, the condition, and the return transform. This post proves it on three warm-up problems. The loop body — while (lo < hi), gap-form midpoint, hi = mid on true, lo = mid + 1 on false — is byte-for-byte identical in all three. Only the surrounding decisions move. The last problem, integer square root, is where the return transform earns its keep: we search for the first value that is too large and return left - 1.

    Series roadmap. (1) The template · (2) Basic applications · (3) Capacity & partition · (4) Rates & days · (5) Kth smallest · (6) Inclusion–exclusion · (7) Playbook & capstone.

    The unchanging skeleton (from Part 1)

    long long firstTrue(long long lo, long long hi,
                    const std::function<bool(long long)>& condition) {
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        if (condition(mid)) hi = mid;      // keep candidate
        else                lo = mid + 1;  // discard
    }
    return lo;
}

    First Bad Version (LeetCode 278)

    Problem 278: versions 1..n were released in order. A bad commit broke version $b$, and every version from $b$ onward is bad. You have an API isBadVersion(v). Find the first bad version with as few API calls as possible.

    This is the first-true template with almost nothing to add — the problem is a monotone boolean.

    Monotonicity. "Every version after a bad one is also bad" is precisely the false→false→true→true structure. isBadVersion is our condition already; we just locate the flip.
    DecisionValue
    Bounds[1, n]. Version n is the sentinel: if only n is bad, the search lands there; the problem guarantees at least one bad version, so no "impossible" case.
    ConditionisBadVersion(mid) — already monotone.
    Returnleft unchanged. The first true is the answer.

    Solution

    // bool isBadVersion(int version);  // provided by the judge
int firstBadVersion(int n) {
    int lo = 1, hi = n;                 // hi = n is a guaranteed-true sentinel
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;   // overflow-safe: n can be ~2^31-1
        if (isBadVersion(mid)) hi = mid;    // mid could be the first bad
        else                   lo = mid + 1;// mid is good, discard it
    }
    return lo;                          // first bad version
}

    The hi = n bound matters: with n near INT_MAX, the naive (lo + hi)/2 overflows. The gap form lo + (hi - lo)/2 is mandatory here, not optional.

    n = 5, first bad = 4

    lo=1, hi=5. mid=3, good → lo=4. lo=4, hi=5, mid=4, bad → hi=4. lo==hi==4, return 4 in two API calls.

    Search Insert Position (LeetCode 35)

    Problem 35: given a sorted array of distinct integers and a target, return the index where the target is, or where it would be inserted to keep the array sorted.

    The insert position is defined as the first index whose value is not less than the target — i.e. the first index where nums[i] >= target. That is a monotone condition on a sorted array, so it is lower_bound, and here we return it directly with no validation, because the question asks for the position rather than confirmation of a match.

    DecisionValue
    Bounds[0, n]. The sentinel n is a real answer here: if the target exceeds every element, it belongs at the end, index n.
    Conditionnums[mid] >= target.
    Returnleft unchanged — and left == n is a valid answer, not "not found."

    Solution

    int searchInsert(const std::vector<int>& nums, int target) {
    int lo = 0, hi = (int)nums.size();   // hi = n: target may go past the end
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (nums[mid] >= target) hi = mid;   // first index reaching target
        else                     lo = mid + 1;
    }
    return lo;                            // insertion index in [0, n]
}
    Contrast with Part 1’s exact match. Same condition, same loop. The only difference is the return: exact match adds a validation comparison to distinguish "present" from "absent" and returns -1 on a miss; search-insert wants the boundary itself, so it returns left raw. One template, two return transforms.

    nums = [1, 3, 5, 6], target = 2

    lo=0, hi=4. mid=2, nums[2]=5 ≥ 2 → hi=2. mid=1, nums[1]=3 ≥ 2 → hi=1. mid=0, nums[0]=1 < 2 → lo=1. Return 1. Target 7 would converge on the sentinel 4 — append at the end.

    Integer Sqrt (LeetCode 69)

    Problem 69: given a non-negative integer x, return $\lfloor\sqrt{x}\rfloor$ — the largest integer r with $r^2 \le x$. This is the first problem where the answer is a last true, not a first true, and the template handles it with a return transform.

    Reframing "largest r with r² ≤ x" as a first-true

    Our template finds the first true, but we want the last value satisfying $r^2 \le x$. The standard trick: search for the first value that breaks the property, then step back one.

    Define condition(k) = (k*k > x). As k grows, $k^2$ only increases, so once $k^2 > x$ it stays that way — monotone. The false region is $\{k : k^2 \le x\}$ and the true region is $\{k : k^2 > x\}$. The first true k is the smallest integer whose square exceeds x, so:

    $$\lfloor\sqrt{x}\rfloor = (\text{first } k \text{ with } k^2 > x) - 1$$
    k: 0 1 2 3 4 5 6 ... (x = 17) k*k > 17: F F F F F T T ^ ^ last false first true = 5 floor(sqrt(17)) = 5 - 1 = 4

    Making it overflow-safe

    The condition multiplies k*k. For x up to INT_MAX $\approx 2.1\times10^9$, the answer reaches 46340, and candidate k values near the top of our range squared overflow a 32-bit int. Two robust fixes:

    • Wide type: compute the product in long long. With k at most $x + 1 \le 2^{31}$, $k^2 \le 2^{62}$, comfortably inside long long’s $\approx 9.2\times10^{18}$ range.
    • Division: for k > 0, test k > x / k instead of k*k > x, which never multiplies. (Integer division truncates, but for the strict comparison this still separates the regions correctly.)

    We also need a sentinel bound that is guaranteed true. Take hi = x + 1: since $(x+1)^2 = x^2 + 2x + 1 > x$ for every x ≥ 0, condition(hi) is always true, so the search can never fall off the top. The low bound is 0.

    Solution (wide-type condition)

    int mySqrt(int x) {
    long long lo = 0, hi = (long long)x + 1;   // hi = x+1 is a true sentinel
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        if (mid * mid > (long long)x) hi = mid;    // condition: k^2 exceeds x
        else                          lo = mid + 1;
    }
    return (int)(lo - 1);                       // last k with k^2 ≤ x
}

    Because x + 1 is always a true value, lo can never converge on 0’s predecessor; the smallest possible first-true is 1 (when x = 0), giving lo - 1 = 0 correctly. There is no fabricated success path: the return is a pure arithmetic transform of a boundary the invariant guarantees.

    Why not hi = x? For x = 1, the first k with $k^2 > 1$ is k = 2, but x = 1 would exclude it from the range and the sentinel would not be true. hi = x + 1 keeps the sentinel honest for every input, including x = 0 and x = 1.

    x = 8

    lo=0, hi=9. mid=4, 16>8 → hi=4. mid=2, 4>8? no → lo=3. lo=3, hi=4, mid=3, 9>8 → hi=3. Converged lo=3; return 3 - 1 = 2. Check: $2^2 = 4 \le 8 < 9 = 3^2$. Correct.

    Three Problems, One Loop

    Placed side by side, the only differences are the three decisions. Print this table on the inside of your eyelids.

    ProblemBoundsCondition(mid)Return
    First Bad Version (278)[1, n]isBadVersion(mid)left
    Search Insert (35)[0, n]nums[mid] ≥ targetleft
    Exact match (704)[0, n]nums[mid] ≥ targetleft, then validate else -1
    Integer Sqrt (69)[0, x+1]mid*mid > xleft - 1
    The pattern behind the return column. "First true" → return left. "Present or absent" → return left then validate. "Last false / largest satisfying value" → search the first-broken condition and return left - 1. These three transforms cover a huge fraction of interview binary searches.

    Common Mistakes

    • Sqrt with int multiplication. mid*mid in 32-bit overflows for large x and gives wrong or negative comparisons. Use long long or the division test.
    • Sqrt sentinel too small. hi = x breaks for x ∈ {0, 1}; use hi = x + 1 so the sentinel is always true.
    • Search-insert returning -1 for a miss. The problem wants the insertion index, which may be n; there is no "not found."
    • Overflow in First Bad Version. With n near INT_MAX, (lo + hi)/2 overflows; the gap form is required.
    • Forgetting the -1 transform in sqrt. Returning left gives the first k that is too big — one more than the true answer.

    Complexity

    All three run in $O(\log R)$ where R is the range length: $O(\log n)$ for the array problems and $O(\log x)$ for the square root, with $O(1)$ extra space. Each condition call is $O(1)$, so there is no hidden multiplier here — that comes in Part 3, where the condition becomes a full greedy scan.

    Key Takeaways

    • First Bad Version is the template with no changes: the API is the monotone condition, return left.
    • Search Insert is lower_bound returned raw; the sentinel n is a legitimate answer (append at end).
    • Integer Sqrt shows the return transform: search the first k with $k^2 > x$, then return left - 1.
    • Keep the sqrt overflow-safe with a wide-type product (or division test) and a sentinel bound hi = x + 1 that is always true.
    • Across all four problems the loop is identical; only bounds, condition, and return move.
