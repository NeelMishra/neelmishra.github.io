    Monotone Predicates & Binary Search on the Answer

    March 2026 · 28 min read

    The first two posts searched inside a sorted array. This one performs the single most important mental leap in the whole series: you stop searching an array altogether. Instead, the answer you want is some number living in a range $[\mathit{lo}, \mathit{hi}]$, and you have a function feasible(x) that returns true or false. If that function is monotone — once it flips it never flips back — binary search finds the exact boundary where it changes. No array required.

    Series roadmap. (1) Fundamentals · (2) Boundary search · (3) Binary search on the answer · (4) Minimize max / maximize min · (5) Rotated arrays · (6) Peaks & mountains · (7) Order statistics · (8) Median of two arrays · (9) Real-valued search · (10) Recognition & capstone.

    The Conceptual Shift

    Forget arrays for a moment. Picture a numeric range of candidate answers, say every integer from $\mathit{lo}$ to $\mathit{hi}$. For each candidate $x$ you can ask a yes/no question and get back a boolean:

    $$\texttt{feasible}(x) \in \{\text{true}, \text{false}\}$$

    The crucial requirement is that this predicate is monotone: as $x$ increases, feasible changes value at most once. There are two shapes:

    • false…false, true…true — once true, always true. We want the smallest $x$ that is feasible (the first true).
    • true…true, false…false — once false, always false. We want the largest $x$ that is feasible (the last true).

    Either way there is exactly one boundary where the value flips, and binary search finds it in $O(\log(\mathit{hi}-\mathit{lo}))$ probes. The predicate is the search space; the array, if there even is one, is only a tool feasible uses internally.

    The unifying insight. A sorted array search is just the special case where feasible(i) = (a[i] >= target). That predicate is false for small indices (elements below the target) and true from the first index whose element reaches the target onward — a textbook monotone false…true pattern. Every boundary-style binary search is secretly "find the first input where a monotone predicate becomes true." Once you see that, the array stops being special: you can binary search over speeds, capacities, days, distances, or any orderable quantity. Parts 5–6 later show structural variants (rotated arrays and peaks) whose proof is instead that one chosen half is guaranteed to retain a solution.

    So the recipe for the rest of this series is always the same three questions:

    1. What single number am I trying to find? That is the answer, and it lives in a range.
    2. Given a guess $x$, can I write a boolean feasible(x)?
    3. Is that predicate monotone? If yes, binary search. If I cannot prove it, I must not.

    Proving Monotonicity

    Binary search on the answer is only correct if the predicate is monotone. This is not a formality you can skip — it is the entire justification for throwing away half the range. The clean way to prove it is a one-step argument:

    General argument (for "find the smallest feasible $x$", i.e. false…true). Show that if $x$ is feasible then $x+1$ is also feasible. If every feasible value forces its successor to be feasible too, then feasibility, once achieved, can never be lost as $x$ grows — exactly the false…true shape. Symmetrically, for a "find the largest feasible $x$" (true…false) predicate, show that if $x$ is feasible then $x-1$ is feasible.

    The intuition that makes this almost automatic: for minimization problems, a larger budget makes the task easier. If you can finish some job with resource level $x$, then with $x+1$ (more time, more speed, more capacity) you can certainly still finish it — you had strictly more room and could just ignore the extra.

    Concrete example. "Can I finish all the work in at most $x$ days if I work at a fixed pace?" Suppose the answer is yes at $x$ days. Then at $x+1$ days you have one extra day; do exactly what you did before and finish a day early — still feasible. So the predicate canFinishInDays(x) is monotone false…true, and the smallest feasible $x$ is the minimum number of days. The same shape appears for "eat all bananas within $h$ hours at speed $k$" (larger $k$ is easier), "cut boards of total length $\ge L$ with blade height $x$", and countless others.

    If you cannot prove monotonicity, binary search is invalid. A predicate that flips true→false→true (or wiggles) will make binary search silently return a wrong boundary — the code runs, produces a number, and that number is meaningless. Recognizing which problems are genuinely monotone (and which only look monotone) is a skill in itself; we devote Part 10 to the recognition patterns and to the traps where monotonicity fails.

    The Two Canonical Templates

    Every answer-space binary search collapses into one of two templates depending on whether you want the first feasible value or the last. Memorize both; they differ in exactly two places (the midpoint rounding and the update rules).

    Template A — minimize feasible (smallest x with feasible(x) == true)

    Predicate shape: false…false, true…true. We shrink toward the first true.

    // Find the smallest x in [LOW, HIGH] with feasible(x) == true.
int minimizeFeasible() {
    int lo = LOW, hi = HIGH;      // inclusive bounds; answer in [lo, hi]
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;   // rounds DOWN
        if (feasible(mid)) hi = mid;    // mid might BE the answer -> keep it
        else               lo = mid + 1;// mid is too small -> discard it
    }
    return lo;                    // lo == hi == first feasible value
}

    Template B — maximize feasible (largest x with feasible(x) == true)

    Predicate shape: true…true, false…false. We shrink toward the last true.

    // Find the largest x in [LOW, HIGH] with feasible(x) == true.
int maximizeFeasible() {
    int lo = LOW, hi = HIGH;
    while (lo < hi) {
        int mid = lo + (hi - lo + 1) / 2;  // rounds UP
        if (feasible(mid)) lo = mid;       // mid works -> keep it, push up
        else               hi = mid - 1;   // mid fails -> discard it
    }
    return lo;                    // lo == hi == last feasible value
}

    Why does Template B need the +1 (round-up) midpoint? Consider the danger zone where the interval has shrunk to two adjacent values, so hi == lo + 1. With the ordinary round-down midpoint mid = lo + (hi - lo) / 2 we would get mid == lo. In Template B, a feasible mid executes lo = mid, i.e. lo = lo — nothing changes, hi stays put, and the loop spins forever. Rounding up with lo + (hi - lo + 1) / 2 makes mid == hi in that case, so a feasible test moves lo up to hi (loop ends) and an infeasible test moves hi down to lo (loop ends). Either branch strictly shrinks the interval, which is exactly the guarantee we proved in Part 1 that makes the loop terminate.

    Rule of thumb. The pointer that can be assigned mid (without the ±1) dictates the rounding. Template A assigns hi = mid, so round down (bias mid away from hi). Template B assigns lo = mid, so round up (bias mid away from lo). Mismatch the rounding and you get an infinite loop.

    Choosing Inclusive Bounds

    Both templates use an inclusive interval $[\mathit{lo}, \mathit{hi}]$: the true answer must sit somewhere inside it, endpoints included. Picking the bounds is where correctness is won or lost. There are two common strategies.

    • Sentinel bounds. Choose a lo that is provably infeasible and a hi that is provably feasible (for a minimize search). You do not need them tight — you only need to be certain the flip happens between them. Example: for "minimum eating speed," speed $0$ is clearly infeasible-ish so start at $1$, and speed = the largest pile size clearly lets you finish every pile in one hour, so it is feasible.
    • Known-feasible endpoints. Sometimes a natural extreme is guaranteed to satisfy the predicate. Set hi to that extreme directly (e.g. the maximum array value, the total sum, the full length). This is usually the smallest correct upper bound and keeps the iteration count low.
    Too-tight bounds silently miss the answer. If you set hi below the true answer, binary search returns hi — a wrong value, no crash. Always sanity-check that the extreme you chose really is feasible. When in doubt, err generous.
    Too-loose bounds are safe. An over-large hi or over-small lo only costs a handful of extra iterations, because the count grows as $\log(\mathit{hi}-\mathit{lo})$. Doubling the range adds exactly one iteration. When uncertain, prefer bounds that are obviously wide enough over bounds that are cleverly tight.

    One more obligation: the answer must actually exist inside the range. If it is possible that no value is feasible (e.g. the task cannot be done at all), the return value lo is only a candidate — verify feasible(lo) once at the end and report "impossible" if it fails, rather than trusting the boundary blindly.

    Complexity

    Let check be the cost of a single feasible() call and let $\text{range} = \mathit{hi} - \mathit{lo} + 1$ be the number of integer candidates. Binary search performs $O(\log(\text{range}))$ probes, each costing $O(\text{check})$:

    $$O\big(\text{check} \cdot \log(\mathit{hi} - \mathit{lo} + 1)\big)$$

    Concrete example. Suppose feasible(x) scans an array of $n = 10^5$ elements, so $\text{check} = O(n)$, and the answer ranges over speeds from $1$ to $10^9$. Then $\log_2(10^9) \approx 30$ probes, each doing $10^5$ work, for about $30 \times 10^5 = 3 \times 10^6$ operations — instantaneous. A linear scan of all $10^9$ candidate speeds, each costing $10^5$, would be $10^{14}$ operations — hopeless. The logarithm on the range is what makes answer-space search practical.

    Exponential Search for an Unknown Upper Bound

    Sometimes you cannot name a safe hi up front — the input is unbounded, implicit, or streamed. The fix is exponential (galloping) search: start with a tiny hi and double it until the predicate becomes true, guaranteeing you bracket the answer, then binary search the narrowed window.

    #include <climits>
#include <stdexcept>

// Find the smallest x >= 1 with feasible(x) == true, upper bound unknown.
long long exponentialThenBinary() {
    long long lo = 1, hi = 1;
    while (!feasible(hi)) {
        if (hi == LLONG_MAX)
            throw std::out_of_range("no feasible value in long long range");
        lo = hi + 1;   // every value through the old hi is known false
        hi = (hi > LLONG_MAX / 2) ? LLONG_MAX : hi * 2;
    }
    // feasible(hi) is true; [lo, hi] contains the first true value.
    while (lo < hi) {                // standard minimize template
        long long mid = lo + (hi - lo) / 2;
        if (feasible(mid)) hi = mid;
        else               lo = mid + 1;
    }
    return lo;
}

    The doubling phase makes only $O(\log(\text{answer}))$ probes before it overshoots the true answer, and the subsequent binary search over the bracket between the last false probe and the first true probe is another $O(\log(\text{answer}))$ probes. So the overall cost stays $O(\text{check} \cdot \log(\text{answer}))$ even though we never knew a bound in advance. The saturation guard matters in real code: unchecked signed overflow in hi *= 2 is undefined behavior in C++.

    Where this shows up. Exponential search is the standard tool for unbounded or implicit inputs: an API that only tells you isBadVersion(x), a monotone function with no stated ceiling, or searching an unbounded sorted stream where you can only ask "is the element at position $i$ ≥ target?" You gallop i = 1, 2, 4, 8, … until you pass the target, then binary search the last doubling window.

    A Fully Worked Example

    Let us run the entire pipeline on LeetCode 1283 — Find the Smallest Divisor Given a Threshold. Given an array a and an integer threshold, find the smallest positive divisor $x$ such that

    $$\sum_{i} \left\lceil \frac{a_i}{x} \right\rceil \le \texttt{threshold}.$$

    Step 1 — identify the answer. We want a single number: the divisor $x$. It lives in the range of positive integers.

    Step 2 — write feasible(x). Compute the sum of ceilings and compare to the threshold. Note $\lceil a_i / x \rceil = (a_i + x - 1) / x$ in integer arithmetic.

    bool feasible(const vector<int>& a, int x, int threshold) {
    long long sum = 0;                 // long long: sum can exceed int range
          for (int v : a) sum += (v + (long long)x - 1) / x; // widen before addition
    return sum <= threshold;
}

    Step 3 — prove monotonicity. As the divisor $x$ grows, each term $\lceil a_i / x \rceil$ is non-increasing (dividing by a larger number cannot produce a larger ceiling). So the whole sum is non-increasing in $x$. If the sum is $\le$ threshold at some $x$, it is still $\le$ threshold at $x+1$. That is precisely "if $x$ is feasible then $x+1$ is feasible" — a monotone false…true predicate. A larger divisor makes the sum smaller, which makes the task easier. Template A applies.

    Step 4 — choose bounds. The smallest sensible divisor is $x = 1$ (giving the largest possible sum). The divisor never needs to exceed max(a): once $x \ge \max a_i$, every ceiling is exactly $1$, so the sum equals $n$ and cannot shrink further. Hence lo = 1, hi = max(a), and the answer is guaranteed inside (the problem promises a solution exists).

    int smallestDivisor(vector<int>& a, int threshold) {
    int lo = 1, hi = 0;
    for (int v : a) hi = max(hi, v);       // hi = max(a)
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;      // round down (minimize template)
        if (feasible(a, mid, threshold)) hi = mid;   // mid works, try smaller
        else                             lo = mid + 1;// mid too small
    }
    return lo;                             // smallest feasible divisor
}

    Step 5 — numeric dry run. Take a = [1, 2, 5, 9] and threshold = 6. Then lo = 1, hi = max(a) = 9.

    lohimidsum of ceilingsfeasible? (≤ 6)action
    1951+1+1+2 = 5truehi = 5
    1531+1+2+3 = 7falselo = 4
    4541+1+2+3 = 7falselo = 5
    55———lo == hi, stop

    The loop returns 5. Check: with divisor $5$ the sum is $\lceil 1/5\rceil+\lceil 2/5\rceil+\lceil 5/5\rceil+\lceil 9/5\rceil = 1+1+1+2 = 5 \le 6$ (feasible), while divisor $4$ gives $1+1+2+3 = 7 > 6$ (infeasible). So $5$ is indeed the smallest feasible divisor. Notice how the search touched only $3$ candidate divisors instead of scanning all $9$.

    Common Mistakes

    Non-monotone predicate. The predicate wiggles (false→true→false). Binary search assumes a single flip; if there are several, it returns some arbitrary boundary. Always prove the one-step property before trusting the result.
    Wrong midpoint rounding for maximize. Using the round-down midpoint in Template B causes an infinite loop when hi == lo + 1, because lo = mid is a no-op. Maximize needs lo + (hi - lo + 1) / 2.
    Off-by-one bounds. A hi set just below the true answer, or a lo set just above it, makes the search return the wrong endpoint with no error. Verify both bounds bracket the flip.
    Forgetting long long in feasible(). Sums of ceilings, total lengths, or accumulated costs routinely overflow 32-bit int. Accumulate in long long (or compare incrementally with early exit) so the predicate itself does not lie.
    Assuming an answer exists. If it is possible that no value is feasible, check feasible(lo) once at the end and report "impossible" instead of returning a meaningless boundary.

    Key Takeaways

    • You are not searching an array — the answer lives in a numeric range $[\mathit{lo}, \mathit{hi}]$ and feasible(x) is a boolean.
    • A sorted-array search is the special case feasible(i) = (a[i] >= target).
    • Binary search is valid only if the predicate is monotone; prove it with the one-step argument ("if $x$ works, $x\pm1$ works").
    • Template A (minimize): round down, feasible ⇒ hi = mid, else lo = mid + 1.
    • Template B (maximize): round up (hi - lo + 1), feasible ⇒ lo = mid, else hi = mid - 1 — the +1 prevents an infinite loop.
    • Use inclusive bounds that provably bracket the flip; too-loose is safe, too-tight silently fails.
    • Cost is $O(\text{check} \cdot \log(\mathit{hi}-\mathit{lo}+1))$; use overflow-guarded exponential search when hi is unknown.
    • Guard against overflow (long long) and against the "no feasible answer" case.
