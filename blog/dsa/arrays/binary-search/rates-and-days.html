    Rates & Days: Koko, Bouquets, and Smallest Divisor

    August 2026 · 24 min read

    Part 3 searched for a capacity that partitions a sequence into groups. This post keeps the same "binary search on the answer" idea but changes what the feasibility check computes: instead of counting groups, we count time. Three classic problems — Koko Eating Bananas (875), Minimum Days to Make m Bouquets (1482), and Smallest Divisor Given a Threshold (1283) — all reduce to the same template. Along the way we handle the two details that make these fiddly in practice: overflow-safe ceiling arithmetic and the impossible case that must be detected before the search even starts.

    Series roadmap. (1) The template · (2) Basic applications · (3) Capacity & partition · (4) Rates & days · (5) Kth smallest · (6) Inclusion–exclusion · (7) Playbook & capstone.

    Ceiling Arithmetic, Done Safely

    Two of these problems compute "how many time units does rate r take" as a sum of ceilings. The ceiling of a division shows up constantly, and the naive floating-point version (ceil((double)a / r)) is a trap: for large values, doubles lose integer precision and round incorrectly. Do it with integers:

    Integer ceiling division

    // ceil(a / b) for a >= 0, b > 0, without floating point or pre-division addition.
long long ceilDiv(long long a, long long b) {
    return a / b + (a % b != 0);
}

    The familiar identity is $\lceil a/b \rceil = \lfloor (a + b - 1)/b \rfloor$ for positive b, but a + b - 1 can overflow near the type limit. The quotient-plus-remainder form above is equivalent and avoids that pre-division addition entirely.

    Koko Eating Bananas (LeetCode 875)

    Problem 875: Koko has piles of bananas and H hours before the guards return. She picks an eating speed k (bananas/hour). Each hour she eats from a single pile; if the pile has fewer than k, she finishes it and stops for that hour. Find the minimum integer speed that clears every pile within H hours.

    A pile of size p takes $\lceil p/k \rceil$ hours. Total hours $= \sum_i \lceil p_i / k \rceil$, and Koko finishes in time iff that sum is $\le H$.

    DecisionValue
    Bounds[1, max(piles)]. Speed 0 is meaningless; at speed max(piles) every pile takes exactly one hour, so hours = n ≤ H (the constraints guarantee H ≥ n), making it a true sentinel.
    ConditionhoursNeeded(k) ≤ H, where hoursNeeded sums the per-pile ceilings.
    Returnleft — the minimum feasible speed.
    Monotonicity. Eating faster never takes more hours: increasing k can only shrink each $\lceil p_i/k \rceil$. So hoursNeeded is non-increasing in k, and feasible flips from false (too slow) to true (fast enough) exactly once.

    Solution (with early exit)

    int minEatingSpeed(std::vector<int>& piles, int H) {
    long long lo = 1, hi = 0;
    for (int p : piles) hi = std::max(hi, (long long)p);   // hi = max pile
    auto hoursNeeded = [&](long long k) {
        long long hours = 0;
        for (int p : piles) {
            hours += (p + k - 1) / k;      // ceil(p / k), integer-safe
            if (hours > H) return hours;   // early exit: already too slow
        }
        return hours;
    };
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        if (hoursNeeded(mid) <= H) hi = mid;    // fast enough: try slower
        else                       lo = mid + 1;// too slow: go faster
    }
    return (int)lo;
}

    The early exit in hoursNeeded stops summing the moment the hour count exceeds H — there is no point finishing the loop once we know the speed is too slow. It does not change correctness (the return value is still $> H$), only constant-factor speed.

    piles = [3, 6, 7, 11], H = 8

    lo=1, hi=11. At k=4: $\lceil3/4\rceil+\lceil6/4\rceil+\lceil7/4\rceil+\lceil11/4\rceil = 1+2+2+3 = 8 \le 8$, feasible. At k=3: $1+2+3+4 = 10 > 8$, infeasible. The search converges on 4.

    Minimum Days to Make m Bouquets (LeetCode 1482)

    Problem 1482: bloomDay[i] is the day flower i blooms. To make one bouquet you need k adjacent flowers that have all bloomed. Find the minimum number of days to wait so you can assemble m bouquets (each bouquet uses distinct flowers). Return -1 if impossible.

    The impossible case comes first

    Each bouquet consumes k distinct flowers, so m bouquets need m*k flowers. If m*k > n, no amount of waiting helps — there are simply not enough flowers. This must be checked before the search, both because it is the honest answer (-1) and because otherwise the sentinel bound would be a lie (the top of the range would still be infeasible, breaking the invariant).

    Overflow note. Compare as (long long)m * k > n. With m and k each up to $10^5$, the product reaches $10^{10}$, which overflows 32-bit int and could wrap to a small positive value, silently skipping the impossibility check.

    The feasibility condition: adjacency runs

    Fix a candidate day d. A flower is "available" iff bloomDay[i] ≤ d. Scan left to right, tracking the length of the current run of consecutive available flowers. Every time a run reaches k, complete a bouquet and reset the run to zero (those k flowers are used up). A gap (an unbloomed flower) also resets the run. Feasible iff we complete at least m bouquets.

    DecisionValue
    Bounds[min(bloomDay), max(bloomDay)]. On the max day every flower is available; if m*k ≤ n that is enough bouquets, so max is a true sentinel.
    ConditionbouquetsBy(d) ≥ m via the adjacency-run scan.
    Returnleft, after the m*k > n impossibility guard returns -1.

    Solution

    int minDays(std::vector<int>& bloomDay, int m, int k) {
    int n = (int)bloomDay.size();
    if ((long long)m * k > n) return -1;          // impossible: not enough flowers

    long long lo = LLONG_MAX, hi = 0;
    for (int b : bloomDay) { lo = std::min(lo, (long long)b); hi = std::max(hi, (long long)b); }

    auto bouquetsBy = [&](long long d) {
        int made = 0, run = 0;
        for (int i = 0; i < n; i++) {
            if (bloomDay[i] <= d) {
                if (++run == k) { made++; run = 0; }   // complete a bouquet
                if (made >= m) return made;            // early exit
            } else {
                run = 0;                                // gap breaks the run
            }
        }
        return made;
    };
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        if (bouquetsBy(mid) >= m) hi = mid;   // enough bouquets: wait fewer days
        else                      lo = mid + 1;// not enough: wait longer
    }
    return (int)lo;
}
    Monotonicity. Waiting longer never removes an available flower — the set of bloomed flowers only grows with d. A run available on day d is still available on day d+1, so bouquetsBy is non-decreasing. The greedy "complete a bouquet as soon as a run hits k" is optimal because delaying a completion can never create more bouquets.

    bloomDay = [1, 10, 3, 10, 2], m = 3, k = 1

    m*k = 3 ≤ 5, possible. With k=1 every bloomed flower is its own bouquet, so bouquetsBy(d) = count of flowers with bloomDay ≤ d. We need 3 such flowers: days 1, 2, 3 give flowers {0}, {0,4}, {0,4,2} = 3 flowers on day 3. Day 2 gives only 2. Answer 3.

    Find the Smallest Divisor Given a Threshold (LeetCode 1283)

    Problem 1283: given nums and a threshold, pick a positive integer divisor d; the cost is $\sum_i \lceil nums_i / d \rceil$. Find the smallest d whose cost is $\le$ threshold.

    This is Koko with the words swapped: divisor plays the role of speed, and the ceiling-sum cost plays the role of hours. Larger d shrinks every ceiling, so the cost is non-increasing — monotone, first-true.

    DecisionValue
    Bounds[1, max(nums)]. At d = max(nums) every term is 1, so cost $= n \le$ threshold (the constraints guarantee threshold ≥ n) — a true sentinel.
    Conditioncost(d) ≤ threshold.
    Returnleft.

    Solution

    int smallestDivisor(std::vector<int>& nums, int threshold) {
    long long lo = 1, hi = 0;
    for (int x : nums) hi = std::max(hi, (long long)x);   // hi = max element
    auto cost = [&](long long d) {
        long long s = 0;
        for (int x : nums) {
            s += (x + d - 1) / d;          // ceil(x / d), integer-safe
            if (s > threshold) return s;   // early exit
        }
        return s;
    };
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        if (cost(mid) <= threshold) hi = mid;   // cheap enough: try a smaller divisor
        else                        lo = mid + 1;// too costly: divisor too small
    }
    return (int)lo;
}

    nums = [1, 2, 5, 9], threshold = 6

    At d=5: $1+1+1+2 = 5 \le 6$, feasible. At d=4: $1+1+2+3 = 7 > 6$, infeasible. Answer 5.

    One Template, Three Rates

    ProblemBoundsCondition(mid)Extra handling
    Koko (875)[1, max(piles)]$\sum \lceil p_i/mid\rceil \le H$early exit on hours
    Bouquets (1482)[min, max] bloomadjacency runs $\ge m$m*k > n → -1
    Smallest Divisor (1283)[1, max(nums)]$\sum \lceil x_i/mid\rceil \le T$early exit on cost

    Every one returns left; the loop is identical to Part 1. Only the condition and bounds move, plus one impossibility guard for bouquets.

    Complexity

    All three are $O(n \log V)$ time and $O(1)$ extra space, where V is the value range (max pile, max bloom day, or max element). The $\log V$ factor is at most ~30 for values up to $10^9$, and each feasibility check is a single linear scan — the early exits shave the constant but not the asymptotics.

    Common Mistakes

    • Floating-point ceilings. ceil((double)p / k) misrounds for large integers; use (p + k - 1) / k in long long.
    • Skipping the m*k > n check (or doing it in 32-bit). Without it, the sentinel bound is not actually feasible and the search returns a wrong day instead of -1.
    • Starting Koko/divisor at lo = 0. Division by zero. The minimum meaningful rate is 1.
    • Not resetting the run on a gap in bouquets. Bouquets require adjacent flowers; an unbloomed flower breaks the run.
    • Resetting run to 1 instead of 0 after completing a bouquet. The k flowers are consumed; the next bouquet must start a fresh run from the following flower.

    Key Takeaways

    • "Rate/day" problems binary search the rate; the condition sums time (ceilings) or counts greedy events (bouquets).
    • Use integer ceiling division in long long; never floating point.
    • Koko and Smallest Divisor are the same problem — a ceiling-sum cost that decreases with the rate.
    • Bouquets adds two wrinkles: an impossible guard (m*k > n in 64-bit) and greedy adjacency runs that reset on gaps and on completion.
    • Early exits speed up the feasibility scan without changing the answer.
    • What changed from Part 3: the condition counts time/events instead of groups; bounds become [1, max] or [min, max]; one problem needs an impossibility check.
