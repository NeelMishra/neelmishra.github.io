    Peaks & Mountain Arrays

    March 2026 · 22 min read

    Every binary search so far in this series has leaned on one comfortable assumption: the data is globally sorted, so a comparison at the middle tells us which entire half to throw away. This post breaks that assumption. We will binary search arrays that are not sorted at all and still converge in $O(\log n)$. The trick is a local direction test: compare two adjacent cells and prove that at least one peak survives in the uphill half. Unlike first-true search, the sequence of slope answers in a jagged array need not be monotone; correctness comes from preserving an existence invariant, not from locating a single boolean flip.

This installment is where "the array must be sorted" finally stops being a prerequisite.

    Peak Element (LeetCode 162)

    A peak element is an entry that is strictly greater than both of its neighbors. Formally, index $i$ is a peak of array $a$ of length $n$ if $a[i-1] < a[i]$ and $a[i] > a[i+1]$. To make the endpoints behave, we imagine two virtual sentinels: $a[-1] = -\infty$ and $a[n] = -\infty$. Under this convention every array of length $\ge 1$ has at least one peak — the global maximum is always a peak, and so is any local maximum. The problem does not ask for the global maximum; it asks for any peak index, which is exactly what lets us go faster than the $O(n)$ scan.

    The array is not sorted. There is no global order to exploit. What we have instead is a local slope. Look at mid and its right neighbour mid+1:

    • If a[mid] < a[mid+1], the terrain is rising as we step right. Walking uphill from mid+1 must eventually hit a peak — either the values keep climbing until index $n-1$ (a peak, because $a[n]=-\infty$) or they turn downward at some point (creating a peak). So a peak exists in $[mid+1, hi]$: set lo = mid+1.
    • Otherwise a[mid] > a[mid+1] (strictly, since the standard constraints forbid equal adjacent elements), the terrain is falling to the right. Then mid itself is either already a peak or there is a higher point to its left, so a peak exists in $[lo, mid]$: set hi = mid.

    Because the "else" branch keeps mid in the live interval, we must use hi = mid (not hi = mid - 1), and the loop condition is while (lo < hi). When the loop exits, lo == hi and that single surviving index is a peak.

    Find Peak Element — C++

    int findPeakElement(vector<int>& a) {
    int lo = 0, hi = (int)a.size() - 1;   // closed interval [lo, hi]
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;     // mid < hi, so mid+1 is in range
        if (a[mid] < a[mid + 1])
            lo = mid + 1;                 // slope rises: peak strictly to the right
        else
            hi = mid;                     // slope falls: peak at mid or to the left
    }
    return lo;                            // lo == hi == a peak index
}

    Why we never read out of bounds. The only risky access is a[mid + 1]. Inside the loop the guard lo < hi holds, so $lo \le hi - 1$. The midpoint satisfies

    $$mid = lo + \left\lfloor \frac{hi - lo}{2} \right\rfloor \le lo + \frac{hi - lo}{2} \le \frac{lo + hi}{2} < hi \le n-1.$$

    Since $mid < hi \le n-1$, we get $mid + 1 \le hi \le n-1$, which is a valid index. The access is always safe — there is no separate boundary check needed, and that is precisely why the closed form with hi = mid is so clean.

    Why it is correct. Maintain the loop invariant:

    Invariant: there is always at least one peak index within the closed interval $[lo, hi]$ (using the $-\infty$ sentinels at both ends).

    Initially $[0, n-1]$ contains the global maximum, which is a peak, so the invariant holds. Each iteration preserves it: if a[mid] < a[mid+1] we argued a peak lives in $[mid+1, hi]$ and we set lo = mid+1; otherwise a peak lives in $[lo, mid]$ and we set hi = mid. The interval strictly shrinks every step (either lo increases or hi decreases), so the loop terminates. When lo == hi the interval is a single index that, by the invariant, must be a peak. The whole thing runs in $O(\log n)$ time and $O(1)$ space.

    Why a Local Rule Suffices

    It feels almost too good: we compare only two adjacent cells, yet we discard half the array. How can a purely local observation justify a global elimination when the array is arbitrary? The answer is a continuity-style argument on discrete slopes.

    Important distinction. On [1,3,2,4,1], the tests a[i] < a[i+1] are true, false, true, false — not monotone. This algorithm is therefore not a first-true boundary search. It is still binary search because every local comparison proves that one chosen half contains at least one acceptable answer.

    Extend the array with the sentinels $a[-1] = a[n] = -\infty$. Define the discrete slope at position $i$ as the sign of $a[i+1] - a[i]$. At the far left edge the slope is $+$ (we rise from $-\infty$ into $a[0]$); at the far right edge the slope is $-$ (we fall from $a[n-1]$ into $-\infty$). Any sequence of $\pm$ signs that begins with $+$ and ends with $-$ must contain at least one "$+$ then $-$" transition, and that transition is exactly a peak. This is a discrete analogue of the intermediate value theorem: a signal that starts going up and ends going down has to turn around somewhere.

    Now the binary search. When we observe a[mid] < a[mid+1] (slope $+$ at mid), the sub-array $[mid+1, hi]$ still begins going up (into mid+1) and still ends going down (into the sentinel or into whatever falls at hi). So the same start-up/end-down structure is preserved on the right half, guaranteeing a peak there. Symmetrically, an observed slope $-$ preserves the structure on the left half up to and including mid. We never skip past all peaks, because the half we keep always retains the up-then-down shape that forces a peak to exist inside it.

    Many peaks, any peak. A general array can have many peaks — a jagged sequence like [1,3,2,4,1,5,2] has three. Binary search does not find the peak; it finds a peak, whichever one the halving happens to funnel toward. That is fine because the problem only demands one, and it is the reason we can beat the $O(n)$ scan that would be forced if we needed, say, the global maximum specifically.

    Boundary Safety

    The peak search is short, but the boundary handling is where most buggy versions go wrong. Three things deserve care.

    1. The mid + 1 access. The predicate reads a right neighbour, so if you ever evaluate a[mid + 1] when mid can equal n - 1, you index one past the end — undefined behaviour in C++. The safe pattern couples the predicate with the interval choice: use hi = n - 1, while (lo < hi), and hi = mid in the else branch. As proven above this forces mid < hi ≤ n - 1, so mid + 1 is in range. The classic bug looks like this:

    Buggy: while (lo <= hi) { mid = ...; if (a[mid] < a[mid + 1]) ... }. With lo <= hi and hi = n - 1, mid can reach n - 1, and a[mid + 1] reads a[n] — out of bounds. The < condition plus hi = mid is what prevents this.

    2. Tiny arrays. For n == 1 the loop body never runs (lo == hi == 0 immediately) and we return index 0, which is correct: a lone element beats both $-\infty$ sentinels. For n == 2 we do exactly one comparison of a[0] versus a[1] and return the larger index. An empty array (n == 0) has no peak and no valid answer; guard it upstream if your inputs allow it, since hi = -1 would make the initial interval empty.

    3. hi = n - 1 versus hi = n. With the slope predicate we deliberately keep hi = n - 1 because the answer is an actual array index and the else branch retains mid. A half-open hi = n framing works for boundary/lower-bound searches (Part 2) where hi is an insertion position, but here it would let mid reach n - 1 and reintroduce the a[mid + 1] overflow. Match the interval convention to the predicate: because our predicate looks rightward, we cap hi at the last real index.

    Peak Index in a Mountain Array (LeetCode 852)

    A mountain array is a stricter, friendlier cousin. It strictly increases up to a summit and then strictly decreases: there exist an index $p$ with $a[0] < a[1] < \dots < a[p] > a[p+1] > \dots > a[n-1]$, and $n \ge 3$. The summit $p$ is the unique peak. We can reuse the exact same slope predicate; the only difference from LeetCode 162 is that here the answer is guaranteed unique, so there is no ambiguity about which peak we land on.

    Peak Index in a Mountain Array — C++

    int peakIndexInMountainArray(vector<int>& a) {
    int lo = 0, hi = (int)a.size() - 1;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < a[mid + 1])
            lo = mid + 1;   // still climbing: summit is to the right
        else
            hi = mid;       // already descending: summit is at mid or left
    }
    return lo;              // unique summit
}

    Dry run on a = [0, 2, 5, 8, 6, 1], with $n = 6$, so lo = 0, hi = 5. The summit is at index 3 (value 8).

    lo=0, hi=5

    mid = 0 + (5 - 0)/2 = 2. Compare a[2]=5 with a[3]=8. Since $5 < 8$ we are still climbing, so the summit is strictly to the right. Set lo = 3.

    lo=3, hi=5

    mid = 3 + (5 - 3)/2 = 4. Compare a[4]=6 with a[5]=1. Since $6 > 1$ we are descending, so the summit is at mid or to the left. Set hi = 4.

    lo=3, hi=4

    mid = 3 + (4 - 3)/2 = 3. Compare a[3]=8 with a[4]=6. Since $8 > 6$ we are descending. Set hi = 3.

    lo=3, hi=3 → done

    lo == hi == 3. The loop exits and we return 3, the summit (value 8). Four comparisons for six elements — and it would still be about $\log_2 n$ for a mountain of a million entries.

    Find in Mountain Array (LeetCode 1095)

    This problem stacks two ideas. Given a mountain array (accessed through an opaque MountainArray API with a costly get(i)) and a target, return the smallest index whose value equals the target, or -1. The plan:

    1. Find the summit $p$ using the slope predicate above.
    2. Search the ascending half $[0, p]$ with an ordinary ascending binary search. Because we want the smallest index and the left half comes first, if we find the target here we can return immediately.
    3. Otherwise search the descending half $[p+1, n-1]$ with a binary search whose comparator is flipped, since that half is sorted in decreasing order.

    Find in Mountain Array — C++

    // The provided interface:
// class MountainArray {
//   public: int get(int index);
//           int length();
// };

class Solution {
    // Ascending binary search on [lo, hi]; returns index of target or -1.
    int searchAsc(MountainArray& m, int lo, int hi, int target) {
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            int v = m.get(mid);
            if (v == target) return mid;
            if (v < target) lo = mid + 1;   // ascending: go right when too small
            else            hi = mid - 1;
        }
        return -1;
    }
    // Descending binary search on [lo, hi]; comparator flipped.
    int searchDesc(MountainArray& m, int lo, int hi, int target) {
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            int v = m.get(mid);
            if (v == target) return mid;
            if (v > target) lo = mid + 1;   // descending: go right when too big
            else            hi = mid - 1;
        }
        return -1;
    }
public:
    int findInMountainArray(int target, MountainArray& m) {
        int n = m.length();
        // 1) locate the summit via the slope predicate
        int lo = 0, hi = n - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (m.get(mid) < m.get(mid + 1)) lo = mid + 1;
            else                             hi = mid;
        }
        int peak = lo;
        // 2) try the ascending half first (smallest index wins)
        int idx = searchAsc(m, 0, peak, target);
        if (idx != -1) return idx;
        // 3) then the descending half
        return searchDesc(m, peak + 1, n - 1, target);
    }
};

    The two-comparator subtlety. A single binary search template only works on a monotone region. The ascending half rises, so "value too small → go right"; the descending half falls, so the relationship inverts and "value too big → go right". Reusing the ascending comparator on the descending half would drive the search the wrong way and miss the target. Keeping the two searches as separate helpers — one for each monotone direction — makes the flip explicit and hard to get wrong.

    Cost. Each get() is an expensive call (LeetCode caps you at 100 for the hidden tests). We make three binary searches: one to find the peak and two to search the halves. Each is $O(\log n)$ calls, so the total is $O(\log n)$ — comfortably under the budget. Searching the ascending half first also guarantees the smallest matching index without extra work, since every index in $[0, p]$ is less than any index in $[p+1, n-1]$.

    Searching a Bitonic / Rotated-Peak Array

    Zoom out and a single pattern governs this whole family. A bitonic array (one that rises then falls) — and, more generally, any array with a small, findable set of "pivot" points where monotonicity breaks — is searched in two moves: locate the pivot/peak with a slope-based binary search, then run an ordinary monotone binary search on each side with the correct comparator direction. The peak search does not need global order; the per-side searches do, but each side is individually monotone, so the classic template applies once you flip the comparator for descending runs.

    This is the same skeleton we used for rotated sorted arrays in Part 5: there the pivot was the rotation point (the minimum) and each side was ascending; here the pivot is a maximum and the two sides run in opposite directions. In both cases the move is identical — find the one place the order breaks, then binary search the ordered pieces. Once you see "locate the break, then search each monotone run," rotated arrays, mountains, and bitonic search all collapse into a single technique.

    Common Mistakes

    1. Using <= instead of < in the slope test and landing on a plateau. The peak-element and mountain problems assume no equal adjacent elements. If inputs allow plateaus, the standard strict-peak proof no longer applies: an equality gives no uphill direction, and a strict peak may not exist at all. Some non-strict peak definitions admit modified algorithms, but do not apply this template without re-proving the invariant for that definition.
    2. Out-of-bounds a[mid + 1]. Pairing the right-looking predicate with while (lo <= hi) or hi = mid - 1 lets mid reach the last index and read past the end. Use while (lo < hi) with hi = mid so that mid < hi always holds.
    3. Choosing the wrong half after finding the peak. In Find-in-Mountain, searching the descending half first (or merging both halves into one search) breaks the "smallest index" guarantee and mixes two monotone directions. Search the ascending half $[0, p]$ first, then the descending half $[p+1, n-1]$.
    4. Forgetting the descending-half comparator flip. Reusing the ascending comparator on the descending side sends the search the wrong direction and returns -1 for values that are present. The descending search must use "value too big → go right".

    Key Takeaways

    • You do not need a sorted array. A local direction predicate — comparing a[mid] with a[mid+1] — is enough to halve the search space whenever following the uphill slope is guaranteed to reach a peak.
    • Sentinels make peaks exist. Treating a[-1] = a[n] = -∞ guarantees at least one peak in any non-empty array; the up-then-down slope structure forces a turn-around.
    • Match the interval to the predicate. Because the predicate looks rightward, use lo=0, hi=n-1, while(lo<hi), and hi=mid; then mid < hi ≤ n-1 keeps a[mid+1] in bounds.
    • Mountains are the strict, unique-peak case and reuse the identical predicate (LeetCode 852).
    • Compose peak-finding with monotone search (LeetCode 1095): find the summit, search the ascending half, then the descending half with a flipped comparator — all in $O(\log n)$.
    • The general pattern: locate where monotonicity breaks, then binary search each monotone run — the same skeleton behind rotated and bitonic arrays.
