    Introduction

    Nine posts, one skill: proving that a middle comparison lets you discard half the candidates. Most chapters do that by exposing a monotone boundary; rotated arrays and peak search use a structural guarantee that the retained half still contains a solution. This capstone is the page to reread before an interview or contest: a recognition decision tree, synthesis table, failure modes, exponential search, practice ladder, and self-assessment quiz.

    The whole series in one sentence. Binary search repeatedly discards a half only after proving that half cannot contain the required answer. Usually that proof is a monotone false→true boundary; in structural variants such as rotated arrays and peaks, it is a direct guarantee that one half retains a solution.

    When NOT to Binary Search

    Binary search is seductive because it is fast, so it is over-applied. For boundary and answer-space searches, the tested predicate must be monotone (all false then all true, or the reverse). Structural variants have a different obligation: each comparison must prove that the half you keep contains at least one valid answer. If you can prove neither statement, halving is unjustified and the code can quietly return nonsense.

    Failure mode 1: non-monotone predicate

    A general “does value x occur?” query over an unsorted array has no monotone boundary, and comparing a[mid] with x gives no structural reason to prefer either side. Peak search in Part 6 is different: its slope booleans may also wiggle, but an uphill edge proves a peak exists to the right and a downhill edge proves one exists at mid or to the left. That half-retention proof is what arbitrary membership lacks.

    The tell. At mid, you must be able to state why every discarded candidate is impossible, or at least why the retained half contains a valid answer when any answer is acceptable. “It usually works” is not a proof — construct the adversarial input. 
    // WRONG: binary searching an UNSORTED array for a value.
// a = [5, 2, 9, 1, 7]; target = 9.
// a[mid]=a[2]=9 happens to hit, but on target=1 the comparison
// a[mid] < target tells you nothing about which side 1 is on.
// Correct tool: a linear scan (O(n)) or a hash set.

    Failure mode 2: bad bounds

    Even with a monotone predicate, the answer must actually lie inside [lo, hi]. Two classic bugs:

    • Too tight: initializing hi = max(a) when the true answer is sum(a) (as in Split Array Largest Sum when k = 1). The search converges to a wrong, infeasible value.
    • Wrong low: starting lo = 0 for a ship-capacity problem where the ship must at least carry the heaviest item — lo should be max(a), or you will accept an impossible capacity.
    • Off-by-one exclusive/inclusive: initializing hi = n (half-open) but then writing hi = mid - 1 (closed update). Pick one interval convention, as hammered home in Part 1.

    Failure mode 3: infinite loops

    The single most common runtime bug. It happens when an iteration fails to shrink the interval:

    SymptomCauseFix
    Hangs when 2 elements remainlo = mid with a round-down midpointUse round-up mid = lo + (hi - lo + 1)/2 whenever a branch does lo = mid
    Hangs, closed intervalwhile (lo < hi) but update is hi = mid - 1 / lo = mid + 1 with an early-return match missingMatch the loop test to the update rule (Part 1)
    Hangs on realswhile (lo < hi) on double — they are never exactly equalUse fixed iterations or while (hi - lo > eps) (Part 9)
    Hangs, duplicatesAmbiguous a[lo]==a[mid]==a[hi] not handledlo++; hi--; and accept $O(n)$ worst case (Part 5)
    Rule of thumb for the midpoint. If any branch keeps mid as a candidate on the left (lo = mid), round the midpoint up. If a branch keeps mid on the right (hi = mid), round down (the default). This one rule prevents nearly every binary-search infinite loop.

    Exponential Search for an Unknown Upper Bound

    Sometimes you have a monotone predicate but no idea how large hi should be — an unbounded or implicit input (a stream, an infinite grid, a mathematical value with no obvious cap). Exponential search (also called galloping or doubling) finds a valid bracket first, then binary searches inside it.

    Exponential search: find the first true

    #include <climits>
#include <stdexcept>

// pred is monotone: false...false, true...true, and eventually true.
long long firstTrue() {
    long long lo = 1, hi = 1;
    while (!pred(hi)) {
        if (hi == LLONG_MAX)
            throw std::out_of_range("no true value in long long range");
        lo = hi + 1;                    // all values through old hi are false
        hi = (hi > LLONG_MAX / 2) ? LLONG_MAX : hi * 2;
    }
    while (lo < hi) {                   // ordinary boundary search
        long long mid = lo + (hi - lo) / 2;
        if (pred(mid)) hi = mid;
        else           lo = mid + 1;
    }
    return lo;
}

    If the answer is $A$, the doubling phase and the final binary search each take $O(\log A)$ probes. The saturation guard prevents signed overflow and surfaces the case where no true value exists in the representable domain. The same trick searches an unbounded sorted stream (double the index until you pass the target, then binary search the last window).

    The 30-Second Playbook

    1. Name the search space. Is it an index range, a value range, a real interval, a partition cut, or an abstract answer? That choice picks the family.
    2. State the elimination proof. For boundary/answer searches, prove feasible is monotone. For rotated/peak searches, prove the chosen half retains a solution. No proof, no binary search.
    3. Set inclusive bounds that provably contain the answer. A provably-infeasible low and a provably-feasible high; use exponential search if the high is unknown.
    4. Pick the interval convention and the matching midpoint rounding. Round up if any branch does lo = mid; round down otherwise.
    5. Mind the types. Use long long for sums/products/counts that can overflow; use fixed iterations for reals.
    6. Sanity-check the ends. Confirm the loop terminates (interval strictly shrinks) and that the impossible case is handled.

    Series Summary

    • Binary search is one halving strategy applied to many search spaces: index, boundary, answer, value, partition, and real interval. Most are monotone-boundary searches; rotated arrays and peaks use structural half-retention proofs.
    • The half-open / first-true framing (Part 2) generalizes cleanly to answer-space optimization (Parts 3–4) and order statistics (Part 7).
    • Arrays that are not globally sorted — rotated (Part 5) and mountain (Part 6) — still admit $O(\log n)$ search via a local comparison.
    • Partition search (Part 8) and real-valued search (Part 9) show binary search need not compare against a stored array element at all.
    • Knowing when not to binary search — non-monotone predicates, bad bounds, infinite loops — is as valuable as knowing the templates.
    • When the bound is unknown, exponential search brackets the answer in $O(\log A)$ and hands off to an ordinary boundary search.
