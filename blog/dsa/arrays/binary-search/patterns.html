    Template Playbook & Capstone

    August 2026 · 24 min read

    Six posts, one template. Every problem in this series — from First Bad Version to Ugly Number III — was solved by the same five-line loop, changing only the bounds, the condition, and the return transform. This capstone is the page to reread before an interview or contest: a reusable worksheet, a synthesis table covering all eleven problems, the failure modes that cause 90% of binary-search bugs, a graduated practice ladder, an interactive recognition decision tree, and a self-assessment quiz.

    The whole series in one sentence. Reframe the task as minimize k such that condition(k) is true, prove condition is monotone, bracket the answer in an inclusive range with a true sentinel, and let the first-true loop find the false→true boundary.

    The template, one last time

    long long firstTrue(long long lo, long long hi,
                    const std::function<bool(long long)>& condition) {
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        if (condition(mid)) hi = mid;      // keep candidate
        else                lo = mid + 1;  // discard
    }
    return lo;   // first true, or the sentinel if none
}

    The Five-Question Worksheet

    Face a new problem? Answer these five questions in order. If you can answer all five, the code writes itself.

    1. Name the search space. What single value are you searching for — an array index, a capacity, a rate, a threshold, a value in an implicit multiset? Write it down explicitly. If you cannot name one monotone axis, binary search may not apply.
    2. State and prove monotonicity. Define condition(x) and argue that if it holds at x it holds at every x' > x (or the reverse). No proof, no binary search. This is the step people skip and then wonder why the answer is off by one.
    3. Derive the bounds. Find a lo below or at the smallest possible answer and a hi that is a guaranteed-true sentinel. Common patterns: [1, max], [max(element), sum], [0, spread], [1, n*min]. Handle any impossible case before the loop.
    4. Choose the return value. Is the answer left directly, left then validated to distinguish present/absent, or left - 1 because you searched for the first value that breaks the property? Never fabricate a success-shaped default.
    5. Audit overflow. Use lo + (hi-lo)/2. Are products (mid*mid, a*b), sums (running loads, counts), or LCMs at risk? Promote to long long, divide before multiplying, and cap values that can exceed the range.

    Failure Modes

    1. Non-monotone condition

    The single most common mistake: applying binary search to a predicate that goes true→false→true. Halving is only valid when one comparison provably eliminates a whole side. Always write down the monotonicity argument (worksheet step 2); if you cannot, the algorithm is wrong regardless of how clean the code looks.

    2. Bad bounds / dishonest sentinel

    If hi is not actually a true value, the search can converge on a position that satisfies nothing (Bouquets without the m*k > n guard is the textbook case). If lo is above the real answer (e.g. starting a capacity search above max(element) is fine, but starting above the optimum is not), you miss it entirely. Verify: condition(lo-1) should be false-or-out-of-range and condition(hi) should be true.

    3. Infinite loop from the wrong midpoint

    The first-true template rounds the midpoint down and pairs it with hi = mid. Rounding up (lo + (hi-lo+1)/2) with hi = mid lets mid == hi when hi - lo == 1, so the interval never shrinks. Round-up belongs only to the mirror-image last-true template (which pairs with lo = mid).

    Broken: mid = lo + (hi - lo + 1)/2; if (cond(mid)) hi = mid; else lo = mid + 1; — spins forever at hi - lo == 1.
    Fixed: mid = lo + (hi - lo)/2; if (cond(mid)) hi = mid; else lo = mid + 1; — always progresses because lo ≤ mid < hi.

    4. Overflow

    Four places bite: the midpoint ((lo+hi)/2), squared/multiplied values (mid*mid, a*b), running aggregates (loads, sums, counts that reach $10^{10}$–$10^{18}$), and LCMs. Fixes: gap-form midpoint, long long, divide-before-multiply, and capped LCMs. When in doubt, promote to 64-bit and test the condition with division instead of multiplication.

    5. Wrong return transform

    Returning left when the problem wants the last false (left - 1, as in sqrt), or forgetting the validation that turns lower_bound into an exact-match "or -1", or ignoring the sentinel that signals "impossible." Decide the return deliberately (worksheet step 4); do not let it default.

    Self-Assessment Quiz

    For each scenario, pick the family and the moving part that actually applies. The distractors are the mistakes people really make.

    The 30-Second Playbook

    1. Can I phrase it as "minimize k with condition(k) true"? If not, it may not be binary search.
    2. Is condition monotone? Prove it in one sentence.
    3. What is [lo, hi]? Is hi a genuine true sentinel? Any impossible case to reject first?
    4. Return left, left+validation, or left - 1?
    5. Where can it overflow? Promote to long long, divide before multiplying, cap large values.

    Series Summary

    • One template solves all eleven problems; only bounds, condition, and return change.
    • The hard work is always the same three things: naming the monotone search space, proving the condition, and deriving honest bounds with a true sentinel.
    • Returns are usually left; the exceptions are left - 1 (last-true, e.g. sqrt) and left+validation (exact match).
    • The four overflow traps — midpoint, products, aggregates, LCMs — all have the same cure: 64-bit types and divide-before-multiply.
    • When a first-true boundary sits on a step-function that only jumps at real values, the answer is provably a real value, not a phantom threshold.
