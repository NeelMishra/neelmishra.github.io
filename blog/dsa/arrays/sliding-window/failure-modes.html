    Failure Modes & Alternatives

    March 2026 · 22 min read

    Introduction

    Part 1 listed the conditions under which sliding window is invalid. This post makes that concrete: four problems that look like sliding window candidates, are not, and have their own correct linear (or near-linear) techniques. Being able to name the correct alternative — and explain why sliding window specifically fails — is as important to interviews and contests as knowing the window template itself.

    Not Sliding Window: Minimum Window Sort

    Given an array, find the length of the smallest subarray that, if sorted, would make the entire array sorted.

    Example: arr = [1, 2, 5, 3, 7, 10, 9, 12]. The answer is 5 (sort the subarray [5, 3, 7, 10, 9] from index 2 to 6).

    Why this is not a sliding window: there is no single incrementally-updated window state that grows and shrinks based on a validity check. The two boundaries are each computed by an independent, one-directional linear scan that never revisits or "shrinks" anything — a boundary scan, not a window. Calling this "sliding window" because it involves subarrays and runs in $O(n)$ is exactly the kind of misclassification Part 1 warned about.

    Approach

    Find the right boundary

    Scan from left to right, tracking the running maximum. The last position where arr[i] < max_so_far is the right boundary of the unsorted region.

    Find the left boundary

    Scan from right to left, tracking the running minimum. The last position where arr[i] > min_so_far is the left boundary.

    Compute the answer

    The minimum window to sort is [left_boundary..right_boundary], with length right_boundary - left_boundary + 1.

    Code

    int findUnsortedSubarray(vector<int>& arr) {
    int n = arr.size();
    int maxSoFar = INT_MIN, minSoFar = INT_MAX;
    int rightBound = -1, leftBound = -1;

    // Left to right: find right boundary
    for (int i = 0; i < n; i++) {
        maxSoFar = max(maxSoFar, arr[i]);
        if (arr[i] < maxSoFar) rightBound = i;
    }

    // Right to left: find left boundary
    for (int i = n - 1; i >= 0; i--) {
        minSoFar = min(minSoFar, arr[i]);
        if (arr[i] > minSoFar) leftBound = i;
    }

    if (rightBound == -1) return 0;  // already sorted
    return rightBound - leftBound + 1;
}
// Time: O(n), Space: O(1)

    Not Sliding Window: Subarray Sum Equals K (Mixed Signs)

    Given an array (any mix of positive, negative, zero) and integer k, count the number of subarrays whose sum equals exactly k.

    Why sliding window fails here: Part 9 proved that shrinking a sum window is only monotonic when every element is positive. With mixed signs, there is no valid shrink rule at all — a smaller window is not guaranteed to have a smaller sum.

    The correct tool is a running prefix sum plus a hash map counting how many times each prefix value has been seen. A subarray [i+1, j] sums to k exactly when prefix[j] - prefix[i] == k, i.e. prefix[i] == prefix[j] - k. Count, for each j, how many earlier prefixes equal prefix[j] - k.

    int subarraySum(vector<int>& arr, int k) {
    unordered_map<long long, int> seen;
    seen[0] = 1;  // empty prefix, for subarrays starting at index 0
    long long prefix = 0;
    int total = 0;

    for (int x : arr) {
        prefix += x;
        auto it = seen.find(prefix - k);
        if (it != seen.end()) total += it->second;
        seen[prefix]++;
    }
    return total;
}
// Time: O(n), Space: O(n)

    This is not a window at all — there is no left/right pointer pair and nothing "slides." It's a single forward pass maintaining a running total and a frequency map, which is why it works regardless of sign.

    Not Sliding Window: Shortest Subarray with Sum at Least K (Negatives Allowed)

    Given an array that may contain negative numbers, and an integer k, find the length of the shortest contiguous subarray with sum ≥ k. (This is the negatives-allowed version of Part 5's Minimum Size Subarray Sum, which required positivity.)

    Approach: Monotonic Deque Over Prefix Sums

    Build the prefix sum array P where P[0] = 0 and P[i] = P[i-1] + arr[i-1]. We want the shortest j - i with P[j] - P[i] ≥ k and j > i. Maintain a deque of indices into P with increasing P values:

    Try to close out valid pairs

    While the front of the deque gives a valid pair (P[j] - P[front] ≥ k), record the length and pop it — any later j can only make that same front give a longer (worse) length, so once satisfied, discard it.

    Maintain increasing prefix order

    While the back of the deque has P[back] ≥ P[j], pop it — a later index with an equal-or-smaller prefix sum dominates it as a future left endpoint (shorter distance, equal-or-better difference).

    Push and continue

    Push j onto the back and move to the next j.

    int shortestSubarray(vector<int>& arr, int k) {
    int n = arr.size();
    vector<long long> prefix(n + 1, 0);
    for (int i = 0; i < n; i++) prefix[i + 1] = prefix[i] + arr[i];

    deque<int> dq;  // indices into prefix[], increasing prefix values
    int best = INT_MAX;

    for (int j = 0; j <= n; j++) {
        while (!dq.empty() && prefix[j] - prefix[dq.front()] >= k) {
            best = min(best, j - dq.front());
            dq.pop_front();
        }
        while (!dq.empty() && prefix[j] <= prefix[dq.back()]) {
            dq.pop_back();
        }
        dq.push_back(j);
    }
    return (best == INT_MAX) ? -1 : best;
}
// Time: O(n), Space: O(n)
    This is a monotonic deque (Part 7's tool), but not a sliding window: the deque here indexes into the prefix sum array to answer a completely different query (find any valid pair, not maintain a single contiguous window's extremum), and there is no left/right two-pointer scan with an expand/shrink invariant. It's a legitimate $O(n)$ solution to a problem that superficially resembles Part 5, but the actual mechanism is unrelated to sliding window.

    Not Sliding Window: Binary Search on the Answer

    Some "find the minimum X such that a feasibility check passes" problems sound window-shaped ("minimum capacity," "minimum speed," "minimum days") but the feasibility check is not about a single contiguous window at all — it's a full linear scan of the whole array for each candidate value of X, and the values of X form a monotonic search space.

    Example: Koko Eating Bananas (LeetCode 875) — find the minimum eating speed such that all bananas are eaten within h hours. "Can Koko finish at speed s?" is answered by one $O(n)$ scan; feasibility is monotonic in s (faster speed never hurts), so binary search over s gives $O(n \log(\max\text{value}))$ total.

    bool canFinish(vector<int>& piles, int speed, int h) {
    long long hours = 0;
    for (int p : piles) hours += (p + speed - 1) / speed;  // ceil division
    return hours <= h;
}

int minEatingSpeed(vector<int>& piles, int h) {
    int lo = 1, hi = *max_element(piles.begin(), piles.end());
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (canFinish(piles, mid, h)) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}
// Time: O(n log(max(piles))), Space: O(1)
    Recognition signal: if the "window" you'd need to check validity for is the entire array every time (not a contiguous sub-range that incrementally updates), and the quantity you're optimizing has a monotonic feasibility property, you're looking at binary search on the answer, not sliding window.

    True Two Pointers vs. Sliding Window

    "Two pointers" is a broader family that includes sliding window as one member, but also includes techniques with a genuinely different structure:

    AspectSliding windowOpposite-end two pointers
    Pointer movementBoth move in the same direction, left never passes rightStart at opposite ends and move towards each other
    What's being maintainedAn aggregate over a contiguous rangeTypically no shared aggregate — each step re-evaluates a pairwise condition
    PreconditionMonotonic validity as one boundary movesUsually requires the array to be sorted (or sortable), so moving a pointer has a predictable effect on the compared quantity
    ExampleLongest substring without repeatsTwo Sum on a sorted array; Container With Most Water

    The two-pointers series on this blog (Arrays · Two Pointers) covers the opposite-ends and same-direction variants in full; the "same-direction" variant there overlaps substantially with the fixed/variable window templates in this series, while opposite-ends pointers are a distinct technique that happens to share the name.

    Summary: Matching Problems to Techniques

    SignalCorrect technique
    Contiguous subarray/substring, monotonic validity as one boundary movesSliding window (Parts 2–11)
    "Minimum subarray to sort/fix" via independent prefix/suffix extremaBoundary scan (two independent linear passes)
    "Count subarrays with sum/property = k," mixed signs allowedPrefix sum + hash map
    "Shortest subarray with sum ≥ k," negatives allowedMonotonic deque over prefix sums
    "Minimum/maximum X such that check(X) is feasible," feasibility monotonic in XBinary search on the answer
    Pairwise condition on a sorted array, pointers converge from both endsOpposite-end two pointers

    Key Takeaways

    • Not every "find the optimal subarray" problem is a sliding window — boundary scans compute independent extrema in one-directional passes with no shared incrementally-updated window state.
    • Mixed-sign sum problems need prefix sums (counting: hash map; shortest-with-threshold: monotonic deque over the prefix array), because sliding window's shrink argument specifically requires positivity.
    • Binary search on the answer applies when feasibility of a candidate value is monotonic and checking it requires a full scan, not an incrementally maintained window.
    • "Two pointers" is a broader family than sliding window; opposite-end two pointers is a genuinely different technique that usually requires sorted input.
    • Correctly classifying a problem among these alternatives is itself a skill worth practicing deliberately — Part 13's decision tree formalizes the classification process.
