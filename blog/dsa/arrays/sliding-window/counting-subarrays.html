    Counting Subarrays: atMost/Exactly & Contribution

    March 2026 · 20 min read

    Introduction

    Parts 4 and 5 measured a single number: the length of the best window. This post asks a different question — how many valid subarrays are there in total? Counting needs one more idea on top of expand/shrink: the contribution technique, which turns "the window [left, right] is valid" into "there are exactly right - left + 1 valid subarrays ending at right."

    The Contribution Technique

    Suppose you maintain a variable-size window [left, right] such that [left, right] is the largest valid suffix ending at right — i.e. every subarray [start, right] with left ≤ start ≤ right is valid, and [left - 1, right] (if it exists) is not. Then:

    Contribution identity: the number of valid subarrays ending exactly at right is right - left + 1 — one for each choice of starting index from left to right.

    Summing this quantity over every right from $0$ to $n-1$ counts every valid subarray exactly once, because every subarray has exactly one right endpoint. This requires the validity condition to be prefix-monotonic in the window: if [start, right] is valid, then [start + 1, right] must also be valid (shrinking a valid window from the left never invalidates it). "At most K distinct/odd/etc." conditions have exactly this property, which is why the technique pairs so naturally with the at-most template from Part 4.

    The atMost(k) − atMost(k−1) Identity

    Counting subarrays that satisfy "exactly k" of some property directly is awkward: expanding can turn a valid window invalid and there's no simple shrink rule. Counting "at most k" is easy (contribution technique above), and there's a clean bridge between the two:

    Identity: exactly(k) = atMost(k) - atMost(k - 1). The count of subarrays with the property valued exactly $k$ equals the count with the property at most $k$ minus the count with the property at most $k-1$.

    This works for any property that is monotonic in the sense above — distinct-element count, count of odd numbers, count of elements exceeding a threshold, and more. Once you have a correct atMost(k) function, exactly(k) is one subtraction away.

    Worked Example: Exactly K Distinct Elements

    Given an array and an integer k, count the number of subarrays with exactly k distinct elements.

    Example: arr = [1, 2, 1, 2, 3], k = 2. The answer is 7.

    long long atMostKDistinct(vector<int>& arr, int k) {
    if (k < 0) return 0;

    int n = arr.size();
    unordered_map<int, int> freq;
    int left = 0;
    long long count = 0;

    for (int right = 0; right < n; right++) {
        freq[arr[right]]++;

        while ((int)freq.size() > k) {
            freq[arr[left]]--;
            if (freq[arr[left]] == 0) freq.erase(arr[left]);
            left++;
        }
        count += right - left + 1;  // contribution: all subarrays ending at right
    }
    return count;
}

long long exactlyKDistinct(vector<int>& arr, int k) {
    return atMostKDistinct(arr, k) - atMostKDistinct(arr, k - 1);
}
// Time: O(n), Space: O(k)

    Why right - left + 1?

    Consider the window [left..right]. Every subarray that ends at right and starts at any index from left to right has at most k distinct elements — that is right - left + 1 subarrays:

    • [left..right]
    • [left+1..right]
    • ...
    • [right..right]

    Any subarray starting before left would have more than k distinct elements (that's exactly why left stopped there), so this list is complete and none of these subarrays overlaps with a different right's list — each subarray has exactly one right endpoint, so there is no double counting.

    Worked Example: Count Number of Nice Subarrays

    Given an array of integers and an integer k, a subarray is called nice if it contains exactly k odd numbers. Count the number of nice subarrays.

    Example: arr = [1, 1, 2, 1, 1], k = 3. The answer is 2.

    Reusing the identity: atMost(k) here counts subarrays with at most k odd numbers, using "count of odd numbers in the window" as the monitored property instead of "count of distinct elements." The window-management code barely changes.

    long long atMostKOdd(vector<int>& arr, int k) {
    if (k < 0) return 0;

    int n = arr.size();
    int left = 0;
    int oddCount = 0;
    long long count = 0;

    for (int right = 0; right < n; right++) {
        if (arr[right] % 2 != 0) oddCount++;

        while (oddCount > k) {
            if (arr[left] % 2 != 0) oddCount--;
            left++;
        }
        count += right - left + 1;
    }
    return count;
}

int numberOfSubarrays(vector<int>& arr, int k) {
    return atMostKOdd(arr, k) - atMostKOdd(arr, k - 1);
}
// Time: O(n), Space: O(1)
    Pattern recognition: both worked examples share one skeleton — maintain a monotonic property, shrink while it exceeds k, add right - left + 1 to a running total, then subtract two calls to get the exact count. Only the property being tracked (distinct count vs. odd count) changes.

    Edge Cases

    • k = 0: atMost(-1) must return 0 (guard for negative k), so exactly(0) = atMost(0).
    • k larger than any subarray can achieve: atMost(k) naturally saturates at $\binom{n+1}{2}$ (every subarray), and exactly(k) correctly returns 0 once k exceeds what's achievable.
    • Overflow: the total count of subarrays is $O(n^2)$, which overflows a 32-bit int for $n$ around $65{,}000$ or more — always accumulate in long long.
    • Empty array: both atMost functions correctly return 0 with an empty loop.

    Common Mistakes

    • Trying to count "exactly k" directly with one shrink loop: there is no clean single-pass shrink rule for "exactly," because expanding can move you from below k to above k without ever equaling it — that's precisely why the atMost/exactly bridge exists.
    • Forgetting the k - 1 case can go negative: always guard atMost against negative k rather than assuming the caller never passes k = 0.
    • Using int for the running count: the total number of subarrays is quadratic in n; use long long.
    • Misreading right - left + 1 as "window size" instead of "count of valid subarrays ending here": they're numerically the same quantity, but conflating the two ideas makes it easy to add the wrong term when the monitored property differs from window size (e.g., counting distinct elements, not total elements).

    Key Takeaways

    • The contribution technique counts right - left + 1 valid subarrays ending at each right, and summing over all right counts every valid subarray exactly once.
    • It requires the validity condition to be prefix-monotonic: shrinking a valid window from the left must never make it invalid.
    • exactly(k) = atMost(k) - atMost(k - 1) converts a hard-to-shrink "exactly" condition into two easy "at most" passes.
    • The same skeleton (track a monotonic property, shrink while it exceeds k, accumulate contribution) works for distinct-count, odd-count, sum-based, and many other properties — only the tracked property changes.
    • Always accumulate counts in a wide integer type; the total is quadratic in n.
