    Sum & Product Windows: Positivity and Monotonicity

    March 2026 · 18 min read

    Introduction

    Part 5 flagged, without proving, that minimum-size-subarray-sum requires positive values. This post makes that precise, extends the same idea to products, and then deliberately breaks it — walking through a concrete counterexample so the failure is not just asserted but seen.

    Why Positivity Is the Load-Bearing Assumption

    Recall the correctness argument from Part 1: shrinking the window must move its validity monotonically — once you start shrinking, continuing to shrink should never make the window "more valid then less valid then more valid again" in a way that requires backtracking. For a sum-threshold window (windowSum ≥ target), this monotonicity holds only because:

    Positivity claim: if every arr[i] > 0, then for any fixed right, windowSum([left, right]) is strictly decreasing as left increases. Removing an element from a window of all-positive numbers can only shrink the sum, never grow it.

    This single fact is what guarantees "once the window is valid (sum ≥ target), shrinking will eventually make it invalid, and the shrink loop's stopping point is unambiguous." Without it, there is no guarantee that a smaller window (subset of indices) has a smaller sum — the entire premise of "shrink until invalid" collapses.

    Problem: Subarray Product Less Than K

    Given an array of positive integers and an integer k, count the number of contiguous subarrays where the product of all elements is strictly less than k.

    Example: arr = [10, 5, 2, 6], k = 100. The answer is 8.

    Approach

    Positivity gives the same guarantee for products that it gave for sums: for positive values, growing the window can only grow (or keep equal, if a value were 1) the product, and shrinking can only shrink it. That means the exact same "shrink while invalid, contribute right - left + 1" recipe from Part 6 applies directly, with product replacing distinct-count as the monitored quantity.

    int numSubarrayProductLessThanK(vector<int>& arr, int k) {
    if (k <= 1) return 0;  // no positive product is ever < 1

    int n = arr.size();
    long long product = 1;
    int left = 0;
    int count = 0;

    for (int right = 0; right < n; right++) {
        product *= arr[right];

        while (product >= k) {
            product /= arr[left];
            left++;
        }
        count += right - left + 1;  // contribution, same identity as Part 6
    }
    return count;
}
// Time: O(n), Space: O(1)

    Why k ≤ 1 is a special case: every element is a positive integer, so every subarray's product is at least 1. If k ≤ 1, no subarray can have product strictly less than k, and the main loop's invariant (product starts at 1 and only grows) would otherwise force endless shrinking. Handle it up front rather than relying on the loop to self-correct.

    What Breaks With Zero or Negative Values

    Both examples above depend on positivity twice: once for monotonicity (shrink is well-defined) and once for products specifically, division must be safe (no divide-by-zero). Watch both fail on a tiny example.

    Counterexample 1: A Single Negative Number Breaks Monotonic Shrinking

    Take arr = [4, -2, 5] and suppose we want the shortest subarray with sum ≥ 5, using the Part 5 template verbatim.

    WindowSum"Valid" (sum ≥ 5)?
    [4]4No
    [4, -2]2No — smaller than the previous window's sum, even though it's larger
    [4, -2, 5]7Yes
    [-2, 5]3No
    [5]5Yes — the true answer, length 1

    The template's shrink loop, upon reaching the valid window [4, -2, 5] (sum 7), would try shrinking: remove 4 to get [-2, 5] with sum 3 — invalid — and stop shrinking there, reporting length 3 as its best answer while completely missing the true shortest window [5] (length 1) because it never independently considers starting fresh from index 2. The algorithm isn't merely suboptimal here; it returns the wrong answer, because "adding -2 then 5" doesn't monotonically track "sum keeps growing as we include more of the window," so shrinking one element at a time can skip past the actual optimum.

    The takeaway: this is not an edge case to patch — it's a structural failure. With mixed-sign values, no amount of tweaking the shrink condition recovers the sliding-window guarantee, because the core monotonicity claim is simply false. Part 12 covers the actual correct tool for this exact problem (LeetCode 862, shortest subarray with sum at least K with negatives allowed): a monotonic deque over prefix sums, not a sliding window.

    Counterexample 2: A Zero Breaks Division in the Product Window

    Take arr = [10, 0, 5], k = 3, using the product-less-than-K template verbatim.

    • right = 0: product = 10. 10 ≥ 3, shrink: product /= arr[0] = 10 ⇒ product = 1, left = 1. Contribution 1.
    • right = 1: product *= 0 ⇒ product = 0. 0 ≥ 3? No — loop doesn't shrink. Contribution right - left + 1 = 1.
    • right = 2: product *= 5 ⇒ product = 0. Still < 3. Contribution 3 — but this counts [0,5], [0] is already counted... wait, contribution here is right - left + 1 = 2 - 1 + 1 = 2, counting [arr[1], arr[2]] and [arr[2]], both with product 0, both correctly < 3. So far no crash.

    The crash scenario is different: once a 0 is included and then the window needs to shrink past it later (e.g. a subsequent large product forces left to advance past the zero), the code executes product /= arr[left] where arr[left] == 0 — integer division by zero, undefined behavior in C++. Even ignoring the crash, once a zero has been multiplied in, product is stuck at exactly 0 and can never be "un-multiplied" back to a meaningful positive value by continuing to divide by later, non-zero elements that were never actually part of collapsing the zero out.

    Fix, if zeros must be supported: treat a zero as a hard window reset. When arr[right] == 0, every subarray ending at right that includes an earlier nonzero run has product 0 (which is < any k > 0), so you can count those directly, then reset product = 1 and left = right + 1 rather than ever dividing by the zero. This requires special-casing zero explicitly — the naive division-based template must not be used unmodified once zeros are possible.

    Edge Cases

    • k ≤ 1 for product-less-than-k: return 0 immediately (see callout above).
    • Single element greater than or equal to k: contributes 0 to the count on its own; the shrink loop must correctly advance left past right itself if needed (guard against left > right making the window empty with product reset to 1).
    • All elements equal to 1: product stays 1 forever if k > 1; every subarray is valid, and the count equals $\binom{n+1}{2}$ — make sure the accumulator type doesn't overflow.
    • Very large k or long positive runs: use long long for the running product; it can exceed 32-bit range quickly even for modest array values.

    Common Mistakes

    • Applying the sum or product window template to arrays that might contain negatives or zeros without checking the constraints first. Always confirm positivity is guaranteed by the problem statement before reaching for this pattern.
    • Using int instead of long long for running products — products grow multiplicatively and overflow far sooner than sums do.
    • Forgetting the k ≤ 1 guard and getting an infinite or incorrect shrink loop.
    • Assuming "sliding window doesn't work with negatives" means "no O(n) solution exists" — it means this specific technique doesn't apply; Part 12 shows the prefix-sum-plus-deque alternative that still achieves $O(n)$.

    Key Takeaways

    • Sum and product sliding windows both depend on positivity for the same reason: only positive values guarantee that shrinking monotonically shrinks the aggregate.
    • Product windows additionally require care around k ≤ 1 (immediate 0) and zeros (which break the division-based removal and require an explicit reset).
    • A single negative number is enough to make the shrink-based template return a wrong answer, not merely a suboptimal one — this is a correctness bug, not a performance concern.
    • "Sliding window doesn't apply" is not the same as "no linear algorithm exists" — Part 12 shows the deque-over-prefix-sums technique that correctly handles negative values for the shortest-subarray-with-sum-at-least-K problem.
