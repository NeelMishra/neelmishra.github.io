    Sliding Window Foundations

    March 2026 · 20 min read

    This is the opening post of a 13-part sliding-window mastery series. It builds the model precisely enough that every later post can lean on it instead of re-deriving it: what a window is, the invariant that makes shrinking safe, a real proof of the $O(n)$ bound (not just an assertion), the signals that tell you a problem wants a window, and — just as important — the signals that tell you it does not.

    The Window Model

    A sliding window is a contiguous, inclusive range of indices $[\text{left}, \text{right}]$ over an array or string that you scan left to right, maintaining some aggregate state (a sum, a frequency table, a count of distinct elements, a max) for exactly the elements currently inside the range. Its width is therefore $\text{right} - \text{left} + 1$. Instead of recomputing the aggregate from scratch every time the range changes, you update it incrementally: add the element that just entered, remove the element that just left.

    Core idea: Reuse computation from the previous window position. Only the two boundary elements changed — the new right edge and the old left edge — so only those two updates are needed, regardless of how large the window is.

    Why It Beats the Brute Force

    Consider the problem: find the maximum sum of any contiguous subarray of size $k$ in an array of $n$ elements.

    Brute Force: $O(n \times k)$

    For every starting index, sum up $k$ elements. If $n = 10{,}000$ and $k = 1{,}000$, that is 10 million operations.

    int maxSum = INT_MIN;
for (int i = 0; i <= n - k; i++) {
    int sum = 0;
    for (int j = i; j < i + k; j++) {
        sum += arr[j];
    }
    maxSum = max(maxSum, sum);
}

    Sliding Window: $O(n)$

    Compute the sum of the first window. Then, for each subsequent position, subtract the element leaving the window and add the element entering it. Only two operations per step, regardless of $k$.

    int sum = 0;
for (int i = 0; i < k; i++) sum += arr[i];
int maxSum = sum;

for (int i = k; i < n; i++) {
    sum += arr[i] - arr[i - k];   // add new, remove old
    maxSum = max(maxSum, sum);
}
    Key insight: Consecutive windows overlap in $k - 1$ elements. The brute force throws that overlap away and recomputes it; the sliding window reuses it.

    The Invariant That Makes It Correct

    Every sliding-window algorithm, fixed or variable, must preserve one invariant whenever either boundary moves:

    State invariant: The maintained state always describes exactly the elements in the current inclusive window arr[left..right] — no more, no fewer. Adding arr[right] and removing arr[left] must update that state in lockstep with the pointer movement.

    Validity is not required at the same phase in every template. What must be true is that the window has the right validity state at the exact moment the answer is updated:

    • Fixed-size: evaluate only after the width reaches $\text{right} - \text{left} + 1 = k$. There is no expand/shrink choice — both boundaries then advance together.
    • Longest-valid and at-most counting: after expanding, shrink while invalid. The window is valid when its length or contribution is recorded.
    • Shortest-valid and coverage: after expanding, shrink while valid. Record each valid candidate before removing its leftmost element. The loop deliberately stops on the first invalid window, which is the correct starting state for the next expansion.

    The correctness argument in both cases reduces to the same two claims:

    1. Safety: shrinking the window (moving left forward) never discards a state that the algorithm still needs to consider once it has already been accounted for in the answer.
    2. Completeness: every window that could possibly be optimal is visited (even if only implicitly, via the answer update) before the algorithm moves past it.

    Claim (1) is exactly where the monotonic property comes in, covered in When Sliding Window Does Not Apply below: shrinking must move the window's validity in a single direction as elements are removed, or you cannot know when to stop shrinking without looking further ahead than $O(1)$.

    Fixed-Size vs Variable-Size Windows

    Aspect Fixed-Size Window Variable-Size Window
    Window size Constant $k$, given in the problem Changes dynamically based on a condition
    Left pointer movement Advances exactly one step per iteration Advances when the window violates (or satisfies) a constraint
    Right pointer movement Advances exactly one step per iteration Advances to expand the window
    Typical problems Max sum of size k, averages of subarrays, fixed-length anagram checks Longest/shortest substring or subarray under a constraint
    Complexity $O(n)$, exactly one pass $O(n)$ amortized (proved below)

    Parts 2–3 of this series cover fixed-size windows in depth; parts 4–6 cover variable-size windows (longest, shortest, and counting variants).

    Proving $O(n)$: The Amortized Argument

    The fixed-size case is trivially $O(n)$: the outer loop runs $n - k$ times and each iteration does $O(1)$ work. The variable-size case is the one people wave their hands at — here is the actual argument.

    A variable-size window scan has an outer loop over right (running $n$ times) and, nested inside it, an inner while loop that advances left. The inner loop's trip count is not bounded per outer iteration — in principle left could jump all the way from $0$ to right in a single outer step. So a naive "nested loop ⇒ $O(n^2)$" reading is wrong; you have to bound the total work, not the per-iteration worst case.

    Aggregate / potential argument: Consider left as a pointer that only ever moves forward (it is never reset backward). Across the entire algorithm, right takes each index $0, \dots, n-1$ exactly once, and left takes each index $0, \dots, n-1$ at most once. Every unit of work inside either loop body is charged to exactly one pointer advance. Therefore the total work is bounded by $(\text{advances of right}) + (\text{advances of left}) \le n + n = 2n = O(n)$.

    Formally: let $L_i$ and $R_i$ denote the value of left/right after the $i$-th outer iteration. $R_i$ increases by exactly 1 every outer iteration, so $\sum \Delta R_i = n$. $L_i$ is non-decreasing over the whole run (the shrink loop never moves left backward), and $L_i \le n$ always, so the telescoping sum $\sum \Delta L_i = L_{\text{final}} - L_{\text{initial}} \le n$. If each unit of $\Delta L$ or $\Delta R$ does $O(1)$ work (a hash-map update, a sum add/subtract), the total work across the whole algorithm is $O(n) + O(n) = O(n)$ — even though any single outer iteration's inner loop can, in isolation, look like it costs up to $O(n)$.

    This is the standard amortized analysis technique (aggregate method): bound the total cost across all operations rather than the worst case of a single operation, because the "expensive" operations are rare enough, or rather here impossible to repeat past their budget, that the average holds exactly.

    What must be true for this proof to hold: the shrink condition must be monotonic in left — once the window becomes valid (or invalid) purely as a function of which elements are inside it, advancing left must never need to be undone. If your shrink logic could ever require moving left backward, the pointer is no longer monotonic and this proof (and the technique) breaks down.

    Recognition Signals

    Look for these signals in a problem statement:

    • Contiguous subarray or substring: the problem is about a contiguous segment, not an arbitrary subset or subsequence.
    • "Longest / shortest / maximum-length / minimum-length" subarray or substring satisfying some condition.
    • "Sum (or aggregate) of every subarray of size k": a direct fixed-size window application.
    • Frequency or distinct-count constraints: "at most k distinct characters," "no repeating characters," "contains all characters of t."
    • A monotonic validity condition: adding an element to the window can only push the window towards being more valid or more invalid, never both, so shrinking has a well-defined stopping point.
    • Brute force is $O(nk)$ or $O(n^2)$ from a double loop over subarray start/end — a strong hint that the redundant recomputation can be collapsed into $O(n)$.
    Rule of thumb: if the problem asks for an optimal contiguous subarray/substring and the naive solution enumerates all $O(n^2)$ start/end pairs, ask whether the validity of a window can be maintained incrementally as one pointer advances. If yes, sliding window applies.

    When Sliding Window Does Not Apply

    This section matters as much as the recognition signals above — misapplying sliding window to a problem that lacks the monotonic property produces code that looks plausible, compiles, passes a couple of hand-picked test cases, and is wrong. Watch for:

    • Non-contiguous selections: if the elements you're combining do not need to be adjacent in the original array (subsequence problems, "pick any k elements"), there is no window to slide — you need DP, greedy, or a different structure entirely.
    • No monotonic validity: if adding an element to the window can make it more valid in one case and less valid in another (the canonical failure: subarray sums with mixed positive and negative numbers, where shrinking from the left might increase or decrease the sum unpredictably), the "shrink while invalid" loop has no correct stopping rule. See Part 9 for a full worked counterexample.
    • The aggregate is not incrementally updatable both ways: sums, counts, and frequency tables support $O(1)$ add and remove. Maximum/minimum do not support $O(1)$ remove with a plain scalar — removing the current maximum requires knowing the next-largest element, which is why Part 7 introduces the monotonic deque instead of trying to force a plain window to track it.
    • Global optimization requiring non-local information: problems where the best window boundary depends on information outside any local range (many DP formulations, some interval-scheduling variants) are not sliding-window problems just because they mention "subarray."
    • The problem is secretly a boundary scan or two-pass computation, not a window: some problems that "smell" like sliding window (e.g. "find the minimum subarray to sort so the whole array becomes sorted") are solved by tracking prefix/suffix extrema in two independent linear passes, with no shared, incrementally-updated window state at all. Calling that "sliding window" is a common but incorrect classification — Part 12 draws this line precisely.

    Complexity Summary

    Variant Time Space Why
    Fixed-size $O(n)$ $O(1)$ Single pass, constant work per step
    Variable-size $O(n)$ amortized $O(k)$ or $O(|\Sigma|)$ Each index visited by left and by right at most once each; space depends on the auxiliary structure
    Brute force $O(nk)$ or $O(n^2)$ $O(1)$ Recomputes the full subarray aggregate at every start index

    Key Takeaways

    • A sliding window maintains an incrementally-updated aggregate over a contiguous range, avoiding recomputation of shared elements between consecutive windows.
    • The single invariant — the window always represents exactly its current range, and (for variable windows) is valid — unifies the fixed-size and variable-size variants.
    • The $O(n)$ bound for variable windows is an amortized argument: left and right each advance at most $n$ times in total, so total work is $O(n)$ even though a single iteration's inner loop is not individually bounded.
    • The technique requires a monotonic validity condition. Without it (e.g. sums with negative numbers, non-contiguous selections, extrema requiring $O(1)$ removal), sliding window either doesn't apply or needs a different supporting data structure.
    • Some "smells like sliding window" problems are actually boundary scans, prefix-sum problems, or two-pointer problems on sorted data — not sliding window. Part 12 draws this distinction explicitly.
