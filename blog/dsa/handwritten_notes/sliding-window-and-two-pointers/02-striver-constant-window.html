    Striver Constant Window: Maximum Points You Can Obtain from K Cards (LC 1423)

    October 2026 · 8 min read · Handwritten Notes

    Expanded from handwritten competitive coding study note: 02_Striver_Constant_window.pdf

    Fixed-size sliding windows are usually introduced on contiguous subarrays of length $k$. One of the cleanest twists in competitive programming—covered in Striver's sliding-window series and captured in 02_Striver_Constant_window.pdf—is recognizing that choosing $k$ elements from either end of an array is secretly a constant-size window rotating across the wrap-around boundary between index $0$ and index $n - 1$.

    1. Problem Statement & Examples

    Given $n$ cards arranged in a row with scores cardScore[0 .. n - 1], you must choose exactly $k$ cards. In each step, you may take one card from either the beginning or the end of the remaining row. Return the maximum total score you can obtain.

    • Example 1: cardScore = [1, 2, 3, 4, 5, 6], $k = 3$ $\implies$ Output: 15.
      Explanation: Choosing the rightmost three cards $6, 5, 4$ yields $4 + 5 + 6 = 15$.
    • Example 2: cardScore = [5, 4, 1, 8, 7, 1, 3], $k = 3$ $\implies$ Output: 12.
      Explanation: Pick $5$ from the beginning, then $4$ from the beginning, then $3$ from the end for $5 + 4 + 3 = 12$.

    2. Why Greedy Fails & Why There Are NOT $2^k$ Outcomes

    Trap 1: Myopic Greedy ("Pick the Larger End") Fails

    Consider cardScore = [1, 100, 1, 1, 10] with $k = 2$. At step 1, the right end ($10$) beats the left end ($1$), so a greedy rule picks $10$ and then picks $\max(1, 1) = 1$ for a total of $11$—completely missing the $100$ sitting behind the left $1$, where taking two cards from the left gives $1 + 100 = 101$!

    If greedy fails, what about branching on "take left vs. take right" at every step? Since each of the $k$ steps offers $2$ choices, a naive recursion tree explores $O(2^k)$ paths. The key insight annotated directly on the handwritten page collapses that exponential tree into a linear scan:

    Core Combinatorial Observation: Only $k + 1$ Valid Subsets Exist!

    Addition is commutative—the interleaved order in which you pick left vs. right cards does not change which cards end up in your hand! Whether you pick Left, Right, Left or Left, Left, Right, you end up holding the exact same subset: the first $2$ elements and the last $1$ element.

    In general, after $k$ picks, if $j$ of those picks came from the left ($0 \le j \le k$), then the remaining $k - j$ picks must be the rightmost $k - j$ elements:

    • 1st combination ($j = k$): All $k$ elements from the left, $0$ from the right.
    • Remaining $k$ combinations ($j = k - 1, k - 2, \dots, 0$): First $j$ elements from the left $+$ last $k - j$ elements from the right.

    Not $2^k$ combinations—there are at most $k + 1$ distinct valid subsets!

    3. Brute $\to$ Better $\to$ Optimal Progression

    Approach Idea Time Space
    1. Brute-Force Recursion Try left pick and right pick at each of the $k$ steps: $f(l, r, \text{rem})$ $O(2^k)$ $O(k)$ stack
    2. Prefix & Suffix Arrays Precompute $\text{pref}[0..k]$ and $\text{suff}[0..k]$, then check $\max_{0 \le j \le k}(\text{pref}[j] + \text{suff}[k - j])$ $O(k)$ $O(k)$
    3. Striver Constant-Window Rotation Compute initial left $k$-sum lsum; in $k$ steps trade one right-most prefix card for one right-end card in rsum $O(k)$ $O(1)$
    4. Dual Minimum Middle Window Unpicked cards form a contiguous subarray of length $n - k$; compute $\text{totalSum} - \min(\text{window of size } n - k)$ $O(n)$ $O(1)$
    Why Striver's $O(k)$ Rotation Beats the $O(n)$ Middle-Subarray Trick When $k \ll n$ Both Approach 3 and Approach 4 use $O(1)$ extra space, and both are great to mention in interviews. However, if $n = 10^6$ and $k = 5$, the complementary middle-subarray approach still scans all $10^6$ elements to compute $\text{totalSum}$, whereas Striver's boundary rotation touches only the first $k$ and last $k$ elements—running in strict $O(k)$ time without ever reading indices $[k .. n - k - 1]$!

    4. Visual Dry Run on cardScore = [5, 4, 1, 8, 7, 1, 3], $k = 3$

    Let's trace all $k + 1 = 4$ valid prefix–suffix windows on Example 2 from the handwritten note ($n = 7, k = 3$):

    Iteration Removed from Left (i) Added from Right (rIndex) lsum rsum lsum + rsum maxSum
    Initial ($3\text{L}, 0\text{R}$) — (sum [0..2]) — $5 + 4 + 1 = 10$ $0$ $10$ $10$
    i = 2, rIndex = 6 $-\text{card}[2] = -1$ $+\text{card}[6] = +3$ $9$ $3$ $12$ $12$
    i = 1, rIndex = 5 $-\text{card}[1] = -4$ $+\text{card}[5] = +1$ $5$ $4$ $9$ $12$
    i = 0, rIndex = 4 $-\text{card}[0] = -5$ $+\text{card}[4] = +7$ $0$ $11$ $11$ $12$

    Similarly, on Example 1 ([1, 2, 3, 4, 5, 6], $k = 3$), the four combinations produce $1+2+3 = 6 \to 1+2+6 = 9 \to 1+5+6 = 12 \to 4+5+6 = \mathbf{15}$.

    5. Clean C++ & Python Implementations

    #include <algorithm>
#include <vector>

class Solution {
public:
    int maxScore(const std::vector<int>& cardPoints, int k) {
        int n = static_cast<int>(cardPoints.size());
        long long lsum = 0, rsum = 0;

        // 1st combination: take all k elements from the left prefix [0 .. k-1]
        for (int i = 0; i < k; ++i) {
            lsum += cardPoints[i];
        }
        long long maxSum = lsum;

        // Remaining k combinations: shrink left prefix j = k-1..0, grow right suffix
        int rIndex = n - 1;
        for (int i = k - 1; i >= 0; --i) {
            lsum -= cardPoints[i];
            rsum += cardPoints[rIndex--];
            maxSum = std::max(maxSum, lsum + rsum);
        }

        return static_cast<int>(maxSum);
    }
};
    def max_score(card_points: list[int], k: int) -> int:
    lsum = sum(card_points[:k])
    rsum = 0
    max_sum = lsum

    r_idx = len(card_points) - 1
    for i in range(k - 1, -1, -1):
        lsum -= card_points[i]
        rsum += card_points[r_idx]
        r_idx -= 1
        if lsum + rsum > max_sum:
            max_sum = lsum + rsum

    return max_sum

    6. Complexity Proof & Key Edge Cases

    • Time Complexity — $\mathcal{O}(k)$: The initial prefix loop runs exactly $k$ times, and the sliding transition loop runs exactly $k$ times ($2k$ additions/subtractions in total). Even if $n = 10^5$ and $k = 10$, only $20$ array accesses are performed.
    • Space Complexity — $\mathcal{O}(1)$: Only scalar accumulators (lsum, rsum, maxSum, rIndex) are stored.

    Edge Cases Checklist

    • $k == n$ (take every card): The initial loop sums all $n$ elements into lsum; the second loop shifts every element from lsum to rsum keeping lsum + rsum constant and valid ($r\text{Index}$ walks from $n - 1$ down to $0$ without going out of bounds). You can also short-circuit if (k == n) return accumulate(...);.
    • $k == 1$: Initial lsum = cardPoints[0], then one iteration tests rsum = cardPoints[n - 1], returning $\max(\text{cardPoints}[0], \text{cardPoints}[n - 1])$.
    • 64-bit Accumulators: In LeetCode 1423, $k \le 10^5$ and $\text{cardPoints}[i] \le 10^4$, so the sum fits in $10^9$ (int), but in Codeforces variants where $\text{cardPoints}[i] \le 10^9$, using long long prevents signed 32-bit overflow.
    • Negative Card Values: Unlike variable-size sliding windows—which break when negative numbers destroy monotonicity—this constant-window rotation enumerates all $k + 1$ legal states explicitly, so it remains 100% exact even if cardPoints contains negative numbers! (Just initialize maxSum = lsum, never 0.)
