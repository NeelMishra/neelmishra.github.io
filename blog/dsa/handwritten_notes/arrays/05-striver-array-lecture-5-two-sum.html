    Striver Array Lecture 5: Two Sum — Complement Hash Map vs. Sorted Two Pointers (LC 1)

    October 2026 · 8 min read · Handwritten Notes

    Expanded from handwritten competitive coding study note: 05_Striver_lecture_5.pdf (1 page) · Jump to original scan

    Two Sum is LeetCode's #1 problem for good reason: depending on whether the interviewer asks for a Yes / No existence check or the original 0-based indices, two completely different data-structure trade-offs emerge — trading $\mathcal{O}(N)$ hash-table memory against $\mathcal{O}(N \log N)$ sorting + converging two pointers.

    1. Problem Statement & The Two Variants

    Given an array of $N$ integers and an integer target, we may not reuse the same index twice ($i \ne j$). On Page 1's handwritten example arr = [2, 6, 5, 8, 11]:

    • For target = 14: Variant 1 (Existence) outputs Yes because $6 + 8 = 14$; Variant 2 (LeetCode 1 — Indices) outputs [1, 3].
    • For target = 15: no two distinct slots sum to $15$ $\implies$ Variant 1 outputs No; Variant 2 outputs [-1, -1].

    2. Brute Force $\to$ One-Pass Complement Hash Map

    1. Brute Force ($\mathcal{O}(N^2)$ time, $\mathcal{O}(1)$ space): Run outer loop $i = 0 \dots N - 1$ and inner loop $j = i + 1 \dots N - 1$ (starting at $i + 1$ avoids both duplicate checks $(j, i)$ and illegal self-pairs $(i, i)$). Whenever arr[i] + arr[j] == target, return {i, j}.
    2. Approach 1 — One-Pass Complement Hash Map ($\mathcal{O}(N)$ expected / $\mathcal{O}(N \log N)$ tree map, $\mathcal{O}(N)$ space): Instead of scanning forward for a partner of arr[i], ask whether the exact algebraic complement $$\text{need} = \text{target} - \text{arr}[i]$$ has already been visited at some earlier index $j < i$!
      • Check seen.find(need) before inserting seen[arr[i]] = i.
      • Why check before inserting? On arr = [3, 3] with target = 6, at $i = 0$ seen is empty so we record seen[3] = 0; at $i = 1$ we look up need = 3, immediately find index $0$, and return {0, 1} without ever overwriting index $0$ or pairing index $0$ with itself!
      • Optimality for Variant 2 (LeetCode 1): When original indices are required, sorting destroys original index positions unless you allocate an $\mathcal{O}(N)$ auxiliary array of (value, originalIndex) pairs anyway — making the one-pass hash map strictly superior in runtime ($\mathcal{O}(N)$ vs. $\mathcal{O}(N \log N)$) at the same $\mathcal{O}(N)$ space!

    3. $\mathcal{O}(1)$-Space Optimal for Existence: Sort + Converging Two Pointers

    When Variant 1 (Yes / No or returning the pair of values) is asked under an $\mathcal{O}(1)$ extra-space constraint, sort the array in non-decreasing order first ($\mathcal{O}(N \log N)$), then place l = 0 at the minimum element and r = N - 1 at the maximum element.

    Monotonic Elimination Proof: Why One Pointer Dies Every Step

    Suppose the active search window is $l < r$ on sorted array $a[0] \le a[1] \le \dots \le a[N - 1]$, and let $S = a[l] + a[r]$:

    • If $S < \text{target}$: Even paired with the largest remaining element $a[r]$, $a[l]$ produces a sum smaller than target. Therefore, for every $k \in (l, r)$, $a[l] + a[k] \le a[l] + a[r] < \text{target}$. Element $a[l]$ can never participate in a valid pair inside $[l..r]$ $\implies$ safely discard $l$ via l++!
    • If $S > \text{target}$: Even paired with the smallest remaining element $a[l]$, $a[r]$ overshoots target. For every $k \in (l, r)$, $a[k] + a[r] \ge a[l] + a[r] > \text{target}$. Element $a[r]$ can never participate in a valid pair $\implies$ safely discard $r$ via r--!
    • If $S == \text{target}$: Distinct indices $l < r$ sum to target $\implies$ return true!
    Complete step-by-step trace on sorted [2, 5, 6, 8, 11] with target = 14 (Page 1).
    Step l (arr[l]) r (arr[r]) Sum $S$ Reasoning & Pointer Move

    4. Clean Reference Implementations (C++ & Python)

    #include <bits/stdc++.h>
using namespace std;

// Variant 2 (LeetCode 1): Return original 0-based indices in O(N) avg time, O(N) space
vector<int> twoSum(const vector<int>& nums, int target) {
    unordered_map<long long, int> seen;
    seen.reserve(nums.size() * 2);

    for (int i = 0; i < (int)nums.size(); ++i) {
        long long need = (long long)target - nums[i];
        auto it = seen.find(need);
        if (it != seen.end()) {
            return {it->second, i};
        }
        seen[nums[i]] = i;
    }
    return {-1, -1};
}

// Variant 1: Yes/No existence check in O(N log N) time, O(1) extra space
bool twoSumExists(vector<int> nums, long long target) {
    sort(nums.begin(), nums.end());
    int l = 0, r = (int)nums.size() - 1;
    while (l < r) {
        long long sum = (long long)nums[l] + nums[r];
        if (sum == target) return true;
        if (sum < target) ++l;
        else --r;
    }
    return false;
}
    def two_sum_indices(nums: list[int], target: int) -> list[int]:
    """LeetCode 1: O(N) expected time, O(N) space."""
    seen: dict[int, int] = {}
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:
            return [seen[need], i]
        seen[x] = i
    return [-1, -1]


def two_sum_exists(nums: list[int], target: int) -> bool:
    """Variant 1: O(N log N) time, O(1) extra space (in-place sort)."""
    nums.sort()
    l, r = 0, len(nums) - 1
    while l < r:
        s = nums[l] + nums[r]
        if s == target:
            return True
        if s < target:
            l += 1
        else:
            r -= 1
    return False

    5. Complexity Comparison & Key Edge Cases

    Trade-off matrix across Two Sum approaches.
    Approach Time Complexity Extra Space Best For
    Nested Loops (Brute Force)$\mathcal{O}(N^2)$$\mathcal{O}(1)$Baseline only ($N \le 10^3$)
    One-Pass Hash Map$\mathcal{O}(N)$ avg / $\mathcal{O}(N \log N)$ tree$\mathcal{O}(N)$Variant 2 (returning original indices)
    Sort + Two Pointers$\mathcal{O}(N \log N)$$\mathcal{O}(1)$Variant 1 (Yes/No under $\mathcal{O}(1)$ space), and foundation for 3Sum / 4Sum!
    • Strict inequality while (l < r): Never write l <= r! If l == r, nums[l] + nums[l] == target would illegally use a single element twice (e.g. falsely matching 7 + 7 = 14 on [2, 7, 11]).
    • 32-bit Signed Overflow: When nums[i] or target approaches $\pm 10^9$ or INT_MIN, cast (long long)target - nums[i] and (long long)nums[l] + nums[r] so subtraction/addition never overflows!
