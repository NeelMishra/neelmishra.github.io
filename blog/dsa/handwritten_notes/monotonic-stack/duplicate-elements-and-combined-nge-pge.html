    Part 3: The [2, 2] Duplicate Trap — Strict vs. Non-Strict Comparisons & Single-Pass NGE + PGE

    October 2026 · 14 min read

    Expanded from MonotonicStack_01_A_comprehensive_guide_and_template.pdf (Pages 4–6) · View original handwritten pages

    When all elements in an array are distinct, < and <= behave identically. In real interview and contest problems, however, duplicate values are the #1 source of Wrong Answers in monotonic stack code. Look back at our summary table from Part 2:

    • Next Greater Element (NGE) pops while arr[stack.top()] < arr[i] (strict inequality).
    • Previous Greater Element (PGE) pops while arr[stack.top()] <= arr[i] (non-strict inequality).

    Why do two problems that both ask for a strictly greater element require different operators in their while loops? Let's trace the minimal two-element array from Pages 4–6 of the handwritten notes:

    $$\text{arr} = [2,\; 2]$$

    Because neither 2 has a strictly larger value anywhere in [2, 2], the ground-truth answer for both PGE and NGE is [-1, -1].

    1. Why Previous Greater (PGE) Fails with < and Must Use <=

    We want PGE[1] (for the second 2) to be -1 ("no valid previous greater"). Compare what happens at $i = 1$ under <= vs. <:

    Correct PGE Approach — Uses <= (Pop Equal Duplicates)

    1. $i = 0$ (arr[0] = 2): Stack is empty $\implies \text{PGE}[0] = -1$. Push index 0. Stack: [0].
    2. $i = 1$ (arr[1] = 2):
      • Check arr[stack.top()] <= arr[1] $\implies$ is 2 <= 2? Yes $\implies$ pop index 0!
      • Stack becomes empty $\implies$ no strictly greater element left $\implies$ PGE[1] = -1.
      • Push index 1. Stack: [1].

    Result: PGE = [-1, -1] — Correct!

    Wrong PGE Approach — Uses Only < (Leaves Equal Duplicates on Stack)

    1. $i = 0$ (arr[0] = 2): Stack is empty $\implies \text{PGE}[0] = -1$. Push index 0. Stack: [0].
    2. $i = 1$ (arr[1] = 2):
      • Check arr[stack.top()] < arr[1] $\implies$ is 2 < 2? No $\implies$ do not pop!
      • Outside the while loop, stack is non-empty ([0]), so we set PGE[1] = arr[0] = 2!

    Result: PGE = [-1, 2] — Wrong! Because we failed to pop equal elements, the earlier duplicate 2 stayed on top of the stack and masqueraded as "strictly greater" than 2.

    2. Why Next Greater (NGE) Fails with <= and Must Use <

    Now compute Next Greater Element (NGE) on the exact same array arr = [2, 2]. We want NGE[0] (for the first 2) to be -1:

    Correct NGE Approach — Uses < (Do Not Pop Equal Duplicates)

    1. $i = 0$ (arr[0] = 2): Stack empty, push 0. Stack: [0].
    2. $i = 1$ (arr[1] = 2):
      • Check arr[stack.top()] < arr[1] $\implies$ is 2 < 2? No $\implies$ do not pop!
      • Push 1. Stack: [0, 1].
    3. End of loop: Both indices 0 and 1 remain unpopped on the stack, keeping their default -1.

    Result: NGE = [-1, -1] — Correct!

    Wrong NGE Approach — Uses <= (Falsely Pops Equal Duplicates)

    1. $i = 0$ (arr[0] = 2): Stack empty, push 0. Stack: [0].
    2. $i = 1$ (arr[1] = 2):
      • Check arr[stack.top()] <= arr[1] $\implies$ is 2 <= 2? Yes $\implies$ pop index 0!
      • Inside the while loop, popping index 0 assigns NGE[0] = arr[1] = 2!

    Result: NGE = [2, -1] — Wrong! Using <= caused the second 2 to pop the first 2 and falsely label itself as strictly greater.

    3. Computing Strict NGE & Strict PGE Together in a Single Pass

    Many online guides try to compute both previousGreater and nextGreater in a single loop by merging the two templates directly:

    Watch Out for Both Halves of the Duplicate Trap ([2, 2] and [2, 2, 5])

    Look closely at why naive merging creates a tug-of-war between < and <=:

    1. If you use <= in the while loop and add if (arr[stackTop] < arr[i]) nextGreater[stackTop] = i; inside the loop, it fixes [2, 2] (returning [-1, -1]), but consider arr = [2, 2, 5]: at $i = 1$, the second 2 pops the first 2 (index 0) off the stack without setting nextGreater[0], so when 5 arrives at $i = 2$, index 0 is already gone from the stack and misses 5!
    2. Instead, what happens if we keep < in the while loop (so equal duplicates like [0:2, 1:2] stay on the stack until a truly greater element like 5 pops all of them)?
      • nextGreater is 100% exact: Every index is popped if and only if it meets its first strictly greater element to the right.
      • How do we get previousGreater[i] after the < loop? Right after while (!st.empty() && arr[st.top()] < arr[i]) terminates, every element between st.top() + 1 and i - 1 was strictly smaller than arr[i]. Thus st.top() is either strictly greater than arr[i] (in which case PGE[i] = st.top()), or equal to arr[i] (in which case i has the exact same Previous Greater Element as st.top(), which we already computed in prevGreater[st.top()])!
    // Exact Single-Pass Strict NGE + Strict PGE (Handles [2, 2], [2, 2, 5], and all duplicates!)
pair<vector<int>, vector<int>> findStrictNgeAndPgeSinglePass(const vector<int>& arr) {
    int n = arr.size();
    vector<int> prevGreater(n, -1), nextGreater(n, -1);
    stack<int> st; // Type 4: Non-increasing (equal allowed so no duplicate misses its NGE!)

    for (int i = 0; i < n; ++i) {
        // Strictly '<' ensures equal elements are NEVER popped prematurely
        while (!st.empty() && arr[st.top()] < arr[i]) {
            int stackTop = st.top();
            st.pop();
            nextGreater[stackTop] = i;
        }

        if (!st.empty()) {
            // If st.top() has an equal value, reuse its already-computed strict PGE in O(1)!
            prevGreater[i] = (arr[st.top()] == arr[i]) ? prevGreater[st.top()] : st.top();
        }

        st.push(i);
    }
    return {prevGreater, nextGreater};
}

    5. Bonus: When Is Asymmetric < + <= Used Intentionally?

    There is one famous problem family where pairing strict on one side and non-strict on the other is not a bug, but a deliberate counting trick: Sum of Subarray Minimums / Maximums (LeetCode 907 & LeetCode 2104).

    • When answering boundary queries ("What is the Next Greater and Previous Greater element of $i$?"), both sides must be strictly greater, so on [2, 2] the answer is PGE = [-1, -1] and NGE = [-1, -1].
    • When summing $\max(B)$ over all subarrays $B$ on [2, 2], there are $3$ subarrays: [2] (index 0), [2] (index 1), and [2, 2] (indices 0..1). If both 2s claimed [2, 2] (using strict boundaries on both sides), [2, 2] would be double-counted! Defining the left boundary as strictly greater (>) and the right boundary as greater-or-equal (>=)—which is precisely what the unguarded <= loop computes!—assigns [2, 2] uniquely to the rightmost 2 so every subarray is counted exactly once.

    Final Takeaway Summary

    • Standalone PGE / PSE: Must pop equal elements (<= for PGE, >= for PSE) so the surviving stack top is strictly greater/smaller.
    • Standalone NGE / NSE: Must pop only strictly violating elements (< for NGE, > for NSE) so duplicates never falsely claim each other.
    • Single-Pass Strict NGE + Strict PGE: Pop with strict < and set prevGreater[i] = (arr[st.top()] == arr[i]) ? prevGreater[st.top()] : st.top().
