    Combination Sum (LeetCode 39): Unlimited Reuse, Sorted Cutoff & $O(N^{\lceil \text{target}/m \rceil})$ Bound

    October 2026 · 8 min read · Handwritten Notes

    Expanded from handwritten competitive coding study note: 05_Combination_Sum.pdf

    In Subsets (LC 78), each index could be picked at most once, so our recursive call advanced to j + 1. What changes when any number may be picked an unlimited number of times, yet reordered duplicates like [2, 3, 2] and [3, 2, 2] are still forbidden? 05_Combination_Sum.pdf traces how changing j + 1 to j on a sorted array solves both problems without a hash set, and derives the exact worst-case recursion depth $D = \lceil \text{target} / m \rceil$.

    Problem Statement

    LeetCode 39 · Combination Sum

    Given an array of distinct positive integers candidates and a positive integer target, return a list of all unique combinations of candidates where the chosen numbers sum to target. The same number from candidates may be chosen an unlimited number of times. Two combinations are unique if the frequency of at least one chosen number differs.

    Example from note: candidates = [2, 3, 6, 7], target = 7 → [[2, 2, 3], [7]].

    Intuition: Why Sorting + Passing j Eliminates Hash Maps

    At the bottom of page 1 of 05_Combination_Sum.pdf, looking at the naive tree where branch 2, 3 tries 2, 3, 2 raises a natural question:

    “Q) Since repeated elements are allowed, can we iterate from the start & have a hashMap?”
    Answer (Pages 1–2): “Not needed—the same can be achieved with sorting & iterating only from the current index.”

    Sorting candidates in ascending order and looping for (int j = i; j < n; ++j) while recursing with dfs(j, ...) gives us two guarantees simultaneously:

    1. Zero duplicate permutations: Passing j (instead of j + 1) lets us pick candidates[j] again and again (2 → 2,2 → 2,2,2), but once the loop moves to j = 1 (value 3), no child call can ever revisit j = 0 (value 2). Thus [2, 2, 3] is generated once in non-decreasing order, while [2, 3, 2] and [3, 2, 2] never exist in the tree!
    2. Immediate sorted cutoff (break): As page 2 notes, “any number greater than my current number cannot achieve targetSum if the current combination already yields sum > targetSum.” The moment candidates[j] > rem (as at 2,2,2,2 = 8 > 7 or 2,2,6 = 10 > 7), we break out of the entire loop rather than testing larger siblings like 2,2,7!

    Clean C++ & Python Implementations

    #include <algorithm>
#include <vector>
using namespace std;

class Solution {
    void dfs(int i, int rem, const vector<int>& cand,
             vector<int>& path, vector<vector<int>>& ans) {
        if (rem == 0) {
            ans.push_back(path);  // valid combination summing to target!
            return;
        }

        for (int j = i; j < (int)cand.size(); ++j) {
            if (cand[j] > rem) break;          // sorted cutoff: all cand[j' > j] > rem too!

            path.push_back(cand[j]);
            dfs(j, rem - cand[j], cand, path, ans);  // pass j (NOT j + 1) to allow reuse!
            path.pop_back();
        }
    }

public:
    vector<vector<int>> combinationSum(vector<int>& candidates, int target) {
        sort(candidates.begin(), candidates.end());  // O(N log N) before recursion
        vector<vector<int>> ans;
        vector<int> path;
        dfs(0, target, candidates, path, ans);
        return ans;
    }
};
    class Solution:
    def combinationSum(self, candidates: list[int], target: int) -> list[list[int]]:
        candidates.sort()
        ans: list[list[int]] = []
        path: list[int] = []
        n = len(candidates)

        def dfs(i: int, rem: int) -> None:
            if rem == 0:
                ans.append(path[:])
                return
            for j in range(i, n):
                if candidates[j] > rem:
                    break
                path.append(candidates[j])
                dfs(j, rem - candidates[j])  # stay at j for unlimited reuse
                path.pop()

        dfs(0, target)
        return ans

    Time & Space Complexity Proof (05_Combination_Sum.pdf, Page 2)

    Page 2 derives the exact worst-case recursion bounds in terms of $N = |\text{candidates}|$, $m = \min(\text{candidates}) \ge 1$, and $k =$ number of valid solutions:

    Worst-Case Depth, Nodes, and Total Work

    • Maximum recursion depth $D$: In the deepest branch we repeatedly pick the minimum element $m$ until reaching or exceeding $\text{target}$, giving: $$D = \left\lceil \frac{\text{target}}{m} \right\rceil.$$
    • Upper bound on recursion nodes: At each depth we branch across at most $N$ choices (for j = i; j < N; j++), so total tree nodes are bounded by $O(N^D) = O\bigl(N^{\lceil \text{target}/m \rceil}\bigr)$.
    • Internal work vs. leaf copy work: Every internal node does $O(1)$ constant push/pop work. Each of the $k$ valid solution leaves copies a vector of length up to $D = \lceil \text{target}/m \rceil$ (note: page 2 writes $O(kN)$ shorthand in the time line and writes the exact max length $\lceil \text{target}/m \rceil$ in the space line!): $$\text{Total Time} = O\!\left(N^{\lceil \text{target}/m \rceil} + k \cdot \left\lceil\frac{\text{target}}{m}\right\rceil + N \log N\right).$$
    • Auxiliary Space (Recursion Stack + path): $O\bigl(\lceil \text{target} / m \rceil\bigr)$.
    • Result Array Space: $O\bigl(k \cdot \lceil \text{target} / m \rceil\bigr)$ ($k$ valid solutions, each holding at most $\lceil \text{target} / m \rceil$ elements).

    Key Edge Cases

    • Why candidates[j] >= 1 is essential: If 0 or negative integers were allowed with unlimited reuse, rem - 0 == rem would loop forever to infinite depth! Because LeetCode guarantees candidates[j] >= 2 (or $\ge 1$ in general positive versions), every recursive step strictly decreases rem.
    • target < min(candidates) (e.g., candidates = [2], target = 1): The very first iteration hits cand[0] > rem and breaks immediately, returning [] in $O(1)$.
