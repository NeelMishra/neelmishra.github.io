    Tarjan's Algorithm for Bridges in an Undirected Graph (Striver G-55)

    October 2026 · 12 min read · Handwritten Notes

    Expanded from handwritten competitive coding study note: 01_Undirected_graph_Striver_trajan_g_55.pdf

    In network reliability problems (famously LeetCode 1192 — Critical Connections in a Network), a single cable failure can split an entire cluster into isolated islands unless a cycle provides a backup route. Finding every such single-edge bottleneck — called a bridge or cut-edge — by deleting edges one at a time takes quadratic $\mathcal{O}(E(V + E))$ time. Robert Tarjan's DFS timestamp algorithm solves the entire problem in a single $\mathcal{O}(V + 2E)$ traversal using just two integer arrays: tin[] and low[].

    1. Problem Statement & Core Definition

    Definition: Bridge (Cut-Edge) in an Undirected Graph

    Given an undirected (bidirectional) graph $G = (V, E)$, an edge $e = (u, v) \in E$ is a bridge if removing $e$ strictly increases the number of connected components of $G$. Equivalently, $(u, v)$ is a bridge if and only if $(u, v)$ does not lie on any simple cycle in $G$.

    Goal: Print or return all bridges in $G$ (order of endpoints $(u, v)$ vs. $(v, u)$ does not matter; prerequisite: standard DFS).

    On Page 1 of the handwritten note, we examine a 12-vertex graph built from three cycles — square 1–2–3–4–1, diamond 6–7–8–9–6, and triangle 10–11–12–10 — linked together by three bottleneck edges: 4–5, 5–6, and 8–10. Cutting any edge inside a square, diamond, or triangle leaves the graph in 1 piece, whereas cutting 4–5, 5–6, or 8–10 immediately breaks the graph into 2 components.

    2. Progression: Brute Force $\to$ Cycle-Span Observation $\to$ Optimal Tarjan DFS

    1. Brute Force — $\mathcal{O}(E \cdot (V + E))$:
      • First count baseline connected components $C_0$ using DFS.
      • For each edge $e_i = (u, v) \in E$, temporarily ignore $e_i$ and run a full $\mathcal{O}(V + E)$ DFS from $u$. If $v$ is no longer reachable from $u$, report $(u, v)$ as a bridge.
      • For $V, E = 10^5$ (as in LeetCode 1192), $E(V + E) \approx 2 \times 10^{10}$ operations — guaranteed TLE.
    2. Better Observation — Every Non-Tree Edge Is an Ancestor Back-Edge:
      • Root a DFS spanning tree at any vertex (say 1). A classic property of undirected DFS is that cross-edges between unrelated subtrees cannot exist: every edge in $G$ is either a DFS tree edge going down to a newly discovered child, or a back-edge connecting a descendant back up to an already-visited ancestor!
      • Therefore, a non-tree back-edge can never be a bridge (it closes a cycle with the tree path). Only the $\le V - 1$ DFS tree edges are bridge candidates, and a tree edge $(u, v)$ ($u$ parent of $v$) is protected iff some back-edge jumps from $v$'s subtree strictly above $(u, v)$ to $u$ or an ancestor of $u$.
    3. Optimal — Tarjan's Two-Array DFS ($\mathcal{O}(V + 2E)$ Time, $\mathcal{O}(V)$ Extra Space):
      • Instead of walking tree paths for each back-edge, assign every node an increasing DFS arrival step tin[node] so "ancestor of u" simply means $\text{timestamp} \le \text{tin}[u]$!
      • Compute low[node] bottom-up during DFS post-order as the minimum reachable tin from node's subtree without reusing the direct tree edge back to parent. If $\text{low}[\text{child}] \gt \text{tin}[\text{node}]$, the child's entire subtree is trapped at timestamps strictly after node, proving $(\text{node}, \text{child})$ is a bridge!

    3. Intuition Behind tin[] and low[]

    The Two Tracking Arrays (Page 1)

    • tin[node] (Time of Insertion): The DFS step counter when node is first reached. Stamped once on entry and never modified. If $a$ is a proper ancestor of $b$ in the DFS tree, then $\text{tin}[a] \lt \text{tin}[b]$.
    • low[node] (Lowest Time of Insertion): Initialized to tin[node] on entry (conceptually, unvisited neighbors contribute $+\infty$ until explored). As DFS explores every neighbor it of node apart from parent, low[node] records the earliest tin reachable from node's DFS subtree via tree edges and back-edges.

    Bridge Verdict for DFS Tree Edge $(\text{node} \to \text{it})$:

    $$\text{low}[\text{it}] \;\gt\; \text{tin}[\text{node}] \;\Longleftrightarrow\; (\text{node}, \text{it}) \text{ is a Bridge}$$

    Why must low[] ignore parent? Because the graph is bidirectional: when DFS steps from 8 down to 9, 8 is sitting inside adj[9]. If 9 were allowed to look right back along the tree edge 9–8 it just arrived on, low[9] would absorb tin[8] = 8 even if 8–9 were a dead-end leaf edge! Skipping if (it == parent) continue; asks the true reliability question: "If the direct link node — it breaks, can it still reach node or earlier through ANOTHER path?"

    4. Step-by-Step tin[] / low[] Dry Run (Pages 1–3)

    Following the exact DFS order in the handwritten note starting at vertex 1 with timer = 1:

    1. Forward Descent 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9 (Page 1):
      • DFS marks each node visited and stamps initial tin/low: 1(1/1) → 2(2/2) → 3(3/3) → 4(4/4) (suppose 4 explores neighbor 5 before 1, as drawn on Page 1) → 5(5/5) → 6(6/6) → 7(7/7) → 8(8/8) → 9(9/9).
      • Critical state at node 9 (9/9): All adjacent nodes of 9 are already visited (8 and 6)! Neighbor 8 is parent, so we ignore it. Neighbor 6 is visited, so we do not recurse into 6, nor do we test 9–6 for a bridge — instead, 9 updates low[9] = min(9, 6) = 6, changing 9/9 to 9/6.
    2. Backtracking 9 → 8 — Q: Can 8–9 be a bridge? (Page 2):
      • Returning from DFS(9) to 8, node 8 first pulls up low[8] = min(8, low[9]) = 6 (8/8 → 8/6).
      • Now test the bridge condition on tree edge 8–9: $\text{low}[9] \gt \text{tin}[8] \implies 6 \gt 8$, which is False!
      • Handwritten intuition: To reach 8 took $8$ steps, while 9 has an adjacent vertex via which it reaches step $6$ (node 6). Even if edge 8–9 is deleted, 9 walks $9 \to 6 \to 7 \to 8$, so connectivity survives!
    3. Exploring Triangle 8 → 10 → 11 → 12 (Pages 2–3):
      • From 8 (8/6), unvisited neighbor 10 continues the traversal: 10(10/10) → 11(11/11) → 12(12/12).
      • At 12: neighbor 11 is parent (ignored), while neighbor 10 (10/10) is already visited $\implies$ low[12] = min(12, 10) = 10 (12/10).
      • Q: Can 11–12 be a bridge? Returning to 11 updates low[11] = min(11, low[12]) = 10. Check $\text{low}[12] \gt \text{tin}[11] \implies 10 \gt 11$ (False — 12 reaches step 10 at node 10 and walks $10 \to 11$ in 1 step).
      • Q: Is 10–11 a bridge? Returning to 10 (10/10) updates low[10] = min(10, low[11]) = 10. Check $\text{low}[11] \gt \text{tin}[10] \implies 10 \gt 10$ (False!). Because only the edge 10–11 is removed while vertex 10 remains intact, 11 still reaches 10 via $11 \to 12 \to 10$.
    4. Returning 10 → 8 — Q: Is 8–10 a bridge? (Page 3):
      • Back at 8 (8/6): low[8] = min(6, low[10]) = min(6, 10) = 6.
      • Test $\text{low}[10] \gt \text{tin}[8] \implies 10 \gt 8$ — TRUE! Subtree {10, 11, 12} is stuck at minimum timestamp $10$ and cannot reach 8 or any earlier step. Report Bridge 8–10!
    5. Final Unwind 8 → 7 → 6 → 5 → 4 → 3 → 2 → 1:
      • 8 (8/6) → 7 (7/7): low[7] = min(7, 6) = 6; $\text{low}[8] = 6 \le \text{tin}[7] = 7$ (not a bridge).
      • 7 (7/6) → 6 (6/6): low[6] = min(6, 6) = 6; $\text{low}[7] = 6 \le \text{tin}[6] = 6$ (not a bridge; visited neighbor 9 is skipped as a cycle edge).
      • 6 (6/6) → 5 (5/5): low[5] = min(5, 6) = 5; $\text{low}[6] = 6 \gt \text{tin}[5] = 5$ $\implies$ Report Bridge 5–6!
      • 5 (5/5) → 4 (4/4): $\text{low}[5] = 5 \gt \text{tin}[4] = 4$ $\implies$ Report Bridge 4–5! Next, 4 inspects its remaining neighbor 1 (1/1) (already visited!), updating low[4] = min(4, 1) = 1.
      • 4 (4/1) → 3 (3/1) → 2 (2/1) → 1 (1/1): low = $1$ propagates all the way up, so $\text{low}[4]=1 \le 3$, $\text{low}[3]=1 \le 2$, and $\text{low}[2]=1 \le 1$ — none of the square's edges are bridges!

    5. Crucial Subtlety: Strict > vs. >= and tin[it] vs. low[it]

    • Why Bridges use strict low[it] > tin[node] (never >=): Look at triangle edge 10–11 above, where $\text{low}[11] = 10 = \text{tin}[10]$. Deleting edge 10–11 leaves vertex 10 alive, so reaching timestamp $\text{tin}[10]$ is completely sufficient to reconnect 11 to 10 (and through 10 to 8). By contrast, in Articulation Points (G-56), vertex 10 itself is deleted, forcing the inequality to tighten to $\text{low}[\text{it}] \ge \text{tin}[\text{node}]$.
    • Why we never run the bridge check in the else (visited) branch (Page 3 triple-star note): If vis[it] == 1 and it != parent, edge $(\text{node}, \text{it})$ is a non-tree back-edge closing a cycle between it and node's tree path. Cycle edges can never be bridges!
    • min(low[node], low[it]) vs. min(low[node], tin[it]) on visited back-edges: On Page 4's code screenshot (line 22), the else branch writes low[node] = min(low[node], low[it]). For Bridges, both low[it] and tin[it] produce identical answers: any visited non-parent neighbor it in undirected DFS is a strict ancestor of node, so $\text{low}[\text{it}] \le \text{tin}[\text{it}] \lt \text{tin}[\text{node}]$, meaning both pull low[node] strictly below tin[node] (and $\le \text{tin}[\text{it}]$). However, for Articulation Points, borrowing low[it] across a cut-vertex it is a fatal bug because deleting it severs the path that gave it its smaller low! Writing low[node] = min(low[node], tin[it]) in the else branch is mathematically exact for both Bridges and Articulation Points.

    6. Clean C++ & Python Implementation (LeetCode 1192 / Striver G-55)

    #include <bits/stdc++.h>
using namespace std;

class Solution {
private:
    int timer = 1;

    void dfs(int node, int parent, vector<int>& vis,
             const vector<vector<int>>& adj,
             vector<int>& tin, vector<int>& low,
             vector<vector<int>>& bridges) {
        vis[node] = 1;
        tin[node] = low[node] = timer;
        timer++;

        for (int it : adj[node]) {
            if (it == parent) continue;
            if (vis[it] == 0) {
                dfs(it, node, vis, adj, tin, low, bridges);
                low[node] = min(low[node], low[it]);

                // Can the edge (node --- it) be a bridge?
                if (low[it] > tin[node]) {
                    bridges.push_back({it, node});
                }
            } else {
                // Already visited non-parent ancestor => back-edge closing a cycle
                low[node] = min(low[node], tin[it]);
            }
        }
    }

public:
    vector<vector<int>> criticalConnections(int n, vector<vector<int>>& connections) {
        vector<vector<int>> adj(n);
        for (const auto& e : connections) {
            adj[e[0]].push_back(e[1]);
            adj[e[1]].push_back(e[0]);
        }

        vector<int> vis(n, 0), tin(n, 0), low(n, 0);
        vector<vector<int>> bridges;

        // Loop over all vertices so disconnected components are also handled
        for (int i = 0; i < n; i++) {
            if (!vis[i]) {
                dfs(i, -1, vis, adj, tin, low, bridges);
            }
        }
        return bridges;
    }
};
    import sys
sys.setrecursionlimit(200_000)

def critical_connections(n: int, connections: list[list[int]]) -> list[list[int]]:
    adj = [[] for _ in range(n)]
    for u, v in connections:
        adj[u].append(v)
        adj[v].append(u)

    vis = [False] * n
    tin = [0] * n
    low = [0] * n
    bridges: list[list[int]] = []
    timer = 1

    def dfs(node: int, parent: int) -> None:
        nonlocal timer
        vis[node] = True
        tin[node] = low[node] = timer
        timer += 1

        for it in adj[node]:
            if it == parent:
                continue
            if not vis[it]:
                dfs(it, node)
                low[node] = min(low[node], low[it])
                if low[it] > tin[node]:
                    bridges.append([node, it])
            else:
                low[node] = min(low[node], tin[it])

    for i in range(n):
        if not vis[i]:
            dfs(i, -1)

    return bridges

    7. Time & Space Complexity Proof (Page 3)

    • Time Complexity — $\mathcal{O}(V + 2E)$:
      • Building the undirected adjacency list from $E$ edges takes $\mathcal{O}(E)$ pushes.
      • Each vertex $u \in \{0, \dots, V-1\}$ is entered by dfs at most once because vis[u] = 1 is set immediately on entry ($\mathcal{O}(V)$ recursive calls).
      • Inside dfs(node), the loop scans $\deg(\text{node})$ neighbors doing $\mathcal{O}(1)$ work per neighbor. Summing across all vertices gives $\sum_{u \in V} \deg(u) = 2E$. Total time: $\mathcal{O}(V + 2E)$.
    • Space Complexity — $\mathcal{O}(V + 2E) + \mathcal{O}(3V)$:
      • $\mathcal{O}(V + 2E)$ to store the bidirectional adjacency list adj (if built from an edge list).
      • $\mathcal{O}(3N) = \mathcal{O}(V)$ for the three tracking arrays vis[], tin[], and low[], plus $\mathcal{O}(V)$ worst-case DFS call-stack depth on a path graph.

    8. Key Edge Cases to Watch

    • No Special Root Exception Needed for Bridges: Unlike Articulation Points, low[it] > tin[root] works identically at the starting vertex (parent == -1)! If root 1 has a single leaf edge 1–2, $\text{low}[2] = 2 \gt \text{tin}[1] = 1$ rightly flags 1–2; in our 12-node square, back-edge 4–1 lowers $\text{low}[2] = 1 \not\gt 1$, rightly sparing 1–2.
    • Disconnected Graphs: A bridge increases the total number of connected components in $G$ (e.g., from $3$ components to $4$). Always wrap dfs(i, -1, ...) inside for (int i = 0; i < n; i++) if (!vis[i]) rather than calling only dfs(0, -1, ...).
    • Trees & Single-Edge Graphs: Every edge of a tree has zero back-edges, so $\text{low}[\text{it}] = \text{tin}[\text{it}] \gt \text{tin}[\text{node}]$ holds for all $V - 1$ edges.
    • Parallel Multi-Edges (Codeforces Multigraphs): In simple graphs (like LeetCode 1192), if (it == parent) continue; skips the unique parent tree edge. If a multigraph can contain two parallel edges between u and v, pass the incoming edge index parentEdgeId instead of parent so the second parallel edge is treated as a cycle-closing back-edge!
