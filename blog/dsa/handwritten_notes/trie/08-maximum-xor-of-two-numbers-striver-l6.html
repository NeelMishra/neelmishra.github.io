    Maximum XOR Across Two Arrays with a Binary Trie (Striver L6)

    October 2026 · 8 min read · Handwritten Notes

    Expanded from handwritten competitive coding study note: 08_Striver_L6_Maximum_XOR_of_Two_Numbers_in_an_array.pdf

    Armed with the 32-bit bitwise primitives from Striver Lecture 5, Striver Trie Lecture 6 tackles the foundational Binary Trie problem: finding the maximum cross-array XOR $A \oplus B$ where $A$ must come from arr1 (size $N$) and $B$ must come from arr2 (size $M$). Unlike LeetCode 421 (where both operands are drawn from a single array), the two-array formulation enforces strict bipartite separation—making the separation between insert(A) on arr1 and getMax(B) on arr2 crystal clear.

    1. Problem Statement & Why You Cannot Pool Both Arrays

    Maximum XOR Across Two Arrays (Striver L6 / Coding Ninjas)

    You are given two non-empty arrays of non-negative 32-bit integers, arr1 of length $N$ and arr2 of length $M$. Find the maximum possible value of

    $$\max_{\substack{A \in \text{arr1} \\ B \in \text{arr2}}} (A \oplus B)$$

    Two-Array Asymmetric Rule: Never Insert Both Arrays into the Same Trie!

    Suppose arr1 = [1, 30] ($\texttt{00001}_2, \texttt{11110}_2$) and arr2 = [2, 3] ($\texttt{00010}_2, \texttt{00011}_2$):

    • If you carelessly merged both arrays into one pool, $1 \oplus 30 = \mathbf{31}$ ($\texttt{11111}_2$) would pair two elements that both belong to arr1!
    • Across valid cross-array pairs $(A, B) \in \text{arr1} \times \text{arr2}$, the four candidates are $1 \oplus 2 = 3$, $1 \oplus 3 = 2$, $30 \oplus 2 = 28$, and $30 \oplus 3 = \mathbf{29}$.

    By inserting only arr1 into the Binary Trie and querying getMax(B) (without inserting $B$!) for each $B \in \text{arr2}$, every root-to-leaf path in the Trie is guaranteed to represent a genuine element $A \in \text{arr1}$!

    2. Progression: $O(N \cdot M)$ Brute Force $\to$ $O(32(N + M))$ Binary Trie

    • Brute Force (Nested Pairwise Scan): Compute arr1[i] ^ arr2[j] over all $N \cdot M$ pairs. For $N, M \le 10^5$, $N \cdot M = 10^{10}$ operations triggers Time Limit Exceeded.
    • Optimal 32-Bit Binary Trie:
      1. Minimal 2-Pointer Node: Each BitNode stores only BitNode* links[2] = {nullptr, nullptr} (index 0 for bit $0$, index 1 for bit $1$). Because every path has fixed depth $32$ (from bit $31$ down to bit $0$), no bool flag is needed!
      2. Phase 1 — Insert arr1 ($O(32 N)$): For each $A \in \text{arr1}$, extract bits $i = 31 \dots 0$ via int bit = (A >> i) & 1; and walk/allocate down links[bit].
      3. Phase 2 — Greedy Opposite-Bit Query getMax(B) ($O(32 M)$): Given $B \in \text{arr2}$, initialize maxNum = 0 and walk from root for $i = 31 \dots 0$:
        • Let bit = (B >> i) & 1. To make bit $i$ of $A \oplus B$ equal to $1$, we want an element $A$ in the current subtree whose $i$-th bit is 1 - bit!
        • If node->containsKey(1 - bit) exists: Turn ON bit $i$ in maxNum (maxNum |= (1 << i)) and step into node->get(1 - bit).
        • Otherwise: No surviving candidate in arr1 has opposite bit 1 - bit; since the Trie is non-empty, node->get(bit) must exist! Step into node->get(bit) (contributing $0$ at bit $i$).

    Proof of Greedy Optimality

    Why is taking 1 - bit at level $i$ unconditionally better than taking bit, even if taking bit matched opposite bits at every single lower level $i-1, i-2, \dots, 0$? Because

    $$2^i \gt \sum_{j=0}^{i-1} 2^j = 2^i - 1$$

    Securing $+2^i$ at position $i$ guarantees a cross-array XOR of at least $(\text{prefix}) + 2^i$, whereas taking bit caps every number in that sibling subtree at $(\text{prefix}) + (2^i - 1)$!

    4. Clean C++ Implementation (With Smaller-Array Memory Optimization)

    Because XOR is commutative ($A \oplus B = B \oplus A$), if $N \gg M$ (say $N = 10^6$ and $M = 100$), we can swap the roles of arr1 and arr2 so the Binary Trie is always built on the smaller array—shrinking space from $O(32 N)$ down to $O(32 \min(N, M))$ for free!

    #include <bits/stdc++.h>
using namespace std;

struct Node {
    Node* links[2] = {nullptr, nullptr};

    bool containsKey(int bit) const { return links[bit] != nullptr; }
    Node* get(int bit) const { return links[bit]; }
    void put(int bit, Node* node) { links[bit] = node; }
};

class Trie {
private:
    Node* root;

public:
    Trie() : root(new Node()) {}

    void insert(int num) {
        Node* node = root;
        for (int i = 31; i >= 0; i--) {
            int bit = (num >> i) & 1;
            if (!node->containsKey(bit)) {
                node->put(bit, new Node());
            }
            node = node->get(bit);
        }
    }

    int getMax(int num) const {
        Node* node = root;
        int maxNum = 0;
        for (int i = 31; i >= 0; i--) {
            int bit = (num >> i) & 1;
            // Greedily take opposite bit (1 - bit) whenever available!
            if (node->containsKey(1 - bit)) {
                maxNum |= (1U << i);
                node = node->get(1 - bit);
            } else {
                node = node->get(bit);
            }
        }
        return maxNum;
    }
};

int maxXOR(int n, int m, vector<int>& arr1, vector<int>& arr2) {
    // Space optimization: build the Trie on the smaller array!
    const vector<int>& buildArr = (n <= m) ? arr1 : arr2;
    const vector<int>& queryArr = (n <= m) ? arr2 : arr1;

    Trie trie;
    for (int a : buildArr) {
        trie.insert(a);
    }

    int maxi = 0;
    for (int b : queryArr) {
        maxi = max(maxi, trie.getMax(b));
    }
    return maxi;
}

    5. Complexity Proof, Edge Cases & Offline Query Extension

    • Time Complexity: Building the Trie performs $32 \cdot \min(N, M)$ steps; querying performs $32 \cdot \max(N, M)$ steps $\implies$ $O(32 \cdot (N + M)) = O(N + M)$ linear time!
    • Space Complexity: At most $1 + 32 \cdot \min(N, M)$ nodes, each holding $2$ pointers $\implies$ $O(32 \cdot \min(N, M))$.
    • Key Edge Cases & Natural Follow-Up (Striver L7 / LeetCode 1707):
      • Zeros in input (arr1 = [0], arr2 = [0]): Inserts 32 consecutive 0 edges; getMax(0) misses 1 at every bit and returns 0.
      • Duplicate values inside arr1: Reuses the exact same 32-node path without allocating any extra nodes.
      • Offline Bounded Queries (max_{A <= m_i} (A ^ x_i)): Because insert and getMax are completely decoupled in this Lecture 6 design, if queries specify an upper bound $A \le m_i$ (LeetCode 1707), you simply sort arr1 and sort queries by $m_i$, inserting elements of arr1 with $A \le m_i$ incrementally before calling trie.getMax(x_i)!
