    Hierarchical k-means and trees: split the space and merge a forest

    October 2026 · 8 min read

    A tree index recursively divides the corpus into smaller subsets so a query can descend in logarithmic depth instead of scanning flat lists. Yet every hard partition introduces a boundary hazard: a query sitting just to the right of a split plane will descend into the right subtree even when its true nearest neighbor sits just to the left.

    Two mechanisms make hierarchical trees practical for approximate nearest-neighbor search: priority-queue backtracking across close branches (used in hierarchical k-means and FLANN) and aggregating candidate leaves across an ensemble of randomized midpoint trees (used in Spotify's Annoy).

    Trace a split boundary that separates a query from its nearest neighbor

    Four points · one partition boundary

    The query is $q=(0.1,0.0)$. Stored points are $A=(-0.2,0.0)$, $B=(0.6,0.0)$, $C=(1.0,0.0)$, and $D=(-1.4,0.0)$. The true nearest neighbor is $A$ at squared L2 distance $0.09$, but a root split at $x_1=0$ sends $q$ into the right leaf $\{B,C\}$.

    Suppose the root level clusters the four points into a left child $\{A,D\}$ with centroid $\mu_L=(-0.8,0.0)$ and a right child $\{B,C\}$ with centroid $\mu_R=(0.8,0.0)$. The perpendicular bisector between $\mu_L$ and $\mu_R$ is the line $x_1=0.0$.

    Why does the root route $q$ away from $A$? The extreme point $D=(-1.4,0.0)$ pulls the left centroid $\mu_L$ out to $(-0.8,0.0)$, giving $d^2(q,\mu_L)=0.81$, whereas the right centroid sits closer at $d^2(q,\mu_R)=0.49$. A greedy single-path traversal inspects only $\{B,C\}$ and returns $B$ ($0.25$) instead of $A$ ($0.09$).

    Hierarchical k-means builds a balanced multi-way routing tree

    Flat IVF partitions the corpus into $K_{\text{list}}$ coarse cells in one step, which still requires $O(K_{\text{list}}d)$ work to score the query against every coarse centroid. When $K_{\text{list}}$ is tens of thousands, flat centroid scoring becomes a bottleneck on its own.

    Hierarchical k-means (HKM) replaces one large codebook with a tree of small k-means problems using branching factor $K_b$ (commonly $8$ to $64$). Each internal node partitions its assigned subset into $K_b$ child clusters until a leaf holds at most $S_{\max}$ points:

    $$\text{Tree height } H \approx \left\lceil \log_{K_b}\!\left(\frac{N}{S_{\max}}\right) \right\rceil, \qquad \text{Single-path routing cost } \approx H K_b d.$$

    For $N=1{,}000{,}000$, $S_{\max}=64$, and $K_b=16$, a flat quantizer with $15{,}625$ lists requires $15{,}625$ centroid comparisons, whereas a four-level HKM tree performs $4\times 16=64$ centroid comparisons along a single root-to-leaf descent.

    To recover boundary neighbors without exhaustive tree traversal, Muja and Lowe's FLANN maintains a single min-heap of unvisited internal branches ordered by their centroid distance $d^2(q,\mu)$ (or hyperplane margin). After scoring the first leaf, the search pops the closest pending branch from the heap and descends to its best leaf until the inspection limit $L_{\max}$ is reached.

    Random midpoint hyperplanes and tree forests in Annoy

    Running k-means at every internal node can be expensive at build time. Spotify's Annoy (Approximate Nearest Neighbors Oh Yeah) instead constructs binary trees using lightweight random two-point splits. At each internal node with subset $S$:

    1. Sample two points $u,v\in S$ (or run a few iterations of 2-means) to define a normal vector $n = u - v$ and midpoint $m = \frac{1}{2}(u + v)$.
    2. Split $S$ by the hyperplane $(u-v)^\top(x - m) = 0$, sending points with $(u-v)^\top x \le (u-v)^\top m$ to the left child and the rest to the right child.
    3. Stop splitting when $|S| \le S_{\max}$ and store the remaining vector IDs in a contiguous leaf array.

    For query $q$, the signed margin to an internal split hyperplane is:

    $$\Delta(q; u, v) = (u - v)^\top\!\left(q - \frac{u + v}{2}\right), \qquad d_{\text{plane}}(q) = \frac{|\Delta(q; u, v)|}{\lVert u - v\rVert_2}.$$

    Instead of relying on one tree where $q$ and its true neighbor might be separated near the root, Annoy builds a forest of $T$ independent trees (`n_trees`). A second tree that chooses pivots $A=(-0.2,0.0)$ and $C=(1.0,0.0)$ places its midpoint at $x_1=0.4$. Both $q=(0.1,0.0)$ and $A=(-0.2,0.0)$ fall on the left side ($x_1\le 0.4$) of Tree 2's root split, placing $A$ directly in $q$'s initial leaf.

    Verify greedy descent, priority-queue backtracking, and forest union

    The Python snippet below reproduces the four-point split puzzle, showing why greedy descent in Tree 1 returns $B$, while either a two-branch priority-queue budget or a two-tree forest recovers $A$:

    import heapq
import numpy as np

q = np.array([0.1, 0.0])
corpus = {
    "A": np.array([-0.2, 0.0]),
    "B": np.array([0.6, 0.0]),
    "C": np.array([1.0, 0.0]),
    "D": np.array([-1.4, 0.0]),
}

def sq_l2(u, v):
    diff = u - v
    return float(np.dot(diff, diff))

# Tree 1 splits at x1 = 0.0 (midpoint of centroids (-0.8, 0) and (0.8, 0))
tree1 = {"split": 0.0, "left": ["A", "D"], "right": ["B", "C"]}
# Tree 2 uses pivots A=(-0.2, 0) and C=(1.0, 0), midpoint x1 = 0.4
tree2 = {"split": 0.4, "left": ["A", "D"], "right": ["B", "C"]}

def search_trees(trees, max_leaves):
    heap = []
    for idx, tree in enumerate(trees):
        margin = abs(float(q[0]) - tree["split"])
        near = tree["left"] if q[0] <= tree["split"] else tree["right"]
        far = tree["right"] if q[0] <= tree["split"] else tree["left"]
        heapq.heappush(heap, (0.0, idx, "near", near))
        heapq.heappush(heap, (margin, idx, "far", far))
    candidates = set()
    for _ in range(max_leaves):
        if not heap:
            break
        _, _, _, leaf = heapq.heappop(heap)
        candidates.update(leaf)
    ranked = sorted((sq_l2(q, corpus[k]), k) for k in candidates)
    return ranked[0][1], round(ranked[0][0], 4), sorted(candidates)

assert search_trees([tree1], max_leaves=1) == ("B", 0.25, ["B", "C"])
assert search_trees([tree1], max_leaves=2) == ("A", 0.09, ["A", "B", "C", "D"])
assert search_trees([tree1, tree2], max_leaves=2) == ("A", 0.09, ["A", "B", "C", "D"])
print("Tree 1 (1 leaf):", search_trees([tree1], max_leaves=1))
print("Tree 1 (2 leaves):", search_trees([tree1], max_leaves=2))
print("Forest (1 leaf per tree):", search_trees([tree1, tree2], max_leaves=2))

    In Annoy, each tree's root is pushed into the priority queue with initial margin $\infty$ (so all $T$ root-to-leaf paths are traversed first), and close sibling branches are explored in decreasing order of hyperplane margin until the total number of inspected points reaches search_k.

    Why classical KD-trees stall on dense RAG embeddings

    An exact KD-tree prunes a sibling branch only when the distance from $q$ to the axis-aligned splitting coordinate $j$, $|q_j - \tau|$, exceeds the current best full-dimensional distance $R = \min_{x\in W}\lVert q - x\rVert_2$. For roughly isotropic $d$-dimensional embeddings, a single coordinate difference accounts for roughly $1/\sqrt{d}$ of the full Euclidean norm:

    $$\mathbb{E}\bigl[(q_j - x_j)^2\bigr] \approx \frac{1}{d}\lVert q - x\rVert_2^2 \implies |q_j - \tau| \ll \lVert q - x_{\text{nearest}}\rVert_2 \quad \text{for large } d.$$

    At $d=768$, the hypersphere around $q$ of radius $\lVert q - x_{\text{nearest}}\rVert_2$ intersects almost every coordinate hyperplane near $q$, forcing an exact KD-tree to visit nearly the entire dataset. Approximate tree methods stay fast only because they cap leaf inspections via search_k or $L_{\max}$ and use full-dimensional oblique splits (centroids or midpoint hyperplanes) that align with the data manifold.

    In production RAG workloads, tree forests like Annoy excel when an index is built once, serialized to disk, and shared across read-only worker processes via mmap. However, because every tree stores its own leaf ID lists, memory scales linearly with `n_trees`, and dynamic insertions or deletions typically require rebuilding the forest. Compare the HNSW and Annoy internals guide for a side-by-side memory and traversal trace.

    Check the operating assumptions

    Does increasing n_trees in Annoy change the stored vector coordinates?

    No. The vector array is stored once; each additional tree adds internal split hyperplanes and leaf ID lists. More trees increase index file size and offer more independent entry leaves per query, while search_k bounds total candidate scoring work.

    Why can a larger branching factor Kb in hierarchical k-means reduce tree depth without reducing routing work?

    A single root-to-leaf descent scores $K_b$ centroids at each of $\lceil\log_{K_b}(N/S_{\max})\rceil$ levels, costing roughly $K_b \log_{K_b}(N/S_{\max})$ distance evaluations. Making $K_b$ too large approaches a flat IVF scan; making $K_b$ too small increases the number of split boundaries a query can sit near.

    If a query filter excludes all IDs inside the initially visited leaves, what happens?

    Post-filtering the candidates gathered within search_k can return fewer than K results or an empty set. Either the priority queue must keep popping branches until K eligible IDs are scored, or the application must fall back to a filter-aware plan.
