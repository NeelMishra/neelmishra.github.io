    DiskANN and Vamana: route with RAM codes and fetch vectors from SSD

    October 2026 · 9 min read

    In-memory HNSW stores uncompressed vectors and multi-layer adjacency lists in RAM—costing over 3 GB per million 768-dimensional float32 vectors. Simply memory-mapping an HNSW graph onto an NVMe SSD fails: every expanded node scores all of its neighbors, triggering dozens of scattered 4 KB SSD page reads per hop.

    Subramanya and colleagues' DiskANN solves billion-scale retrieval on a single workstation with two co-designed ideas: the single-layer Vamana graph, whose $\alpha$-pruning rule embeds long-range shortcuts directly into the base graph, and a two-tier storage layout that routes queries using compact Product Quantization codes in RAM while fetching full-precision vectors and neighbor lists together in a single 4 KB SSD read per hop.

    Why Vamana replaces HNSW's hierarchy with alpha-occlusion pruning

    One source node · three candidates · alpha = 1.0 versus alpha = 1.6

    Source node $p=(0,0)$ considers candidates $a=(1.0,0.8)$, $b=(1.1,0.7)$, and $c=(2.0,0.0)$. Under HNSW's $\alpha=1.0$ rule, selecting $a$ prunes both the redundant nearby $b$ and the distant $c$, because $a$ is closer to $c$ ($1.2806$) than $p$ is ($2.0000$). Under Vamana's $\alpha=1.6$ rule, $b$ is still pruned, but the long-range shortcut $(p,c)$ survives.

    Recall HNSW's diversity rule: an already selected neighbor $r\in R$ occludes candidate $e$ whenever $d(r,e) \le d(p,e)$. Vamana's RobustPrune introduces a slack multiplier $\alpha \ge 1$ and occludes $e$ only when routing through $r$ shrinks the distance to $e$ by at least a factor of $1/\alpha$:

    $$\text{Occlude } e \quad\Longleftrightarrow\quad \exists\, r\in R \text{ such that } \alpha \cdot d(r, e) \le d(p, e).$$

    When $\alpha = 1.0$, any neighbor $r$ that is even slightly closer to $e$ than $p$ is blocks the direct edge $(p,e)$. When $\alpha > 1$ (commonly $\alpha=1.2$ to $1.6$), $r$ blocks $(p,e)$ only if $r$ sits close enough to $e$ to make substantial geometric progress. Otherwise, $p$ keeps the direct long-range edge to $e$.

    Instead of inserting vectors one by one with random upper layers, Vamana initializes a single-layer random out-degree-$R$ graph, starts every search at the corpus medoid $s = \arg\min_{x_i}\sum_j d(x_i,x_j)$, and runs two global refinement passes over all nodes: Pass 1 with $\alpha=1.0$ to clean random edges into a local mesh, and Pass 2 with $\alpha > 1$ to weave long-range shortcuts across the graph.

    Co-locate full vectors and neighbor IDs in one 4 KB SSD page

    Why can DiskANN expand a graph node in a single SSD read whereas a naive on-disk graph takes dozens? During graph traversal, expanding a node $v$ requires two things:

    1. Its outgoing neighbor list $N_{\text{out}}(v)$ so those neighbors can be added to the candidate frontier.
    2. Its exact full-precision coordinate vector $x_v\in\mathbb{R}^d$ so $v$ can be placed accurately in the final top-$K$ result heap.

    DiskANN stores both items contiguously inside one fixed-size disk record aligned to a 4,096-byte SSD page:

    $$\text{RecordBytes}(d, R) = \underbrace{4d}_{\text{float32 vector } x_v} + \underbrace{4}_{\text{degree } |N_{\text{out}}(v)|} + \underbrace{4R}_{\text{uint32 neighbor IDs}}.$$

    For $d=768$ float32 coordinates ($3{,}072$ bytes) and degree cap $R=64$ ($256$ bytes), each node record occupies $3{,}072 + 4 + 256 = 3{,}332$ bytes—fitting comfortably inside a single 4 KB NVMe page read.

    Verify Vamana RobustPrune and the 4 KB SSD page budget in Python

    import math
import numpy as np

p = np.array([0.0, 0.0])
candidates = {
    "a": np.array([1.0, 0.8]),
    "b": np.array([1.1, 0.7]),
    "c": np.array([2.0, 0.0]),
}

def dist(u, v):
    return float(np.linalg.norm(u - v))

def robust_prune(source, pool, alpha, max_degree=2):
    ordered = sorted(pool, key=lambda k: dist(source, pool[k]))
    selected = []
    for cand in ordered:
        if len(selected) >= max_degree:
            break
        occluded = any(
            alpha * dist(pool[r], pool[cand]) <= dist(source, pool[cand])
            for r in selected
        )
        if not occluded:
            selected.append(cand)
    return selected

assert robust_prune(p, candidates, alpha=1.0, max_degree=2) == ["a"]
assert robust_prune(p, candidates, alpha=1.6, max_degree=2) == ["a", "c"]

# Check 4 KB SSD page layout for d=768 float32 and R=64 uint32 neighbor IDs
d, R = 768, 64
record_bytes = 4 * d + 4 + 4 * R
assert record_bytes == 3332 and record_bytes <= 4096
print("alpha=1.0 neighbors:", robust_prune(p, candidates, alpha=1.0))
print("alpha=1.6 neighbors:", robust_prune(p, candidates, alpha=1.6))
print("SSD node record bytes:", record_bytes, "(fits in one 4096B page)")

    Compare HNSW and DiskANN / Vamana across memory tiers

    Why graph design changes when the index moves from RAM to NVMe SSD.
    Design choiceIn-memory HNSWDiskANN / Vamana
    Graph layersNested multi-layer skip-graph hierarchySingle-layer graph with $\alpha > 1$ long-range edges
    Entry pointRandomly promoted top-layer nodeGlobal corpus medoid $s$ (plus optional cached entry points)
    Neighbor scoring during routingFull vector distances in RAMRAM-resident PQ lookup tables; exact float32 read only for expanded beam nodes
    Deletions and updatesOften tombstone flags (`mark_deleted`) until rebuildFreshDiskANN consolidates streaming inserts and runs local $\alpha$-pruning repairs

    Notice how DiskANN avoids a separate final disk pass for reranking: every time the beam search expands one of its $W$ frontier nodes from SSD to read its outgoing links, that same 4 KB SSD page already delivers the node's uncompressed float32 vector for exact scoring.

    Check the operating assumptions

    Why does DiskANN keep PQ codes in RAM if full-precision vectors are already on SSD?

    Expanding one node exposes up to R = 64 neighbor IDs. Fetching 64 separate 4 KB SSD pages just to decide which neighbor is closest to the query would turn every graph hop into 64 random disk reads. RAM PQ codes score all 64 neighbors in nanoseconds so the SSD only reads the 1 to W best nodes per hop.

    What happens if the RAM PQ codes are too coarse (for example, 4 bytes per 768-d vector)?

    Even though exact float32 vectors are read for every expanded node, the beam search relies on PQ distances to decide which nodes to expand next. Severely distorted PQ distances misdirect the beam away from the true neighborhood, so the right SSD pages are never fetched.

    When can a single-node SSD record exceed the 4 KB page boundary?

    If a 1,536-dimensional or 3,072-dimensional embedding is stored in float32 (6,144 or 12,288 bytes before neighbor IDs), a node record spans 2 to 4 SSD pages. Storing FP16 or SQ8 coordinates in the disk record or aligning to 8 KB / 16 KB blocks keeps each hop contiguous.
