    GGUF and K-quants: format versus quantizer

    October 2026 · 5 min read

    GGUF is a container format, not a single quantization algorithm. It describes metadata, tensor information, and tensor payloads so a compatible runtime can load a model. Those payloads can use floating-point or quantized tensor types. Asking whether “GGUF is better than AWQ” mixes a packaging choice with a method for selecting approximated weights.

    Separate three layers of the artifact

    • Container: GGUF records key-value metadata, tensor names, dimensions, types, and data offsets. Metadata can include tokenizer and architecture information.
    • Tensor encoding: a ggml type defines how a block of values and its auxiliary fields reconstruct a tensor.
    • Conversion policy: a model-level quantization preset decides which tensor types to use across the model. Not every tensor must have the same width.

    A filename such as Q4_K_M usually describes a conversion preset, not a distinct per-weight scalar datatype. The medium preset can assign higher-precision encodings to selected tensors. Inspect the tensor types and the converter revision rather than treating the filename as proof that every parameter occupies exactly four bits.

    What a K-quant block adds

    K-quants use superblocks containing smaller groups, with compactly encoded local quantization parameters. The exact structure depends on the type. For the standard 256-value Q4_K layout, eight groups of 32 weights share local six-bit scale and minimum parameters, together with two FP16 superblock factors. Four-bit weight codes provide the main payload.

    The corresponding reconstruction has the structure

    $$\widehat w_{g,i}=d\,s_g\,q_{g,i}-d_{\min}\,m_g.$$

    The fields $s_g$ and $m_g$ are compact local parameters, while $d$ and $d_{\min}$ are superblock factors. This is why “four-bit” does not fully describe the block. For a toy decoded group with $d=0.01$, $s_g=3$, $d_{\min}=0.02$, $m_g=2$, and code $q=7$, the reconstruction is $0.01(3)(7)-0.02(2)=0.17$. Field packing and parameter estimation are separate implementation details.

    Count the auxiliary bytes

    In that 256-value layout, weight codes require 128 bytes, packed scale/minimum fields require 12 bytes, and the two FP16 factors require 4 bytes. Thus the block takes 144 bytes, or $144(8)/256=4.5$ bits per weight. That is a property of this block layout, not a complete model average: mixed tensor types, unquantized tensors, alignment, and metadata change the file total.

    Follow dequantize_row_q4_K in the source to understand decoding, and the corresponding quantization routines to understand how parameters are chosen. Different types have different formulas; extrapolating Q4_K's minimum term to every K-quant would be incorrect. Source on the main development branch can evolve, so reproducible experiments should record a commit.

    The container does not prescribe calibration

    Some conversion paths derive quantization parameters directly from weights. Others can use an importance matrix from representative activation data to weight reconstruction error where supported. Neither follows merely from the .gguf extension. Record whether an importance matrix was used, its data distribution, and the actual quantizer settings, then evaluate a held-out workload.

    Loading and computing are different promises

    llama.cpp can execute across CPU and accelerator backends, but support and optimized kernels vary by tensor type and backend. A runtime may use floating-point or quantized intermediate operands internally; GGUF alone specifies no universal activation precision. CPU instruction sets, GPU offload, memory bandwidth, context length, and KV-cache settings all affect results.

    Can I infer speed or quality from Q4_K_M alone?

    No. Keep the model revision, converter commit, tensor-type mixture, calibration choices, backend, and workload with your measurements. The preset name is a starting point for inspection, not an evaluation result.
