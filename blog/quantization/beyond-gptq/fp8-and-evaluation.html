    FP8 and evaluation: match the format to the workload

    October 2026 · 5 min read

    Eight-bit floating point and eight-bit integers use the same number of payload bits but distribute their reconstruction values differently. Integer grids have approximately constant absolute spacing within a scale group. Floating-point spacing grows with magnitude. FP8 therefore offers a different range-versus-resolution tradeoff, not a guarantee of better accuracy or native acceleration everywhere.

    Spend the bits on range or precision

    The FP8 formats paper proposes E4M3 and E5M2: one sign bit, then respectively four or five exponent bits, with three or two fraction bits. Within the normal interval from 1 up to 2, E4M3 values are spaced by $0.125$; E5M2 values are spaced by $0.25$. An unscaled $1.30$ rounds to $1.25$ in both, while $1.40$ rounds to $1.375$ in E4M3 and $1.5$ in E5M2.

    The proposed E4M3 format has maximum finite magnitude 448 and does not represent infinity; E5M2 has maximum finite magnitude 57,344 and retains infinity representations. Those details describe the paper's encodings. Other variants use different special-value conventions, so a runtime's exact dtype must be checked rather than inferred from “FP8.”

    More exponent bits make E5M2 attractive for wider-ranging values, such as gradients in training; E4M3 offers finer precision and is used for forward operands in the paper's mixed-format approach. This is not a rule that every inference tensor requires E4M3, or that all FP8 training uses the same format assignment.

    An exponent does not remove scaling

    $$q=\operatorname{FP8}(x/s),\qquad \widehat x=sq.$$

    Here $s$ is an external reconstruction scale. If a tensor has maximum magnitude 1,000, mapping it into an E4M3 range can use $s=1000/448\approx2.23214$. The largest value then maps to 448, but smaller values must share that choice and may lose resolution or underflow. Real implementations need margin, special-value handling, and a policy for updating the scale.

    Static scaling can use calibration statistics; dynamic scaling derives scales during execution, sometimes using a history of observed maxima. More local scaling can improve numerical behavior while requiring additional metadata and compatible kernels. Record the granularity and policy. FP8 names a format family; it does not specify a complete calibration or execution algorithm.

    A controlled comparison

    Begin with a floating-point reference and hold its model revision, tokenizer, prompt template, and evaluation data fixed. Compare the candidate in the same runtime where possible, and document differences when that is impossible. Avoid evaluating only on the calibration examples.

    1. Numerics: check for clipping, underflow, NaNs, and layer-output drift on representative inputs. These diagnostics locate problems but do not replace task evaluation.
    2. Quality: measure held-out perplexity and relevant tasks, including coding, multilingual, or long-context cases when needed. Use fixed decoding settings and seeds for generated-output comparisons.
    3. Memory: separate checkpoint bytes from peak resident memory. Count scales, workspaces, activations, adapters if present, and the KV cache.
    4. Execution: report prefill throughput or time to first token separately from decode throughput and per-token latency. Include input/output lengths, batch size, concurrency, device, backend, and warm-up policy.

    Prefill may expose large matrix-multiply opportunities, whereas low-batch decode can be constrained by weight traffic. Neither regime is universal: attention, cache traffic, and scheduling can change the bottleneck. Report measured results for the stated workload rather than inventing a speedup from the bit count.

    Choose the system, not the slogan

    Native FP8 support and efficient scaling kernels are hardware- and backend-dependent. Wider accumulation and floating-point non-matmul operations remain important. A weight-only four-bit model may address a memory constraint that W8A8 or FP8 does not; QLoRA addresses adapter-training memory instead. The right comparison begins with the constraint, then asks which supported numerical path meets the quality budget.

    What should a reproducible result include?

    The model and runtime revisions, exact tensor formats, scale policy, calibration data, evaluation settings, hardware, memory measurements, and separate prefill/decode results. “FP8 was faster” without that context is not a transferable conclusion.
