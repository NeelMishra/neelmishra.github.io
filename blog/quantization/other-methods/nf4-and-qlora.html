    NF4 and QLoRA: storage is not training precision

    October 2026 · 5 min read

    NF4 is a four-bit representation. QLoRA is a fine-tuning method that uses a quantized frozen base and trainable low-rank adapters. Neither name says that every forward operation, gradient, and optimizer state uses four bits.

    A nonuniform codebook

    An affine integer grid has uniformly spaced reconstructed values. NormalFloat4 (NF4) instead uses sixteen nonuniform codebook values, designed with normally distributed weights in mind, with an exactly representable zero. A four-bit code selects an entry; it is not a conventional floating-point number with independently interpreted exponent and mantissa fields.

    For a weight block, let $a=\max_i|w_i|$ and let $c_k$ be the normalized codebook entries. A simplified view of encoding and reconstruction is

    $$k_i=\operatorname{argmin}_k|w_i/a-c_k|,\qquad \widehat{w}_i=a\,c_{k_i}.$$

    Handle an all-zero block separately. For nonzero blocks, the codebook gives more resolution near its dense central region than a uniform grid. Block normalization and the real weight distribution matter: “designed for normal weights” is not a guarantee that every layer or architecture will prefer NF4.

    Double quantization compresses the scales

    Four-bit codes still need block scales. For example, a 64-weight block with a 32-bit scale pays another $32/64=0.5$ bits per weight, before other overhead. Double quantization compresses these quantization constants using a second quantizer and its own metadata. It does not mean applying the same four-bit rounding to the weights twice.

    The second quantizer can perturb the reconstructed scale, so it has an accuracy cost as well as a memory benefit. Report effective storage including both levels of constants instead of quoting only the four-bit payload.

    What QLoRA trains

    With our $C\times D$ weight layout, write a rank-$r$ adapter as $AB$, where $A$ is $C\times r$ and $B$ is $r\times D$. A simplified adapted layer is

    $$Y=X\widehat{W}+\frac{\lambda}{r}XAB.$$

    The quantized base reconstructs $\widehat{W}$ for computation and remains frozen. Gradients train the adapters and flow through the computation graph to other trainable components; they do not update the base's discrete four-bit codes. The forward compute dtype is a separate choice, commonly BF16 when supported. Adapter parameters, gradients, activations, and optimizer state are not all four-bit.

    QLoRA also introduces paged optimizers to manage memory spikes. Paging can help memory management, but it is not an unlimited-memory promise and does not eliminate activation memory. Sequence length, batch size, checkpointing, and which modules receive adapters still matter.

    Fine-tuning success is not a serving benchmark

    Evaluate the adapter together with the same quantized base used for training. Merging an adapter into dequantized weights and requantizing can introduce new error; test the merged artifact separately. A runtime might serve base-plus-adapter or a merged checkpoint, and those paths need not have the same memory or latency.

    Use QLoRA when the question is how to fit adapter fine-tuning into the memory budget. Use a separate serving evaluation to decide whether its resulting representation is suitable for production. It is not interchangeable with AWQ merely because both can use four-bit stored weights.

    Is QLoRA quantization-aware training?

    Not in the sense of updating the base model's weights under fake quantization. QLoRA learns adapters on a frozen quantized base; the next note covers training parameters with quantization simulation in the loop.
