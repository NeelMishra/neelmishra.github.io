    3. TurboQuant: theoretical limits, KV-cache compression, and vector search

    October 2026 · 5 min read

    In Part 1 and Part 2, we saw how TurboQuant rotates a unit vector, rounds each coordinate with a fixed lookup table ($\mathrm{TurboQuant}_{\mathrm{mse}}$), and spends $1$ bit on the residual to keep dot products unbiased ($\mathrm{TurboQuant}_{\mathrm{prod}}$). Two practical questions remain: how close is TurboQuant to the best possible quantizer, and how does it work inside a real LLM KV cache or vector database?

    Why every extra bit cuts squared error by 4x

    When we use $b$ bits per coordinate, our lookup table has $2^b$ buckets. Adding $1$ more bit doubles the number of buckets ($2^{b+1} = 2 \cdot 2^b$) and cuts the width of each bucket in half.

    Because rounding error is proportional to bucket width, cutting the bucket width by $2\times$ cuts the squared rounding error by $2^2 = 4\times$. Information theory (Shannon distortion-rate theory) proves that no quantizer of any kind — even an expensive multi-dimensional codebook — can beat this $1 / 4^b$ scaling on unit vectors:

    $$D_{\mathrm{mse}}^{\star}(b) \ge \frac{1}{4^b}, \qquad D_{\mathrm{prod}}^{\star}(b) \ge \frac{\lVert y \rVert_2^2}{d \cdot 4^b}.$$

    Comparing TurboQuant's actual error against $1 / 4^b$ shows that independent 1D lookup tables after a random rotation stay within a small constant factor ($1.45\times$ to $2.43\times$ for reconstruction) of the theoretical limit across all bit-widths:

    How TurboQuant compresses an LLM KV cache to 2.5 and 3.5 bits

    In a Transformer such as Llama-3.1-8B-Instruct, each attention head has $d = 128$ channels. In practice, a few channels carry much larger values than the rest. Instead of rotating all $128$ channels together, TurboQuant splits each head into $32$ outlier channels and $96$ regular channels and gives the outlier channels $1$ extra bit:

    • $2.5$-bit recipe: quantize the $32$ outlier channels at $3$ bits and the $96$ regular channels at $2$ bits. The average codebook cost is $(32 \times 3 + 96 \times 2) / 128 = 2.25$ bits per channel. Storing two FP16 norms per $128$-channel block ($32 / 128 = 0.25$ bits per channel) brings the total to $2.5$ bits per channel.
    • $3.5$-bit recipe: quantize the $32$ outlier channels at $4$ bits and the $96$ regular channels at $3$ bits ($(32 \times 4 + 96 \times 3) / 128 = 3.25$ bits), plus $0.25$ bits for the norms, for a total of $3.5$ bits per channel.

    At $3.5$ bits per channel — more than a $4.5\times$ memory reduction over FP16 — TurboQuant matches the uncompressed model's LongBench score ($50.06$) and achieves $0.997$ needle-in-a-haystack recall up to $104\text{k}$ tokens.

    Why vector search needs zero indexing time

    Traditional vector databases compress embeddings using Product Quantization (PQ). Before PQ can compress a single vector, it must run $k$-means clustering across the database to train custom codebooks, which takes minutes to hours whenever new documents arrive.

    Because TurboQuant rotates every vector into the same known bell curve, its lookup table is fixed in advance. Indexing a new batch of vectors requires only a fast rotation and a table lookup — taking about $0.001\text{ seconds}$ instead of hundreds of seconds of $k$-means training, while beating PQ and RabitQ on top-$k$ recall at $2$ to $4$ bits per dimension.

    When to use each method

    • Use $\mathrm{TurboQuant}_{\mathrm{mse}}$ when you want to reconstruct the vector $\tilde{x}$ itself with minimum squared error.
    • Use $\mathrm{TurboQuant}_{\mathrm{prod}}$ when compressed vectors are consumed by dot products $\langle y, \tilde{x} \rangle$ (attention scores in a KV cache or similarity scores in vector search) at $2$ to $4$ bits.
    • Use PolarQuant when you want an angle-based lookup table that avoids storing per-block scale factors and runs at $3.5\text{--}3.9$ bits per coordinate.
