    TurboQuant: rotate the vector, round, then fix the dot product

    October 2026 · 4 min read

    When a language model generates a long reply, it saves a key vector and a value vector for every token it has seen. This growing memory is the KV cache. Vector search engines face the same storage problem when holding millions of embedding vectors.

    Unlike model weights, which are fixed before serving, KV-cache vectors are created live during generation. We need to compress each vector into $2$ to $4$ bits per number on the fly, without pausing to train a custom lookup table or storing extra scale numbers for every small group of coordinates.

    Google's TurboQuant family — built from PolarQuant, QJL, and TurboQuant — solves this in four simple steps:

    1. Save the length once: store the vector's overall length $\lVert x \rVert_2$ as a single number and divide $x$ by it, so the vector has length $1$.
    2. Rotate to spread out spikes: multiply the unit vector by a fixed random rotation matrix $\Pi$. Rotation keeps lengths and dot products exactly the same, but spreads any huge outlier evenly across all coordinates.
    3. Round with one fixed lookup table ($\mathrm{TurboQuant}_{\mathrm{mse}}$): after rotation, every coordinate follows the same bell-shaped distribution. A single precomputed lookup table rounds each coordinate without needing per-block scale factors.
    4. Spend 1 bit on the leftover error ($\mathrm{TurboQuant}_{\mathrm{prod}}$): rounding slightly shrinks the vector and makes dot products too small. Saving $1$ sign bit per coordinate of the leftover error (using QJL) removes this bias.

    Two goals: reconstruct the vector, or preserve its dot product

    Let $x$ be a vector of $d$ numbers (for example, $d = 128$ in one attention head), and let $\tilde{x}$ be the compressed vector after we quantize $x$ to $b$ bits per coordinate. Depending on how $\tilde{x}$ is used, we care about one of two errors:

    $$\text{Reconstruction error: }\ \lVert x - \tilde{x} \rVert_2^2 = \sum_{j=1}^{d} (x_j - \tilde{x}_j)^2, \qquad \text{Dot-product error: }\ \bigl(\langle y, x \rangle - \langle y, \tilde{x} \rangle\bigr)^2.$$

    Here $y$ is a query vector and $\langle y, x \rangle = \sum_{j=1}^{d} y_j x_j$ is the dot product used to compute attention scores. Part 2 shows why a quantizer designed only for reconstruction error systematically makes $\langle y, \tilde{x} \rangle$ too small, and how spending the last bit on the residual fixes it.

    The distinctions to keep straight

    • Weight quantization (GPTQ) versus KV-cache quantization (TurboQuant): GPTQ compresses fixed model weights once before deployment using calibration data. TurboQuant compresses new activation/key/value vectors live during inference with no calibration step.
    • Per-block scales versus one vector norm: standard $2$-bit quantizers save a 16-bit scale and 16-bit zero-point every $32$ numbers, which adds $1$ extra bit per number ($50\%$ overhead). TurboQuant rotates the vector so one length number covers all $d$ coordinates.
    • $\mathrm{TurboQuant}_{\mathrm{mse}}$ versus $\mathrm{TurboQuant}_{\mathrm{prod}}$: use $\mathrm{TurboQuant}_{\mathrm{mse}}$ when you want $\tilde{x}$ itself to be as close as possible to $x$. Use $\mathrm{TurboQuant}_{\mathrm{prod}}$ when you compute dot products $\langle y, \tilde{x} \rangle$ (such as attention scores or cosine similarity).
    • Cartesian lookup ($\mathrm{TurboQuant}_{\mathrm{mse}}$) versus polar angles (PolarQuant): both start by rotating the vector. $\mathrm{TurboQuant}_{\mathrm{mse}}$ rounds the rotated coordinates directly; PolarQuant converts pairs of coordinates into angles first.

    A small result you can check by hand

    In the worked 4-number example, we take a key vector $x = [0.9, -0.3, 0.3, 0.1]$ (where the first number is a large spike) and a query vector $y = [0.7, -0.5, 0.5, 0.1]$. Their true dot product is $\langle y, x \rangle = 0.94$.

    Rotating $x$ and rounding to $1$ bit shrinks the dot product to $0.5585$. Adding the $1$-bit QJL correction on the leftover error brings the dot product back to $0.9906$ on our single test matrix, and to $0.9408$ on average across $40{,}000$ random draws. You can run python3 tools/check_turboquant.py to verify every number in the series.
