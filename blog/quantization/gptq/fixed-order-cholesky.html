    Fixed order, and what is precomputed

    October 2026 · 8 min read

    The update formula is Optimal Brain Quantization. The loop is still: feed calibration data through the layer, store the MSE for each remaining row, quantize one row, and adjust the floating-point weights that are left. This note is the first schedule change: stop searching for the easiest row. That fixed order is what makes the inverse rows knowable before the first snap. The other two changes, lazy writes and Cholesky, are the next note.

    A fixed order is slightly worse and much cheaper

    OBQ always snaps the remaining weight with the smallest score. On a large, heavily parameterized layer the paper finds that this greedy pass is only a small improvement over any fixed order. The reason it gives is the one the video spends time on. Greedy search leaves the expensive weights until the end. By then few full-precision weights remain, so the compensation those hard weights needed is no longer available. You have traded a few early, easy snaps for a tail of error you cannot repair.

    GPTQ quantizes every row in the same order. Because $H_F$ depends only on the remaining input columns, that shared order means every row has the same free set $F$ and the same $H_F^{-1}$. The inverse update from equation (3) runs once per column, not once per weight. The cost moves from $O(d_{\text{row}}\cdot d_{\text{col}}^3)$ to $O(\max\{d_{\text{row}}\cdot d_{\text{col}}^2,\, d_{\text{col}}^3\})$, a factor of $\min(d_{\text{row}}, d_{\text{col}})$. On a transformer projection that factor is thousands, which is the "orders of magnitude" in the paper. It is an operation count, not the four GPU hours. The four hours are the measured end-to-end quantization of OPT-175B and BLOOM-176B.

    A known order also tells you, before the first snap, which inverse-Hessian entries column $q$ will need: the part of row $q$ from the diagonal to the right, in the matrix that still contains columns $q, q+1, \ldots$. You can prepare those entries instead of discovering them with an elimination step between columns. The video reads that as a GPU scheduling win: the kernel is not waiting on a serial elimination to learn what the next column requires. The paper reads it as the algebraic reason a triangular factor is enough.

    The authors' code has a later flag, actorder, that permutes columns by descending Hessian diagonal and then still walks left to right. That is not OBQ's greedy loop, and it is not Algorithm 1. If you see it in a config, it is a column permutation applied before the fixed pass.

    What is precomputed, and why that is fewer eliminations

    The object stored before the first snap is not a quantized weight. It is the inverse-Hessian row each column will read. Section 4 of the paper is this schedule. Use it with the layout warning from the video: the printed Hessian is $2XX^{\mathsf T}$ only after $X$ is $(\text{in},\text{tokens})$. A PyTorch activation is $(\text{tokens},\text{in})$. Transpose first, as add_batch does, and then Algorithm 1 applies. Form $2XX^{\mathsf T}$ on the untransposed tensor and you precompute a tokens-by-tokens matrix. Every later update is then in the wrong coordinates. The paper's objective line has that orientation slip. The precompute inherits it. The code that transposes first is the path that matches the printed algorithm.

    Two facts make the rows knowable before any weight moves. The order is fixed and shared, so when column $q$ is reached the free columns are $q,q+1,\ldots$ for every output row. You know that set before the first quant call. And $H_F=2X_F X_F^{\mathsf T}$ depends only on those input columns, not on $W$. The inverse row for column $q$ does not depend on which grid point column $q-1$ snapped to.

    What column $q$ actually reads is one row: row $q$ of the inverse of the Hessian on the still-free columns, from the diagonal to the right. Columns already quantized are absent from that row. Producing those rows one at a time is the Gaussian-elimination downdate: eliminate $0$, read the new row for column $1$, eliminate $1$, and so on. Cholesky of the full inverse writes every such row before the loop. The paper's difference is a scale. Elimination leaves the inverse's own row. Cholesky divides row $q$ by $\sqrt{[H^{-1}]_{qq}}$. That is why Algorithm 1 divides the weight error by the factor's diagonal, not by the inverse's diagonal.

    The checked three-weight inverse shows the scale. Row 0 of $H^{-1}$, from the diagonal right, is $(1.92250,-2.56343,-0.35974)$. The upper Cholesky factor of that same inverse has row $(1.38654,-1.84880,-0.25945)$. The first entry of the inverse divided by the first entry of the factor is $1.38654$, which is $\sqrt{1.92250}$. The stored row is the inverse row divided by the square root of its pivot. Zeros below the diagonal are the columns already out of the free set. That is the triangle on the video slide, with this matrix's own numbers rather than the slide's rounded illustration.

    The speedup from this storage is an operation count, and it is the sentence the video author said they would take on faith. OBQ gives each output row its own greedy order, so each row has its own sequence of free sets. The elimination runs $d_{\text{row}}\cdot d_{\text{col}}$ times. The cost is $O(d_{\text{row}}\cdot d_{\text{col}}^3)$. GPTQ has one order, so it builds one factor, $O(d_{\text{col}}^3)$, and applies each stored row to every output row, $O(d_{\text{row}}\cdot d_{\text{col}}^2)$. The cost is $O(\max\{d_{\text{row}}\cdot d_{\text{col}}^2,\, d_{\text{col}}^3\})$. The ratio is $\min(d_{\text{row}}, d_{\text{col}})$. A square $4096\times 4096$ projection shares the elimination 4096 ways. That factor is about 3.6 orders of magnitude in the elimination count. The paper's "more than three orders of magnitude" is this comparison with OBQ, not a claim that GPTQ is 1000 times faster than round-to-nearest. The measured clock for OPT-175B and BLOOM-176B is still about four GPU hours.

    The inverse rows also have no serial dependence on the snaps. Column $q$'s stored row depends on the free-set, which the order fixes, and on $X$, which the calibration pass fixes. A kernel that quantizes column $q$ loads that row. It does not wait for an elimination that has to finish after column $q-1$. The weight update is still serial. Rounding column $q$ uses $W$ after columns $0,\ldots,q-1$ have been compensated. The video considers turning the whole problem parallel if inversion were free. That would be true of the inverse rows. It is not true of $W$. The paper does not quantize columns independently. It precomputes $H^{-1}$ and still walks columns in order.

    Do not file the lazy batch under this precompute. The batch changes when the weight matrix is written. It does not reduce the elimination count. The next note is that other speedup.
