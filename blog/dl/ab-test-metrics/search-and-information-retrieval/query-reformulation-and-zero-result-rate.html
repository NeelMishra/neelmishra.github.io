    Query Reformulation Rate (QRR), Zero-Result Rate (ZRR) & Autocomplete Keystroke Savings

    October 2026 · Query Understanding, Recall & Typeahead Evaluation

    Ranking models (Stage-2 / Stage-3 rerankers) can only order candidates that Stage-0 Query Understanding (spell correction, synonym expansion, query rewriting, autocomplete) and Stage-1 Lexical + Dense Retrieval successfully surface. When query understanding or retrieval fails, users experience three direct symptoms: they type more characters than necessary (low Keystroke Savings $\text{KSS}$), hit empty or near-empty SERPs (high Zero-Result Rate $\text{ZRR}$), and manually rewrite their own queries in frustration (high Query Reformulation Rate $\text{QRR}$).

    1. Query Reformulation Rate (QRR): Lexical & Semantic Formulations

    When a search engine fails to understand a user's query $q_i$—due to a typo, vocabulary mismatch (searching "cardiomegaly" vs. "enlarged heart"), overly narrow attributes, or poor ranking—the user often issues a modified query $q_{i+1}$ moments later. Query Reformulation Rate ($\text{QRR}$) measures the proportion of queries that are immediately followed by a dissatisfied, same-intent rewrite.

    Measuring Same-Intent Query Similarity $\operatorname{Sim}(q_i, q_{i+1})$

    Not every consecutive query pair $(q_i, q_{i+1})$ in a session is a reformulation: a user who finishes buying running shoes and then searches for protein powder is starting a new task. Conversely, a user who rewrites "macbook screen flickering" to "apple m3 display glitch" shares zero content words beyond implicit semantics, yet is clearly reformulating the exact same intent! We therefore define a hybrid similarity score combining three signals:

    1. Normalized Character Levenshtein Similarity (captures typo/spelling edits):
      $$S_{\text{edit}}(q_i, q_{i+1}) = 1 - \frac{d_{\text{Lev}}(q_i, q_{i+1})}{\max\bigl(|q_i|, |q_{i+1}|\bigr)} \in [0, 1]$$
      For example, $q_i = \text{"balenciaga snekers"}$ and $q_{i+1} = \text{"balenciaga sneakers"}$ has $d_{\text{Lev}} = 1$ and $S_{\text{edit}} = 1 - 1/19 = 0.947$.
    2. Token Jaccard / Containment Similarity (captures specification & generalization): Let $W(q)$ be the set of stemmed tokens in $q$. When a user adds or drops a qualifier (e.g., "wireless keyboard" $\to$ "wireless mechanical keyboard mac"), the Overlap Coefficient (Szymkiewicz–Simpson) and Jaccard index are:
      $$S_{\text{jaccard}}(q_i, q_{i+1}) = \frac{|W(q_i) \cap W(q_{i+1})|}{|W(q_i) \cup W(q_{i+1})|}, \qquad S_{\text{contain}}(q_i, q_{i+1}) = \frac{|W(q_i) \cap W(q_{i+1})|}{\min\bigl(|W(q_i)|, |W(q_{i+1})|\bigr)}$$
    3. Dense Bi-Encoder Semantic Cosine Similarity (captures synonym & paraphrase rewrites): Using the search engine's query embedding model $\mathbf{e}(q) \in \mathbb{R}^d$ ($\|\mathbf{e}(q)\|_2 = 1$):
      $$S_{\text{sem}}(q_i, q_{i+1}) = \mathbf{e}(q_i)^\top \mathbf{e}(q_{i+1})$$

    Formal Definition of Dissatisfied Query Reformulation Rate ($\text{QRR}$)

    We declare query $q_i$ to have suffered a dissatisfied reformulation ($R_i = 1$) if and only if:

    $$R_i = \mathbb{I}\bigl[\Delta t_{i,i+1} \le \tau_w\bigr] \cdot \mathbb{I}\!\left[\max\bigl(S_{\text{edit}},\, S_{\text{jaccard}},\, S_{\text{sem}}\bigr) \ge \gamma\right] \cdot \mathbb{I}\bigl[\neg\text{Satisfied}(q_i)\bigr]$$

    where $\Delta t_{i,i+1} = t(q_{i+1}) - t_{\text{last\_event}}(q_i) \le \tau_w$ (typically $\tau_w = 180\text{s}$), $\gamma$ is the calibrated threshold on each similarity scale (e.g. $S_{\text{edit}} \ge 0.70$ or $S_{\text{jaccard}} \ge 0.40$ or $S_{\text{sem}} \ge 0.75$), and $\neg\text{Satisfied}(q_i)$ verifies that $q_i$ had neither a long-dwell satisfied click ($d \ge 30\text{s}$) nor a terminal conversion action. The Query Reformulation Rate across all queries is then:

    $$\text{QRR} = \frac{\sum_{u=1}^N \sum_{q_i \in \mathcal{Q}_u} R_i}{\sum_{u=1}^N |\mathcal{Q}_u|}$$

    Why include $\mathbb{I}[\neg\text{Satisfied}(q_i)]$? Because in exploratory research or multi-attribute shopping, a user might search "sony wh-1000xm5 review", read a comprehensive review for $3\text{ minutes}$ (satisfied!), and then search "sony wh-1000xm5 vs bose quietcomfort ultra". That second query is a natural progression of a satisfied session, not a failure of query $q_i$.

    2. Zero-Result Rate (ZRR), Low-Recall Rate & The Fallback Trap

    Let $\mathcal{D}(q)$ denote the set of candidate documents or products returned by the retrieval pipeline for query $q$. The Zero-Result Rate ($\text{ZRR}$) and Low-Recall Rate ($\text{LRR}@k_{\min}$) are defined as:

    $$\text{ZRR} = \frac{1}{|\mathcal{Q}|}\sum_{q \in \mathcal{Q}} \mathbb{I}\bigl[|\mathcal{D}(q)| = 0\bigr], \qquad \text{LRR}@k_{\min} = \frac{1}{|\mathcal{Q}|}\sum_{q \in \mathcal{Q}} \mathbb{I}\bigl[|\mathcal{D}(q)| < k_{\min}\bigr]$$

    where $k_{\min}$ (typically $k_{\min} = 3$ or $5$) flags sparse pages that barely fill the top viewport.

    The Classic ML System Design Pitfall — "Gaming ZRR to Zero":

    Any engineer can reduce $\text{ZRR}$ from $4.2\%$ to $0.00\%$ overnight by switching boolean AND matching to OR matching, removing distance thresholds on vector ANN search, or returning top-selling popular items whenever $|\mathcal{D}(q)| = 0$. If you show irrelevant products on a previously empty page, $\text{ZRR}$ drops by $-100\%$, but Bad Abandonment and Pogo-Sticking skyrocket and user trust erodes!

    Measuring True Recall Quality: Rescued-Query Success Rate

    Whenever an experiment modifies query rewriting, spell correction, synonym expansion, or dense vector retrieval to reduce $\text{ZRR}$, you must evaluate the Null-Recovery / Fallback Success Rate alongside $\text{ZRR}$:

    $$\text{Rescued-Success-Rate} = \Pr\bigl(\text{SatClick}(q) \;\big|\; q \in \mathcal{Q}_{\text{rescued}}\bigr)$$

    In an online A/B test (or counterfactual interleaving shadow log where the Control retrieval pipeline is run in silent shadow mode on Treatment queries), identify the subset of Treatment queries $\mathcal{Q}_{\text{rescued}}$ that would have returned zero results under Control ($|\mathcal{D}_C(q)| = 0$ but $|\mathcal{D}_T(q)| > 0$). A healthy query-expansion or hybrid-retrieval launch achieves both:

    • $\Delta \text{ZRR} < 0$ (significant reduction in empty SERPs), and
    • $\text{Rescued-Success-Rate} \ge \tau_{\text{viable}}$ ( typically $\ge 20\%\text{–}35\%$ of rescued queries produce a satisfied click or conversion, with Pogo-Sticking below the guardrail ceiling).

    3. Autocomplete / Typeahead Metrics: Keystroke Savings (KSS) & Prefix MRR

    Search evaluation starts before the user presses Enter. As the user types a character prefix $p = c_1 c_2 \dots c_\ell$, the Query Autocomplete (QAC) model ranks a slate of $K$ candidate query completions $(s_1, s_2, \dots, s_K)$. How do we evaluate QAC models in online A/B tests?

    Keystroke Savings ($\text{KSS}$)

    Let $|q_{\text{final}}|$ be the character length of the submitted query $q_{\text{final}}$, and let $\ell_{\text{typed}}$ be the number of characters the user physically typed before clicking/selecting an autocomplete suggestion (if the user types the entire query without selecting a suggestion, $\ell_{\text{typed}} = |q_{\text{final}}|$). Keystroke Savings ($\text{KSS}$) measures the fraction of typing effort eliminated by the typeahead system:

    $$\text{KSS}(q) = \max\!\left(0,\; 1 - \frac{\ell_{\text{typed}}(q)}{|q_{\text{final}}(q)|}\right) \in [0, 1)$$

    For example, if a user wants to search "postgresql deadlock detection" ($29$ characters), types "postgres dead" ($\ell_{\text{typed}} = 13$ characters), and taps suggestion #1, then:

    $$\text{KSS}(q) = 1 - \frac{13}{29} = \frac{16}{29} \approx 55.17\%$$

    Prefix Reciprocal Rank & The "Autocomplete Steering" Guardrail

    Alongside $\text{KSS}$, autocomplete A/B tests track:

    • Autocomplete Engagement / Selection Rate ($\text{QAC-CTR}$): Fraction of submitted queries originating from a typeahead suggestion click rather than a raw Enter keystroke.
    • Selected-Suggestion Mean Reciprocal Rank ($\text{QAC-MRR}$): At the keystroke state where the user selects suggestion $s_r$ at rank $r \in \{1, \dots, K\}$, $\text{RR} = 1/r$ (or $0$ if no suggestion is selected).
    • Post-Autocomplete Session Success & Reformulation Guardrail: If a QAC ranker over-weights historical head-query popularity, a user typing "iphone 15 pro max camera l..." (intending "camera lens replacement") might prematurely tap "iphone 15 pro max camera specs" at rank $1$, boost $\text{KSS}$, immediately realize the SERP is wrong, and reformulate! Therefore, every QAC experiment must verify that Post-Autocomplete $\text{QRR}$ does not increase and overall Session Success Rate ($\text{SSR}$) is neutral or positive.

    4. Worked Numerical Example: Query Expansion + Autocomplete Upgrade

    Let us walk through a concrete 4-query session log comparing how $\text{KSS}$, $\text{QRR}$, and $\text{ZRR}$ are computed:

    Query $i$ Typed Prefix ($\ell_{\text{typed}}$) Submitted Query $q_i$ ($|q_i|$) Hits $|\mathcal{D}(q_i)|$ SERP Outcome Metric Contributions
    $q_1$ (t=0s) "pythn dataclss" ($14$) "pythn dataclss" ($14$, No QAC) $0$ Zero results ($0$ clicks) $\text{KSS}_1 = 0$, $\text{ZRR}_1 = 1$, $R_1 = 1$ (reformulated in $8\text{s}$, $S_{\text{edit}} = 14/16 = 0.875 \ge 0.70$)
    $q_2$ (t=8s) "python data" ($11$) "python dataclass default list" ($29$, QAC #1) $42$ Click Rank 2, Dwell = $6\text{s}$ (Bounce) $\text{KSS}_2 = 1 - 11/29 = 62.1\%$, $\text{ZRR}_2 = 0$, $R_2 = 1$ (unsatisfied + rewritten in $15\text{s}$, $S_{\text{sem}} = 0.84 \ge 0.75$)
    $q_3$ (t=23s) "dataclasses field" ($17$) "dataclasses default_factory python" ($34$, QAC #2) $18$ Click Rank 1, Dwell = $110\text{s}$ (Satisfied!) $\text{KSS}_3 = 1 - 17/34 = 50.0\%$, $\text{ZRR}_3 = 0$, $R_3 = 0$ (Satisfied!)
    $q_4$ (t=180s) "pytest fixt" ($11$) "pytest fixtures scope" ($21$, QAC #1) $65$ Click Rank 1, Dwell = $95\text{s}$ (Satisfied!) $\text{KSS}_4 = 1 - 11/21 = 47.6\%$, $\text{ZRR}_4 = 0$, $R_4 = 0$ (terminal query)

    Across these $4$ queries:

    • Average Keystroke Savings ($\overline{\text{KSS}}$): $\frac{0 + 0.6207 + 0.5000 + 0.4762}{4} = \mathbf{39.92\%}$ (or Character-Weighted $\text{KSS} = 1 - \frac{14+11+17+11}{14+29+34+21} = 1 - \frac{53}{98} = \mathbf{45.92\%}$).
    • Zero-Result Rate ($\text{ZRR}$): $1 / 4 = \mathbf{25.0\%}$.
    • Query Reformulation Rate ($\text{QRR}$): Queries $q_1$ and $q_2$ were both unsatisfied and immediately rewritten with high lexical/semantic similarity ($R_1 = 1, R_2 = 1, R_3 = 0, R_4 = 0$), yielding $\text{QRR} = 2 / 4 = \mathbf{50.0\%}$.

    5. Reference Python Implementation: QRR, ZRR & Keystroke Savings

    import numpy as np
from dataclasses import dataclass
from typing import List, Dict, Optional

def levenshtein_similarity(s1: str, s2: str) -> float:
    s1, s2 = s1.strip().lower(), s2.strip().lower()
    if not s1 and not s2:
        return 1.0
    m, n = len(s1), len(s2)
    dp = list(range(n + 1))
    for i in range(1, m + 1):
        prev, dp[0] = dp[0], i
        for j in range(1, n + 1):
            temp = dp[j]
            cost = 0 if s1[i - 1] == s2[j - 1] else 1
            dp[j] = min(dp[j] + 1, dp[j - 1] + 1, prev + cost)
            prev = temp
    return 1.0 - (dp[n] / max(m, n))

def token_jaccard(s1: str, s2: str) -> float:
    w1, w2 = set(s1.lower().split()), set(s2.lower().split())
    if not w1 or not w2:
        return 0.0
    return len(w1 & w2) / len(w1 | w2)

@dataclass
class QueryRecord:
    user_id: int
    timestamp_sec: float
    typed_chars: int
    submitted_query: str
    qac_selected_rank: int            # 0 if not selected, else 1..K
    num_results: int
    is_satisfied: bool                # Long-dwell click >=30s, terminal action, or Good Aband.
    embedding: Optional[np.ndarray] = None  # L2-normalized query vector

def compute_qrr_zrr_kss_metrics(
    records: List[QueryRecord],
    reformulation_window_sec: float = 180.0,
    edit_thresh: float = 0.70,
    jaccard_thresh: float = 0.40,
    sem_thresh: float = 0.75,
    low_recall_k: int = 3,
) -> Dict[str, float]:
    # Sort each user's queries chronologically
    by_user: Dict[int, List[QueryRecord]] = {}
    for r in records:
        by_user.setdefault(r.user_id, []).append(r)

    total_q = 0
    zrr_count = 0
    low_recall_count = 0
    qrr_count = 0
    kss_values = []
    qac_mrr_values = []

    for u, q_list in by_user.items():
        q_list.sort(key=lambda x: x.timestamp_sec)
        for i, q in enumerate(q_list):
            total_q += 1
            q_len = max(len(q.submitted_query), 1)
            kss = max(0.0, 1.0 - (q.typed_chars / q_len))
            kss_values.append(kss)
            qac_mrr_values.append(1.0 / q.qac_selected_rank if q.qac_selected_rank > 0 else 0.0)

            if q.num_results == 0:
                zrr_count += 1
            if q.num_results < low_recall_k:
                low_recall_count += 1

            # Check if q_i was followed by a dissatisfied same-intent reformulation q_{i+1}
            if (not q.is_satisfied) and (i + 1 < len(q_list)):
                q_next = q_list[i + 1]
                dt = q_next.timestamp_sec - q.timestamp_sec
                if 0 <= dt <= reformulation_window_sec:
                    s_edit = levenshtein_similarity(q.submitted_query, q_next.submitted_query)
                    s_jacc = token_jaccard(q.submitted_query, q_next.submitted_query)
                    s_sem = (
                        float(np.dot(q.embedding, q_next.embedding))
                        if (q.embedding is not None and q_next.embedding is not None)
                        else 0.0
                    )
                    if (s_edit >= edit_thresh) or (s_jacc >= jaccard_thresh) or (s_sem >= sem_thresh):
                        qrr_count += 1

    return {
        "Zero_Result_Rate": zrr_count / max(total_q, 1),
        "Low_Recall_Rate": low_recall_count / max(total_q, 1),
        "Query_Reformulation_Rate": qrr_count / max(total_q, 1),
        "Mean_Keystroke_Savings": float(np.mean(kss_values)) if kss_values else 0.0,
        "Autocomplete_MRR": float(np.mean(qac_mrr_values)) if qac_mrr_values else 0.0,
    }

    6. Self-Check & ML System Design Interview Exercises

    1. Suppose you deploy an automatic neural spell-corrector that silently rewrites typos (e.g., "iphne 16 case" $\to$ "iphone 16 case"). Which metrics should move, and what guardrail protects users querying rare proper nouns or code symbols?

    Expected positive shifts: Zero-Result Rate ($\text{ZRR}\downarrow$), Query Reformulation Rate ($\text{QRR}\downarrow$), and Session Success Rate ($\text{SSR}\uparrow$) should all improve substantially on misspelled queries.
    Critical guardrail: Spell-Recourse / "Search Instead For Original Query" Click Rate! When an aggressive spell-corrector rewrites a valid rare proper noun, medical term, part number, or code identifier (e.g., rewriting "kubectl" to "cube control"), users click the "Search instead for [original]" escape link or immediately re-type the original query in quotes. Tracking the Override / Recourse Rate acts as the precision guardrail for automatic query rewriting.

    2. Why can a successful Query Reformulation reduction ($\text{QRR}\downarrow$) make your per-query Conversion Rate ($\text{Orders} / \text{Queries}$) go UP while your per-session Conversion Rate ($\text{Orders} / \text{Sessions}$) stays flat?

    Suppose $1{,}000$ sessions result in $100$ orders in both Control and Treatment ($\text{Session CVR} = 10.0\%$ in both). If Treatment eliminates $300$ wasted reformulation queries so total queries drop from $2{,}000 \to 1{,}700$, then per-query conversion $\text{Orders} / \text{Queries}$ mechanically rises from $100 / 2{,}000 = 5.0\%$ to $100 / 1{,}700 = 5.88\%$ ($+17.6\%$ relative lift!) purely from shrinking the denominator. While reducing wasted queries is a genuine friction reduction (fewer queries per order), you must report Orders per User and Orders per Session so you don't mistake denominator contraction for incremental order volume.

    3. In an enterprise code search tool, you add a "Related Queries" chip bar at the top of the SERP. Suddenly, $\text{QRR}$ increases by $+6\%$, yet Session Success Rate also increases by $+2\%$. Why?

    Clicking a "Related Query" chip generates a new query $q_{i+1}$ that is lexically and semantically similar to $q_i$ within seconds—which triggers a naive $\text{QRR}$ detector! You must separate Manual Typed Reformulation Rate (a friction/failure signal where the user has to edit the search box themselves) from Assisted Query Refinement Clicks (clickable facet pills or query-refinement chips that help users narrow broad exploratory queries).
