    Code Copilot Acceptance Rate, 30-Minute Code Survival / Persistence & Keystroke Savings

    October 2026 · 10 min read

    In inline AI code completion (GitHub Copilot, Cursor Tab, Google's internal ML code completion), developers press `Tab` on roughly $25\%\text{–}35\%$ of ghost-text suggestions. Yet optimizing a model or invocation policy purely for Acceptance Rate ($\text{AR}$) is a textbook Goodhart's Law trap. Learn why $\text{AR}$ can be gamed by conservative triggering and trivial single-token completions, how to compute $k$-Minute Code Persistence / Survival Rate via Myers diff at $15/30\text{ minutes}$ or `git commit`, and how to combine Acceptance, Persistence, and Suggestion Length into Net Persisted Characters Per Coding Hour.

    1. Copilot Acceptance Rate ($\text{AR}$) & The Opportunistic Triggering Paradox

    Suppose developer $u \in \{1, \dots, N\}$ is randomized to an IDE copilot experiment arm. During active coding sessions, the copilot filtering/invocation classifier decides to display $S_u$ inline ghost-text suggestions (where each suggestion $j$ has character length $L_{u,j}$), of which the developer accepts $A_u \le S_u$ by pressing `Tab`. The aggregate Acceptance Rate ($\text{AR}$) is the ratio of user-clustered sums:

    $$\operatorname{AR} = \frac{\sum_{u=1}^N A_u}{\sum_{u=1}^N S_u}.$$

    Two Ways $\operatorname{AR}$ Is Routinely Gamed in A/B Tests:

    1. Invocation Suppression (The Denominator Trick): A selective invocation filter that suppresses suggestions whenever confidence $\hat{p}_{\text{accept}} < 0.60$ cuts shown suggestions $\sum_u S_u$ by $-70\%$. Because only ultra-obvious completions remain in the denominator, $\operatorname{AR}$ jumps from $28\%$ to $52\%$, while total accepted completions per coding hour $\frac{1}{N}\sum_u A_u$ plunges by $-45\%$!
    2. Horizon Truncation (Single-Line vs. Multi-Line Bias): Suggesting a single closing parenthesis `);` or `return None` has a $65\%$ acceptance rate, whereas suggesting a complete 12-line function body has a $22\%$ acceptance rate—even though one accepted 12-line function saves $30\times$ more developer time than a closing parenthesis!

    2. $k$-Minute Code Persistence / Survival Rate (Myers Diff & AST Retention)

    Even when a developer presses `Tab` to accept a multi-line suggestion, they frequently do so just to get the code into the buffer so they can read, edit, or immediately `Ctrl+Z` undo it when they spot a subtle bug. In empirical studies at GitHub and Google, $15\%\text{–}30\%$ of accepted code characters are deleted or rewritten within 30 minutes!

    For each accepted suggestion $j$ with initial inserted text $s_j^{(0)}$ (containing $|s_j^{(0)}|$ non-whitespace characters or AST tokens), the IDE extension snapshots the tracked text region at horizon $\Delta t \in \{5\text{m}, 15\text{m}, 30\text{m}, \text{git commit}\}$ to obtain the surviving region $s_j^{(\Delta t)}$. Using the Longest Common Subsequence ($\operatorname{LCS}$) / Myers diff algorithm, the character-level and token-level survival fraction for suggestion $j$ is:

    $$\pi_j(\Delta t) = \frac{\operatorname{LCS\_Length}\bigl(s_j^{(0)},\, s_j^{(\Delta t)}\bigr)}{\bigl|s_j^{(0)}\bigr|} \in [0, 1].$$

    Aggregating across all accepted suggestions $\mathcal{A}_u$ of user $u$ gives the Length-Weighted $k$-Minute Code Persistence Rate ($\text{CPR}_{\Delta t}$):

    $$\operatorname{CPR}_{\Delta t} = \frac{\sum_{u=1}^N \sum_{j \in \mathcal{A}_u} \operatorname{LCS\_Length}\bigl(s_{u,j}^{(0)},\, s_{u,j}^{(\Delta t)}\bigr)}{\sum_{u=1}^N \sum_{j \in \mathcal{A}_u} \bigl|s_{u,j}^{(0)}\bigr|}.$$
    • Immediate Undo / Rollback Rate ($\Delta t = 30\text{s}$): The fraction of accepted suggestions where $\pi_j(30\text{s}) < 0.20$ measures "Phantom Acceptances" (reflexive `Tab` followed by `Ctrl+Z` or backspace).
    • Pre-Commit Survival Rate: Measuring $\pi_j(\text{commit})$ when the developer stages changes for a pull request verifies that the AI-generated code passed local unit tests, type-checkers, and linter checks.

    3. Net Persisted AI Characters & Percentage of Committed Code Written by AI

    To unify trigger frequency, acceptance rate, completion length, and 30-minute survival into a single gaming-proof North Star metric normalized by active coding time $H_u$ (or total characters committed $C_u^{\text{total}}$), production copilot teams use two composite OECs:

    $$\operatorname{Persisted\ AI\ Chars\ / \text{Hour}} = \frac{\sum_{u=1}^N \sum_{j \in \mathcal{A}_u} \operatorname{LCS\_Length}\bigl(s_{u,j}^{(0)}, s_{u,j}^{(30\text{m})}\bigr)}{\sum_{u=1}^N H_u} = \underbrace{\frac{\bar{S}}{\bar{H}}}_{\text{Trigger Rate}} \times \underbrace{\operatorname{AR}}_{\text{Acceptance}} \times \underbrace{\bar{L}_{\text{acc}}}_{\text{Mean Length}} \times \underbrace{\operatorname{CPR}_{30\text{m}}}_{\text{Persistence}},$$
    $$\operatorname{AI\ Code\ Share\ (\%\ of\ Committed\ Code)} = \frac{\sum_{u=1}^N \text{Persisted AI Characters in Commits}_u}{\sum_{u=1}^N \text{Total Net Characters Added in Commits}_u}.$$

    Notice how every gaming loophole is closed:

    • If the model triggers too rarely, $\bar{S}/\bar{H}$ drops.
    • If the model spams noisy suggestions, $\operatorname{AR}$ drops (and cognitive-load guardrails like Explicit `Esc` Dismissal Rate spike).
    • If the model only suggests 2-character tokens, $\bar{L}_{\text{acc}}$ drops.
    • If the model suggests plausible-looking buggy code that developers have to delete 5 minutes later, $\operatorname{CPR}_{30\text{m}}$ drops!

    Worked numerical example: Short-Line vs. Full-Block Completion Models

    Over $1{,}000$ active developer coding hours per arm:

    • Control ($C$, conservative single-line completion): Triggers $80$ times/hour, $\operatorname{AR}_C = 35.0\%$ ($28.0$ acceptances/hour), mean accepted length $\bar{L}_C = 25\text{ chars}$, $30\text{-min}$ persistence $\operatorname{CPR}_{30\text{m}, C} = 88\%$.
      • $\text{Persisted AI Chars / Hour}_C = 80 \times 0.35 \times 25 \times 0.88 = \mathbf{616.0\text{ chars/hr}}$.
    • Treatment ($T$, multi-line block completion): Triggers $70$ times/hour, $\operatorname{AR}_T = 27.0\%$ ($18.9$ acceptances/hour—a $-8.0\text{ pp}$ drop in raw Acceptance Rate!), but mean accepted length is $\bar{L}_T = 65\text{ chars}$ and $30\text{-min}$ persistence is $\operatorname{CPR}_{30\text{m}, T} = 80\%$.
      • $\text{Persisted AI Chars / Hour}_T = 70 \times 0.27 \times 65 \times 0.80 = \mathbf{982.8\text{ chars/hr}}$ (a $+59.5\%$ gain in persisted code velocity!).

    4. Python Implementation: LCS Code Persistence, AI Code Share & Delta Method SE

    import difflib
import numpy as np
from scipy import stats

def compute_lcs_persistence(initial_snippet: str, surviving_snippet: str) -> tuple[int, int]:
    """
    Computes non-whitespace character length of initial snippet and LCS surviving characters.
    """
    s0 = "".join(initial_snippet.split())
    s1 = "".join(surviving_snippet.split())
    if not s0:
        return 0, 0
    matcher = difflib.SequenceMatcher(None, s0, s1)
    kept = sum(block.size for block in matcher.get_matching_blocks())
    return len(s0), kept

def evaluate_copilot_ab(
    shown_u: np.ndarray, accepted_u: np.ndarray,
    accepted_chars_u: np.ndarray, persisted_30m_chars_u: np.ndarray,
    coding_hours_u: np.ndarray
):
    """
    Computes user-clustered Acceptance Rate (AR), 30-Minute Code Persistence Rate (CPR_30m),
    and Persisted AI Characters per Coding Hour with Delta Method standard errors.
    """
    ar = float(np.sum(accepted_u) / np.sum(shown_u))
    cpr_30m = float(np.sum(persisted_30m_chars_u) / np.sum(accepted_chars_u))
    persisted_per_hr = float(np.sum(persisted_30m_chars_u) / np.sum(coding_hours_u))

    # Delta method linearized residual for Persisted Chars / Coding Hour
    z_u = (persisted_30m_chars_u - persisted_per_hr * coding_hours_u) / np.mean(coding_hours_u)
    se_persisted_hr = float(np.std(z_u, ddof=1) / np.sqrt(len(z_u)))

    return {
        "Acceptance_Rate_%": round(100 * ar, 2),
        "Persistence_30m_%": round(100 * cpr_30m, 2),
        "Mean_Accepted_Len_Chars": round(float(np.sum(accepted_chars_u) / np.sum(accepted_u)), 1),
        "Persisted_Chars_Per_Hour": round(persisted_per_hr, 2),
        "Persisted_Chars_Per_Hour_SE": round(se_persisted_hr, 2),
    }

if __name__ == "__main__":
    s_init = "def calc_discount(price, rate):\n    return price * (1.0 - rate)\n"
    s_30m  = "def calc_discount(price: float, rate: float) -> float:\n    return round(price * (1.0 - rate), 2)\n"
    init_len, kept_len = compute_lcs_persistence(s_init, s_30m)
    print(f"Snippet LCS Persistence: {kept_len}/{init_len} = {100*kept_len/init_len:.1f}%")

    rng = np.random.default_rng(77)
    N = 2_000
    hrs = rng.gamma(4.0, 2.0, N)
    shown = rng.poisson(75 * hrs)
    acc = rng.binomial(shown, 0.30)
    acc_chars = acc * rng.lognormal(3.6, 0.4, N)
    pers_chars = acc_chars * rng.beta(8.0, 2.0, N)
    print("Copilot Telemetry Summary:", evaluate_copilot_ab(shown, acc, acc_chars, pers_chars, hrs))

    5. Self-Check Questions

    Why does increasing IDE ghost-text debounce latency from $150\text{ ms}$ to $450\text{ ms}$ often increase Acceptance Rate ($\text{AR}$) while decreasing total AI-assisted code written?

    Because at $450\text{ ms}$ latency, fast typists have already typed the next several characters before the suggestion arrives, causing the IDE client to cancel/suppress the stale completion before rendering it. Only developers who have paused and are actively waiting for help ever see a rendered suggestion—creating severe denominator selection bias in $\text{AR} = N_{\text{accepted}}/N_{\text{shown}}$. Always normalize by total typing opportunities or active coding hours!

    What downstream engineering guardrail metrics should be tracked on pull requests in enterprise Copilot deployments to ensure higher AI Code Share does not degrade codebase health?

    Track CI/CD First-Attempt Build & Test Pass Rate, PR Review Turnaround / Revision Cycles, Static Analysis / Security Vulnerability Flag Rate, and 14-Day Code Churn (re-editing or reverting recently merged lines).
