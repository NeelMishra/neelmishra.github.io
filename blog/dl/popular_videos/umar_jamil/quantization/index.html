    Quantization explained: from integer grids to PTQ and QAT

    October 2026 · Full lecture notes · 4 interactive labs · PyTorch examples

    Follow the original lesson

    This post follows Umar Jamil's Quantization explained with PyTorch: Post-Training Quantization, Quantization-Aware Training (50:54). The chapter links come from the video's description; the explanations follow his slides and four accompanying notebooks. The prose, diagrams, and small worked examples here are original, not a transcript.

    The route stays with this lecture: number representation, affine quantization, calibration, integer arithmetic, range selection, granularity, PTQ, and QAT. The downloadable code uses the same MNIST network shape as his demonstration.

    A quantized value is an integer code with a conversion rule. The integer alone does not tell you the original weight or activation. Keep the code, its scale, and its zero point together:

    $$\widehat{x}=s(q-z).$$

    Most of the lesson is about choosing $s$ and $z$, using those codes in a layer, and limiting the error introduced by this conversion. If the notation gets crowded, return to that equation.

    1. Why spend fewer bits on a model?

    Video: 01:10 · Slides 4 and 5

    Umar starts with the storage bill. A model with seven billion parameters needs $7\times10^9\times4=28\times10^9$ bytes for FP32 parameters. That is 28 GB in decimal units, before accounting for activations or other runtime memory. Storing the same number of weight codes in eight bits takes 7 GB, plus the scales, zero points, biases, and any values left in higher precision.

    That is a fourfold reduction in the raw weight payload. It is not automatically a fourfold reduction in the complete model file, peak memory, or inference time. Serialization has overhead, and inference still needs intermediate tensors.

    The other motivation is computation. Hardware with efficient low-precision kernels can read fewer bytes and perform integer multiply-accumulate operations cheaply. This matters on the small devices Umar discusses. The benefit depends on the available kernels and workload: converting a tensor to INT8 does not, by itself, make a floating-point implementation run faster.

    The trade: use a smaller set of representable values, accept some numerical error, and check whether the model's task accuracy remains acceptable. The goal is useful inference, not merely a smaller dtype.

    2. What a fixed number of bits can represent

    Video: 03:42 · Slides 7 and 8

    With $b$ bits there are $2^b$ possible bit patterns. An unsigned integer assigns them to $0,\ldots,2^b-1$. Three bits can encode eight numbers; eight bits can encode 256.

    Signed two's-complement integers use the most significant bit with a negative place value. For bits $u_{b-1},\ldots,u_0$,

    $$v=-u_{b-1}2^{b-1}+\sum_{i=0}^{b-2}u_i2^i.$$

    For example, the eight-bit pattern 11111101 represents $-128+64+32+16+8+4+1=-3$. The signed eight-bit range is $[-128,127]$, while the unsigned range is $[0,255]$. Two's complement has one representation of zero.

    This unequal signed range will matter when we build a symmetric quantizer. To use equal positive and negative endpoints, Umar's slides reserve -128 and use $[-127,127]$.

    Python's ordinary int can grow to use more storage for large values. That does not mean an INT8 tensor element can grow beyond eight bits. Accelerated tensor operations use fixed-width dtypes, so casting an out-of-range value is not a substitute for clipping it.

    3. Why a float has an exponent

    Video: 07:25 · Slide 9

    Binary fractions use negative powers of two, just as decimal fractions use negative powers of ten. The number $0.15625$ is $0.00101_2$, which can be written as $1.01_2\times2^{-3}=1.25\times2^{-3}$.

    For a normal FP32 value with sign bit $\sigma$, stored exponent $E$, and fraction bits $f_i$, the value is

    $$(-1)^\sigma\,2^{E-127}\left(1+\sum_{i=1}^{23}f_i2^{-i}\right).$$

    For $0.15625$, $\sigma=0$, $E=124$, and the fraction contributes $2^{-2}=0.25$. The leading 1 is implicit for normal numbers. Zero, subnormal values, infinities, and NaNs use special exponent cases; the formula above is not their decoding rule.

    Floating-point spacing changes with the exponent. Uniform integer quantization instead uses one fixed step size within a selected range. An INT8 code can represent a fractional weight because the scale supplies the units. The stored integer need not resemble the weight's ordinary rounded decimal value.

    4. Where quantization enters a neural network

    Video: 09:16 · Slides 11 to 13

    A linear layer computes $Y=XW+B$. Here $X$ is the input activation, $W$ contains learned weights, and $B$ contains biases. Quantization can change the representation of the weights and activations used in this calculation.

    That slide notation uses an input-by-output matrix $W$. PyTorch stores Linear.weight in output-by-input order instead, so its forward calculation is $XW_{\text{stored}}^\top+B$. The dot products are the same; the storage layout is transposed.

    Each tensor may have a different scale and zero point. Consequently, the result of multiplying two integer codes is not automatically a correctly encoded output activation. We will derive that rescaling in the multiply-accumulate section.

    Dequantization returns a floating-point approximation. If several original values chose the same integer code, that code cannot tell us which original value it came from. No conversion back to FP32 restores those lost differences.

    5. Derive the asymmetric quantizer

    Video: 15:38 · Slides 15 and 16

    Let the selected real interval be $[\beta,\alpha]$, with $\beta\leq0\leq\alpha$. For an unsigned $b$-bit quantizer, the codes run from $q_{\min}=0$ to $q_{\max}=2^b-1$. There are $2^b$ codes but only $2^b-1$ gaps between the endpoints.

    The scale is the amount of real-number distance covered by one integer step:

    $$s=\frac{\alpha-\beta}{2^b-1}.$$

    We also need the code that represents real zero. It is called the zero point, $z$. Before rounding, mapping $\beta$ to code zero suggests $z=-\beta/s$. The stored zero point must be an integer in the code range:

    $$z=\operatorname{clip}\!\left(\operatorname{round}(-\beta/s),\,0,\,2^b-1\right).$$

    Now divide a value by the scale, round to an integer step, shift by the zero point, and clip to the allowed codes:

    $$q=\operatorname{clip}\!\left(\operatorname{round}(x/s)+z,\,0,\,2^b-1\right),\qquad \widehat{x}=s(q-z).$$

    The name asymmetric means the real interval need not be centered on zero. It does not mean unequal spacing: neighboring reconstructed values are still exactly $s$ apart.

    A small grid you can calculate by hand

    Use four bits so the codes are easy to see. Choose $[\beta,\alpha]=[-1,2]$. Then $q_{\max}=15$, $s=3/15=0.2$, and $z=5$. For $x=0.86$,

    $$q=\operatorname{round}(0.86/0.2)+5=4+5=9,\qquad \widehat{x}=0.2(9-5)=0.8.$$

    Code zero reconstructs to $-1$. Real zero is code five. Padding a quantized activation with literal code zero would therefore insert $-1$, not silence. Using the zero point for padding is one reason exact representation of real zero matters.

    Endpoint rounding and positive-only tensors

    Once $z$ is rounded, the actual reconstructed endpoints are $s(0-z)$ and $s(q_{\max}-z)$. They can differ slightly from the selected $\beta$ and $\alpha$. Zero remains exact because $s(z-z)=0$.

    If all observed values are positive, extend the interval to include zero before computing the scale. Likewise, extend a negative-only interval up to zero. The formulas here assume that invariant. The downloadable example also handles an all-zero tensor with a positive scale instead of dividing by zero.

    Here and in the code, round uses ties-to-even, as torch.round does. Runtime rounding rules and floating-point arithmetic near an exact half-step can affect boundary cases. The worked values above avoid those ties.

    6. Symmetric quantization removes the offset

    Video: 18:34 · Slide 17

    Choose $A=\max_i|x_i|$ and a real interval $[-A,A]$. With the symmetric signed convention used in the slides, $Q=2^{b-1}-1$, the codes run from $-Q$ to $Q$, and the zero point is zero:

    $$s=\frac{A}{Q},\qquad q=\operatorname{clip}\!\left(\operatorname{round}(x/s),-Q,Q\right),\qquad \widehat{x}=sq.$$

    For our four-bit example, $A=2$, $Q=7$, and $s=2/7\approx0.285714$. The grid covers $[-2,2]$, even though our smallest input is only $-1$. The extra unused negative range makes the spacing wider than the asymmetric grid's $0.2$.

    For distributions close to zero-centered, symmetric quantization can be a good fit and avoids a weight zero-point correction. A strongly one-sided activation, such as a ReLU output, can use more of the available codes with an asymmetric range. Neither choice guarantees a lower model loss; the distribution and the layer's sensitivity matter.

    Separate the dtype from the quantizer's convention. INT8 can store -128. Reserving that code is a symmetric-grid choice, not a hardware limitation. Library quantizers may use a different signed range; check their $q_{\min}$, $q_{\max}$, and qscheme.

    7. Quantize, dequantize, then measure the error

    Video: 20:57 · Umar's from-scratch notebook

    Umar's first notebook makes a tensor, applies both quantizers, reconstructs the values, and compares mean squared error. This short PyTorch version does the same calculation for the asymmetric hand-worked example:

    import torch

x = torch.tensor([-1.0, -0.73, 0.0, 0.86, 1.72, 2.0],
                 dtype=torch.float64)
bits = 4
lo, hi = min(float(x.min()), 0.0), max(float(x.max()), 0.0)
qmax = 2**bits - 1
scale = (hi - lo) / qmax if hi != lo else 1.0
zero = max(0, min(qmax, round(-lo / scale)))
q = (torch.round(x / scale) + zero).clamp(0, qmax).to(torch.uint8)
x_hat = (q.to(x.dtype) - zero) * scale
mse = (x - x_hat).square().mean()

print(q.tolist())       # [0, 1, 5, 9, 14, 15]
print(float(mse))       # approximately 0.00248333

    Convert the codes to a wider or floating dtype before subtracting the zero point. Otherwise unsigned subtraction can wrap. Clipping also happens before casting to the storage dtype.

    This snippet stores four-bit codes in byte-sized uint8 elements for readability. It does not pack two codes into each byte. The converted eight-bit models later in the post demonstrate actual reduced-precision weight storage.

    For values that round without being clipped, the reconstruction error has magnitude at most half a grid step, $s/2$. Once a value is outside the grid's coverage, that bound no longer applies. A value of 1000 clipped to a reconstructed endpoint near 150 has an error near 850, regardless of how small $s$ is.

    Tensor MSE is a useful diagnostic, but it is not a model accuracy measurement. A small change to a sensitive activation can matter more than a larger change elsewhere. The PTQ and QAT demonstrations eventually test the classifier, rather than stopping at weight MSE.

    8. Who chooses activation ranges, and when?

    Video: 24:16 · Slides 19 and 20

    Trained weights are available before deployment, so we can inspect their values ahead of inference. Activation values depend on the input. The output of a layer is not known just by looking at its parameter tensor.

    With dynamic quantization, an activation range is chosen at runtime from the current input to an operation. The weights can still be prequantized. This avoids a separate static activation-calibration pass, at the cost of runtime range estimation and conversions. PyTorch's dynamic quantized linear layer accepts and returns floating-point tensors at its public boundary; that does not mean its internal multiplication uses only floats.

    With static quantization, run representative examples through the model first. An observer records activation statistics, such as extrema or a histogram. Use those statistics to select the scales and zero points that the converted model will use later. This forward-only data-collection stage is calibration.

    QuestionDynamicStatic
    Activation range chosenDuring inference, for the current activation inputBefore deployment, from calibration statistics
    Separate activation calibrationNot needed for the dynamic linear workflowNeeded for the PTQ workflow in this lesson
    Runtime considerationRange estimation and quantization overheadFixed ranges can clip unfamiliar activations

    Calibration needs representative inputs, not target labels: no loss is backpropagated and no optimizer updates the weights. Preserve inference preprocessing, input shapes, and the kinds of examples the model will receive. Calibration on unusually easy or narrow inputs can make later activations saturate.

    Dynamic versus static answers when activation parameters are chosen. PTQ versus QAT answers whether training accounts for quantization. These are different questions, so do not treat all four words as competing names for the same choice.

    9. The integer multiply-accumulate, derived

    Video: 27:57 · Slide 21 · The derivation Umar links

    Take one output of a linear layer, $y=\sum_i x_iw_i+b$. Substitute the reconstruction rules for the activation and weight:

    $$\widehat{y}=s_xs_w\sum_i(q_{x,i}-z_x)(q_{w,i}-z_w)+b.$$

    The expensive inner sum can now use integer operands. A multiply-accumulate unit multiplies a pair and adds the product to an accumulator. The accumulator must be wider than the input codes because many products are summed. INT8 operands commonly accumulate in INT32.

    If the bias is represented in the accumulator's units, its scale is $s_b=s_xs_w$ and its zero point is zero:

    $$q_b=\operatorname{round}\!\left(\frac{b}{s_xs_w}\right),\qquad a=\sum_i(q_{x,i}-z_x)(q_{w,i}-z_w)+q_b.$$

    Now $\widehat{y}=s_xs_wa$. To store the output using its own $s_y,z_y$, requantize it:

    $$q_y=\operatorname{clip}\!\left(\operatorname{round}\!\left(\frac{s_xs_w}{s_y}a\right)+z_y,\ q_{\min,y},q_{\max,y}\right).$$

    The multiplier $s_xs_w/s_y$ is usually implemented with an integer multiplier and shift in an integer kernel. We use the real-valued ratio here to make the units visible. The input scales determine the accumulator's units; an output observer chooses a useful output grid. Calibration does not change the algebra of the dot product.

    One output, with every number visible

    Let $x=[0.4,1.2]$, $w=[-0.5,1.0]$, and $b=0.1$. Choose $s_x=0.2,z_x=3$ and $s_w=0.1,z_w=0$. The activation codes are $[5,9]$; the weight codes are $[-5,10]$.

    $$a=(5-3)(-5)+(9-3)(10)+5=-10+60+5=55.$$

    The bias code is five because $0.1/(0.2\times0.1)=5$. Dequantizing the accumulator gives $0.02\times55=1.1$, exactly the float dot product in this example. With output scale $s_y=0.1$ and zero point $z_y=7$, the output code is $11+7=18$, which also reconstructs to $1.1$.

    Follow one output through the integer layer

    The accumulator starts with the bias, as in Umar's MAC diagram. The animation plays once when it comes into view; use the controls to inspect or replay a step. With reduced motion enabled, Play shows the final step immediately.

    The accumulator starts at bias code 5.

    Why subtracting zero points changes the multiplication

    For $n$ terms, expanding the centered sum gives

    $$\sum_i q_{x,i}q_{w,i}-z_w\sum_iq_{x,i}-z_x\sum_iq_{w,i}+nz_xz_w.$$

    A kernel can precompute some weight-related sums instead of subtracting a zero point inside every multiply. Symmetric weights have $z_w=0$, removing two terms. Multiplying uncentered asymmetric codes and simply attaching $s_xs_w$ afterward would compute the wrong quantity.

    The derivation uses an integer bias for clarity, as Umar's slides do. The PyTorch CPU modules in the accompanying eager-mode example expose float biases; their backend handles bias addition. Do not infer the bias dtype of a library module solely from the weight dtype.

    10. A wider range preserves outliers but coarsens the grid

    Video: 30:05 · Slides 22 to 24 · Umar's range-selection notebook

    We have used observed minima and maxima as the range. That is only one policy. An observer collects statistics; the range-selection strategy decides which part of those statistics gets represented well.

    Suppose almost every value is between $-50$ and $150$, but one value is 1000. An eight-bit min-max grid must cover $[-50,1000]$, giving $s=1050/255\approx4.117647$. Without that outlier the spacing would be $200/255\approx0.784314$. One extreme value has made the grid over five times coarser for everyone else.

    A percentile policy chooses lower and upper quantiles instead of the full extrema. This narrows the spacing for the main population while clipping the tail. Umar's notebook uses the 0.01st and 99.99th percentiles and explicitly computes error excluding the injected outlier. That exclusion is part of the result's meaning.

    PolicyWhat it choosesWhat to watch
    Min-maxThe observed extremaA rare extreme value can waste resolution in the main population.
    PercentileSelected lower and upper quantilesBetter resolution for many values trades against large clipping error in the tails.
    MSE searchA candidate range minimizing reconstruction MSEClipping error must be included if the objective covers the entire tensor.
    Cross-entropy searchA candidate range preserving a softmax distributionIt weights errors differently from raw tensor MSE; it does not guarantee an unchanged ordering.

    For MSE selection, try candidate intervals, reconstruct the values using each interval, and choose the one with the smallest $\frac1N\sum_i(x_i-\widehat{x}_i)^2$. A grid search is a direct implementation of the idea Umar describes.

    For his cross-entropy example, form $p=\operatorname{softmax}(v)$ and $\widehat{p}=\operatorname{softmax}(\widehat{v})$, then minimize $-\sum_i p_i\log\widehat{p}_i$. The original probability distribution acts as the target. Since its entropy is fixed during the range search, minimizing this cross-entropy also minimizes $\mathrm{KL}(p\|\widehat{p})$.

    Report the population you measured. A percentile range can lower MSE on the ordinary values while raising MSE on the whole tensor. Neither result alone tells you whether clipping the outlier improves model accuracy.

    11. Which values share a scale?

    Video: 34:40 · Slide 25

    Umar compares layer-wise and channel-wise ranges. In a per-tensor weight quantizer, every value in one weight tensor shares a scale and, for an affine quantizer, a zero point. In a per-channel quantizer, each selected channel gets its own parameters.

    Take a two-output linear layer with the following rows:

    $$W_{\text{stored}}=\begin{pmatrix} -0.04&-0.01&0.02&0.05\\ -20&-5&10&20 \end{pmatrix}.$$

    A shared symmetric INT8 scale is $20/127\approx0.157480$. Every first-row magnitude is below half a step, so the entire small row rounds to zero. With a separate scale for that row, $0.05/127\approx0.000393701$, those small values become distinguishable again. The second row keeps its larger scale.

    For PyTorch nn.Linear, weights have shape [out_features, in_features]; output-channel weight quantization uses axis zero. Each output row is a dot product with its own weight scale. The activation tensor need not also use per-channel quantization.

    Finer granularity requires more metadata and a kernel that supports the chosen scheme. It addresses differing channel ranges, not every source of error. Keep granularity, range policy, and symmetry separate: one says who shares parameters, one chooses the interval, and one says whether that interval is centered on zero.

    12. Post-training quantization in PyTorch

    Video: 35:49 · Slide 26 · Umar's PTQ notebook

    The demonstration uses MNIST: flatten a $28\times28$ image to 784 inputs, pass through two 100-unit linear layers with ReLU, then produce ten class logits. Train the floating-point model before applying static PTQ.

    QuantStub and DeQuantStub mark the intended float/integer boundaries in this eager-mode workflow. Before conversion they do not perform the deployed integer computation. After conversion, the input stub quantizes the activation and the output stub dequantizes the logits.

    from torch import nn
from torch.ao import quantization as quant

class DigitMLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.quant = quant.QuantStub()
        self.fc1 = nn.Linear(784, 100)
        self.relu1 = nn.ReLU()
        self.fc2 = nn.Linear(100, 100)
        self.relu2 = nn.ReLU()
        self.fc3 = nn.Linear(100, 10)
        self.dequant = quant.DeQuantStub()

    def forward(self, images):
        x = self.quant(images.flatten(1))
        x = self.relu1(self.fc1(x))
        x = self.relu2(self.fc2(x))
        return self.dequant(self.fc3(x))

    Starting from a trained instance called float_model, the conversion stages are:

    import copy
import torch

torch.backends.quantized.engine = "qnnpack"  # CPU backend for this example
prepared = copy.deepcopy(float_model).cpu().eval()
prepared.qconfig = quant.get_default_qconfig("qnnpack")
prepared = quant.prepare(prepared, inplace=False)

with torch.no_grad():
    for images, _ in calibration_loader:
        prepared(images.cpu())  # labels are deliberately unused

int8_model = quant.convert(prepared, inplace=False)
print(int8_model.fc1.weight().dtype)  # torch.qint8
print(int8_model.fc1.weight().int_repr())

    The prepared PTQ model still computes with floating-point weights and activations. Its observers record statistics without intentionally perturbing the forward values. Conversion is the stage that installs quantized modules and packs the weights.

    Evaluate the converted model on held-out examples with the same preprocessing as the baseline. Compare accuracy and serialized size. Checking only int_repr() proves that codes exist, not that the classifier still works.

    13. Let training see the quantization error

    Video: 43:05 · Slides 28 to 31 · Umar's QAT notebook

    PTQ asks a trained floating-point model to tolerate conversion afterward. Quantization-aware training puts the conversion's effect into the forward pass during training, so the task loss can guide weights toward values that work well on the quantization grid.

    A fake quantizer quantizes and immediately dequantizes a value:

    $$F(x)=s\left(\operatorname{clip}\!\left(\operatorname{round}(x/s)+z,q_{\min},q_{\max}\right)-z\right).$$

    The output is floating point, but it lies on the same reconstruction grid used by the intended quantizer. The forward pass experiences rounding and clipping; the trainable master weights remain floating point. The optimizer is not directly updating an INT8 weight tensor.

    Why the straight-through estimator is needed

    Within a rounding bin, changing $x$ a little does not change $F(x)$. Its true derivative is zero almost everywhere and is undefined at the jumps. Backpropagating that derivative would give training almost no useful signal through the fake quantizer.

    Umar introduces the straight-through estimator, or STE. Use the quantized forward value, but replace its derivative with an approximation. The common clipped STE diagram is

    $$\frac{\partial F}{\partial x}\approx \begin{cases}1,&\beta\leq x\leq\alpha,\\0,&x\text{ outside the clipping interval.}\end{cases}$$

    For an in-range value, an incoming loss gradient passes through to the floating-point master value. This lets the optimizer move that value across bins over multiple steps. For a clipped value, the illustrated estimator blocks the gradient. Exact boundary conventions vary: PyTorch's fake-quantization mask checks whether the rounded code is within range, so its boundary can differ by roughly half a grid step.

    The STE is a surrogate, not the mathematical derivative of rounding. Its purpose is to provide a useful training signal for a discontinuous forward calculation.

    Forward values round; backward gradients use a surrogate

    Prepare in training mode, then convert in evaluation mode

    qat_model = copy.deepcopy(float_model).cpu().train()
qat_model.qconfig = quant.get_default_qat_qconfig("qnnpack")
qat_model = quant.prepare_qat(qat_model, inplace=False)
optimizer = torch.optim.Adam(qat_model.parameters(), lr=0.0001)

for images, labels in training_loader:
    optimizer.zero_grad()
    logits = qat_model(images.cpu())
    loss = nn.functional.cross_entropy(logits, labels.cpu())
    loss.backward()
    optimizer.step()

qat_model.eval()
qat_int8 = quant.convert(qat_model, inplace=False)

    Use the QAT qconfig here, not an observer-only PTQ qconfig: QAT needs fake quantizers that alter the forward values. Preparation also requires training mode; conversion happens after training in evaluation mode.

    Umar's notebook prepares QAT before training the model. The snippet above starts from an already trained float model and fine-tunes it, which makes the PTQ/QAT comparison easier to follow. Both use the same idea: training sees the quantization grid before the final conversion.

    A floating-point optimum can land between grid points. Rounding to its nearest point may produce a poor task loss. QAT evaluates the loss at quantized forward values while moving the underlying float weights, so it can find a different region whose available grid points work better. This is why matching every original weight as closely as possible is not the same objective as preserving task accuracy.

    QAT can help, but it is not a guarantee. It needs labeled training data, an optimizer, and additional training. Check the converted model; a good fake-quantized training loss alone is not the deployment result.

    Static PTQ changed the correct-prediction count by three images in this run and reduced serialized size by about 3.80 times. QAT had an extra epoch, so its higher accuracy does not isolate the benefit of fake quantization. Different seeds, training budgets, calibration inputs, and backends can produce different results.

    15. Keep the choices separate

    By the end of Umar's lesson, each term answers a specific question:

    ChoiceQuestion it answers
    Bit widthHow many integer codes are available?
    Symmetric or asymmetricIs the real interval centered on zero, or does it need an offset?
    Range policyWhich values should the available grid cover?
    Per-tensor or per-channelWhich values share a scale and zero point?
    Dynamic or staticWhen are activation quantization parameters chosen?
    PTQ or QATDoes training see quantization's effect before deployment?

    Start with the reconstruction equation $\widehat{x}=s(q-z)$. Use it to check the units in a layer. Then decide what range and granularity suit the tensors, whether activation ranges can be calibrated ahead of time, and whether the resulting model needs quantization-aware training. Finally, measure the converted model on the task it is supposed to perform.
