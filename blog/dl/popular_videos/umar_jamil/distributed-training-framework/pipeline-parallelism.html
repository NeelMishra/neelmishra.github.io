    Pipeline Parallelism from First Principles

    September 2026 · 24 min read · Distributed Training from First Principles

    Layers are sequential, and that is the whole problem. Put layer 1 on device 0 and layer 2 on device 1 and device 1 has nothing to do until device 0 finishes. Pipelining recovers the lost time by keeping several batches in flight at once, and everything interesting is about how many, and what that costs in memory.

    Splitting by depth

    Data parallelism replicates the model and splits the batch. Pipeline parallelism does the opposite: it splits the model and passes the batch through. With $P$ stages, stage $p$ owns a contiguous run of $L/P$ layers.

    What it costs to communicate

    Only the activations crossing stage boundaries, a tensor of shape $(B,S,d)$, sent point-to-point to exactly one neighbour. There is no collective and no all-reduce. For a 4096-wide model this is small compared to sending gradients.

    What it buys

    Each device stores $1/P$ of the parameters, gradients and optimizer state — the same factor as ZeRO-3, but with far less traffic. Pipelining is the cheapest way to spread a model across nodes over a slow network.

    The bubble

    Run one batch through a 4-stage pipeline and watch the devices. Stage 0 computes, then stage 1, then 2, then 3; the backward pass returns in reverse. At every instant exactly one device is busy.

    $$\text{utilization}=\frac1P.$$

    Four devices to get one device's throughput is worse than useless. The fix is to break the minibatch into $m$ microbatches and push them in one after another, so that while stage 1 works on microbatch 1, stage 0 has already started microbatch 2.

    The bubble is the idle time at the start, while the pipeline fills, and at the end, while it drains. It does not disappear with microbatching — it is amortized over more useful work.

    Count it. Let one microbatch's forward-plus-backward cost on one stage be $t$. A perfect pipeline would take $m\,t$. The real pipeline needs $P-1$ extra slots to fill and drain:

    $$T=(m+P-1)\,t,\qquad \boxed{\text{bubble fraction}=\frac{T-mt}{T}=\frac{P-1}{m+P-1}.}$$

    Two readings of that formula matter. It falls as $m$ grows, and it rises with $P$. Setting it below a target $\epsilon$ requires

    $$m\ \ge\ \frac{1-\epsilon}{\epsilon}(P-1),$$

    so a 10% bubble needs $m\ge 9(P-1)$: 28 microbatches for 4 stages, 64 for 8, 136 for 16.

    The memory that pipelining creates

    Microbatching is not free, and the price is activation memory. A microbatch's activations must be kept from the moment its forward pass runs until its backward pass consumes them. In a plain all-forward-then-all-backward schedule, stage 0 runs every forward before any backward, so it holds activations for all $m$ microbatches at once.

    $$\text{peak activation memory at stage }0\ \propto\ m\times(\text{activations for one microbatch}).$$
    The two knobs fight each other. Raising $m$ shrinks the bubble and grows activation memory, in direct proportion. This tension is the entire subject of pipeline scheduling: the next note shows how 1F1B keeps the same bubble fraction while capping in-flight activations at $P$ rather than $m$.

    The imbalance is also spatial. Stage 0 holds the most activations and stage $P-1$ the fewest, because the last stage's microbatches are consumed almost immediately. Memory is therefore lopsided across the pipeline even when compute is perfectly balanced.

    Balancing the stages

    The pipeline runs at the speed of its slowest stage, so an uneven split wastes time on every microbatch, not just once. Equal layer counts are the obvious split and usually the wrong one:

    Source of imbalanceEffectMitigation
    Embedding table on stage 0Large parameter and gradient memory, but almost no compute.Give stage 0 extra transformer blocks to compensate.
    Output head and loss on the last stageA $V\times d$ matmul plus a softmax over the vocabulary is genuinely expensive, and the logits tensor is huge.Give the last stage fewer blocks; compute the loss in chunks.
    Tied embeddings across stages 0 and $P-1$One tensor lives on two devices and receives gradients on both.An explicit all-reduce between those two ranks before the step.
    Heterogeneous devices or interconnectsThe slowest link throttles everything.Profile, then assign layers by measured time rather than by count.
    Balance by measured time, not by layer count. Profile one microbatch per candidate split and equalize wall-clock, not parameters. A 5% imbalance costs 5% of every microbatch for the whole run.

    What the implementation must get right

    1

    Send and receive in a deadlock-free order. If every stage posts a blocking receive before its send, the pipeline deadlocks instantly. Either alternate the order by parity of the rank, or use non-blocking primitives and wait afterwards.

    2

    Shapes must be known in advance. The receiver has to allocate before the data arrives. Variable sequence lengths mean either padding to a fixed shape or sending metadata first.

    3

    Accumulate gradients across microbatches. Each microbatch produces a partial gradient; the optimizer must step once, after all $m$ have been accumulated. This is the time-domain version of the same summation argument from the autograd note.

    4

    Scale the loss by $1/m$. Otherwise the accumulated gradient is $m$ times too large — the same trap as gradient accumulation without pipelining.

    Pipeline versus tensor parallelism

    PipelineTensor
    Split alonglayers (depth)inside each matmul (width)
    Communicationpoint-to-point, once per stage boundarycollective, several times per block
    Volume per steplowhigh
    Tolerates slow linksyes — use across nodesno — keep inside a node
    Main costthe bubble, and activation memorybandwidth, and synchronization

    They are complementary, which is why production runs combine them: tensor parallel within a node over the fast fabric, pipeline parallel across nodes over the slow one, data parallel on top. The device-mesh note assembles exactly that.

    Takeaway

    Pipelining gives you a $1/P$ memory reduction for almost no bandwidth, at the cost of a bubble of $(P-1)/(m+P-1)$. Microbatching shrinks the bubble in proportion to $m$ and grows activation memory in proportion to $m$. Resolving that trade is what pipeline schedules are for.
