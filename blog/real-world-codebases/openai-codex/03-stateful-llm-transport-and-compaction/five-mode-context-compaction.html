    4. Five-Mode Context Compaction: Speculative Async Prefix Splicing, Post-Turn Compaction & Cross-Model comp_hash Handshakes

    October 2026 · 18 min read · Chapter 4

    In a toy agent, context compaction is a twenty-line if tokens > limit { summarize(history) } check that freezes the UI for fifteen seconds mid-task and wipes out recent tool outputs. In OpenAI Codex, compaction spans ten dedicated modules (compact*.rs and session/async_compaction.rs) orchestrating five distinct compaction modes across a three-watermark token ladder—capable of compacting a prefix speculatively in the background while the foreground turn keeps running tools, hiding compaction latency behind turn boundaries, and negotiating cross-model latent state transitions via comp_hash.

    1. The Three-Watermark Token Ladder & Five Compaction Modes

    Inside core/src/session/context_window.rs (lines 53-118), Codex evaluates active token usage $T_{\text{active}}$ under two configurable accounting scopes: either AutoCompactTokenLimitScope::Total ($T_{\text{scope}} = T_{\text{active}}$) or BodyAfterPrefix ($T_{\text{scope}} = \max(0,\, T_{\text{active}} - T_{\text{prefill}})$), capped by the effective context window $W_{\text{eff}} = \lfloor W_{\text{ctx}} \cdot p_{\text{eff}} / 100 \rfloor$. Using overflow-free i128 integer cross-multiplication, Codex orders three escalating watermarks:

    $$100\,T_{\text{active}} \ge p_{\text{async}}\,W_{\text{ctx}} \;\;(\tau_{\text{async}}) \quad\prec\quad 100\,T_{\text{active}} \ge p_{\text{post}}\,W_{\text{eff}} \;\;(\tau_{\text{post}}) \quad\prec\quad T_{\text{scope}} \ge L_{\text{scope}} + B_{\text{fallback}} \;\vee\; T_{\text{active}} \ge W_{\text{eff}} \;\;(\tau_{\text{hard}}).$$

    2. Speculative Async Prefix Splicing Without Stopping the Turn

    Mode 3 (session/async_compaction.rs) solves one of the hardest concurrency problems in agentic harnesses: how do you compact an 80,000-token prefix over a 6-second background HTTP call while the foreground agent continues executing tools and appending new items?

    Trace the choreography across async_compaction.rs, compact_remote_v2.rs, and session/mod.rs:

    1. Wait for Backend Model Pin (async_compaction.rs:63-66): On PreTurn, maybe_start refuses to launch until turn_state.is_some() so the foreground WebSocket establishes the server’s sticky-routing pin first.
    2. Read-Only Sticky Routing Over Side-Channel HTTP (compact_remote_v2.rs:295-314): Background compaction cannot share the foreground turn’s WebSocket mutex without blocking streaming tool steps. Instead, it clones the captured turn_state string into a throwaway Arc<OnceLock<String>> and executes over ResponsesHttpExecutor—achieving GPU KV-cache affinity on the same backend replica without mutating foreground WebSocket continuation state!
    3. Atomic CAS Prefix Splicing (session/mod.rs:4538-4578): Suppose background compaction captured prefix $H[0..k]$ at history version $g$, and while it ran, the foreground agent appended live tool calls and outputs $S_{\text{live}} = H_{\text{now}}[k..]$. When take_ready or wait_for_pending adopts the candidate, replace_compacted_history re-validates $g$, $k$, and auth_owner_generation under the session mutex and splices the compacted prefix directly ahead of the untouched live suffix:
    // codex-rs/core/src/session/mod.rs (lines 4548-4577, condensed)
// Validate immediately before slicing and replacing the captured prefix.

}

    Even better: what if a tool dumped 90,000 tokens into $S_{\text{live}}$ while background compaction was running, leaving the newly spliced history still over $\tau_{\text{hard}}$? Lines 42-54 of compact_remote_v2_installation.rs re-check context_window_token_status immediately after prefix adoption and, if status.token_limit_reached is still true, seamlessly fall back once to a full foreground compaction!

    3. Cross-Model comp_hash Handshakes & cyber_access_program Pairing

    Unlike Mode 1’s human-readable Markdown summary, Remote V2’s ResponseItem::Compaction carries an opaque encrypted state blob whose internal format is tied to a specific model compatibility family—advertised in model metadata as ModelInfo.comp_hash. What happens when a user switches mid-session from Model $A$ to Model $B$?

    Inside maybe_run_previous_model_inline_compact (session/turn.rs:1491-1583), Codex detects two cross-model hazards before Turn $B$ samples:

    • CompactionReason::CompHashChanged: Both models declare comp_hash values and $\text{comp\_hash}(A) \neq \text{comp\_hash}(B)$.
    • CompactionReason::ModelDownshift: The user switched from a larger-window model to a smaller-window model ($W_A > W_B$) and $T_{\text{active}}$ already exceeds $W_B$’s auto-compact or full context window!
    // codex-rs/core/src/session/turn.rs (lines 1518-1529 & 1564-1581, condensed)
let mut previous_model_turn_context = turn_context
    .with_model(previous_model.clone(), &sess.services.models_manager)
    .await;
// `with_model` preserves the current turn's access program. Restore the previous
// turn's program so compaction uses the same model/cyber_access_program pair as that turn.
previous_model_turn_context.cyber_access_program = cyber_access_program::for_provider(
    &previous_model_turn_context.config,
    previous_turn_settings.cyber_access_program,
);
let step_context = sess
    .capture_step_context(Arc::new(previous_model_turn_context), cancellation_token)
    .await?;
// The previous model summarizes the old window; the current model owns its replacement.
let replacement_step_context = sess
    .capture_speculative_step_context(Arc::clone(turn_context), cancellation_token)
    .await?;

    Notice the split-context design (step_context vs. replacement_step_context): Model $A$ compacts the old window (using Model $A$’s restored cyber_access_program so the backend never rejects a mismatched (model_A, program_B) header pair!), while Model $B$ owns the replacement WorldState and TurnContextItem! And if Model $A$’s endpoint errors out (e.g., temporary capacity outage or deprecated model slug), should_retry_with_current_model (compact_model_fallback.rs:10-33) automatically retries compaction once using Model $B$ and records codex.compaction.model_fallback telemetry.

    4. Concurrent User-Goal Edits & Checkpoint Lineage

    Two final invariants in Session::replace_compacted_history (session/mod.rs:4508-4640) ensure compaction never silently drops state:

    1. Out-of-Band User Goal Edits (session/mod.rs:4598-4618): Users or UI clients can publish UserGoalUpdate edits asynchronously while a full foreground compaction (CompactedHistoryInstallation::Complete) is running. Codex snapshots input_goal_ids before compaction starts and, before swapping the history, appends any UserGoalUpdate items in live history whose IDs were neither in input_goal_ids nor in replacement_goal_ids—preserving concurrent user steering in exact arrival order!
    2. Multi-Subsystem Checkpoint Atomicity (session/mod.rs:4631-4640): Every persisted CompactedItem atomically bundles replacement_history, guardian_history (so safety supervision retains provenance across compactions), retained_context, mcp_resource_origins, mcp_attribution, and the AutoCompactWindowIds lineage chain (window_number, first_window_id, previous_window_id).

    5. Questions worth answering

    Why does collect_compaction_output (compact_remote_v2.rs:389-394) use a biased tokio::select! polling stream.next() before cancellation.cancelled() on background compactions?

    If a background compaction finishes in the same tick that session shutdown cancels shutdown_cancellation, polling stream.next() first ensures ResponseEvent::Completed is drained and its token consumption is accurately charged to record_rollout_budget_usage rather than lost!

    Why does async_compaction::maybe_start (async_compaction.rs:117, 126) acquire a TaskTracker token inside sess.state.lock() before running prepared_input.await outside the lock?

    Acquiring launch = tasks.token() before dropping the mutex guarantees that if session shutdown runs in the tiny window while prepared_input.await is normalizing history outside the lock, async_compaction::shutdown’s tasks.wait().await will still wait for the launch to finish or cancel cleanly—preventing orphan background tasks after shutdown.
