    Heaps of Pairs, Tuples & Structs

    July 2026 · 20 min read

    Real heap problems rarely store bare integers. You store a distance and the node it belongs to, a task and its deadline, a value and the index it came from. The moment an element has more than one field, you have to decide what “bigger” means — and C++ has strong opinions and a few sharp edges. This post covers how std::pair, std::tuple, and your own structs behave in a heap, and how to bend them to the order you actually want.

    std::pair Compares Lexicographically

    std::pair has a built-in operator< that compares lexicographically: first is the primary key, and second is consulted only to break ties on first. Because priority_queue defaults to std::less, a priority_queue<pair<int,int>> is a max-heap on first, with larger second winning ties.

    #include <queue>

std::priority_queue<std::pair<int,int>> pq;
pq.push({2, 5});
pq.push({2, 9});
pq.push({2, 1});
auto t = pq.top();   // {2, 9} — first ties at 2, so the largest second wins

    The tie-break is not a footnote; it is the whole reason people reach for pairs. Above, all three entries share first == 2, so the heap falls through to second and picks 9. std::tuple behaves identically, just with more fields compared left to right — tuple<int,int,int> compares the first, then the second, then the third. The animation walks a small pair heap and lights up which field decided each comparison.

    Ordering by the Second Element

    Often the field you care about is second, not first. You have two honest options.

    Option A — a comparator on .second. Keep the natural {key, payload} layout and tell the heap to look at the second field:

    using PI = std::pair<int,int>;   // {id, weight}
auto byWeight = [](const PI& a, const PI& b) { return a.second < b.second; };
std::priority_queue<PI, std::vector<PI>, decltype(byWeight)> pq(byWeight);
// max-heap on weight; id rides along untouched

    Option B — put the sort key first. The competitive-programming reflex is to simply store {weight, id} so the default lexicographic order does the work — no comparator at all:

    using PI = std::pair<int,int>;   // {weight, id}
std::priority_queue<PI> pq;      // default max-heap on weight, ties by id

    Both are legitimate. Option B is shorter and inlines perfectly, which is why you see it everywhere in contest code. But it forces you to reorder your data purely to satisfy the container, and it silently changes the tie-break to “by id,” which may not be what you want. Option A keeps your data in its natural shape and makes the ordering explicit at the cost of a few more characters. Prefer B for throwaway speed, A for code that other people read.

    The Dijkstra Idiom

    The single most common pair-heap in existence:

    using State = std::pair<int,int>;   // {distance, node}
std::priority_queue<State, std::vector<State>, std::greater<>> pq;
pq.push({0, source});
// ... pop the nearest unsettled node each iteration

    Two decisions are baked into that line, and both follow from the lexicographic rule. Distance goes first because you want the heap ordered by distance; put the node first and it would order by node id, which is meaningless. std::greater makes it a min-heap because Dijkstra always wants the closest frontier node next, and a min-heap surfaces the smallest distance. The node rides in second purely as a passenger. This gives the familiar $O((V + E)\log V)$ shortest-path bound. Dijkstra also famously does without decrease-key by pushing duplicates and skipping stale pops — the full pattern, including why that is correct, is in Part 7.

    Custom Structs: operator< or an External Comparator

    For your own types there are two routes, and choosing well saves a lot of friction.

    Route A — overload operator<. Define operator< as a member (or free function) and the default std::less just works. This is best when the type has one natural order that everyone agrees on.

    struct Task {
    int priority;
    int id;
    bool operator<(const Task& o) const { return priority < o.priority; }
};

std::priority_queue<Task> pq;   // max-heap: HIGHEST priority on top
    The same inversion, one more time: your operator< returns “less than,” yet the heap is a max-heap — top() is the greatest Task by that operator<. If you were thinking “I defined less-than, so I’ll get the smallest,” you will get the exact opposite. To pop the smallest instead, keep operator< as the honest “less than” and pass std::greater<>, or supply an external comparator. Never lie in operator< to fake a min-heap — every other use of the type (sorting, std::set, std::map) will then be wrong.

    Route B — an external comparator. Supply the order at the priority_queue declaration instead of baking it into the type. This is best when different call sites need different orders, or when you cannot modify the type (it lives in a library):

    struct Task { int priority; int id; };   // no operator< at all

auto byPriority = [](const Task& a, const Task& b) { return a.priority < b.priority; };
std::priority_queue<Task, std::vector<Task>, decltype(byPriority)> pq(byPriority);

    The C++20 operator<=>

    C++20’s three-way comparison operator, the spaceship, collapses all the boilerplate. Defaulting it generates all six relational operators — including the operator< that priority_queue needs — from one line:

    #include <compare>

struct Task {
    int priority;
    int id;
    auto operator<=>(const Task&) const = default;
};

std::priority_queue<Task> pq;   // works immediately: max-heap by priority, then id

    There is one thing you must know about the defaulted version: it compares members in declaration order, which is exactly lexicographic. So the order in which you list the members is the tie-break order. Put priority before id and you get “by priority, then id”; swap the two lines and you silently get “by id, then priority.” Member order is now a semantic decision, not just a layout one. When one natural order exists and it matches declaration order, defaulted <=> is the cleanest option in the language.

    Multi-Key Ordering With Tie-Breaking

    Serious scheduling needs several keys at once. Suppose you want tasks ordered by priority descending, then earliest deadline, then insertion order for stability. The correct comparator chains the keys, falling through to the next only when the current one ties:

    struct Task { int priority; int deadline; int seq; };

struct TaskCmp {
    bool operator()(const Task& a, const Task& b) const {
        if (a.priority != b.priority) return a.priority < b.priority;  // higher priority on top
        if (a.deadline != b.deadline) return a.deadline > b.deadline;  // earlier deadline on top
        return a.seq > b.seq;                                          // earlier insertion on top
    }
};
std::priority_queue<Task, std::vector<Task>, TaskCmp> pq;
    The classic multi-key bug: writing return a.priority < b.priority || a.deadline < b.deadline;. This is not a strict weak ordering — it is neither asymmetric nor transitive — and feeding it to a heap is undefined behaviour, exactly like the <= mistake from Part 4. The fix is the chained form above: compare the primary key; only if it ties do you look at the next. The pattern is always a.x != b.x ? (a.x < b.x) : <next key>.

    Worked Trace: Task Scheduling

    Push these five tasks as {priority, deadline, seq} and pop them all. The comparator above should yield: highest priority first; within equal priority, earliest deadline; within equal deadline, earliest insertion.

    push {2, 5, 0}   // T1
push {5, 9, 1}   // T2
push {2, 3, 2}   // T3
push {5, 9, 3}   // T4
push {2, 3, 4}   // T5
    pop #task{priority, deadline, seq}why it came out here
    1T2{5, 9, 1}highest priority (5); ties T4 on priority & deadline, wins on smaller seq
    2T4{5, 9, 3}the other priority-5 task, later insertion
    3T3{2, 3, 2}priority 2, earliest deadline (3); ties T5 on deadline, wins on smaller seq
    4T5{2, 3, 4}same priority & deadline as T3, later insertion
    5T1{2, 5, 0}priority 2, latest deadline (5) — last out

    Pop order: T2, T4, T3, T5, T1. Every tie was resolved by the next key in the chain, and the seq field guaranteed a deterministic answer even when priority and deadline were identical.

    Heaps Are Not Stable

    A heap makes no promise about the relative order of equal elements. If two tasks compare equal, which one pop() hands you first is unspecified and can change between library versions or even between runs. When ties must resolve deterministically — and in scheduling they almost always must — the fix is exactly what seq did above: attach a monotonically increasing sequence number at insertion and use it as the final tie-breaker.

    struct Item { int key; long long seq; };
long long counter = 0;

struct StableCmp {
    bool operator()(const Item& a, const Item& b) const {
        if (a.key != b.key) return a.key < b.key;
        return a.seq > b.seq;   // equal keys: earliest inserted pops first (FIFO)
    }
};
// on every push: pq.push({key, counter++});

    Because seq is unique and ever-increasing, no two items are ever truly equal, so the ordering becomes total and stable. Use seq > b.seq for FIFO among equals (earliest inserted pops first) or seq < b.seq for LIFO.

    Heaps of Pointers or Indices

    When elements are large — a struct with a big payload — copying them on every sift is wasteful, since each heap operation performs $O(\log n)$ moves. Store a Task* or an int index instead, and let the comparator dereference:

    std::vector<Task> tasks = load();   // the real objects live here

// Heap of INDICES into tasks, ordered by priority.
auto byPriority = [&tasks](int i, int j) { return tasks[i].priority < tasks[j].priority; };
std::priority_queue<int, std::vector<int>, decltype(byPriority)> pq(byPriority);
for (int i = 0; i < (int)tasks.size(); ++i) pq.push(i);

    You now move cheap integers through the heap while the heavy objects stay put. Two hazards come with the convenience. First, if you store raw Task* and the underlying std::vector reallocates (or an object is destroyed), those pointers dangle — prefer indices, which survive reallocation as long as you do not erase or reorder elements. Second, this is a stateful comparator: it captures tasks by reference, so mutating the priorities of items still in the heap silently corrupts the invariant, exactly the trap from Part 4. Freeze the keys while the heap holds their indices.
