    The Binary Heap From Scratch

    July 2026 · 20 min read

    Before you reach for std::priority_queue, build the thing underneath it once. A binary heap is small enough to hold entirely in your head — two operations, one array, one invariant — and once you have written it by hand, every surprising behaviour of priority_queue traces straight back to a decision you make here.

    This post derives the structure from its single defining property, packs it into an array, explains sift-up and sift-down, proves the result that trips up most people — that you can build a heap in $O(n)$, not $O(n \log n)$ — and ends with a complete, compilable MaxHeap class.

    The one idea to carry: a heap is partially ordered, not sorted. It promises only that every parent outranks its children. That is weak enough to maintain in $O(\log n)$ per change, yet strong enough to hand you the single best element in $O(1)$. Everything below is a consequence of that trade.

    The Shape: A Complete Binary Tree

    A binary heap is not any binary tree — it is a complete one. A complete binary tree is filled level by level, top to bottom, and each level fills strictly left to right. Every level is entirely full except possibly the last, and the last level packs its nodes against the left edge with no gaps.

    That constraint is easy to mistake for an aesthetic preference. It is not — completeness is the load-bearing wall of the entire structure, and it buys two concrete things.

    First, it bounds the height. A complete tree over $n$ nodes has height exactly $\lfloor \log_2 n \rfloor$ — as short as a binary tree with $n$ nodes can be, because every level except the last is full. Since the two heap operations do work proportional to the height, that guarantees $O(\log n)$ per insert and removal. A heap can never degrade into a linked list the way an unbalanced binary search tree can; the shape rule forbids it by construction.

    Second — the part people underrate — completeness means there are no holes. Number the nodes in level order (root 0, then left to right down the levels) and they run $0, 1, \dots, n-1$ with nothing skipped. That dense, gap-free numbering is exactly what lets you store the tree in a flat array with no pointers. Take completeness away and the numbering develops holes, the array mapping breaks, and you are back to chasing pointers.

    Packing the Tree Into an Array

    Because the level-order numbering is dense, we can drop the tree nodes into a std::vector at exactly those indices and recover the tree structure with arithmetic. The three formulas C++ heaps use are:

    0-indexed (what the STL uses):
  parent(i) = (i - 1) / 2      // integer division
  left(i)   = 2*i + 1
  right(i)  = 2*i + 2

1-indexed (common in competitive programming, slot 0 unused):
  parent(i) = i / 2
  left(i)   = 2*i
  right(i)  = 2*i + 1

    Derive them rather than memorise them; it is a single counting argument. Number the nodes $0, 1, 2, \dots$ in level order. Every node has exactly two child slots, so the nodes $0, 1, \dots, i-1$ before node $i$ collectively own $2i$ child slots — the array positions $1, 2, \dots, 2i$. The next two free positions therefore belong to node $i$: its left child lands at $2i + 1$ and its right at $2i + 2$. Invert that and the parent formula falls out. A child at index $c$ satisfies $c = 2p + 1$ (left) or $c = 2p + 2$ (right); in both cases integer division gives $\lfloor (c-1)/2 \rfloor = p$, so parent(i) = (i - 1) / 2 works for either child.

    The 1-indexed variant is what many competitive programmers reach for, and it is marginally cheaper. Left child becomes 2*i, a single bit shift with no increment; the parent becomes i / 2, a shift with no decrement. You trade one unused array slot (index 0) for slightly tighter index math — negligible on modern hardware, but real, which is why both conventions appear in the wild. The STL commits to 0-indexing because its heaps live in a vector that starts at 0 like everything else in C++.

    Index iValueLevelparent(i)left(i)right(i)
    0160— (root)1 → 142 → 10
    11410 → 163 → 84 → 7
    21010 → 165 → 96 → 3
    3821 → 147 → —8 → —

    5922 → 10——

    A child index at or past size() simply does not exist — that is how the array encodes “no child here.” There is not a single pointer in that table: the heap is a contiguous vector you have agreed to interpret as a tree, which is also why it is friendlier to the CPU cache than a pointer-based std::map.

    The Heap Property: Ordered, Not Sorted

    The shape rule says nothing about values. The heap property supplies the ordering: in a max-heap, every parent is greater than or equal to each of its children. (A min-heap flips the comparison; that is Part 3.) That is the entire ordering invariant — a purely vertical promise between each node and its direct children.

    The subtlety that catches everyone: this is a partial order, not a total one. The array of a heap is almost never sorted. Siblings have no defined relationship; cousins have none; the only thing guaranteed is that the root is the global maximum. Two heaps built from the very same multiset can look completely different and both be valid. Take the elements $\{1, 2, 3\}$:

    [3, 1, 2]        [3, 2, 1]
    3                3
   / \              / \
  1   2            2   1

    Both satisfy “parent ≥ children” everywhere; both are correct max-heaps; neither array is sorted. There is no canonical heap for a given set of values, which is exactly why you must never assume anything about a heap’s internal array beyond the root.

    One elegant consequence shows how much the invariant already pins down: the second-largest element is always one of the root’s two direct children. The one-line proof: every non-root element is dominated by its parent. If the second-largest sat anywhere but a child of the root, its parent would be $\ge$ it and not the root — a value strictly between it and the maximum — contradicting second-largest. Hence its parent is the root, and you find the runner-up by inspecting exactly two cells.

    Sift-Up: Restoring Order After a Push

    To insert, keep the shape valid first and fix the ordering second. Append the new value at the end of the array — index size() - 1, the next free slot in level order — and the tree is still complete. But the newcomer may be larger than its parent, violating the heap property on the single edge above it. Sift-up (also called bubble-up) walks that one value toward the root, swapping it with its parent as long as it is larger:

    void siftUp(int i) {
    while (i > 0) {
        int parent = (i - 1) / 2;
        if (data[parent] >= data[i]) break;   // parent already outranks us — done
        std::swap(data[parent], data[i]);
        i = parent;
    }
}

    The loop touches one edge per level and climbs at most $\lfloor \log_2 n \rfloor$ levels, so a push costs $O(\log n)$. Crucially, sift-up only ever compares a node with its parent: because the rest of the tree was already a valid heap, the only edge that can be broken is the one directly above the value we just moved. Fix it, move up, repeat.

    Sift-Down: Restoring Order After a Pop

    Removal is the mirror image, and it hides the subtlety that most buggy heaps get wrong. The maximum is at index 0, but you cannot just erase index 0 — that would punch a hole in the middle of the array. Instead, overwrite the root with the last element, shrink the array by one (the shape is still complete), and then push that too-small value back down until order is restored. This is sift-down (or heapify-down):

    void siftDown(int i) {
    int n = (int)data.size();
    for (;;) {
        int l = 2*i + 1, r = 2*i + 2, largest = i;
        if (l < n && data[l] > data[largest]) largest = l;
        if (r < n && data[r] > data[largest]) largest = r;
        if (largest == i) break;              // both children ≤ parent — done
        std::swap(data[largest], data[i]);
        i = largest;
    }
}

    The critical line is that you must swap with the larger of the two children, not just any child that beats the parent. Suppose the node holds 4 with children 8 (left) and 9 (right). Swap with the left child because 8 > 4 and you promote 8 — but its new sibling is 9, so now 9 > 8 and a child outranks its parent again. You have moved the violation, not removed it. Choosing the maximum child guarantees the promoted value is $\ge$ both children, so the new edge is valid and only the subtree below may still need work. Sift-down is $O(\log n)$ for the same height reason as sift-up.

    The asymmetry worth remembering: sift-up compares against one node (the parent) per level; sift-down compares against two (both children) per level to find the larger. That extra comparison per level is why, comparison-for-comparison, sift-down is the more expensive primitive — and it is exactly the primitive the $O(n)$ build below leans on.

    Building a Heap in $O(n)$, Not $O(n\log n)$

    You are handed an unsorted array and asked to turn it into a heap. There are two ways, and the gap between them is the most misunderstood fact about heaps.

    Strategy A — repeated insertion. Start with an empty heap and push each element. Every push is $O(\log n)$, and there are $n$ of them, so this is $O(n \log n)$ — the same cost as sorting.

    Strategy B — bottom-up heapify. Treat the raw array as an already-complete but unordered tree and run sift-down on every internal node, from the last one backwards to the root. Leaves are valid one-element heaps, so you skip them and start at index n/2 - 1:

    void siftDown(std::vector<int>& a, int i, int n) {
    for (;;) {
        int l = 2*i + 1, r = 2*i + 2, largest = i;
        if (l < n && a[l] > a[largest]) largest = l;
        if (r < n && a[r] > a[largest]) largest = r;
        if (largest == i) break;
        std::swap(a[largest], a[i]);
        i = largest;
    }
}

void buildHeap(std::vector<int>& a) {
    int n = (int)a.size();
    for (int i = n / 2 - 1; i >= 0; --i)   // last internal node, backwards to the root
        siftDown(a, i, n);
}

    Processing nodes bottom-up means that whenever you sift-down a node, both of its subtrees are already valid heaps — so a single sift-down suffices to fix that node. Strategy B looks like it should also be $O(n \log n)$: you call sift-down on roughly $n/2$ nodes and each sift-down is $O(\log n)$. That bound is correct but loose, and the true cost is $O(n)$.

    Here is the proof. A node at height $h$ (leaves are height 0) costs $O(h)$ to sift down, and a complete tree contains at most $\lceil n / 2^{h+1} \rceil$ nodes at height $h$. Summing the work over all heights:

    $$\sum_{h=0}^{\lfloor \log_2 n \rfloor} \left\lceil \frac{n}{2^{h+1}} \right\rceil \, O(h) \;=\; O\!\left( n \sum_{h=0}^{\infty} \frac{h}{2^{h+1}} \right) \;=\; O\!\left( \frac{n}{2} \sum_{h=0}^{\infty} \frac{h}{2^{h}} \right).$$

    The remaining series is a standard one that converges to a constant:

    $$\sum_{h=0}^{\infty} \frac{h}{2^{h}} \;=\; 2, \qquad\text{so the whole sum is } \;O\!\left(\tfrac{n}{2}\cdot 2\right) = O(n).$$

    The intuition behind the algebra is the part to internalise. The nodes are not distributed evenly across heights — a complete tree is bottom-heavy. Half of all nodes are leaves at height 0 and cost nothing; a quarter are at height 1 and sift down at most one level; only a single node, the root, pays the full $\log n$. The costly operations touch vanishingly few nodes, so the weighted total collapses to a constant times $n$. Repeated insertion has the opposite profile — it puts the long climbs at the end when the heap is largest — which is why it never escapes $O(n \log n)$.

    The animation below runs both strategies on the same input so you can watch the comparison counters diverge. The array [1, 2, 3, 4, 5, 6, 7] is the worst case for naive insertion — every new element climbs all the way to the root — yet bottom-up heapify still finishes in fewer comparisons, and the gap only widens as $n$ grows.

    ▶ Two Ways to Build a Heap

    Same input, two strategies. Bottom-up sift-down runs from the last internal node backwards; naive insertion pushes elements one at a time. Watch the running comparison count — and the tree and its backing array move together because they are the same memory.

    Worked Trace: Bottom-Up Build of {3, 1, 6, 5, 2, 4}

    Let us heapify [3, 1, 6, 5, 2, 4] by hand with Strategy B. There are $n = 6$ elements, so the internal nodes are indices $0, 1, 2$ and we sift-down from index n/2 - 1 = 2 backwards. The array after each sift-down:

    StepNodeWhat happensArray after
    start—Raw input, viewed as a complete tree.[3, 1, 6, 5, 2, 4]
    1i = 2 (value 6)Only child is 4 at index 5; 6 ≥ 4, so no swap.[3, 1, 6, 5, 2, 4]
    2i = 1 (value 1)Children 5 and 2; larger is 5; 5 > 1, swap 1↔5.[3, 5, 6, 1, 2, 4]
    3ai = 0 (value 3)Children 5 and 6; larger is 6; 6 > 3, swap 3↔6.[6, 5, 3, 1, 2, 4]
    3b3 sinks to i = 2Its child is 4; 4 > 3, swap 3↔4.[6, 5, 4, 1, 2, 3]

    The result [6, 5, 4, 1, 2, 3] is a valid max-heap: 6 dominates 5 and 4; 5 dominates 1 and 2; 4 dominates 3. Note again that it is not sorted — only the root is guaranteed to be the maximum. That single sift-down on index 0 cascaded two levels; every other node settled immediately — the bottom-heavy cost distribution from the proof, on a tiny example.

    A Complete Hand-Rolled MaxHeap

    Putting it together: a fully working max-heap backed by a single std::vector<int>, with the same public surface (push, pop, top, size, empty) you will meet again in std::priority_queue. This compiles as-is under any standard from C++11 onward.

    #include <vector>
#include <utility>   // std::swap

class MaxHeap {
public:
    bool empty() const { return data.empty(); }
    int  size()  const { return (int)data.size(); }
    int  top()   const { return data[0]; }   // precondition: !empty()

    void push(int value) {
        data.push_back(value);
        siftUp(size() - 1);
    }

    void pop() {                              // precondition: !empty()
        data[0] = data.back();                // promote the last element
        data.pop_back();                      // shrink; tree stays complete
        if (!data.empty()) siftDown(0);       // sink it back to its place
    }

private:
    std::vector<int> data;

    void siftUp(int i) {
        while (i > 0) {
            int parent = (i - 1) / 2;
            if (data[parent] >= data[i]) break;
            std::swap(data[parent], data[i]);
            i = parent;
        }
    }

    void siftDown(int i) {
        int n = size();
        for (;;) {
            int l = 2*i + 1, r = 2*i + 2, largest = i;
            if (l < n && data[l] > data[largest]) largest = l;
            if (r < n && data[r] > data[largest]) largest = r;
            if (largest == i) break;
            std::swap(data[largest], data[i]);
            i = largest;
        }
    }
};

    Two design notes that carry straight over to the standard library. First, top() and pop() have a precondition that the heap is non-empty; calling either on an empty heap reads data[0] out of bounds. std::priority_queue makes the identical choice — top() on an empty queue is undefined behaviour, and the caller must guard with empty(). Second, pop() returns void; it removes the maximum but does not hand it back. If you want the value, read top() first, then pop(). That two-step idiom is not an accident either, and Part 2 explains the exception-safety reasoning behind it.

    For reference, every operation’s complexity with the one-line reason for it:

    OperationComplexityWhy
    top()$O(1)$Reads index 0, the guaranteed maximum.
    push()$O(\log n)$One sift-up; amortised, since the vector may reallocate.
    pop()$O(\log n)$One sift-down from the root.
    build via repeated push$O(n \log n)$$n$ pushes, the long climbs land when the heap is largest.
    build via bottom-up heapify$O(n)$Bottom-heavy: cheap sift-downs dominate; the summed heights converge.
    find / delete an arbitrary value$O(n)$A heap is not a search structure; locating the value dominates.
