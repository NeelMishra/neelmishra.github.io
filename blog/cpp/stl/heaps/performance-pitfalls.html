    Performance, Pitfalls & Alternatives

    July 2026 · 21 min read

    You now know how heaps work and where they shine. This closing part is about the sharp edges: the bugs that compile cleanly and fail silently, the performance mistakes that turn an $O(\log n)$ operation into a copy-heavy crawl, and — most importantly — the cases where the honest answer is “do not use a heap at all.” It ends with the decision table the whole series has been building toward.

    Pitfalls: Symptom, Cause, Fix

    Every one of these has bitten someone in production. They share a theme: std::priority_queue trusts you, and the compiler cannot catch a violated contract.

    top() on an empty queue

    Symptom: a crash or garbage value, intermittently. Cause: top() and pop() perform no bounds check — on an empty queue they are undefined behaviour, not an exception. Fix: always guard.

    std::priority_queue<int> pq;
// int x = pq.top();          // UB — there is no element; NOT an std::exception
if (!pq.empty()) {
    int x = pq.top();         // safe
    pq.pop();
}

    A comparator using <=

    Symptom: corrupted ordering, crashes deep in library code, or an infinite loop — often only on large inputs. Cause: a comparator must be a strict weak ordering, meaning comp(a, a) must be false. Writing <= makes it true, which is undefined behaviour. Part 4 covers the rules in full. Fix: use strict < (or >).

    // BROKEN: <= is not a strict weak ordering -> undefined behaviour
auto bad  = [](int a, int b) { return a <= b; };
// FIX: strict comparison
auto good = [](int a, int b) { return a <  b; };

    Forgetting that pop() returns void

    Symptom: int x = pq.pop(); does not compile, or people expect the removed value back. Cause: pop() returns void. It cannot return the element by value, because if the move constructor threw, the element would be lost with the queue already modified — a design choice inherited from std::stack. Fix: read with top(), then pop().

    Mutating an element after pushing it

    Symptom: the heap returns elements in the wrong order, or “loses” the max. Cause: the heap sifts an element into place once, at insertion. If you later change a queued object through an outside pointer — or change data that a stateful comparator reads — nothing re-sifts it, and the invariant is silently wrong. Fix: treat queued elements as immutable; to change a key, remove, modify, and reinsert.

    // Anti-pattern: mutate a live heap element from outside
std::priority_queue<Task*> pq;   // ordered by Task::priority via a comparator
// pq.push(t); ... t->priority = 99;   // the heap does NOT re-order — corruption

// Correct: remove, modify, reinsert (see lazy deletion below for O(log n) removal)

    Expecting order from the underlying container

    Symptom: you peek at the backing vector (or iterate an <algorithm> heap) and it is not sorted. Cause: a heap satisfies only the parent/child property, not a left-to-right order. Only the root is meaningful. Fix: never rely on positional order; use sort_heap if you actually want it sorted.

    The push_heap / pop_heap two-step

    Symptom: using the <algorithm> functions, elements vanish or duplicate. Cause: push_heap assumes you already push_back-ed, and pop_heap does not remove — you must pop_back yourself, as Part 6 details. Fix: memorise the pairing: push_back then push_heap; pop_heap then pop_back.

    Assuming stability for equal elements

    Symptom: two equal-priority items come out in an order you did not expect. Cause: heaps are not stable; equal keys may be reordered arbitrarily. Fix: if insertion order must break ties, fold a monotonically increasing sequence number into the key.

    Storing large objects by value

    Symptom: profiler shows huge time in copy constructors during push/pop. Cause: each sift swaps elements $O(\log n)$ times, and if your type copies expensively, every swap pays for it. Fix: store pointers or indices, or give the type a cheap noexcept move (below).

    Performance

    Reserve, or bulk-load

    std::priority_queue gives you no reserve() — it hides the container. If you push $n$ items one by one, the backing vector reallocates $O(\log n)$ times, copying everything each time. Two clean fixes: construct the queue from a range, which does a single allocation and an $O(n)$ make_heap; or, when you need control, run the <algorithm> functions on a vector you reserve yourself. (There is also a “protected-member” trick — deriving to reach c — but range construction is almost always the right answer.)

    #include <queue>
#include <vector>

std::vector<int> data = load();                         // you own and can reserve() this
std::priority_queue<int> pq(data.begin(), data.end());  // ONE allocation + O(n) make_heap

    vector vs deque as the backing store

    The second template parameter is the container. std::vector is the right default: contiguous, cache-friendly, minimal per-element overhead. std::deque avoids the occasional large reallocation (it grows in fixed-size blocks) but costs an extra indirection on every element access, which shows up in the hot sift loops. Use deque only if a single giant reallocation is genuinely a latency problem. And std::list cannot be used at all — the heap algorithms need random access, which a linked list does not provide.

    Comparator cost

    The comparator runs $O(\log n)$ times per push and per pop. If it is expensive — comparing strings character by character, or recomputing a distance/priority each call — that cost is multiplied by the log factor and dominates. The fix is the classic decorate–sort–undecorate idea: precompute the sort key once and store it alongside the payload, so the comparator only compares a cheap scalar.

    #include <string>
#include <queue>
#include <vector>

struct Item {
    long key;              // precomputed once, at insertion
    std::string payload;   // never touched by the comparator
};
struct ByKey {
    bool operator()(const Item& a, const Item& b) const { return a.key > b.key; }  // min-heap
};
std::priority_queue<Item, std::vector<Item>, ByKey> pq;  // compares a long, not the string

    Move semantics

    Prefer emplace over push to construct in place and skip a temporary. More importantly, give your element type a noexcept move constructor: when the backing vector reallocates, it will move elements only if the move is noexcept — otherwise it must copy them to preserve the strong exception guarantee. A missing noexcept silently turns every growth into a deep copy.

    #include <vector>

struct Widget {
    std::vector<int> buf;
    Widget(Widget&&) noexcept = default;        // lets the heap MOVE, not copy, on reallocation
    Widget& operator=(Widget&&) noexcept = default;
    Widget(const Widget&) = default;
    Widget() = default;
};

    Cache behaviour

    This is the point that matters most at realistic sizes and is invisible in a big-O table. A heap is a contiguous array: a sift walks memory that is mostly already in cache. A std::set is a node per element, each separately allocated and reached by a pointer — every step down the tree is a likely cache miss. At $n$ in the thousands to millions, that constant-factor gap routinely dwarfs the asymptotic differences, which is why a “worse” structure on paper often wins in practice.

    In prose — choose:

    • priority_queue when you repeatedly need the single best element from changing data, especially streaming. It is the smallest, fastest, most cache-friendly option for exactly that job.
    • std::multiset when you need more than the single best: both ends at once (*begin() and *rbegin()), arbitrary erase, membership queries, or ordered iteration. You pay roughly three pointers per node and much worse locality, but you get a genuinely richer interface. This is the most common “actually you wanted a set” correction.
    • Sorted vector when you build once and query many times but rarely mutate — binary search plus contiguous scans, no per-node overhead.
    • nth_element / partial_sort for a one-shot selection on a static array you can reorder.
    • Monotonic deque for sliding-window minimum/maximum, where FIFO expiry beats a heap by a whole log factor.
    The multiset test: the moment your requirements include the word “and” — “the best element and the ability to remove any element,” or “the best and the worst,” or “the best and iterate in order” — you have outgrown priority_queue. A heap gives you one extreme and nothing else cheaply. Reach for std::multiset.

    Lazy Deletion

    A heap cannot remove an arbitrary element in better than $O(n)$ because it cannot find it. The standard workaround, used constantly in Dijkstra and scheduling, is lazy deletion: do not remove eagerly. Mark an element as deleted in a side table, and skip stale entries when they surface at the top. A separate counter tracks the true logical size so size() stays honest.

    #include <queue>
#include <unordered_map>
#include <vector>
#include <functional>

class LazyMinHeap {
    std::priority_queue<int, std::vector<int>, std::greater<int>> pq;
    std::unordered_map<int, int> pending;   // value -> count of pending deletions
    int live = 0;                           // logical size, excluding stale entries
public:
    void push(int x) { pq.push(x); ++live; }

    void erase(int x) { ++pending[x]; --live; }   // O(1): just mark it

    void prune() {                                 // drop stale entries at the top
        while (!pq.empty()) {
            int t = pq.top();
            auto it = pending.find(t);
            if (it != pending.end() && it->second > 0) {
                pq.pop();
                if (--it->second == 0) pending.erase(it);
            } else {
                break;
            }
        }
    }
    int  top()  { prune(); return pq.top(); }
    void pop()  { prune(); pq.pop(); --live; }
    int  size() const { return live; }
};

    The caveat is memory: stale entries linger in the heap until they bubble to the top, so the physical size can exceed the logical size. If deletions vastly outnumber pops, the heap can bloat; periodically rebuilding it from the live elements caps the growth. For the common case — Dijkstra, event simulation — stale entries are consumed quickly and the overhead is negligible.

    Advanced Heaps, Briefly

    Three things worth knowing exist, kept short and honest:

    • d-ary heaps. Give each node $d$ children instead of two. The tree is shallower ($\log_d n$), so push and decrease-key touch fewer levels and the layout is more cache-friendly; the price is $d$ comparisons per level during pop. A 4-ary heap is often measurably faster than binary for push-heavy workloads.
    • Pairing and Fibonacci heaps. These offer $O(1)$ amortised decrease-key on paper, which improves Dijkstra’s bound to $O(E + V \log V)$. In practice their constant factors and pointer overhead mean a plain binary heap with the lazy-delete trick usually wins on real graphs. Reach for them only when a profiler says decrease-key dominates.
    • boost::heap. If you genuinely need mutable priorities with stable handles — update a live element’s key in $O(\log n)$ without remove-and-reinsert — boost::heap provides fibonacci, pairing, and d-ary heaps with handle types. That is the real reason to go outside the standard library.

    The Series in One Screen

    Eight parts, one idea: a heap answers “what is the single best element right now?” for changing data, in $O(1)$ to read and $O(\log n)$ to update, on a flat array with no pointers. The comparator answers “does a have lower priority than b?” and the element never judged lower ends up on top — std::less gives a max-heap, std::greater a min-heap. Beyond that:

    • Need the single best from changing data? priority_queue.
    • Need the k best from a stream? A size-k heap, inverted (min-heap for largest).
    • Need both ends, erase, or ordered iteration? std::multiset.
    • Static array, one-shot k-th? nth_element.
    • Sliding-window extreme? Monotonic deque.
    • Own the container to iterate, reserve, or bulk-load? The <algorithm> heap functions.
