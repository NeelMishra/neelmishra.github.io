    std::priority_queue & the Default Max-Heap

    July 2026 · 19 min read

    In Part 1 you built a heap by hand. The standard library hands you the same machine wrapped in a class you never have to open: std::priority_queue. It is one of the most-used containers in competitive and production C++, and also one of the most surprising, because of a single design choice that catches nearly everyone the first time — it is a max-heap by default, even though its comparator defaults to std::less.

    This post takes the whole type apart: the three template parameters and their defaults, why it is an adaptor rather than a container, exactly why std::less produces a max-heap, the member functions and the two design decisions people trip over (pop() returning void and the total absence of iterators), and the $O(n)$ construction trick most people miss.

    The rule that unlocks the whole series: the comparator answers “does a have lower priority than b?” The element that is never judged lower-priority ends up on top. With the default std::less, “lower priority” means “smaller” — so the largest value rises to top(). Read it that way and the inversion stops being a thing you memorise.

    A Container Adaptor, Not a Container

    std::priority_queue is not a container in the way std::vector or std::map is. It is a container adaptor: a thin class template that wraps an underlying sequence container and re-exposes it through a deliberately narrow interface. It owns no storage-management logic of its own; it holds a container as a member and forwards work to it and to the <algorithm> heap functions.

    It has two siblings built the same way, and seeing all three together makes the pattern obvious — each takes a general-purpose container and restricts it to a single discipline:

    AdaptorDisciplineDefault containerKey access
    std::stackLIFOstd::dequetop() = most recently pushed
    std::queueFIFOstd::dequefront() = least recently pushed
    std::priority_queuehighest-priority-firststd::vectortop() = highest priority

    The adaptor keeps its underlying container in a protected member conventionally named c, and the comparator in a member named comp. “Protected” is a hint about intent: ordinary users get the restricted interface, but a derived class can reach in. That is a legitimate, occasionally useful escape hatch — the only sanctioned way to iterate a priority_queue’s elements — and we use it deliberately, and with caution, in the iterators section below.

    The Full Template Signature

    Every confusing behaviour is spelled out in the declaration. Here it is in full:

    template<
    class T,
    class Container = std::vector<T>,
    class Compare   = std::less<typename Container::value_type>
> class priority_queue;

    Three parameters, two with defaults:

    • T — the element type. The only one you always supply.
    • Container — the backing store, defaulting to std::vector<T>. It must be a random-access sequence container supporting front(), push_back(), and pop_back(); in practice that means std::vector (the default and almost always right) or std::deque.
    • Compare — a binary predicate defining priority, defaulting to std::less<T>. This is the one that surprises people, and the whole next section is about it.

    The parameter order has a practical consequence that trips up beginners: because Compare is third, you cannot name a custom comparator without also naming the container. That is why a min-heap must be spelled out in full — all three arguments, container included:

    #include <queue>
#include <vector>
#include <functional>

std::priority_queue<int> maxHeap;   // Container and Compare defaulted

// A min-heap needs the explicit container just to reach the comparator slot:
std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;

    That min-heap declaration is Part 3 in one line; here it is enough to see why the verbose form is unavoidable.

    Why std::less Gives a Max-Heap

    This is the single most important explanation in the series, so slow down for it. std::less<int> is the comparator that returns a < b. Applied to a heap it does not mean “keep the smallest on top.” It means: the comparator defines which element has lower priority, and the heap keeps the element that is never lower-priority at the root.

    Spell out the logic. comp(a, b) is read as “a has lower priority than b.” With std::less, comp(a, b) is a < b, so “lower priority” is literally “numerically smaller.” The heap keeps whichever element loses to nobody — the one for which comp(x, other) is never satisfied — and with std::less that is the largest value. So top() is the maximum. Swap in std::greater and “lower priority” becomes “numerically larger,” the smallest loses to nobody, and you get a min-heap. One mental model, both heaps.

    The comparison that clears it up: feed the same std::less to std::sort and you get ascending order — smallest first. Feed it to priority_queue and the largest is on top. Same comparator, opposite-looking result. There is no contradiction, and the next paragraph says exactly why.

    Here is the resolution. std::sort with comp places an element early when it is “less” than the others — the “lesser” element goes to the front. A heap does the opposite with the same information: the “lesser” (lower-priority) element sinks to the bottom, so the greater element surfaces at top(). sort puts “lesser” first; the heap puts “lesser” last. The comparator hasn’t changed meaning — the two structures simply read “lesser” from opposite ends. Once you see that, you never have to “remember it backwards” again.

    #include <queue>
#include <vector>
#include <algorithm>
#include <iostream>

int main() {
    std::vector<int> v = {3, 1, 4, 1, 5};

    std::sort(v.begin(), v.end(), std::less<int>());
    for (int x : v) std::cout << x << ' ';   // 1 1 3 4 5  (ascending)
    std::cout << '\n';

    std::priority_queue<int> pq;                // also std::less by default
    for (int x : {3, 1, 4, 1, 5}) pq.push(x);
    std::cout << pq.top() << '\n';            // 5  (the largest is on top)
}

    The Member Functions

    The public interface is small on purpose. Every priority-queue program is built from these:

    MemberEffectComplexity
    top()const reference to the highest-priority element$O(1)$
    push(x)Insert x (copies or moves it in)$O(\log n)$
    emplace(args...)Construct the element in place from args$O(\log n)$
    pop()Remove the top element; returns void$O(\log n)$
    size()Number of elements$O(1)$
    empty()true if there are no elements$O(1)$
    swap(other)Exchange contents with another queue$O(1)$

    The push/emplace distinction is the same one you know from vector. push takes an already-built object and copies or moves it into the container; emplace forwards its arguments to construct the element in place, saving a temporary. For an expensive element type the difference is real:

    #include <queue>
#include <string>
#include <utility>

struct Task {
    int priority;
    std::string name;
    Task(int p, std::string n) : priority(p), name(std::move(n)) {}
    bool operator<(const Task& other) const { return priority < other.priority; }
};

int main() {
    std::priority_queue<Task> pq;
    pq.push(Task(2, "build"));   // build a temporary Task, then move it in
    pq.emplace(5, "deploy");      // construct the Task directly inside the heap
}

    Because Task::operator< compares by priority and the default comparator is std::less, this is a max-heap keyed on priority: top() is the highest-priority task. That is the whole story of ordering custom types, expanded in Part 5.

    A real bug source: top() on an empty queue is undefined behaviour — it reads c.front() on an empty container, no bounds check, no exception. It will not throw std::out_of_range the way vector::at does. Always gate access with if (!pq.empty()). The same applies to pop() on an empty queue.

    Why pop() Returns void

    Newcomers expect pop() to hand back the element it removes, the way many languages’ queues do. It returns void instead, and the reason is exception safety, not oversight.

    Imagine the alternative signature T pop() that removes the top and returns it by value. Returning by value must construct a T in the caller — a copy or move. If that copy/move constructor throws (and for a type holding heap memory it can), the element has already been removed from the container, but the value never reaches the caller. It is gone: not in the queue, not returned, lost. There is no way to write a strongly exception-safe “remove and return” in one step. The standard library’s answer, shared by stack, queue, and priority_queue, is to split the operation: top() lets you observe the element (and copy or move it out on your terms, where a throw leaves the queue untouched), and pop() then discards it and cannot fail to return anything because it returns nothing.

    So the idiom is always two steps: read, then remove.

    #include <queue>
#include <string>
#include <utility>

int main() {
    std::priority_queue<std::string> pq;
    pq.push("gamma");
    pq.push("alpha");

    std::string best = pq.top();   // 1. observe / copy out
    pq.pop();                       // 2. remove; returns void

    // If copying is expensive, you may MOVE out of top() right before popping.
    // top() is const, so this needs a const_cast — safe ONLY because the very
    // next statement destroys the moved-from slot.
    pq.push("delta");
    std::string moved = std::move(const_cast<std::string&>(pq.top()));
    pq.pop();
}

    C++17 did not add a pop_value or a node-extract for these adaptors, so the move-from-top() trick above is the community’s standard workaround when copies hurt. Treat it as a sharp tool: it relies on pop() immediately following, so the object you gutted is destroyed before anyone can observe its moved-from state.

    Construction, Including the $O(n)$ Range Trick

    There are three constructions you actually use, and one of them is a commonly-missed optimisation.

    Default gives an empty max-heap. From a comparator lets you pass a stateful or runtime-chosen comparator object (essential for lambdas — Part 4). And from an existing range is the one to remember: passing a pair of iterators copies the range into the container and heapifies it with a single internal make_heap call, which is $O(n)$. Building the same heap by push-ing $n$ elements one at a time is $O(n \log n)$. Same result, asymptotically cheaper construction:

    #include <queue>
#include <vector>

int main() {
    std::vector<int> v = {5, 1, 8, 3, 9, 2, 7};

    // O(n): one make_heap over the copied range.
    std::priority_queue<int> fast(v.begin(), v.end());

    // O(n log n): n separate sift-ups. Same heap, more work.
    std::priority_queue<int> slow;
    for (int x : v) slow.push(x);
}

    If you already hold the data, prefer the range constructor. The $O(n)$ build is exactly the bottom-up heapify proved in Part 1, invoked for you.

    No Iterators, by Design

    std::priority_queue has no begin(), no end(), no way to range-for over it. That is a deliberate safety decision, not an omission. The heap invariant — every parent outranks its children — is fragile: a single write to the wrong element breaks it silently, and every later top()/pop() then returns garbage. If the adaptor exposed a mutable iterator, any assignment through it could corrupt the heap with no diagnostic. By hiding the container entirely, the class makes that class of bug unrepresentable through its public surface.

    When you genuinely need to inspect every element — logging, debugging, a one-off scan — you have two honest options. The clean one is to not use the adaptor: hold a std::vector and call the <algorithm> heap functions yourself, keeping full iteration (that is Part 6). The other, for when you are already committed to a priority_queue, is the sanctioned escape hatch: derive a small struct and read the protected member c.

    #include <queue>
#include <vector>
#include <iostream>

// priority_queue keeps its container as the protected member `c`.
struct PeekPQ : std::priority_queue<int> {
    const std::vector<int>& heap() const { return c; }   // read-only view of c
};

int main() {
    PeekPQ pq;
    pq.push(3); pq.push(1); pq.push(4); pq.push(1); pq.push(5);
    for (int x : pq.heap()) std::cout << x << ' ';   // heap order, NOT sorted
    std::cout << '\n';                                  // e.g. 5 4 3 1 1
}

    Keep two cautions in mind. The member is guaranteed by the standard to be named c, so this is portable — but expose it read-only as above. Hand out a non-const reference and you have re-opened the exact corruption hole the adaptor was designed to close. And remember what you are looking at: the elements come out in heap order, which is only partially sorted, never a sorted sequence.

    Worked Example: Watching the Vector

    Trace a max-heap of int through four pushes and two pops, following the internal vector c after each public call. This is the exact sequence the animation runs:

    Public callInternal workVector c aftertop()
    pq.push(5)push_back, sift-up[5]5
    pq.push(8)push_back, 8 bubbles over 5[8, 5]8
    pq.push(3)push_back, 3 stays put[8, 5, 3]8
    pq.push(10)push_back, 10 bubbles to root[10, 8, 3, 5]10
    pq.pop()swap root/last, pop_back, sift-down[8, 5, 3]8
    pq.pop()swap root/last, pop_back, sift-down[5, 3]5

    Notice that the vector is never sorted — [10, 8, 3, 5] after the fourth push has 5 sitting after 3 — yet top() is correct at every step. Draining a max-heap to exhaustion, on the other hand, does yield a sorted sequence, because you are repeatedly extracting the current maximum:

    #include <queue>
#include <vector>
#include <iostream>

int main() {
    std::vector<int> v = {5, 1, 8, 3, 9, 2, 7};
    std::priority_queue<int> pq(v.begin(), v.end());   // O(n) build
    while (!pq.empty()) {
        std::cout << pq.top() << ' ';                  // 9 8 7 5 3 2 1  (descending)
        pq.pop();
    }
    std::cout << '\n';
}
