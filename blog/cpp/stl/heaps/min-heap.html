    Building a Min-Heap

    July 2026 · 18 min read

    The default std::priority_queue is a max-heap: top() hands you the largest element. Roughly half the time you want the opposite — the smallest element first, for Dijkstra, for streaming top-K, for merging sorted lists. This post is about the one line that flips it, why that line is shaped the way it is, and the two mistakes almost everyone makes on the way there.

    The One Declaration You Must Memorise

    Here it is, front and centre. Copy it, paste it, keep it somewhere you can find it:

    #include <queue>
#include <vector>
#include <functional>   // std::greater

std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;

minHeap.push(5);
minHeap.push(1);
minHeap.push(8);
std::cout << minHeap.top();   // prints 1 — the SMALLEST

    Three template arguments, in this exact order: the element type (int), the backing container (std::vector<int>), and the comparator (std::greater<int>). The default max-heap lets you write just std::priority_queue<int> because the other two arguments have defaults — std::vector<int> and std::less<int>. The moment you want a different comparator, you lose those defaults, and that is the source of the first great stumbling block.

    Why You Must Name the Container to Name the Comparator

    Template parameters are positional. C++ has no way to say “keep the default container but change the third parameter.” There are no keyword arguments. If you want to supply the third template argument, you must first spell out the second one — even though you are perfectly happy with its default. So the natural-looking two-argument attempt does not do what you hope:

    // WRONG — you meant "int elements, greater comparator".
// The compiler reads it as "int elements, greater<int> CONTAINER".
std::priority_queue<int, std::greater<int>> pq;   // does NOT compile

    The second template parameter is the container type, so the compiler dutifully tries to use std::greater<int> as the storage. But a priority_queue’s container must behave like a sequence: it needs a value_type, a push_back, a pop_back, a front, a size. A comparator has none of those. The error you get is a wall of template noise whose first useful line is essentially:

    error: no type named 'value_type' in 'struct std::greater<int>'

    followed by a cascade about missing front, push_back, and friends. When you see “no type named value_type” pointing at a comparator, this is always the cause: you skipped the container argument. The fix is to name it explicitly:

    std::priority_queue<int, std::vector<int>, std::greater<int>> pq;   // correct
    The mnemonic: “type, tank, test.” The type you store, the tank it lives in (std::vector, always, unless you have a specific reason), and the test that orders it (std::greater for a min-heap). You cannot skip the tank to get to the test.

    Why std::greater Produces a Min-Heap

    This is the part that feels backwards, so read it slowly, because there is a single idea underneath it that makes the whole series click. The comparator answers one question: “does a have lower priority than b?” The element that is never judged to have lower priority is the one that ends up on top.

    With the default std::less, less(a, b) is a < b. So “lower priority” means “numerically smaller.” The smaller values sink; the largest surfaces. That is your max-heap.

    With std::greater, greater(a, b) is a > b. Now “lower priority” means “numerically larger.” The larger values are treated as the low-priority ones, so they sink, and the smallest surfaces. That is your min-heap. Same machinery, opposite verdict, because you changed the definition of “worse.”

    DeclarationComparatortop() for input {5, 1, 8, 3, 9}Heap
    priority_queue<int>std::less (default)9 (largest)max-heap
    priority_queue<int, vector<int>, greater<int>>std::greater1 (smallest)min-heap

    ▶ Same Input, Two Comparators

    Push the same five values — 5, 1, 8, 3, 9 — into a max-heap (std::less) and a min-heap (std::greater) at the same time. Tree and backing array are the same memory; the highlighted root is top(). Watch the two roots diverge immediately.

    The std::sort Contrast That Confuses Everyone

    Here is the trap. In std::sort, std::greater gives you descending order — largest first. In std::priority_queue, std::greater gives you a min-heap — smallest first. The same comparator seems to do opposite things, and that is what makes people distrust the whole system.

    std::vector<int> v = {5, 1, 8, 3, 9};

std::sort(v.begin(), v.end(), std::greater<int>());
// v is now {9, 8, 5, 3, 1}  — DESCENDING, largest first

std::priority_queue<int, std::vector<int>, std::greater<int>> pq(v.begin(), v.end());
// pq.top() is 1            — MIN-HEAP, smallest first

    The resolution is that the two algorithms ask the comparator different questions. std::sort reads comp(a, b) == true as “a should come before b in the output.” With greater, a > b means the larger element comes first, hence descending. std::priority_queue reads the very same comp(a, b) == true as “a has lower priority than b, so a belongs below b in the heap.” With greater, the larger element is the low-priority one, so it sinks and the smaller rises. It is not a contradiction — it is the same predicate answering “who goes first?” in one case and “who is worse?” in the other. Once you internalise that a heap sorts by “who is worst,” the inversion stops surprising you.

    The Transparent Comparator: std::greater<>

    Writing std::greater<int> repeats the element type you already named in the first template argument. Since C++14 you can drop it and write the transparent form with empty angle brackets:

    // C++14 and later — note the empty <> on greater
std::priority_queue<int, std::vector<int>, std::greater<>> minHeap;

    std::greater<> is shorthand for std::greater<void>, a specialization whose operator() is itself a template: it deduces the argument types at the call site instead of fixing them up front. There are two reasons to prefer it. First, it removes a redundant int that can drift out of sync if you later change the element type. Second, for heterogeneous comparisons it can compare without forcing a conversion — irrelevant for a heap of one type, but a genuine benefit elsewhere. For everyday code the win is simply that there is one fewer place to make a typo. The real spelling is std::greater<void>; std::greater<> is just the way you write it.

    The Negation Trick — And Exactly When It Breaks

    You will see this in competitive-programming code and you should recognise it, because it looks clever and is quietly dangerous. Instead of declaring a min-heap, people keep the default max-heap and push the negatives of their values. The largest negated value corresponds to the smallest original value, so the max-heap’s top() is the minimum — after you negate it back:

    std::priority_queue<int> maxHeap;   // ordinary max-heap
int values[] = {5, 1, 8, 3};

for (int x : values) maxHeap.push(-x);      // push the negatives
int smallest = -maxHeap.top();              // negate on the way out -> 1

    It works, for a narrow definition of “works.” Here is the honest list of everything wrong with it:

    • Signed only. On unsigned types negation wraps around modulo 2n, so -x is a huge positive number and the ordering is silently, catastrophically wrong — no warning, no crash, just wrong answers.
    • Overflow on the extreme value. For 32-bit int, -INT_MIN is not representable (its magnitude is one larger than INT_MAX). Negating INT_MIN is undefined behaviour. If any input can be INT_MIN, the trick is a landmine.
    • Numeric only. You cannot negate a std::string, a std::pair, or a struct. The moment your elements are anything but signed numbers, the trick evaporates.
    • Unreadable. Every reader has to notice the two negations and mentally undo them. Forget one and you have a bug that looks like correct code.
    Aspectstd::greater<int>push(-x) into a max-heap
    Works forAny orderable typeSigned numeric types only
    Unsigned typesFineSilently wrong (wraparound)
    INT_MIN in the dataFineUndefined behaviour (-INT_MIN overflows)
    Strings / pairs / structsFineImpossible
    ReadabilityIntent is explicitTwo hidden negations to track
    Extra costNoneNone (but fragile)

    Verdict: use std::greater. Know the negation trick so you can read other people’s code and so you understand why it is a bad default, but do not reach for it yourself. There is no performance reason to — both approaches are $O(\log n)$ per push with identical constants.

    Min-Heaps of Strings, Doubles, and Beyond

    Because std::greater orders by operator>, it works for any type that defines one. A min-heap of strings pops them in ascending lexicographic order:

    std::priority_queue<std::string, std::vector<std::string>, std::greater<>> words;
words.push("pear"); words.push("apple"); words.push("fig");
std::cout << words.top();   // prints "apple"

    Floating-point works too, with one sharp edge worth stating now and revisiting in Part 4. A comparator must impose a strict weak ordering, and NaN breaks it: every comparison involving NaN returns false, so NaN is neither less than nor greater than anything. Feed a NaN into a heap of double and the heap invariant can be violated, giving wrong results or worse. Filter NaN out before it reaches the heap.

    std::priority_queue<double, std::vector<double>, std::greater<>> minH;
// Safe as long as no NaN ever enters. If it might, guard with std::isnan().

    For std::pair, std::tuple, and your own structs, std::greater still works — it just calls their operator>, which for pairs and tuples is lexicographic. That opens up min-heaps keyed on the first field with a tie-breaker on the second, which is exactly the Dijkstra pattern; Part 5 is devoted to it.

    A Type Alias Worth Writing

    The min-heap declaration is long, and you will type it dozens of times. Give it a name once:

    using MinHeap = std::priority_queue<int, std::vector<int>, std::greater<int>>;

MinHeap h;
h.push(4); h.push(2); h.push(7);
std::cout << h.top();   // 2

    This is not just cosmetic. The alias documents intent at a glance — MinHeap h; reads better than a forty-character template — and it gives you a single place to change the backing store or the element type later. In generic code you can template the alias:

    template <class T>
using MinHeap = std::priority_queue<T, std::vector<T>, std::greater<T>>;

MinHeap<long long> big;
MinHeap<std::string> small;

    Worked Trace: {5, 1, 8, 3} Into Both Heaps

    Let us push the four values 5, 1, 8, 3 in that order into a max-heap and a min-heap, and watch the backing array after each operation. Remember: the array is the heap; index 0 is the root, and for index i the parent is (i−1)/2. A new value is appended at the end and then sifts up while it out-prioritises its parent.

    pushmax-heap array (less)max top()min-heap array (greater)min top()
    5[5]5[5]5
    1[5, 1]5[1, 5]1
    8[8, 1, 5]8[1, 5, 8]1
    3[8, 3, 5, 1]8[1, 3, 8, 5]1

    Trace the interesting rows. Pushing 1 into the max-heap: 1 is smaller than its parent 5, so it stays put — [5, 1]. Into the min-heap: 1 is smaller than 5, and in a min-heap smaller means higher priority, so it sifts up and swaps to the root — [1, 5]. Pushing 8 into the max-heap sends it to the root; into the min-heap it is the largest so far, so it sinks to a leaf. By the last row the two arrays share no ordering at all, yet both were built from identical calls in identical order — the only difference is the comparator. Note also that neither array is sorted: [8, 3, 5, 1] satisfies the parent-≥-child rule without being in descending order. A heap is ordered vertically, never left to right.

    Practice

    Min-heaps show up whenever you need the smallest live element, or a bounded “keep the k best” window.

    • LeetCode 703 — Kth Largest Element in a Stream min-heap keep a size-k min-heap; its top() is the k-th largest.
    • LeetCode 215 — Kth Largest Element in an Array min-heap a size-k min-heap solves this in $O(n \log k)$ — smaller than a full sort.
    • LeetCode 23 — Merge k Sorted Lists min-heap a min-heap of the current heads pops the global minimum each step.
    • LeetCode 1046 — Last Stone Weight max-heap the mirror image — do it with the default max-heap and appreciate the contrast.
