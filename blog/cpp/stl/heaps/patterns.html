    Classic Heap Patterns

    July 2026 · 23 min read

    Once priority_queue is routine, the value is in recognition: seeing that a problem is a heap problem before you have written a line. A handful of patterns cover the overwhelming majority of them — top-K, k-way merge, the two-heap median, Dijkstra, and interval scheduling. This post gives each one its tell, its technique, working code, and its complexity, and it is equally honest about the case where a heap is the wrong tool.

    One idea threads through all of them and is worth stating first, because it is the most muddled heap fact in interviews: to track the K largest things, you keep a min-heap. The rest of this post earns that sentence.

    Top-K Largest in O(n log k)

    You are handed a stream of $n$ numbers and want the $k$ largest. The naive answer — sort everything, take the last $k$ — is $O(n \log n)$ and needs all $n$ in memory. The heap answer is $O(n \log k)$ and holds only $k$ elements at a time. But the shape of the heap is the counter-intuitive part.

    Keep a min-heap of size $k$. Its top is the smallest of the $k$ best elements you have seen so far — your weakest current winner. For each new element $x$: if the heap is not yet full, push it; otherwise compare $x$ against the top. If $x$ is larger than your weakest winner, the weakest winner is evicted and $x$ takes its place; if $x$ is not larger, $x$ cannot possibly belong in the top $k$, so you discard it. Every decision is a single $O(\log k)$ comparison against the root.

    Why a min-heap and not a max-heap? Because the operation you repeat is “find and remove the weakest of my current winners.” That is the minimum of the retained set, and a min-heap puts exactly that at top() in $O(1)$. A max-heap would give you the strongest winner cheaply — which you never need to touch. The heap is “inverted” relative to the goal because you evict from the bottom, not the top.

    #include <queue>
#include <vector>
#include <functional>

std::vector<int> topKLargest(const std::vector<int>& nums, int k) {
    std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;  // min on top
    for (int x : nums) {
        if ((int)minHeap.size() < k) {
            minHeap.push(x);                       // room to spare — keep it
        } else if (x > minHeap.top()) {
            minHeap.pop();                         // evict the weakest winner
            minHeap.push(x);                       // and admit x
        }                                          // else: x is too small, drop it
    }
    std::vector<int> result;
    while (!minHeap.empty()) { result.push_back(minHeap.top()); minHeap.pop(); }
    return result;                                 // ascending; reverse for descending
}

    When does a plain heap lose? For a static in-memory array queried once, std::nth_element finds the $k$-th largest in $O(n)$ average and a partition hands you the top $k$ unordered — strictly better than $O(n \log k)$. The size-$k$ heap wins precisely when the data streams: unknown or unbounded length, one pass, bounded memory. That is also why Kth Largest in a Stream is a heap problem while Kth Largest in an Array is often better served by nth_element.

    ApproachTimeSpaceBest when
    Sort, take last k$O(n \log n)$$O(n)$You also need everything sorted anyway
    Size-k min-heap$O(n \log k)$$O(k)$Streaming / unknown length / $k \ll n$

    Top-K Frequent Elements

    The tell: “the $k$ most common / most frequent / highest-scoring.” Count with a hash map, then run the size-$k$ min-heap over the (frequency, value) pairs — keyed on frequency this time. Same $O(m \log k)$ shape, where $m$ is the number of distinct values.

    #include <unordered_map>
#include <queue>
#include <vector>
#include <functional>

std::vector<int> topKFrequent(const std::vector<int>& nums, int k) {
    std::unordered_map<int, int> freq;
    for (int x : nums) ++freq[x];

    using PII = std::pair<int, int>;               // {frequency, value}
    std::priority_queue<PII, std::vector<PII>, std::greater<PII>> minHeap;
    for (const auto& kv : freq) {
        minHeap.push({kv.second, kv.first});
        if ((int)minHeap.size() > k) minHeap.pop();  // keep only the k most frequent
    }
    std::vector<int> result;
    while (!minHeap.empty()) { result.push_back(minHeap.top().second); minHeap.pop(); }
    return result;
}

    There is a linear alternative worth knowing: bucket sort by frequency. A value in an array of length $n$ can appear at most $n$ times, so make $n+1$ buckets indexed by count, drop each value into its bucket, and sweep from the high end collecting $k$. That is $O(n)$ with no heap. Reach for it when $k$ is close to $m$ or when the log factor genuinely matters; the heap is the more general default.

    K-Way Merge

    Merge $k$ sorted lists (or arrays) into one. A min-heap holding the current front of each list lets you repeatedly extract the global minimum and advance only that list. With $N$ total elements the cost is $O(N \log k)$ — the log is $k$, not $N$, because the heap never holds more than $k$ items. The heap entry carries three fields: the value, which list it came from, and its index within that list.

    #include <queue>
#include <vector>

struct HeapItem {
    int val;    // the value
    int list;   // which input list
    int idx;    // position within that list
};
struct ByVal {
    bool operator()(const HeapItem& a, const HeapItem& b) const {
        return a.val > b.val;   // '>' => min-heap: the SMALLEST value sits on top
    }
};

std::vector<int> mergeKSorted(const std::vector<std::vector<int>>& lists) {
    std::priority_queue<HeapItem, std::vector<HeapItem>, ByVal> pq;
    for (int i = 0; i < (int)lists.size(); ++i)
        if (!lists[i].empty()) pq.push({lists[i][0], i, 0});

    std::vector<int> out;
    while (!pq.empty()) {
        HeapItem cur = pq.top(); pq.pop();
        out.push_back(cur.val);
        int next = cur.idx + 1;
        if (next < (int)lists[cur.list].size())
            pq.push({lists[cur.list][next], cur.list, next});  // advance that list only
    }
    return out;
}

    This is exactly how you merge $k$ sorted linked lists too — the linked-list merging post uses the same heap, storing list-head pointers instead of array indices. External merge sort, log-structured merge trees, and streaming joins are all this pattern at scale.

    Two-Heap Running Median

    Numbers arrive one at a time; after each you must report the median. Sorting on every insert is $O(n)$ per query. The elegant answer splits the data into two halves held in two heaps: a max-heap for the lower half (so its top is the largest of the small numbers) and a min-heap for the upper half (its top is the smallest of the big numbers). The two tops straddle the median.

    The invariant that makes it work: the two heaps’ sizes never differ by more than one, and by convention the lower (max) heap carries the extra element when the count is odd. Then the median is lo.top() when the sizes differ, or the average of the two tops when they are equal. Each insertion pushes onto one heap, funnels its top across to keep the halves ordered, then rebalances the sizes — all $O(\log n)$.

    #include <queue>
#include <vector>
#include <functional>

class MedianFinder {
    std::priority_queue<int> lo;                                       // max-heap: lower half
    std::priority_queue<int, std::vector<int>, std::greater<int>> hi;  // min-heap: upper half
public:
    void addNum(int num) {
        lo.push(num);                 // 1. tentatively add to the lower half
        hi.push(lo.top());            // 2. move its max into the upper half — keeps halves ordered
        lo.pop();
        if (hi.size() > lo.size()) {  // 3. rebalance so lo holds the extra when odd
            lo.push(hi.top());
            hi.pop();
        }
    }
    double findMedian() {
        if (lo.size() > hi.size()) return lo.top();       // odd count: middle is lo's top
        return (lo.top() + hi.top()) / 2.0;               // even count: average the two tops
    }
};

    The two-line funnel-then-rebalance is the whole trick: pushing onto lo and immediately shifting its top to hi guarantees every element in lo is $\le$ every element in hi, no matter the arrival order, and the size check keeps the split balanced.

    Dijkstra Without Decrease-Key

    Textbook Dijkstra wants a priority queue with decrease-key: when a shorter path to a node is found, lower that node’s key in place. std::priority_queue has no such operation — you cannot find or modify an interior entry. The standard, universally-used workaround is lazy: never update; just push a fresh (dist, node) entry with the smaller distance, and when you pop a node whose recorded distance is worse than its finalised distance, skip it as stale.

    #include <queue>
#include <vector>
#include <utility>
#include <limits>

using PII = std::pair<int, int>;   // {distance, node}

std::vector<int> dijkstra(const std::vector<std::vector<PII>>& adj, int src) {
    std::vector<int> dist(adj.size(), std::numeric_limits<int>::max());
    std::priority_queue<PII, std::vector<PII>, std::greater<PII>> pq;  // min-heap by distance
    dist[src] = 0;
    pq.push({0, src});
    while (!pq.empty()) {
        auto [d, u] = pq.top(); pq.pop();          // C++17 structured bindings
        if (d > dist[u]) continue;                 // stale entry — a better one was processed already
        for (const auto& [v, w] : adj[u]) {
            if (dist[u] + w < dist[v]) {
                dist[v] = dist[u] + w;
                pq.push({dist[v], v});             // push a fresh, smaller entry instead of decrease-key
            }
        }
    }
    return dist;
}
    Why the stale-skip is correct: the first time a node is popped, it is popped with its smallest distance (that is Dijkstra’s invariant for non-negative edges), so it is finalised then and there. Any later entry for that node carries a distance $\ge$ the finalised one, so the d > dist[u] check discards it before it can do harm. The cost of tolerating duplicates is that the heap can hold up to $O(E)$ entries, making the bound $O(E \log E)$ rather than the $O(E + V \log V)$ of a Fibonacci-heap decrease-key. Since $\log E \lt 2\log V$, that is $O(E \log V)$ — and in practice it is faster than a Fibonacci heap because of constant factors and locality. Every competitive-programming Dijkstra you have seen uses this.

    Interval and Task Scheduling

    The tell here is “how many resources run concurrently” or “merge/aggregate by soonest-finishing.” Meeting Rooms II — the minimum number of rooms for a set of meetings — is a min-heap of end times: sort meetings by start, and for each meeting free a room if the earliest-ending one has finished (top() <= start), then occupy a room with this meeting’s end. The heap size at its peak is the answer.

    #include <vector>
#include <queue>
#include <algorithm>
#include <functional>

int minMeetingRooms(std::vector<std::vector<int>>& meetings) {
    std::sort(meetings.begin(), meetings.end());   // by start time
    std::priority_queue<int, std::vector<int>, std::greater<int>> endTimes;  // soonest end on top
    for (const auto& m : meetings) {
        if (!endTimes.empty() && endTimes.top() <= m[0])
            endTimes.pop();                        // a room freed up before this meeting starts
        endTimes.push(m[1]);                       // occupy a room until this meeting ends
    }
    return (int)endTimes.size();                   // peak concurrency = rooms needed
}

    Task Scheduler (CPU cooldown) is the same family: a max-heap of remaining task counts, greedily running the most frequent task each tick while respecting a cooldown queue. Whenever the phrasing is “always take the most urgent / soonest / most frequent next,” a heap is the natural greedy engine.

    When a Heap Is the Wrong Tool: Sliding-Window Maximum

    Being honest about this matters. For the maximum of every length-$k$ window, a max-heap works: push each element, and on each step discard stale top entries whose index has slid out of the window (lazy deletion). But that is $O(n \log n)$, and it can hold far more than $k$ entries between prunes.

    A monotonic deque does it in $O(n)$. Keep indices in a deque whose values are strictly decreasing; the front is always the window maximum. Each index is pushed and popped at most once, so the whole sweep is linear.

    #include <deque>
#include <vector>

std::vector<int> maxSlidingWindow(const std::vector<int>& nums, int k) {
    std::deque<int> dq;                 // holds indices; their values are strictly decreasing
    std::vector<int> out;
    for (int i = 0; i < (int)nums.size(); ++i) {
        if (!dq.empty() && dq.front() <= i - k) dq.pop_front();      // drop indices that slid out
        while (!dq.empty() && nums[dq.back()] <= nums[i]) dq.pop_back();  // drop smaller-or-equal tails
        dq.push_back(i);
        if (i >= k - 1) out.push_back(nums[dq.front()]);            // front is the window max
    }
    return out;
}

    The lesson generalises: a heap gives you a global extreme cheaply, but when the structure of the queries is a moving window — strictly FIFO expiry — a deque exploits that structure to beat the heap by a whole log factor.

    Map the phrasing to the pattern to the structure. This is the table to internalise.

    Worked Trace: Top-3 Min-Heap

    The stream 5 1 8 3 9 2 7 through a size-3 min-heap. The heap column is shown smallest-first, so the leftmost value is top() — the one an eviction removes.

    read   heap.top()   decision                  heap (min first)
--------------------------------------------------------------
5      —            size 0 < 3, push          {5}
1      5            size 1 < 3, push          {1, 5}
8      1            size 2 < 3, push          {1, 5, 8}
3      1            3 > 1  -> evict 1, push 3 {3, 5, 8}
9      3            9 > 3  -> evict 3, push 9 {5, 8, 9}
2      5            2 > 5? no -> discard 2    {5, 8, 9}
7      5            7 > 5  -> evict 5, push 7 {7, 8, 9}
--------------------------------------------------------------
result: the 3 largest are {7, 8, 9}

    Every kept-or-dropped decision was one comparison against top(). The min-heap earned its place by making “who is the weakest of my winners?” an $O(1)$ question.
