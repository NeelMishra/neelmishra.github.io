    Custom Comparator Functions

    July 2026 · 22 min read

    std::less and std::greater cover the two cases where you order by the value itself. Everything else — order by absolute value, by distance from a target, by a field of a struct, by a key looked up in another array — needs a comparator you write. There are four ways to supply one, they differ in real ways, and one very common mistake in writing them is not a wrong answer but undefined behaviour. This post walks all four forms and the rules every one of them must obey.

    The Comparator Contract

    A heap comparator is a binary predicate: a callable that takes two elements and returns bool. The heap invokes it as comp(a, b), and the meaning is fixed and worth committing to memory:

    comp(a, b) == true means “a has lower priority than b” — equivalently, “a should sit below b in the heap.” The element that is never found to have lower priority than another is the one top() returns. With std::less (a < b), the smallest has lower priority, so the largest rises. Flip the predicate and you flip the heap.

    This is the same rule that runs through the whole series, and it is the fastest way to get a comparator right on the first try. Decide which element you want on top, then write the predicate so that the other element is the one reported as lower priority. If you want the closest-to-a-target element on top, then the farther element has lower priority, so comp(a, b) returns “a is farther than b.” Everything below is just four syntaxes for expressing that one idea.

    Form 1 — A Struct with operator()

    The canonical comparator is a small struct that overloads the function-call operator. It is called a function object, or functor. This is what std::less and std::greater actually are.

    #include <queue>
#include <vector>
#include <cmath>

struct ByAbsValue {
    bool operator()(int a, int b) const {   // note: const
        return std::abs(a) < std::abs(b);    // larger magnitude on top
    }
};

std::priority_queue<int, std::vector<int>, ByAbsValue> pq;
pq.push(-10); pq.push(3); pq.push(-7);
std::cout << pq.top();   // -10  (magnitude 10 is the largest)

    Two details matter and are easy to get wrong. First, operator() should be const: the heap holds the comparator as a member and calls it on a const object, so a non-const operator() can fail to compile or silently prevent the comparator from being used where you expect. Second, for anything heavier than an int — strings, structs, vectors — take the arguments by const& to avoid copying two elements on every single comparison, of which a heap does $O(\log n)$ per operation:

    struct ByLength {
    bool operator()(const std::string& a, const std::string& b) const {
        return a.size() < b.size();   // longest string on top
    }
};

    The functor is the form to reach for when the comparator is reused across several call sites, or when it needs to carry data (a target value, a lookup table) as a member. It names a real type, so you can spell that type wherever you need it, with no decltype gymnastics.

    Form 2 — Lambdas

    Lambdas are where most people get stuck, because a priority_queue is a type and a lambda is a value of an unnamable type. Bridging that gap changed in C++20, so there are two stories to tell.

    Before C++20: the decltype-and-constructor dance

    A lambda’s closure type has, before C++20, no default constructor. The priority_queue needs to store a comparator instance, and if it cannot default-construct one, you must hand it the instance yourself. So there are two moves, and you need both:

    auto cmp = [](int a, int b) { return a > b; };   // a min-heap predicate

// 1. name the comparator TYPE with decltype(cmp)
// 2. PASS the lambda to the constructor so the queue has one to store
std::priority_queue<int, std::vector<int>, decltype(cmp)> pq(cmp);

pq.push(5); pq.push(1); pq.push(8);
std::cout << pq.top();   // 1

    Miss the constructor argument — write pq; instead of pq(cmp) — and pre-C++20 you get a compile error, because the queue tries to default-construct a closure type that has no default constructor. The two steps are not redundant: decltype(cmp) supplies the type the template needs, and (cmp) supplies the value the object needs to hold. This is the single most-copied incantation in competitive C++, and now you know why each half is there.

    C++20: stateless lambdas need no instance

    C++20 made stateless (captureless) lambdas default-constructible and usable in unevaluated contexts. That means you can name the type with decltype on a throwaway lambda expression and skip the constructor argument entirely:

    // C++20 — stateless lambda, default-constructed by the queue, no instance passed
std::priority_queue<int, std::vector<int>,
                    decltype([](int a, int b) { return a > b; })> pq;

pq.push(5); pq.push(1); pq.push(8);
std::cout << pq.top();   // 1

    This compiles under -std=c++20 and is genuinely cleaner. The catch is in the word stateless: the moment the lambda captures anything, it is no longer default-constructible, even in C++20, and you are back to the pre-C++20 dance of naming the type and passing the instance. So this shortcut is for capture-free comparators only.

    The std::function option

    You can sidestep the whole type puzzle by declaring the comparator type as std::function<bool(int,int)>. Any lambda — capturing or not — converts to it, and it is a normal, spellable type:

    #include <functional>

std::function<bool(int,int)> cmp = [](int a, int b) { return a > b; };
std::priority_queue<int, std::vector<int>, std::function<bool(int,int)>> pq(cmp);

    It works and it is flexible, but it is not free. std::function is type-erased: every comparison goes through an indirect call that the compiler generally cannot inline, and a heap comparison sits in the hottest inner loop you have. In benchmarks this is routinely measurably slower — often noticeably so on comparison-bound workloads. Use it when flexibility matters more than the last bit of speed; avoid it in a hot path.

    Form 3 — Function Pointers

    For completeness: a plain free function plus a function-pointer type also works. You pass the function to the constructor, because a function-pointer comparator has no meaningful default value.

    bool cmp(int a, int b) { return a > b; }   // min-heap predicate

std::priority_queue<int, std::vector<int>, bool(*)(int,int)> pq(cmp);

    The downside is performance. Calling through a function pointer is an indirect call the compiler usually cannot inline, so like std::function it loses the inlining that makes a functor or a lambda essentially free. It is slower than a functor and carries no state. There is rarely a reason to prefer it over a functor or a captureless lambda, but you will see it, so it belongs in the catalogue.

    Strict Weak Ordering — The Rules You Cannot Break

    Every comparator you write must impose a strict weak ordering. This is not pedantry: the standard library assumes it, and violating it is undefined behaviour, not a wrong-but-survivable result. The four requirements, with what each actually means:

    • Irreflexivity: comp(a, a) must be false. An element is never lower priority than itself.
    • Asymmetry: if comp(a, b) is true then comp(b, a) must be false. Two elements cannot each be below the other.
    • Transitivity: if comp(a, b) and comp(b, c), then comp(a, c). Priority does not form loops.
    • Transitivity of equivalence: if a is equivalent to b (neither is below the other) and b is equivalent to c, then a is equivalent to c. The “ties” are consistent.
    The bug that bites in production: writing <= where you meant <. The comparator return a <= b; makes comp(a, a) return true, violating irreflexivity. That is undefined behaviour — not merely a wrong order. In practice it can walk off the end of the container, corrupt the heap, loop forever, or appear to work until the input grows. Your comparator must use a strict relation (< or >), never <= or >=. When you need a tie-breaker, break the tie on a different field — never by making the primary comparison non-strict.

    The reason a non-strict comparator is dangerous rather than merely wrong is that the sift routines use the comparator to decide when to stop. If comp(a, a) is true, an element can be judged “lower priority than itself,” and the loop that should terminate keeps swapping, reading past valid indices. The symptom often appears far from the cause, which is what makes it a genuine time-sink to debug.

    Stateful Comparators

    A comparator may carry data. The classic case is a heap of indices ordered by values held in a separate array — you push cheap integers but order them by an external key:

    std::vector<int> score = {30, 10, 50, 20};

// Order indices so the one with the SMALLEST score is on top (a min-heap on score).
auto byScore = [&score](int i, int j) { return score[i] > score[j]; };
std::priority_queue<int, std::vector<int>, decltype(byScore)> pq(byScore);

for (int i = 0; i < 4; ++i) pq.push(i);
std::cout << pq.top();   // 1  (index 1 has the smallest score, 10)

    This is powerful — it is how you keep large objects out of the heap and move only indices — but it comes with a sharp warning. The comparator holds a reference to score. If you mutate score while indices are still in the heap, the ordering the heap was built on quietly becomes false. The heap does not re-sort itself; its invariant is silently corrupted, and top() may no longer be the minimum. Rule: while elements are in a heap ordered by external state, treat that state as frozen. If a key must change, the standard workaround is lazy re-insertion, covered in Part 7.

    The Four Forms, Side by Side

    All four express the same predicate; they differ in verbosity, the standard they need, whether the compiler can inline them, and whether they can hold state.

    FormVerbosityC++ versionInlined?Carries state?
    Functor (struct operator())Most, but explicitC++98YesYes (members)
    LambdaLeastC++11 (decltype + ctor arg); C++20 stateless needs no instanceYesYes (captures), but capturing loses default-construct
    Function pointerLowC++98No (indirect call)No
    std::functionLowC++11No (type-erased)Yes

    The practical takeaway: default to a functor for anything reusable or stateful, and to a lambda for a local one-off — captureless with the C++20 shortcut if you can, or the decltype-plus-constructor form otherwise. Reserve std::function and function pointers for when their flexibility is worth the lost inlining.

    One Comparator, Three Ways

    To prove the forms are interchangeable, here is a single order — “closest to a target value on top” — written as a functor, a pre-C++20 lambda, and a C++20 lambda. The target is 5; the element nearest 5 must surface. Farther means lower priority, so each predicate returns “a is farther than b.”

    #include <queue>
#include <vector>
#include <cmath>

const int TARGET = 5;

// (a) Functor
struct ByDistance {
    bool operator()(int a, int b) const {
        return std::abs(a - TARGET) > std::abs(b - TARGET);
    }
};

// (b) Pre-C++20 lambda: name the type, pass the instance
auto lam = [](int a, int b) { return std::abs(a - TARGET) > std::abs(b - TARGET); };

// (c) C++20 stateless lambda: default-constructed, no instance needed
using PQc = std::priority_queue<int, std::vector<int>,
              decltype([](int a, int b) { return std::abs(a - TARGET) > std::abs(b - TARGET); })>;

int data[] = {1, 8, 4, 11, 7};

std::priority_queue<int, std::vector<int>, ByDistance> pa;
std::priority_queue<int, std::vector<int>, decltype(lam)> pb(lam);
PQc pc;
for (int x : data) { pa.push(x); pb.push(x); pc.push(x); }
// all three pop the same order: 4 7 8 1 11  (distances 1,2,3,4,6 from 5)

    All three produce identical output because they encode the same strict weak ordering; only the plumbing differs. The functor names a type you can reuse; the pre-C++20 lambda needs the constructor argument; the C++20 lambda needs neither because it captures nothing.
