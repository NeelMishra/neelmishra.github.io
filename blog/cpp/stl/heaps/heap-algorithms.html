    The <algorithm> Heap Family

    July 2026 · 21 min read

    std::priority_queue is convenient, but it is a locked box: you cannot iterate it, inspect its middle, serialise it, or bulk-load it after construction. Underneath that box is a set of six free functions in <algorithm> that operate directly on any random-access range — usually a std::vector you still own. Learn them and you can heapify data in place, run heapsort in four lines, validate a heap in a test, and — the payoff of this post — rebuild priority_queue yourself in about twenty-five lines, which retroactively demystifies everything from Part 2 onward.

    All six functions default to std::less, which means max-heap: the comparator answers “does a have lower priority than b?” and the element never judged lower-priority ends up at first. Every function takes an optional trailing comparator, exactly like std::sort.

    Two Layers of Heap API

    The standard library gives you heaps at two levels, and they are not competitors — one is built out of the other. The adaptor hides the container so you cannot corrupt the invariant by writing to the middle. The algorithms hand you the raw range and trust you to keep it a heap. When you need to iterate, inspect, or heapify data you already hold, drop to the algorithms.

    #include <algorithm>   // make_heap, push_heap, pop_heap, sort_heap, is_heap, is_heap_until
#include <vector>
#include <iostream>

int main() {
    std::vector<int> v{3, 1, 6, 5, 2, 4};
    std::make_heap(v.begin(), v.end());   // v is now a max-heap, in place
    std::cout << v.front() << '\n';        // 6 — the largest, always at index 0
}

    Every function below is a member of this family. Read them in the order a heap actually lives its life: build, grow, shrink, sort.

    make_heap — O(n) Heapify

    std::make_heap(first, last[, comp]) rearranges the elements of [first, last) so they satisfy the max-heap property, in place, in $O(n)$ time — at most $3n$ comparisons. It is not $O(n \log n)$; the bottom-up build sums $\sum_h \frac{n}{2^{h+1}} \cdot h = O(n)$ because the cheap deep levels vastly outnumber the expensive shallow ones. Part 1 proves this sum.

    std::vector<int> v{3, 1, 6, 5, 2, 4};
std::make_heap(v.begin(), v.end());
// v == {6, 5, 4, 1, 2, 3}  — a valid max-heap (one of several valid orderings)

    Precondition: none — any random-access range works. This is the single cheapest way to turn a pile of data into a heap. If you find yourself pushing $n$ known elements one at a time to build a heap, stop: construct the vector and call make_heap once, or hand the range to a priority_queue constructor, which does exactly this internally.

    push_heap — Append First, Then Sift

    This one has a contract that trips up nearly everyone. std::push_heap(first, last[, comp]) assumes [first, last-1) is already a heap and that the new element is sitting at last-1. It then sifts that last element up to its correct position in $O(\log n)$. It does not take the value to insert — it works on whatever is already at the back.

    So the insertion is always two steps, in this order:

    v.push_back(7);                       // 1. append to the CONTAINER yourself
std::push_heap(v.begin(), v.end());   // 2. sift that new last element up
// before: {6,5,4,1,2,3,7}  ->  after: {7,5,6,1,2,3,4}

    Reverse the two lines and it breaks silently: push_heap would sift up whatever was previously last, and your real new value would be appended afterward, unheaped. The mental model: push_back grows the tree at the next complete-tree slot; push_heap bubbles it up until its parent is no smaller.

    pop_heap — It Removes Nothing

    Here is the single biggest source of confusion in the whole family. std::pop_heap(first, last[, comp]) does not remove anything and does not shrink the container. It swaps the max element (at first) with the element at last-1, then sifts the new root down so that [first, last-1) is a valid heap again. The old maximum is now sitting at last-1, fully intact. Removing it is your job:

    std::pop_heap(v.begin(), v.end());   // max moves to v.back(); [begin, end-1) is re-heaped
int biggest = v.back();              // read the extracted maximum
v.pop_back();                        // NOW actually remove it from the container
// before: {7,5,6,1,2,3,4}
// after pop_heap:  {6,5,4,1,2,3,7}   <- the 7 is parked at the end, not gone
// after pop_back:  {6,5,4,1,2,3}
    Why the standard splits it this way: algorithms operate on iterators, and iterators cannot resize the container they came from — a raw pointer pair has no idea whether it points into a vector, a C array, or a sub-range. So pop_heap does the only thing an iterator-based function can: it moves the max out of the heap region and leaves the container size to you. This is exactly why the two-step pop_heap + pop_back dance exists, and why forgetting the pop_back leaves a “removed” element haunting the back of your vector.

    The upside of this design is that pop_heap gives you sorted output for free: each pop deposits the next-largest element just before the shrinking heap region. Do it $n$ times and the range is sorted ascending — which is precisely sort_heap.

    sort_heap — Heapsort in Four Lines

    std::sort_heap(first, last[, comp]) assumes [first, last) is already a heap and turns it into a sorted range by repeatedly calling pop_heap, in $O(n \log n)$. For a max-heap (default comparator) the result is ascending.

    std::vector<int> heapsort(std::vector<int> v) {
    std::make_heap(v.begin(), v.end());   // O(n)
    std::sort_heap(v.begin(), v.end());   // O(n log n)
    return v;                             // ascending
}
// {3,1,6,5,2,4} -> make_heap -> {6,5,4,1,2,3} -> sort_heap -> {1,2,3,4,5,6}

    That is a complete, correct, in-place heapsort. So why does std::sort not use it? Be honest about the trade-off:

    Heapsort (make_heap+sort_heap)std::sort (introsort)
    Worst case$O(n \log n)$ — guaranteed$O(n \log n)$ — guaranteed (that is the point of introsort)
    Typical constantsLarger; every sift-down is a long dependent chainSmaller; quicksort partitions stream through memory
    Cache localityPoor — sift-down jumps by factors of twoGood — partitioning is sequential
    Extra space$O(1)$, no recursion$O(\log n)$ recursion stack
    Stable?NoNo

    Introsort runs quicksort for speed, switches to heapsort only when recursion depth exceeds $\approx 2\log n$ (the guard that kills quicksort’s $O(n^2)$ worst case), and finishes small ranges with insertion sort. Heapsort is the safety net, not the default, precisely because of those worse constants and poor locality. When you genuinely need a hard $O(n \log n)$ ceiling with zero extra memory and no recursion — embedded, real-time — heapsort earns its keep.

    is_heap and is_heap_until

    Two validation functions that are worth their weight in tests and assertions. std::is_heap(first, last[, comp]) returns whether the whole range is a heap in $O(n)$. std::is_heap_until(first, last[, comp]) returns an iterator to the first position that breaks the heap property — everything before it is a valid heap.

    #include <cassert>

std::vector<int> v{6, 5, 4, 1, 2, 3};
assert(std::is_heap(v.begin(), v.end()));                 // passes

std::vector<int> broken{6, 9, 4, 1, 2, 3};                // 9 > its parent 6
auto it = std::is_heap_until(broken.begin(), broken.end());
// it points at broken[1] (the 9): the range [begin, it) is a valid heap

    Reach for these whenever you hand-manipulate a heap or write a custom heap structure: an assert(std::is_heap(...)) after each mutation turns a class of silent corruption bugs into loud, immediate failures.

    The Full Lifecycle

    Watch a single vector go through the entire family: make_heap to build, push_back+push_heap to grow, pop_heap+pop_back to shrink, then sort_heap to finish. The tree and the backing array are the same memory. Pay attention to the pop_heap frame — the maximum lands at the end of the array and is still there.

    ▶ make_heap → push_heap → pop_heap → sort_heap

    Each step names the function running. The heap tree is on top; the same bytes as an indexed array are below it. After pop_heap, note the max sitting in the last cell — nothing was removed until pop_back.

    Why Not Just priority_queue?

    The adaptor is the right default when all you ever do is push, pop, and peek. But it deliberately seals the container away, and there is a long list of ordinary things you cannot do through it:

    You want to…std::priority_queueHeap on a vector you own
    Iterate all elementsNo iterators existYes — it is your vector
    Inspect an element that is not the topNoYes, by index
    Serialise / print the contentsNo (must pop everything, destroying it)Yes, read-only
    reserve() capacity up frontNo direct access to the containerYes — v.reserve(n) before building
    Bulk-load $n$ itemsOnly via the range constructorYes — fill, then one make_heap
    Guarantee you cannot corrupt the invariantYes — the whole pointNo — discipline is on you

    And here is the demystifier promised at the top: priority_queue is a thin wrapper over exactly these functions. A faithful, compiling reimplementation of its core is about twenty-five lines — everything from Parts 2–4 is just this:

    #include <vector>
#include <algorithm>
#include <functional>
#include <utility>
#include <cstddef>

template <class T, class Container = std::vector<T>, class Compare = std::less<T>>
class MyPriorityQueue {
    Container c;      // the sealed-away backing store
    Compare  comp;    // "does a have lower priority than b?"
public:
    MyPriorityQueue() = default;
    explicit MyPriorityQueue(const Compare& cmp) : comp(cmp) {}

    bool         empty() const { return c.empty(); }
    std::size_t  size()  const { return c.size(); }
    const T&     top()   const { return c.front(); }   // extreme element at index 0

    void push(const T& value) {
        c.push_back(value);                            // 1. append
        std::push_heap(c.begin(), c.end(), comp);      // 2. sift up  — O(log n)
    }
    template <class... Args>
    void emplace(Args&&... args) {
        c.emplace_back(std::forward<Args>(args)...);    // construct in place
        std::push_heap(c.begin(), c.end(), comp);
    }
    void pop() {
        std::pop_heap(c.begin(), c.end(), comp);       // max -> back, re-heap front
        c.pop_back();                                  // then drop it — O(log n)
    }
};

    That is genuinely close to what your standard library ships. The three template parameters, the void-returning pop(), the missing iterators, the “inverted” std::greater min-heap — all of it falls out of this handful of lines. Nothing about priority_queue is magic; it is push_heap and pop_heap with a lid on the box.

    Heap-Adjacent Tools: partial_sort and nth_element

    Two more <algorithm> functions lean on the heap idea and answer questions people wrongly throw a full heap at. std::partial_sort(first, middle, last) puts the smallest middle - first elements, sorted, at the front and leaves the rest unspecified — it is implemented with a heap and runs in $O(n \log k)$ where $k$ is the prefix length. std::nth_element(first, nth, last) places the element that would be at nth in a fully sorted range into that position, with everything smaller before it and everything larger after, in $O(n)$ average.

    std::vector<int> v = load();
std::size_t k = 3;

std::partial_sort(v.begin(), v.begin() + k, v.end());  // 3 smallest, sorted, up front — O(n log k)
std::nth_element(v.begin(), v.begin() + k, v.end());   // element k in sorted position — O(n) avg

    For a static array you already hold, nth_element beats any heap for “find the k-th” and partial_sort beats it for “the sorted top-k”. The heap wins when data streams in of unknown length — Part 7 makes that boundary precise. One more practical note: priority_queue exposes no reserve(), so if you know the size, prefer a vector you can reserve(n) and then make_heap — you avoid the reallocation churn the adaptor cannot let you skip.

    Worked Trace

    The exact array after each call, starting from {3,1,6,5,2,4} (these are the real values libstdc++ produces — a heap ordering is not unique, but this one is reproducible):

    operation        array
-------------------------------------------
start            {3, 1, 6, 5, 2, 4}
make_heap        {6, 5, 4, 1, 2, 3}     <- O(n); 6 rises to index 0
push_back(7)     {6, 5, 4, 1, 2, 3, 7}  <- container grew; tail may violate heap
push_heap        {7, 5, 6, 1, 2, 3, 4}  <- 7 sifted up to the root, O(log n)
pop_heap         {6, 5, 4, 1, 2, 3, 7}  <- MAX (7) swapped to the END, not removed
pop_back         {6, 5, 4, 1, 2, 3}     <- you shrink the container yourself
sort_heap*       {1, 2, 3, 4, 5, 6}     <- *from a fresh make_heap; ascending
-------------------------------------------

    Trace the pop_heap line by hand: swap index 0 (7) with index 6 (4) → {4,5,6,1,2,3,7}; sift the 4 down over [0,6), its larger child is 6 at index 2, swap → {6,5,4,1,2,3,7}; 4’s only child now is 3, which is smaller, so stop. The 7 never moved from index 6 — it is the extracted maximum, waiting for your pop_back.
