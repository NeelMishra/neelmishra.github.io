    Heaps & Priority Queues — Min-Heap, Max-Heap & Custom Comparators

    July 2026 · 30 min read

    A heap answers one specific question: what is the best item right now, in a collection that keeps changing? Sorting answers it too, but sorting gives you a total order you did not ask for and charges $O(n \log n)$ every time the data changes. A heap gives you only the extreme element — in $O(1)$, with $O(\log n)$ to insert or remove.

    That single trade is why heaps sit underneath Dijkstra's algorithm, every task scheduler, k-way merges, streaming top-K, and the running-median problem. In C++ the abstraction is std::priority_queue, and in practice you only ever declare it in one of three shapes: a max-heap, a min-heap, or a custom-ordered heap. This post covers all three end to end — how to declare them, why they are spelled the way they are, and everything that goes wrong.

    The surprise, up front: std::priority_queue is a max-heap by default. Its comparator defaults to std::less, yet top() returns the largest element. To get a min-heap you pass std::greater. That inversion trips up nearly everyone, and the next section explains exactly why the standard is written that way.

    The Three Declarations, Up Front

    If you came here for the recipe, it is these three lines. The rest of the post is why they work and what breaks them.

    #include <queue>
#include <vector>
#include <functional>
#include <cmath>

// 1. MAX-HEAP — the default. top() is the LARGEST.
std::priority_queue<int> maxHeap;

// 2. MIN-HEAP — top() is the SMALLEST. All three template arguments are
//    required: you cannot name the comparator without naming the container.
std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;

// 3. CUSTOM — any strict weak ordering you like.
struct ByAbsValue {
    bool operator()(int a, int b) const {
        return std::abs(a) < std::abs(b);   // largest magnitude on top
    }
};
std::priority_queue<int, std::vector<int>, ByAbsValue> customHeap;

    The One Rule That Makes All Three Click

    Do not memorise three separate behaviours. Memorise one sentence:

    comp(a, b) == true means “a has lower priority than b” — equivalently, “a belongs below b in the heap.” The element that is never judged lower-priority is the one top() returns.

    Now run the three cases through it. With std::less, comp(a, b) is a < b, so “lower priority” means “numerically smaller”; small values sink and the largest surfaces — a max-heap. With std::greater, comp(a, b) is a > b, so “lower priority” means “numerically larger”; large values sink and the smallest surfaces — a min-heap. With a custom predicate, whatever you declare to be “worse” sinks. Same machinery, three verdicts.

    The std::sort contrast that confuses everyone

    Feed the same std::greater to std::sort and you get descending order — largest first. Feed it to priority_queue and you get a min-heap — smallest first. The same comparator appears to do opposite things:

    std::vector<int> v = {5, 1, 8, 3, 9};

std::sort(v.begin(), v.end(), std::greater<int>());
// v is now {9, 8, 5, 3, 1}  — DESCENDING, largest first

std::priority_queue<int, std::vector<int>, std::greater<int>> pq(v.begin(), v.end());
// pq.top() is 1            — MIN-HEAP, smallest first

    The resolution is that the two algorithms ask the comparator different questions. std::sort reads comp(a, b) == true as “a should come before b in the output,” so with greater the larger element goes first: descending. std::priority_queue reads the very same result as “a is worse than b, so a sinks,” so with greater the larger element sinks and the smaller rises. sort puts “lesser” first; the heap puts “lesser” last. Once you see that, you never have to remember it backwards again.

    What a Heap Actually Is

    A binary heap is a complete binary tree that satisfies the heap property: every parent compares no worse than its children. In a max-heap every parent is $\ge$ its children; in a min-heap every parent is $\le$ its children. That is the entire invariant — note that it says nothing about siblings, which is why a heap is not sorted.

    Two consequences do all the work. First, the extreme element is always at the root, so reading it is $O(1)$. Second — the underrated part — because the tree is complete, it packs into a flat array with no pointers at all:

    parent(i) = (i - 1) / 2
left(i)   = 2 * i + 1
right(i)  = 2 * i + 2

    So a heap is a plain std::vector you have agreed to interpret in a particular way. No nodes, no per-element allocation, and traversal that walks contiguous memory — compare that with std::map, where every element is a separately allocated red-black node reached by chasing pointers.

    Only two operations maintain the invariant. Sift-up (after a push) walks a new element toward the root while it outranks its parent. Sift-down (after a pop) walks the displaced root downward while a child outranks it. Both touch one node per level, hence $O(\log n)$. Step through them here:

    ▶ Sift Up & Sift Down

    The only two operations a heap needs. Push appends to the end and sifts the new value up until its parent is larger; pop moves the last element to the root and sifts it down. Watch the array below the tree — both views are the same memory.

    The cost model

    Memorise this table. Nearly every “should I use a heap here?” decision falls out of it.

    OperationComplexityNote
    top()$O(1)$Just reads element 0.
    push()$O(\log n)$Amortised — the underlying vector may reallocate.
    pop()$O(\log n)$Always a full sift-down of the last element.
    make_heap()$O(n)$Not $O(n \log n)$ — the bottom-up build sums to $O(n)$.
    sort_heap()$O(n \log n)$Repeated pops; this is heapsort.
    Search for arbitrary value$O(n)$A heap is not a search structure. Use a set.
    Delete arbitrary element$O(n)$Finding it dominates. See lazy deletion.
    Decrease-key—Not supported. Workaround in Dijkstra.

    Why is make_heap only $O(n)$? Because a bottom-up build sifts each node down by at most its height, and heights are wildly unequal: half the nodes are leaves with height 0, a quarter have height 1, and so on. The total work is $\sum_{h} \frac{n}{2^{h+1}} \cdot h = n \sum_h \frac{h}{2^{h+1}}$, and that series converges to 1 — giving $O(n)$, at most $3n$ comparisons. Pushing $n$ elements one at a time is $O(n \log n)$ instead, because sift-up pays the full height for the many leaf-level insertions.

    Max-Heap: the Default std::priority_queue

    std::priority_queue is not a container in the way std::vector is. It is a container adaptor: a thin class template that wraps an underlying sequence container and re-exposes it through a deliberately narrow interface. It keeps the container in a protected member named c and the comparator in one named comp, and forwards all real work to c and to the <algorithm> heap functions.

    AdaptorDisciplineDefault containerKey access
    std::stackLIFOstd::dequetop() = most recently pushed
    std::queueFIFOstd::dequefront() = least recently pushed
    std::priority_queuehighest-priority-firststd::vectortop() = highest priority

    The full template signature

    Every confusing behaviour is spelled out in the declaration:

    template<
    class T,
    class Container = std::vector<T>,
    class Compare   = std::less<typename Container::value_type>
> class priority_queue;
    • T — the element type. The only one you always supply.
    • Container — the backing store, defaulting to std::vector<T>. It must be a random-access sequence container providing front(), push_back(), and pop_back(); in practice std::vector (almost always right) or std::deque. std::list cannot be used at all — the heap algorithms need random access.
    • Compare — a binary predicate defining priority, defaulting to std::less<T>, which is what makes the default a max-heap.

    The member functions

    push(x)Insert x (copies or moves it in)$O(\log n)$

    #include <queue>
#include <string>
#include <utility>

struct Task {
    int priority;
    std::string name;
    Task(int p, std::string n) : priority(p), name(std::move(n)) {}
    bool operator<(const Task& other) const { return priority < other.priority; }
};

int main() {
    std::priority_queue<Task> pq;
    pq.push(Task(2, "build"));   // build a temporary Task, then move it in
    pq.emplace(5, "deploy");      // construct the Task directly inside the heap
    // top() is {5, "deploy"} — operator< compares priority, and less => max-heap
}
    A real bug source: top() on an empty queue is undefined behaviour — it reads c.front() with no bounds check and no exception. It will not throw std::out_of_range the way vector::at does. Always gate access with if (!pq.empty()). The same applies to pop().

    Why pop() returns void

    Newcomers expect pop() to hand back the element it removes. It returns void instead, and the reason is exception safety. Imagine the alternative T pop(): returning by value must construct a T in the caller. If that copy or move constructor throws, the element has already left the container but never reaches the caller — gone, unrecoverably. There is no way to write a strongly exception-safe “remove and return” in one step, so the standard splits it: top() lets you observe (and copy out on your terms, where a throw leaves the queue untouched), and pop() then discards.

    std::string best = pq.top();   // 1. observe / copy out
pq.pop();                       // 2. remove; returns void

// If copying is expensive you may MOVE out of top() immediately before popping.
// top() is const, so this needs a const_cast — safe ONLY because the very next
// statement destroys the moved-from slot.
std::string moved = std::move(const_cast<std::string&>(pq.top()));
pq.pop();

    Construction, including the $O(n)$ range trick

    Passing a pair of iterators copies the range into the container and heapifies it with a single internal make_heap, which is $O(n)$. Building the same heap by pushing $n$ elements is $O(n \log n)$. There is also no reserve() on the adaptor — it hides the container — so the range constructor is also how you avoid $O(\log n)$ reallocations:

    std::vector<int> v = {5, 1, 8, 3, 9, 2, 7};

// O(n): one allocation + one make_heap over the copied range.
std::priority_queue<int> fast(v.begin(), v.end());

// O(n log n): n separate sift-ups, plus repeated reallocation. Same heap, more work.
std::priority_queue<int> slow;
for (int x : v) slow.push(x);

    The animation below opens the adaptor up: watch a run of push and pop calls drive the hidden vector through push_heap and pop_heap. The public interface never changes shape; all the motion is underneath.

    Top: the public priority_queue call. Bottom: the private std::vector it forwards to. Each push/pop is really a push_heap/pop_heap plus a push_back/pop_back on that vector.

    No iterators, by design

    std::priority_queue has no begin(), no end(), no way to range-for over it. That is deliberate: the heap invariant is fragile, a single write to the wrong element breaks it silently, and every later top() then returns garbage. Hiding the container makes that class of bug unrepresentable through the public surface.

    When you genuinely need to inspect every element, you have two honest options. The clean one is to skip the adaptor and use the <algorithm> functions on a vector you own. The other is the sanctioned escape hatch — derive and read the protected member c:

    // priority_queue keeps its container as the protected member `c`.
struct PeekPQ : std::priority_queue<int> {
    const std::vector<int>& heap() const { return c; }   // read-only view of c
};

PeekPQ pq;
pq.push(3); pq.push(1); pq.push(4); pq.push(1); pq.push(5);
for (int x : pq.heap()) std::cout << x << ' ';   // e.g. 5 4 3 1 1 — heap order, NOT sorted

    Two cautions. The member is guaranteed by the standard to be named c, so this is portable — but expose it read-only; hand out a non-const reference and you have reopened the exact hole the adaptor closed. And remember what you are looking at: heap order is only partially sorted, never a sorted sequence.

    Watching the vector

    Trace a max-heap of int through four pushes and two pops, following the internal vector c:

    Public callInternal workVector c aftertop()
    pq.push(5)push_back, sift-up[5]5
    pq.push(8)push_back, 8 bubbles over 5[8, 5]8
    pq.push(3)push_back, 3 stays put[8, 5, 3]8
    pq.push(10)push_back, 10 bubbles to root[10, 8, 3, 5]10
    pq.pop()swap root/last, pop_back, sift-down[8, 5, 3]8
    pq.pop()swap root/last, pop_back, sift-down[5, 3]5

    Notice the vector is never sorted — [10, 8, 3, 5] has 5 sitting after 3 — yet top() is correct at every step.

    Min-Heap: std::greater and Nothing Else

    Roughly half the time you want the opposite of the default: the smallest element first, for Dijkstra, streaming top-K, or merging sorted lists. Here is the one line that flips it — copy it, paste it, keep it somewhere you can find it:

    #include <queue>
#include <vector>
#include <functional>   // std::greater

std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;

minHeap.push(5);
minHeap.push(1);
minHeap.push(8);
std::cout << minHeap.top();   // prints 1 — the SMALLEST

    Why you must name the container to name the comparator

    Template parameters are positional. C++ has no way to say “keep the default container but change the third parameter” — there are no keyword arguments. So the natural-looking two-argument attempt does not do what you hope:

    // WRONG — you meant "int elements, greater comparator".
// The compiler reads it as "int elements, greater<int> CONTAINER".
std::priority_queue<int, std::greater<int>> pq;   // does NOT compile

    A priority_queue's container must behave like a sequence: it needs a value_type, a push_back, a pop_back, a front. A comparator has none of those, so you get a wall of template noise whose first useful line is essentially:

    error: no type named 'value_type' in 'struct std::greater<int>'

    When you see “no type named value_type” pointing at a comparator, this is always the cause: you skipped the container argument.

    The mnemonic: “type, tank, test.” The type you store, the tank it lives in (std::vector, always, unless you have a specific reason), and the test that orders it (std::greater for a min-heap). You cannot skip the tank to get to the test.
    DeclarationComparatortop() for input {5, 1, 8, 3, 9}Heap
    priority_queue<int>std::less (default)9 (largest)max-heap
    priority_queue<int, vector<int>, greater<int>>std::greater1 (smallest)min-heap

    ▶ Same Input, Two Comparators

    Push the same five values — 5, 1, 8, 3, 9 — into a max-heap (std::less) and a min-heap (std::greater) at the same time. Tree and backing array are the same memory; the highlighted root is top(). Watch the two roots diverge immediately.

    The transparent comparator: std::greater<>

    Writing std::greater<int> repeats the element type you already named. Since C++14 you can drop it:

    // C++14 and later — note the empty <> on greater
std::priority_queue<int, std::vector<int>, std::greater<>> minHeap;

    std::greater<> is shorthand for std::greater<void>, a specialization whose operator() is itself a template: it deduces argument types at the call site instead of fixing them up front. That removes a redundant int which can drift out of sync if you later change the element type, and for heterogeneous comparisons it can compare without forcing a conversion. For everyday code the win is simply one fewer place to make a typo.

    The negation trick — and exactly when it breaks

    You will see this in competitive-programming code: keep the default max-heap and push the negatives of your values, so the max-heap's top() is the minimum after you negate it back.

    std::priority_queue<int> maxHeap;   // ordinary max-heap
int values[] = {5, 1, 8, 3};

for (int x : values) maxHeap.push(-x);      // push the negatives
int smallest = -maxHeap.top();              // negate on the way out -> 1
    Aspectstd::greater<int>push(-x) into a max-heap
    Works forAny orderable typeSigned numeric types only
    Unsigned typesFineSilently wrong (negation wraps modulo $2^n$)
    INT_MIN in the dataFineUndefined behaviour (-INT_MIN overflows)
    Strings / pairs / structsFineImpossible
    ReadabilityIntent is explicitTwo hidden negations to track
    Extra costNoneNone (but fragile)

    Verdict: use std::greater. Know the negation trick so you can read other people's code and understand why it is a bad default, but do not reach for it. There is no performance reason to — both are $O(\log n)$ per push with identical constants.

    Min-heaps of strings, doubles, and beyond

    Because std::greater orders by operator>, it works for any type that defines one. A min-heap of strings pops them in ascending lexicographic order:

    std::priority_queue<std::string, std::vector<std::string>, std::greater<>> words;
words.push("pear"); words.push("apple"); words.push("fig");
std::cout << words.top();   // prints "apple"

    Floating point works too, with one sharp edge: a comparator must impose a strict weak ordering, and NaN breaks it. Every comparison involving NaN returns false, so NaN is neither less than nor greater than anything, and the heap invariant can be violated. Filter NaN out with std::isnan() before it reaches the heap.

    Finally, give the long declaration a name once and stop retyping it:

    using MinHeap = std::priority_queue<int, std::vector<int>, std::greater<int>>;
MinHeap h;

    Custom Heaps: Writing Your Own Comparator

    std::less and std::greater cover the two cases where you order by the value itself. Everything else — order by absolute value, by distance from a target, by a field of a struct, by a key looked up in another array — needs a comparator you write. There are four ways to supply one, and one very common mistake in writing them is not a wrong answer but undefined behaviour.

    Getting a custom comparator right on the first try is mechanical if you use the rule from the top: decide which element you want on top, then write the predicate so the other element is the one reported as lower priority. Want the closest-to-target on top? Then the farther element is worse, so comp(a, b) returns “a is farther than b.”

    Form 1 — a struct with operator()

    The canonical comparator is a small struct overloading the function-call operator — a function object, or functor. This is exactly what std::less and std::greater are.

    #include <queue>
#include <vector>
#include <cmath>

struct ByAbsValue {
    bool operator()(int a, int b) const {   // note: const
        return std::abs(a) < std::abs(b);    // larger magnitude on top
    }
};

std::priority_queue<int, std::vector<int>, ByAbsValue> pq;
pq.push(-10); pq.push(3); pq.push(-7);
std::cout << pq.top();   // -10  (magnitude 10 is the largest)

    Two details matter. First, operator() should be const: the heap holds the comparator as a member and calls it on a const object. Second, for anything heavier than an int, take arguments by const& — a heap performs $O(\log n)$ comparisons per operation, and copying two strings each time is a real cost:

    struct ByLength {
    bool operator()(const std::string& a, const std::string& b) const {
        return a.size() < b.size();   // longest string on top
    }
};

    Reach for a functor when the comparator is reused across call sites or needs to carry data. It names a real type, so you can spell that type anywhere with no decltype gymnastics.

    Form 2 — lambdas

    Lambdas are where most people get stuck, because a priority_queue is a type and a lambda is a value of an unnamable type. Bridging that gap changed in C++20, so there are two stories.

    Before C++20, a lambda's closure type has no default constructor, so the queue cannot make one for itself — you must hand it the instance. Two moves, and you need both:

    auto cmp = [](int a, int b) { return a > b; };   // a min-heap predicate

// 1. name the comparator TYPE with decltype(cmp)
// 2. PASS the lambda to the constructor so the queue has one to store
std::priority_queue<int, std::vector<int>, decltype(cmp)> pq(cmp);

pq.push(5); pq.push(1); pq.push(8);
std::cout << pq.top();   // 1

    Write pq; instead of pq(cmp) and pre-C++20 you get a compile error. The two steps are not redundant: decltype(cmp) supplies the type the template needs, and (cmp) supplies the value the object must hold.

    C++20 made stateless (captureless) lambdas default-constructible and usable in unevaluated contexts, so you can name the type inline and skip the constructor argument:

    // C++20 — stateless lambda, default-constructed by the queue, no instance passed
std::priority_queue<int, std::vector<int>,
                    decltype([](int a, int b) { return a > b; })> pq;

    The catch is in the word stateless: the moment the lambda captures anything it is no longer default-constructible, even in C++20, and you are back to the decltype-plus-instance dance.

    Forms 3 and 4 — function pointers and std::function

    For completeness, a free function plus a function-pointer type works, as does type-erasing everything through std::function:

    bool cmp(int a, int b) { return a > b; }                        // min-heap predicate
std::priority_queue<int, std::vector<int>, bool(*)(int,int)> pq(cmp);

#include <functional>
std::function<bool(int,int)> f = [](int a, int b) { return a > b; };
std::priority_queue<int, std::vector<int>, std::function<bool(int,int)>> pq2(f);

    Both are not free. A function pointer is an indirect call the compiler usually cannot inline; std::function is type-erased and adds the same indirection plus possible allocation. A heap comparison sits in the hottest inner loop you have, so on comparison-bound workloads this is routinely measurable. Use them when flexibility — choosing the ordering at runtime — genuinely matters; avoid them in a hot path.

    FormVerbosityC++ versionInlined?Carries state?

    LambdaLeastC++11 (decltype + ctor arg); C++20 stateless needs no instanceYesYes (captures), but capturing loses default-construct

    The practical takeaway: default to a functor for anything reusable or stateful, and to a lambda for a local one-off.

    Strict weak ordering — the rules you cannot break

    Every comparator must impose a strict weak ordering. This is not pedantry: the library assumes it, and violating it is undefined behaviour, not a wrong-but-survivable result.

    • Irreflexivity: comp(a, a) must be false. An element is never lower priority than itself.
    • Asymmetry: if comp(a, b) is true then comp(b, a) must be false.
    • Transitivity: if comp(a, b) and comp(b, c), then comp(a, c). Priority does not form loops.
    • Transitivity of equivalence: if a ties with b and b ties with c, then a ties with c.
    The bug that bites in production: writing <= where you meant <. The comparator return a <= b; makes comp(a, a) return true, violating irreflexivity. That is undefined behaviour — in practice it can walk off the end of the container, corrupt the heap, loop forever, or appear to work until the input grows. Use a strict relation (< or >), never <= or >=. When you need a tie-breaker, break the tie on a different field.

    The reason a non-strict comparator is dangerous rather than merely wrong is that the sift routines use it to decide when to stop. If comp(a, a) is true, an element can be judged worse than itself, and a loop that should terminate keeps swapping, reading past valid indices. The symptom shows up far from the cause.

    Stateful comparators

    A comparator may carry data. The classic case is a heap of indices ordered by values held in a separate array — you push cheap integers but order them by an external key:

    std::vector<int> score = {30, 10, 50, 20};

// Order indices so the one with the SMALLEST score is on top (a min-heap on score).
auto byScore = [&score](int i, int j) { return score[i] > score[j]; };
std::priority_queue<int, std::vector<int>, decltype(byScore)> pq(byScore);

for (int i = 0; i < 4; ++i) pq.push(i);
std::cout << pq.top();   // 1  (index 1 has the smallest score, 10)

    This is how you keep large objects out of the heap and move only indices — but it comes with a sharp warning. The comparator holds a reference to score. If you mutate score while indices are still in the heap, the ordering the heap was built on quietly becomes false. The heap does not re-sort itself; its invariant is silently corrupted. Rule: while elements are in a heap ordered by external state, treat that state as frozen. If a key must change, use lazy re-insertion.

    One input, three comparators

    To prove the forms are interchangeable, here is a single order — “closest to 5 on top” — written three ways. Farther means lower priority, so each predicate returns “a is farther than b”:

    const int TARGET = 5;

// (a) Functor
struct ByDistance {
    bool operator()(int a, int b) const {
        return std::abs(a - TARGET) > std::abs(b - TARGET);
    }
};

// (b) Pre-C++20 lambda: name the type, pass the instance
auto lam = [](int a, int b) { return std::abs(a - TARGET) > std::abs(b - TARGET); };

// (c) C++20 stateless lambda: default-constructed, no instance needed
using PQc = std::priority_queue<int, std::vector<int>,
              decltype([](int a, int b) { return std::abs(a - TARGET) > std::abs(b - TARGET); })>;

int data[] = {1, 8, 4, 11, 7};

std::priority_queue<int, std::vector<int>, ByDistance> pa;
std::priority_queue<int, std::vector<int>, decltype(lam)> pb(lam);
PQc pc;
for (int x : data) { pa.push(x); pb.push(x); pc.push(x); }
// all three pop the same order: 4 7 8 1 11  (distances 1,2,3,4,6 from 5)

    ▶ Three Comparators, One Input Stream

    Each Step pushes one value — from 1, 8, 4, 11, 7 — into three heaps at once: std::less (max), std::greater (min), and a distance-to-5 comparator (closest on top). The highlighted root is each top(). Same data, three different winners.

    Custom Order for Pairs, Tuples & Structs

    Most real heaps hold compound values, and most of those need no comparator at all — because std::pair and std::tuple already compare lexicographically: first is the primary key, second only breaks ties.

    std::priority_queue<std::pair<int,int>> pq;
pq.push({2, 5});
pq.push({2, 9});
pq.push({2, 1});
auto t = pq.top();   // {2, 9} — first ties at 2, so the largest second wins

    When the key you care about is second, you have two honest options: write a comparator on .second, or reorder the pair so the key comes first and let the built-in ordering do the work.

    using PI = std::pair<int,int>;

// Option A — natural layout {id, weight}, explicit comparator
auto byWeight = [](const PI& a, const PI& b) { return a.second < b.second; };
std::priority_queue<PI, std::vector<PI>, decltype(byWeight)> pqA(byWeight);

// Option B — store {weight, id} and use the default lexicographic order
std::priority_queue<PI> pqB;   // max-heap on weight, ties by id

    Option B is shorter and inlines perfectly, which is why contest code is full of it; Option A keeps your data in its natural shape and makes the ordering explicit. Prefer B for throwaway speed, A for code other people read.

    Structs: operator< or an external comparator

    For your own types you can either define operator< (the heap picks it up through the default std::less) or pass an external comparator. Define operator< when the type has one natural order used everywhere; use an external comparator when the order is context-specific, or when you need several different orders of the same type. In C++20, auto operator<=>(const T&) const = default; synthesises all six relational operators with member-wise lexicographic semantics.

    Multi-key ordering with tie-breaking

    Serious scheduling needs several keys at once. Order tasks by priority descending, then earliest deadline, then insertion order. The correct comparator chains the keys, falling through only on a tie:

    struct Task { int priority; int deadline; int seq; };

struct TaskCmp {
    bool operator()(const Task& a, const Task& b) const {
        if (a.priority != b.priority) return a.priority < b.priority;  // higher priority on top
        if (a.deadline != b.deadline) return a.deadline > b.deadline;  // earlier deadline on top
        return a.seq > b.seq;                                          // earlier insertion on top
    }
};
std::priority_queue<Task, std::vector<Task>, TaskCmp> pq;
    The classic multi-key bug: writing return a.priority < b.priority || a.deadline < b.deadline;. That is not a strict weak ordering — it is neither asymmetric nor transitive — and feeding it to a heap is undefined behaviour, exactly like the <= mistake. The pattern is always a.x != b.x ? (a.x < b.x) : <next key>.

    That seq field is not decoration. Heaps are not stable: which of two equal elements pop() hands you first is unspecified and can change between library versions. When ties must resolve deterministically, attach a monotonically increasing sequence number at insertion and use it as the final tie-breaker.

    The <algorithm> Heap Family

    std::priority_queue is convenient but a locked box. Underneath it are six free functions in <algorithm> that operate directly on any random-access range — usually a std::vector you still own and can iterate, inspect, serialise, or reserve. All six default to std::less (max-heap) and take an optional trailing comparator, exactly like std::sort.

    FunctionPreconditionEffectCost
    make_heap(f, l)noneRearranges the range into a heap, in place$O(n)$
    push_heap(f, l)[f, l-1) is a heap; new element at l-1Sifts the last element up$O(\log n)$
    pop_heap(f, l)[f, l) is a heapSwaps the root to l-1, re-heaps [f, l-1)$O(\log n)$
    sort_heap(f, l)[f, l) is a heapSorts ascending by repeated pops$O(n \log n)$
    is_heap(f, l)nonetrue if the range is a heap$O(n)$
    is_heap_until(f, l)noneIterator to the first offending element$O(n)$

    Two contracts trip up everyone, and they are mirror images. push_heap does not take the value to insert — you push_back first, then it sifts up whatever is at the back. And pop_heap removes nothing — it parks the max at last-1 and leaves the erasing to you:

    std::vector<int> v{3, 1, 6, 5, 2, 4};
std::make_heap(v.begin(), v.end());   // {6, 5, 4, 1, 2, 3} — a valid max-heap

v.push_back(7);                       // 1. append to the CONTAINER yourself
std::push_heap(v.begin(), v.end());   // 2. sift that new last element up

std::pop_heap(v.begin(), v.end());    // max moves to v.back(); [begin, end-1) re-heaped
int biggest = v.back();               // read the extracted maximum
v.pop_back();                         // NOW actually remove it
    Why the standard splits it this way: algorithms operate on iterators, and iterators cannot resize the container they came from — a raw pointer pair has no idea whether it points into a vector, a C array, or a sub-range. So pop_heap does the only thing an iterator-based function can, and leaves the container size to you. Memorise the pairing: push_back then push_heap; pop_heap then pop_back.

    The upside is that repeated pop_heap deposits each next-largest element just before the shrinking heap region — which is precisely heapsort, in four lines and $O(1)$ extra space:

    std::vector<int> heapsort(std::vector<int> v) {
    std::make_heap(v.begin(), v.end());   // O(n)
    std::sort_heap(v.begin(), v.end());   // O(n log n)
    return v;                             // ascending
}

    std::sort still beats it in practice: introsort runs quicksort for its small constants and sequential access, switching to heapsort only when recursion depth exceeds $\approx 2\log n$. Heapsort is the safety net, not the default, because sift-down jumps by factors of two and destroys cache locality. It earns its keep when you need a hard $O(n \log n)$ ceiling with zero extra memory and no recursion.

    Four Patterns Worth Memorising

    Top-K largest in $O(n \log k)$

    Keep a min-heap of size $k$. Its top is the smallest of the $k$ best elements seen so far — your weakest current winner. For each new element: if the heap is not full, push it; otherwise, if it beats the weakest winner, evict and admit; else discard. The heap is “inverted” relative to the goal because you evict from the bottom, not the top.

    std::vector<int> topKLargest(const std::vector<int>& nums, int k) {
    std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;  // min on top
    for (int x : nums) {
        if ((int)minHeap.size() < k) {
            minHeap.push(x);                       // room to spare — keep it
        } else if (x > minHeap.top()) {
            minHeap.pop();                         // evict the weakest winner
            minHeap.push(x);                       // and admit x
        }                                          // else: x is too small, drop it
    }
    std::vector<int> result;
    while (!minHeap.empty()) { result.push_back(minHeap.top()); minHeap.pop(); }
    return result;                                 // ascending
}

    The size-$k$ heap wins precisely when the data streams: unknown length, one pass, bounded memory. For a static in-memory array queried once, std::nth_element finds the $k$-th largest in $O(n)$ average and beats it.

    K-way merge

    A min-heap holding the current front of each of $k$ sorted lists lets you repeatedly extract the global minimum and advance only that list. With $N$ total elements the cost is $O(N \log k)$ — the log is $k$, not $N$, because the heap never holds more than $k$ items.

    struct HeapItem { int val; int list; int idx; };
struct ByVal {
    bool operator()(const HeapItem& a, const HeapItem& b) const {
        return a.val > b.val;   // '>' => min-heap: the SMALLEST value sits on top
    }
};

std::vector<int> mergeKSorted(const std::vector<std::vector<int>>& lists) {
    std::priority_queue<HeapItem, std::vector<HeapItem>, ByVal> pq;
    for (int i = 0; i < (int)lists.size(); ++i)
        if (!lists[i].empty()) pq.push({lists[i][0], i, 0});

    std::vector<int> out;
    while (!pq.empty()) {
        HeapItem cur = pq.top(); pq.pop();
        out.push_back(cur.val);
        int next = cur.idx + 1;
        if (next < (int)lists[cur.list].size())
            pq.push({lists[cur.list][next], cur.list, next});  // advance that list only
    }
    return out;
}

    Two-heap running median

    Split the data into halves held in two heaps: a max-heap for the lower half and a min-heap for the upper half. The two tops straddle the median. Keep the sizes within one of each other, with the lower heap carrying the extra when the count is odd.

    class MedianFinder {
    std::priority_queue<int> lo;                                       // max-heap: lower half
    std::priority_queue<int, std::vector<int>, std::greater<int>> hi;  // min-heap: upper half
public:
    void addNum(int num) {
        lo.push(num);                 // 1. tentatively add to the lower half
        hi.push(lo.top());            // 2. funnel its max across — keeps the halves ordered
        lo.pop();
        if (hi.size() > lo.size()) {  // 3. rebalance so lo holds the extra when odd
            lo.push(hi.top());
            hi.pop();
        }
    }
    double findMedian() {
        if (lo.size() > hi.size()) return lo.top();       // odd count
        return (lo.top() + hi.top()) / 2.0;               // even count
    }
};

    The funnel-then-rebalance pair is the whole trick: pushing onto lo and immediately shifting its top to hi guarantees every element in lo is $\le$ every element in hi, whatever the arrival order.

    Dijkstra without decrease-key

    Textbook Dijkstra wants decrease-key. std::priority_queue has no such operation, and the universal workaround is lazy: never update; push a fresh (dist, node) entry, and skip stale pops.

    using PII = std::pair<int, int>;   // {distance, node}

std::vector<int> dijkstra(const std::vector<std::vector<PII>>& adj, int src) {
    std::vector<int> dist(adj.size(), std::numeric_limits<int>::max());
    std::priority_queue<PII, std::vector<PII>, std::greater<PII>> pq;  // min-heap by distance
    dist[src] = 0;
    pq.push({0, src});
    while (!pq.empty()) {
        auto [d, u] = pq.top(); pq.pop();          // C++17 structured bindings
        if (d > dist[u]) continue;                 // stale entry — a better one was processed
        for (const auto& [v, w] : adj[u]) {
            if (dist[u] + w < dist[v]) {
                dist[v] = dist[u] + w;
                pq.push({dist[v], v});             // fresh smaller entry instead of decrease-key
            }
        }
    }
    return dist;
}
    Why the stale-skip is correct: the first time a node is popped it is popped with its smallest distance (Dijkstra's invariant for non-negative edges), so it is finalised then and there. Any later entry carries a distance $\ge$ the finalised one, so d > dist[u] discards it. Tolerating duplicates lets the heap hold $O(E)$ entries, giving $O(E \log E) = O(E \log V)$ — and in practice it beats a Fibonacci heap on constants and locality. Note also the two decisions baked into {distance, node}: distance goes first so lexicographic order sorts by it, and std::greater makes it a min-heap so the closest frontier node pops next.

    Pitfalls & Performance

    PitfallSilent or loud?One-line fix
    top()/pop() on emptyLoud-ish (UB, often crash)Guard with !empty()
    Comparator uses <=Silent then catastrophicUse strict <
    Expecting pop() to returnLoud (compile error)top() then pop()
    Mutating a queued elementSilent corruptionRemove, modify, reinsert
    Trusting container orderSilentOnly the root is ordered
    Assuming stabilitySilentAdd a sequence tiebreak
    Reversing push_back/push_heapSilentContainer first, algorithm second

    On performance, four things actually matter. Bulk-load rather than pushing one at a time — the range constructor is one allocation plus an $O(n)$ make_heap. Keep the comparator cheap: it runs $O(\log n)$ times per operation, so precompute expensive keys and store them beside the payload rather than recomputing per comparison. Keep elements cheap to move: every sift swaps $O(\log n)$ times, so give your type a noexcept move constructor or store pointers/indices instead of fat objects. And stay with std::vector as the backing store — std::deque only avoids one large reallocation at the price of an indirection in the hot sift loop.

    Lazy deletion

    A heap cannot remove an arbitrary element in better than $O(n)$ because it cannot find it. The workaround, used constantly in Dijkstra and scheduling, is to not remove eagerly: mark the element deleted in a side table, and skip stale entries when they surface at the top.

    class LazyMinHeap {
    std::priority_queue<int, std::vector<int>, std::greater<int>> pq;
    std::unordered_map<int, int> deleted;   // value -> pending deletions
    int liveCount = 0;
public:
    void push(int x)   { pq.push(x); ++liveCount; }
    void erase(int x)  { ++deleted[x]; --liveCount; }        // O(log n) amortised, no search
    int  size() const  { return liveCount; }
    int  top() {
        while (!pq.empty() && deleted[pq.top()] > 0) {       // discard tombstones lazily
            --deleted[pq.top()];
            pq.pop();
        }
        return pq.top();
    }
};

    The multiset test: the moment your requirements contain the word “and” — “the best element and the ability to remove any element,” or “the best and the worst,” or “the best and iterate in order” — you have outgrown priority_queue. A heap gives you one extreme cheaply and nothing else. Reach for std::multiset.
