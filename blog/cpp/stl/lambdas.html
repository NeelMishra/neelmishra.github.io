    Lambdas — Closures, Captures & the STL

    July 2026 · 28 min read

    Before C++11, passing behaviour to an algorithm meant leaving the call site. You wrote a named struct with an operator(), put it somewhere a template could see it, and then referred back to it from the one line that actually cared. The logic and its use lived in different places, and half of that struct was ceremony.

    // C++98: three lines of boilerplate, defined far from where it is used
struct IsOdd {
    bool operator()(int x) const { return x % 2 != 0; }
};

int n = std::count_if(v.begin(), v.end(), IsOdd());

// C++11: the behaviour lives exactly where it is used
int n = std::count_if(v.begin(), v.end(), [](int x) { return x % 2 != 0; });

    A lambda is not a new kind of function. It is syntax for that struct — the compiler still generates a class with an operator(), and everything surprising about lambdas follows from that one fact. This post starts there, then works through every capture form, mutable, generic and template lambdas, the STL algorithms that lambdas exist to serve, how to store one, and the ways captures go wrong.

    The one sentence to keep: a lambda expression creates an object of a compiler-generated, unnamable class — its closure type. Captures become data members; the parameter list and body become operator(). Every rule below is a consequence of that.

    Anatomy of a Lambda

    The full grammar has five slots, three of which are optional:

    [captures] (params) specifiers -> ret { body }
    • captures — which surrounding variables the closure keeps, and how. The only mandatory part; [] means “none”. The brackets are also what tell the parser “a lambda starts here.”
    • params — ordinary function parameters. Omittable entirely if empty and you need no specifiers: []{ ... } is legal.
    • specifiers — mutable, constexpr (C++17), consteval (C++20), noexcept, attributes.
    • return type — almost always deduced; you spell it when deduction picks the wrong type or the body has multiple returns of different types.
    • body — a normal function body.
    auto add     = [](int a, int b) { return a + b; };            // deduced int
auto addD    = [](int a, int b) -> double { return a + b; };  // forced double
auto greet   = [] { std::cout << "hi\n"; };                    // no params, no ()
auto noThrow = [](int x) noexcept { return x * 2; };           // specifier

    Return-type deduction follows auto rules, which means it strips references and top-level const. If you are returning a reference to something that must stay a reference — the classic case being a lookup function — say so explicitly with -> decltype(auto) or a named type:

    std::map<int, std::string> m;

auto badLookup  = [&m](int k) { return m.at(k); };                  // returns std::string — a COPY
auto goodLookup = [&m](int k) -> std::string& { return m.at(k); };  // returns a reference
auto alsoGood   = [&m](int k) -> decltype(auto) { return m.at(k); }; // preserves whatever at() gives

    What the Compiler Actually Generates

    Every lambda desugars to a class. Once you can perform that translation in your head, nothing about lambdas is mysterious — you just ask “what would the struct look like?”

    int factor = 3;
auto scale = [factor](int x) { return x * factor; };

// The compiler generates something equivalent to:
class __lambda_7_14 {
    int factor;                                   // capture => data member
public:
    explicit __lambda_7_14(int f) : factor(f) {}  // built from the enclosing scope
    int operator()(int x) const                   // params + body => operator(), CONST
    { return x * factor; }
};
auto scale = __lambda_7_14(factor);               // the lambda expression is an OBJECT

    Three consequences fall straight out of that generated class, and they explain most beginner surprises:

    • operator() is const unless you write mutable. That is why modifying a by-value capture is a compile error — you are trying to write to a member through a const member function.
    • Each lambda expression has its own distinct type. Two lambdas with identical text and identical bodies are still two unrelated types, which is why you cannot assign one to the other and why decltype is the only way to name the type.
    • Captures are initialised when the lambda is created, not when it is called. A by-value capture is a snapshot taken at the point the expression is evaluated.

    The Capture Clause in Full

    The capture clause is the whole substance of a lambda. Everything else is function syntax you already know.

    FormMeaningSince
    []Capture nothing. The lambda is stateless, which unlocks several privileges below.C++11
    [x]Capture x by value — a copy, made now, frozen.C++11
    [&x]Capture x by reference — sees later changes, and dangles if x dies first.C++11
    [=]Default capture by value: every odr-used local is copied. Also captures this by pointer inside a member function.C++11
    [&]Default capture by reference: every odr-used local is referenced.C++11
    [=, &x] / [&, x]A default plus explicit exceptions. The exceptions must differ from the default.C++11
    [this]Capture the enclosing object’s this pointer; members are reached through it, so it is effectively by reference.C++11
    [*this]Capture a copy of the whole object. The safe choice for anything asynchronous.C++17
    [y = expr]Init-capture: create a new member initialised from any expression — the only way to move into a lambda.C++14
    [&y = x]Init-capture by reference, optionally under a new name.C++14
    [...args = std::move(pack)]Pack init-capture, for perfectly forwarding a parameter pack into a closure.C++20

    By value versus by reference — the snapshot

    This is the distinction that produces the most confused bug reports, and it is entirely about when the value is read.

    int x = 10;

auto byValue = [x]  { return x; };   // copies 10 into a member, right now
auto byRef   = [&x] { return x; };   // stores a reference to the variable x

x = 99;

std::cout << byValue();   // 10 — the snapshot taken at creation
std::cout << byRef();     // 99 — reads the live variable

    ▶ Snapshot vs Live Link

    Two closures created from the same variable x. Watch what each one holds as x is reassigned, and what each returns when finally called. The by-value closure owns a copy; the by-reference closure owns an arrow.

    The rule that keeps you out of trouble: capture by reference only when the closure cannot outlive the scope it captured from. That is true for algorithm callbacks, which run and finish inside the call. It is not true for anything you store, return, detach onto a thread, or hand to an event loop — those must capture by value, or by shared_ptr.

    The dangling capture

    A reference capture is a raw reference with no lifetime tracking. Return the closure and the referent is gone; you get undefined behaviour that frequently “works” in a debug build:

    // BROKEN: counter dies when makeCounter returns; the closure keeps a reference to it.
auto makeCounter() {
    int counter = 0;
    return [&counter] { return ++counter; };   // dangling — UB on every call
}

// FIXED: the closure owns its state.
auto makeCounter() {
    return [counter = 0]() mutable { return ++counter; };   // C++14 init-capture
}

    The same trap shows up whenever the closure escapes the frame — std::thread, std::async, a callback registry, a coroutine. Enable -Wdangling or run under ASan; the compiler catches only the most obvious cases on its own.

    Why [=] and [&] are worse than they look

    Default captures are convenient and inexact. Two specific problems:

    You cannot see what the closure owns. With [&], adding a variable reference to the body silently extends the closure’s lifetime requirements — a code review of the body alone cannot tell you what must outlive it. Explicit capture lists are self-documenting, and the extra characters are worth it.

    [=] does not copy members — it captures this. Inside a member function, naming a data member implicitly means this->member, so [=] captures the pointer, and your “copy” is nothing of the sort:

    struct Widget {
    int value = 42;

    auto brokenGetter() {
        return [=] { return value; };    // captures THIS, not value — dangles if the Widget dies
    }
    auto safeGetter() {
        return [*this] { return value; }; // C++17: copies the whole Widget into the closure
    }
    auto alsoSafe() {
        return [v = value] { return v; }; // C++14: copies just the member you need
    }
};

    C++20 deprecated the implicit this capture in [=] for exactly this reason; modern compilers warn on it. Prefer [*this], or copy the individual members you actually use.

    Init-capture: the only way to move

    A plain [x] always copies. For a unique_ptr that is not merely slow, it is impossible — the type is move-only. C++14 init-capture creates a fresh member from an arbitrary expression, so you can move, rename, or compute:

    auto p = std::make_unique<Data>();

// auto bad  = [p] { ... };                       // ERROR: unique_ptr is not copyable
auto owner   = [p = std::move(p)] { p->use(); };  // the closure now owns the pointer

auto shorter = [n = someVeryLongName] { ... };            // rename
auto derived = [total = a.size() + b.size()] { ... };     // compute once, at capture time
auto alias   = [&vec = myLongVectorName] { vec.clear(); }; // reference under a new name

    Note that after [p = std::move(p)] the outer p is in a moved-from state. That is intended — ownership has transferred into the closure, and the closure's lifetime now governs the resource.

    mutable, and Why operator() Is Const

    Because the generated operator() is const, by-value captures are read-only inside the body. Adding mutable drops the const:

    int count = 0;

auto broken = [count]  { return ++count; };            // ERROR: assignment to a const member
auto works  = [count]() mutable { return ++count; };   // OK — modifies the closure's OWN copy

works(); works(); works();
std::cout << works();   // 4  — the closure's copy persists between calls
std::cout << count;     // 0  — the original is untouched

    Two things to internalise. First, mutable mutates the closure’s copy, never the original variable — if you wanted the original, you needed [&count]. Second, the copy is state that survives between calls, because it is a data member of an object you are calling repeatedly. That makes a mutable lambda a tidy generator:

    auto nextId = [id = 0]() mutable { return ++id; };
nextId();   // 1
nextId();   // 2
nextId();   // 3
    Watch out when copying a stateful lambda. Passing one to an algorithm by value copies the closure — and therefore its state. std::for_each returns the (possibly modified) functor precisely so you can read the state back out; most algorithms give you no such guarantee, so never rely on a mutable lambda’s counter surviving an algorithm call. Keep the state outside and capture by reference if the count matters.

    Generic and Template Lambdas

    C++14 allows auto parameters. The generated operator() becomes a template, so one closure serves every argument type:

    auto print = [](const auto& x) { std::cout << x << '\n'; };
print(42); print("text"); print(3.14);       // one lambda, three instantiations

auto sum = [](auto a, auto b) { return a + b; };   // heterogeneous by construction

    C++20 adds an explicit template parameter list, which you need whenever you must name the type — to constrain it, to reference it in the body, or to relate two parameters:

    // C++20: name the type so you can use it
auto makeVec = []<typename T>(std::initializer_list<T> il) {
    return std::vector<T>(il);
};

// Constrain it with a concept
auto twice = []<std::integral T>(T x) { return x * 2; };

// Force both arguments to be the SAME type — impossible with plain auto, auto
auto sameOnly = []<typename T>(T a, T b) { return a == b; };

    Perfect forwarding inside a generic lambda uses the same auto&& plus std::forward pattern as a template function. The C++20 form is nicer because you have a name for the type:

    auto forwarder = [](auto&&... args) {
    return callee(std::forward<decltype(args)>(args)...);
};

    Lambdas and the STL — the Actual Payoff

    Lambdas were added to the language largely because the algorithm library was unusable without them. Every algorithm that takes a predicate, a comparator, or a transformation is a lambda site.

    #include <algorithm>
#include <numeric>
#include <vector>
#include <string>

std::vector<std::string> names = {"charlie", "alice", "bob", "dave"};

// Sort by a computed key
std::sort(names.begin(), names.end(),
          [](const std::string& a, const std::string& b) { return a.size() < b.size(); });

// Find the first element matching a runtime condition (captured!)
std::size_t limit = 4;
auto it = std::find_if(names.begin(), names.end(),
                       [limit](const std::string& s) { return s.size() > limit; });

// Count, transform, accumulate
int longOnes = std::count_if(names.begin(), names.end(),
                             [](const auto& s) { return s.size() > 3; });

std::vector<std::size_t> lengths(names.size());
std::transform(names.begin(), names.end(), lengths.begin(),
               [](const std::string& s) { return s.size(); });

std::size_t total = std::accumulate(names.begin(), names.end(), std::size_t{0},
                                    [](std::size_t acc, const std::string& s) { return acc + s.size(); });

    The erase–remove idiom

    The most-misused algorithm in the library. std::remove_if removes nothing — it cannot, because it only has iterators and iterators cannot resize a container. It partitions: survivors are shuffled to the front, and it returns an iterator to the start of the leftover tail. Erasing that tail is your job.

    std::vector<int> v = {1, 2, 3, 4, 5, 6};

// Two steps, always: remove_if partitions, erase shrinks.
v.erase(std::remove_if(v.begin(), v.end(), [](int x) { return x % 2 == 0; }),
        v.end());
// v == {1, 3, 5}

// C++20: one call that does both, and returns how many went away.
std::erase_if(v, [](int x) { return x > 3; });

    ▶ remove_if Partitions, erase Shrinks

    The predicate x % 2 == 0 runs over the vector. Kept elements are compacted toward the front by a write cursor; the tail is left as unspecified junk until erase cuts it off. Watch both cursors.

    Lambdas as comparators

    A comparator passed to std::sort is a plain argument, so a lambda drops straight in. A comparator for an ordered container or a priority_queue is a template parameter, so you must name the closure’s type — the decltype dance:

    auto byLength = [](const std::string& a, const std::string& b) { return a.size() < b.size(); };

std::sort(v.begin(), v.end(), byLength);                       // value — trivial

std::set<std::string, decltype(byLength)> s(byLength);         // type + instance
std::priority_queue<std::string, std::vector<std::string>,
                    decltype(byLength)> pq(byLength);          // same pattern

// C++20: a captureless lambda is default-constructible, so no instance is needed
std::set<std::string, decltype([](const std::string& a, const std::string& b)
                               { return a.size() < b.size(); })> s20;

    The rules a comparator must obey — strict weak ordering, and the undefined behaviour you invoke by writing <= — are the same ones covered in Heaps & Priority Queues. A lambda does not exempt you from them.

    C++20 ranges: lambdas as projections

    Ranges algorithms take an extra projection argument, applied to each element before the predicate sees it. That splits “what to look at” from “how to compare it,” and usually removes the comparator entirely:

    #include <ranges>
#include <algorithm>

struct Person { std::string name; int age; };
std::vector<Person> people = /* ... */;

std::ranges::sort(people, {}, &Person::age);                  // default less, projected onto age
std::ranges::sort(people, {}, [](const Person& p) { return p.name.size(); });

auto adults = people | std::views::filter([](const Person& p) { return p.age >= 18; })
                     | std::views::transform([](const Person& p) { return p.name; });
    One lifetime trap specific to views: a view is lazy, so the lambda you pass is stored and invoked later, during iteration. If that lambda captured a local by reference and the view outlives the local, you are back to a dangling capture — only now the crash happens somewhere in an iteration loop, far from the capture. Capture by value in anything lazy.

    Storing a Lambda: auto, std::function, or a Pointer

    You cannot write the closure type, so how you store one matters.

    StorageCostAccepts captures?Use when
    auto f = ...Zero — concrete type, fully inlinableYesAlways, for a local variable
    Template parameter template<class F>Zero — the type flows throughYesPassing a callable into your own function
    std::function<R(Args)>Indirect call, possible heap allocation, no inliningYesType erasure is genuinely required: heterogeneous storage, ABI boundary, recursion
    R(*fp)(Args)Indirect call, no allocationNo — captureless onlyInterfacing with a C API that takes a function pointer
    std::move_only_function (C++23)Like std::function, but supports move-only capturesYesA closure holding a unique_ptr that must be type-erased
     
    // A captureless lambda implicitly converts to a plain function pointer:
void (*fp)(int) = [](int x) { std::cout << x; };   // fine — no state to carry
// void (*bad)(int) = [n](int x) { ... };          // ERROR: a capturing closure has state

// Prefer a template parameter over std::function for callbacks you own:
template <typename F>
void repeat(int n, F&& f) {                        // inlines; zero overhead
    for (int i = 0; i < n; ++i) f(i);
}
void repeatSlow(int n, const std::function<void(int)>& f);   // type-erased on every call

    The reason a captureless lambda converts to a function pointer and a capturing one does not is, again, the generated class: with no members there is no state to carry, so the compiler can emit a plain static function with the same body. Give it a single capture and that equivalence disappears.

    Recursion, constexpr, and IIFEs

    Recursion is awkward because a lambda has no name inside its own body — auto deduction is not complete until the initialiser ends. There are three answers, in increasing order of quality:

    // (a) C++11: type-erase it so the name exists before the body does. Costs an indirect call.
std::function<int(int)> fact = [&fact](int n) { return n <= 1 ? 1 : n * fact(n - 1); };

// (b) C++14: pass the lambda to itself. Ugly, but zero overhead and fully inlinable.
auto fact2 = [](auto self, int n) -> int { return n <= 1 ? 1 : n * self(self, n - 1); };
fact2(fact2, 5);   // 120

// (c) C++23 "deducing this": the closure can finally name itself.
auto fact3 = [](this auto& self, int n) -> int { return n <= 1 ? 1 : n * self(n - 1); };
fact3(5);          // 120

    Note that (a) captures fact by reference, so the std::function must outlive every call — returning it from a function is another dangling capture.

    constexpr: since C++17 a lambda is implicitly constexpr whenever its body satisfies the constant-expression rules, so it can run at compile time with no annotation. Spell constexpr explicitly when you want the compiler to reject a body that quietly fails those rules.

    constexpr auto square = [](int x) { return x * x; };
static_assert(square(5) == 25);            // evaluated at compile time

    The IIFE — immediately-invoked function expression — is the idiomatic way to initialise a const variable that needs several statements to compute. It keeps the variable const and confines the scratch work:

    const Config cfg = [&] {
    Config c;
    c.load(defaultPath);
    if (overridePath) c.merge(*overridePath);
    c.validate();
    return c;
}();   // note the trailing () — it runs right here

    Pitfalls

    PitfallSilent or loud?Fix
    Reference capture outliving its referentSilent (UB, often works in debug)Capture by value, or by shared_ptr, for anything stored or deferred
    [=] capturing this instead of membersSilent until the object dies[*this] (C++17) or capture the members explicitly
    Modifying a by-value captureLoud (compile error)Add mutable — and know it edits the copy
    Expecting a mutable counter to update the originalSilentCapture by reference if you meant the original
    Assuming remove_if shrinks the containerSilent (leftover junk, wrong size())v.erase(remove_if(...), v.end()) or std::erase_if
    Capturing a loop variable by reference into stored callbacksSilent (all callbacks see the last value)Capture by value inside the loop body
    std::function in a hot loopSilent (just slow)Template parameter or auto
    Capturing a structured binding pre-C++20Loud (compile error on some compilers)Init-capture a copy: [a = a]

    The loop-variable case deserves its code, because it looks harmless:

    std::vector<std::function<void()>> callbacks;

for (int i = 0; i < 3; ++i)
    callbacks.push_back([&i] { std::cout << i; });   // BROKEN: all three reference the same i,
                                                     // which is dead by the time they run

for (int i = 0; i < 3; ++i)
    callbacks.push_back([i] { std::cout << i; });    // correct: each closure owns its own copy

    Cheat Sheet

    // ---- SHAPE ---------------------------------------------------------------
[captures](params) mutable noexcept -> Ret { body }

// ---- CAPTURES ------------------------------------------------------------
[]              // nothing: converts to a function pointer, default-constructible in C++20
[x]             // copy, frozen at creation
[&x]            // reference: must not outlive x
[=] / [&]       // defaults — avoid; [=] also grabs `this` in a member function
[this]          // the object's pointer (by reference in effect)
[*this]         // C++17: a copy of the whole object — safe for async
[y = expr]      // C++14 init-capture: move, rename, or compute
[&y = x]        // init-capture by reference

// ---- STATE ---------------------------------------------------------------
[n = 0]() mutable { return ++n; }      // per-closure state that persists across calls

// ---- GENERIC -------------------------------------------------------------
[](const auto& x) { }                  // C++14 generic
[]<typename T>(T a, T b) { }           // C++20: name the type, constrain it, relate params

// ---- STL -----------------------------------------------------------------
std::sort(b, e, [](auto& a, auto& b){ return a.key < b.key; });
v.erase(std::remove_if(v.begin(), v.end(), pred), v.end());   // or std::erase_if(v, pred)
std::set<T, decltype(cmp)> s(cmp);     // container comparator: type AND instance
std::ranges::sort(v, {}, &T::field);   // C++20 projection instead of a comparator

// ---- STORING -------------------------------------------------------------
auto f = ...;                 // zero cost — always prefer
template <class F> void g(F&&);  // zero cost across a call boundary
std::function<R(A)>           // type erasure: indirect call, maybe an allocation
R(*fp)(A)                     // captureless lambdas only

    Practice

    Each of these is a “write the predicate, pick the capture” exercise — the algorithm is the easy half.

    • LeetCode 791 — Custom Sort String capture capture a rank table and sort by looked-up rank.
    • LeetCode 692 — Top K Frequent Words multi-key a lambda comparator with a frequency key and a lexicographic tie-break.
